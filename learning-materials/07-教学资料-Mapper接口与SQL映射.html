二、知识点详解

K7-1 @Mapper注解与@MapperScan

定义

在 MyBatis / MyBatis-Plus 中，Mapper 接口是 Java 代码访问数据库的入口——它是一个普通的 Java 接口（无需写实现类），框架通过动态代理自动生成实现。但 Spring 容器并不会自动识别 Mapper 接口为 Bean，需要通过以下两种方式之一告诉 Spring"哪些接口是 Mapper，需要被扫描注册"：

  • 方式一：@Mapper 注解——标注在每个 Mapper 接口上，逐个声明。
  • 方式二：@MapperScan 注解——标注在启动类（或任意 @Configuration 类）上，批量扫描指定包下的所有接口。

两者二选一即可，不要同时使用（虽然技术上不冲突，但属于重复声明）。

原理

MyBatis-Plus 在 Spring Boot 启动时会通过 MapperScannerConfigurer 扫描 Mapper 接口，为每个接口生成一个动态代理对象并注册为 Spring Bean。两种注解的区别只在于"扫描入口"：

方式一：@Mapper（接口级注解，逐个声明）

  @Mapper                                    Spring Boot 启动
  public interface UserMapper {         →   扫描所有 @Mapper 注解的接口
      int insert(User user);                 →   为每个接口生成代理对象
  }                                          →   注册为 Bean（名字默认为类名首字母小写）

方式二：@MapperScan（类级注解，批量扫描）

  @SpringBootApplication
  @MapperScan("com.ctts.mapper")        →   扫描 com.ctts.mapper 包下所有接口
  public class CttsApplication {             →   全部视为 Mapper（无需逐个加 @Mapper）
      ...                                    →   批量生成代理并注册为 Bean
  }

问题/场景

场景：CTTS 项目有 5 张表，对应 5 个 Mapper 接口（SysUserMapper、TrainingProjectMapper、TaskMapper、TaskSubmissionMapper、TaskReviewMapper），全部位于 com.ctts.mapper 包下。

问题：如果用 @Mapper 注解，5 个接口每个都要加一遍；如果后续新增表，还要记得加注解，容易遗漏。用 @MapperScan 一次性扫描整个包更省事。

方式一：使用 @Mapper 注解（逐个声明）
package com.ctts.mapper;

import com.baomidou.mybatisplus.core.mapper.BaseMapper;
import com.ctts.entity.SysUser;
import org.apache.ibatis.annotations.Mapper;
import org.apache.ibatis.annotations.Select;

/**
 * 系统用户 Mapper 接口
 * 使用 @Mapper 注解声明为 Mapper，Spring 启动时扫描并生成代理
 */
@Mapper
public interface SysUserMapper extends BaseMapper<SysUser> {

    // 自定义查询：按用户名模糊查询
    @Select("SELECT id, username, name, role, phone, create_time " +
            "FROM sys_user WHERE username LIKE CONCAT('%', #{keyword}, '%')")
    List<SysUser> selectByKeyword(@Param("keyword") String keyword);
}

方式二：使用 @MapperScan 注解（批量扫描，推荐）
package com.ctts;

import org.mybatis.spring.annotation.MapperScan;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

/**
 * CTTS 启动类
 * 使用 @MapperScan 批量扫描 com.ctts.mapper 包下的所有接口
 * 此时 Mapper 接口无需加 @Mapper 注解
 */
@SpringBootApplication
@MapperScan("com.ctts.mapper")  // 批量扫描，推荐方式
public class CttsApplication {
    public static void main(String[] args) {
        SpringApplication.run(CttsApplication.class, args);
    }
}
package com.ctts.mapper;

import com.baomidou.mybatisplus.core.mapper.BaseMapper;
import com.ctts.entity.SysUser;
import org.apache.ibatis.annotations.Select;
import java.util.List;

/**
 * 系统用户 Mapper 接口
 * 注意：这里没有 @Mapper 注解，因为启动类已用 @MapperScan 批量扫描
 */
public interface SysUserMapper extends BaseMapper<SysUser> {

    @Select("SELECT * FROM sys_user WHERE role = #{role}")
    List<SysUser> selectByRole(String role);
}

易错点

  1. @Mapper 与 @MapperScan 同时使用：虽不报错，但属于重复声明。CTTS 项目统一用 @MapperScan，Mapper 接口内不再加 @Mapper。

  2. @MapperScan 包路径写错：

    • 错误：@MapperScan("com.ctts.Mapper")（M 大写，包名实际是小写 mapper）
    • 错误：@MapperScan("com.ctts.mapper.*")（多写了 .*，@MapperScan 直接写包名即可）
    • 正确：@MapperScan("com.ctts.mapper")

  3. @MapperScan 扫描多个包：用 {} 数组语法或逗号分隔：

    @MapperScan({"com.ctts.mapper", "com.ctts.extmapper"})  // 多个包

  4. Mapper 接口不在扫描包下：如果把 SysUserMapper 放到了 com.ctts.dao 包下，但 @MapperScan 扫描的是 com.ctts.mapper，则该接口不会被注册，注入时报 NoSuchBeanDefinitionException。

  5. Mapper 接口未继承 BaseMapper：单独定义一个 @Mapper 接口是可以的（纯注解 SQL），但失去 MyBatis-Plus 内置 CRUD 能力。CTTS 项目所有 Mapper 都应继承 BaseMapper。

  6. @Mapper 注解的包不要搞错：

    • 正确：org.apache.ibatis.annotations.Mapper（MyBatis 提供）
    • 错误：导入其他同名注解

小结

@Mapper 与 @MapperScan 是 MyBatis 注册 Mapper 接口到 Spring 容器的两种方式，本质都是触发 MapperScannerConfigurer 扫描并生成代理。项目实践中推荐 @MapperScan——一次配置全包扫描，新增 Mapper 无需改注解。CTTS 项目采用 @MapperScan("com.ctts.mapper")，后续所有 Mapper 接口均放在 com.ctts.mapper 包下且无需加 @Mapper 注解。

K7-2 BaseMapper接口

定义

BaseMapper<T> 是 MyBatis-Plus 提供的通用 Mapper 接口，封装了单表的 CRUD 操作。开发者只需让自己的 Mapper 接口继承 BaseMapper<实体类>，即可零 SQL 获得 20+ 个通用方法，包括 insert、deleteById、updateById、selectById、selectList 等。

public interface SysUserMapper extends BaseMapper<SysUser> {
    // 不用写任何方法，已经拥有了 BaseMapper 的全部 CRUD 能力
}

原理

MyBatis-Plus 在启动时会解析 BaseMapper 的泛型参数 T（如 SysUser），结合实体类上的 @TableName 注解确定表名，然后自动注入对应的 SQL 到 BaseMapper 的每个方法中。调用 selectById(1L) 时，框架自动执行 SELECT * FROM sys_user WHERE id = 1。

SysUserMapper extends BaseMapper<SysUser>
                     ↓
       泛型 T = SysUser → 解析 @TableName("sys_user") → 确定表名
                     ↓
       自动注入 SQL：
         insert(T)        →  INSERT INTO sys_user (...) VALUES (...)
         deleteById(id)   →  DELETE FROM sys_user WHERE id = ?
         updateById(T)    →  UPDATE sys_user SET ... WHERE id = ?
         selectById(id)   →  SELECT * FROM sys_user WHERE id = ?
         selectList(null) →  SELECT * FROM sys_user
                     ↓
       开发者调用方法 → 框架执行注入的 SQL → 自动映射结果为 T 或 List<T>

问题/场景

场景：CTTS 项目需要为 5 张表（sys_user、training_project、task、task_submission、task_review）各实现 CRUD。如果用原生 MyBatis，每张表都要手写 5 段 XML SQL（insert、update、delete、selectById、selectList），共 25 段 SQL。而继承 BaseMapper 后，25 段 SQL 全部省略。

BaseMapper 常用方法清单（无需记忆全部，掌握前 8 个即可）：

方法签名 功能 SQL 等价

int deleteById(Serializable id) 根据主键删除 DELETE FROM ... WHERE id = ?

package com.ctts;

import com.ctts.entity.SysUser;
import com.ctts.mapper.SysUserMapper;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;

import java.util.Arrays;
import java.util.List;

/**
 * BaseMapper 常用方法演示
 */
@SpringBootTest
public class BaseMapperDemoTest {

    @Autowired
    private SysUserMapper userMapper;  // 继承了 BaseMapper<SysUser>

    @Test
    public void testInsert() {
        SysUser user = new SysUser();
        user.setUsername("testuser");
        user.setPassword("123456");
        user.setName("测试用户");
        user.setRole("student");
        user.setPhone("13900000000");
        int rows = userMapper.insert(user);  // 返回受影响行数
        System.out.println("插入行数 = " + rows);
        System.out.println("自增主键回填 = " + user.getId());  // 主键自动回填到对象
    }

    @Test
    public void testSelectById() {
        SysUser user = userMapper.selectById(1L);
        System.out.println("查询结果 = " + user);
    }

    @Test
    public void testSelectList() {
        // null 表示无条件，查询全部
        List<SysUser> list = userMapper.selectList(null);
        list.forEach(System.out::println);
    }

    @Test
    public void testUpdateById() {
        // 先查出原对象
        SysUser user = userMapper.selectById(1L);
        if (user != null) {
            user.setPhone("13800000099");
            // updateById 只更新非 null 字段
            int rows = userMapper.updateById(user);
            System.out.println("更新行数 = " + rows);
        }
    }

    @Test
    public void testDeleteById() {
        int rows = userMapper.deleteById(5L);
        System.out.println("删除行数 = " + rows);
    }

    @Test
    public void testSelectBatchIds() {
        // 批量查询
        List<SysUser> list = userMapper.selectBatchIds(Arrays.asList(1L, 2L, 3L));
        list.forEach(System.out::println);
    }

    @Test
    public void testSelectCount() {
        long count = userMapper.selectCount(null);
        System.out.println("用户总数 = " + count);
    }
}

易错点

  1. 方法名混淆：

    • updateById、deleteById、selectById 都带 ById 后缀，根据主键操作
    • selectList 是查询多条，返回 List<T>；selectOne 是查询单条（有多条会抛异常）
    • deleteById 的参数是 Serializable（主键值），不是实体对象

  2. updateById 的 null 字段不更新：

    • MyBatis-Plus 默认策略：实体类中值为 null 的字段不会被拼入 UPDATE 语句
    • 如果想把字段更新为 null，需用 UpdateWrapper.set("字段", null) 或 @TableField(updateStrategy = FieldStrategy.IGNORED)
    • 例如 user.setPhone(null); userMapper.updateById(user); 不会把 phone 改成 NULL

  3. insert 后主键回填：

    • 若 @TableId(type = IdType.AUTO)，插入后数据库生成的自增 ID 会自动回填到实体对象的 id 字段
    • 即 userMapper.insert(user); Long id = user.getId(); 能拿到新插入的 ID

  4. selectList(null) 与 selectList(new QueryWrapper<>()) 等价：

    • 传 null 表示无条件查询全部
    • 传空 Wrapper 也是查全部

  5. selectBatchIds 不能传空集合：

    • userMapper.selectBatchIds(Collections.emptyList()) 会生成 WHERE id IN ()，SQL 语法错误
    • 传 null 也不行，需要先判空

  6. 分页方法 selectPage 需要配置插件：

    • 不配置 MybatisPlusInterceptor 分页插件，selectPage 不会真的分页，会查全部
    • 分页插件在第8次课讲解

小结

BaseMapper<T> 是 MyBatis-Plus 的核心增强，继承即得 CRUD——单表的增删改查无需写一行 SQL。掌握 insert、deleteById、updateById、selectById、selectList 这 5 个方法就能覆盖日常 80% 的场景。剩余 20% 的复杂查询（多表关联、动态条件、统计分组）则通过自定义注解 SQL 或 XML SQL 实现，这是接下来 K7-4、K7-5 的内容。

K7-3 实体类与表映射

定义

在 MyBatis-Plus 中，实体类（Entity） 是数据库表在 Java 层的对应物——一张表对应一个实体类，表的一个字段对应实体类的一个属性。为了让框架准确识别"实体类对应哪张表""哪个属性是主键""哪些字段不参与映射"，需要使用三大注解：

  • @TableName：标注实体类对应的数据库表名
  • @TableId：标注主键字段及其生成策略
  • @TableField：标注普通字段的映射关系，或标记非表字段

原理

易错点

  1. 忘记 @TableName 导致表找不到：

    • 实体类名 SysUser，若不加 @TableName("sys_user")，MyBatis-Plus 默认按类名转下划线找表 sys_user（恰好符合规则时能用，但不保险）
    • 实体类名 User，若不加 @TableName("sys_user")，框架找表 user，报 Table 'ctts.user' doesn't exist
    • 建议始终显式加 @TableName，不依赖默认转换

  2. @TableId 主键策略选错：

    • 数据库主键是 AUTO_INCREMENT，却用 IdType.ASSIGN_ID：插入时框架生成雪花 ID 覆盖自增，可能冲突
    • 数据库主键无自增，却用 IdType.AUTO：插入时主键为 null，报错
    • CTTS 项目统一用 IdType.AUTO（数据库均设自增）

  3. @TableField(exist = false) 漏加：

    • 实体类有 confirmPassword 字段但表中无此列，不加 exist = false 会导致 SELECT 时框架拼出 confirm_password 列，报 Unknown column 'confirm_password'

  4. 驼峰映射关闭导致映射失败：

    • 若 application.yml 中误设 map-underscore-to-camel-case: false，则 createTime 不会自动映射到 create_time，查询结果 createTime 为 null
    • 解决：保持默认 true，或用 @TableField("create_time") 显式指定

  5. 使用基本类型而非包装类型：

    • 错误：private int status;（基本类型默认值 0，会被框架认为有值，影响 updateById 的 null 判断）
    • 正确：private Integer status;（包装类型默认 null，不参与更新）
    • 所有实体字段应使用包装类型（Long、Integer、String、LocalDateTime 等）

  6. 时间类型选择：

    • 推荐 LocalDateTime（Java 8+，线程安全），不推荐 Date（老 API，可变，线程不安全）
    • 数据库 DATETIME 对应 Java LocalDateTime；数据库 DATE 对应 Java LocalDate

小结

实体类与表的映射是 MyBatis-Plus 开发的基础——一张表一个实体类，用三大注解建立映射关系。@TableName 定表名、@TableId 定主键、@TableField 定字段（或排除字段）。驼峰自动映射能省去大量 @TableField 注解，但表名与类名不符时必须显式 @TableName。实体类字段一律用包装类型，时间用 LocalDateTime，这是企业开发的基本规范。

K7-4 注解SQL

定义

注解 SQL 指直接在 Mapper 接口的方法上使用 @Select、@Insert、@Update、@Delete 注解编写 SQL 语句的方式。它把 SQL 与 Java 接口紧耦合在一起，适合简单的、固定的 SQL 场景。

  • @Select("SQL") —— 查询
  • @Insert("SQL") —— 新增
  • @Update("SQL") —— 修改
  • @Delete("SQL") —— 删除

参数绑定有两种语法：

  • #{param} —— 预编译占位符（推荐，防 SQL 注入）
  • ${param} —— 字符串拼接（有 SQL 注入风险，仅在特殊场景使用）

原理

MyBatis 解析注解中的 SQL 时，对 #{} 与 ${} 的处理方式完全不同：

@Select("SELECT * FROM sys_user WHERE username = #{username}")
SysUser selectByUsername(String username);

  调用：selectByUsername("admin")
        ↓
#{username} 被替换为预编译占位符 ?
  生成 SQL：SELECT * FROM sys_user WHERE username = ?
  参数通过 PreparedStatement.setString(1, "admin") 绑定
        ↓
  预编译执行，参数会被自动转义，防注入

────────────────────────────────────────────────────

@Select("SELECT * FROM sys_user WHERE username = '${username}'")
SysUser selectByUsernameUnsafe(String username);

  调用：selectByUsernameUnsafe("admin' OR '1'='1")
        ↓
${username} 被直接字符串拼接
  生成 SQL：SELECT * FROM sys_user WHERE username = 'admin' OR '1'='1'
        ↓
  条件永远成立，返回全部用户 → SQL 注入！

#{} 防注入的本质：MyBatis 将 #{} 替换为 JDBC 的 ? 占位符，参数通过 PreparedStatement.setXxx() 绑定，JDBC 驱动会对参数进行转义处理，参数永远不会被当作 SQL 语法的一部分解析。

问题/场景

场景一（查询）：CTTS 项目需要"按用户名模糊查询用户"，用 @Select 实现：

@Select("SELECT * FROM sys_user WHERE username LIKE CONCAT('%', #{keyword}, '%')")
List<SysUser> selectByKeyword(@Param("keyword") String keyword);

场景二（SQL 注入演示）：若用 ${} 拼接用户名查询，攻击者输入 ' OR '1'='1 时会发生什么？

// 危险写法（永远不要这样写！）
@Select("SELECT * FROM sys_user WHERE username = '${username}'")
SysUser selectUnsafe(String username);

// 调用 selectUnsafe("admin' OR '1'='1")
// 实际执行 SQL：SELECT * FROM sys_user WHERE username = 'admin' OR '1'='1'
// 条件恒真，返回所有用户 → 数据泄露

场景三（${} 的合法使用）：动态排序字段必须用 ${}，因为 ORDER BY 后面接的是列名，不能用 ? 占位符：

// 合法使用 ${}：动态排序字段
@Select("SELECT * FROM sys_user ORDER BY ${column} ${order}")
List<SysUser> selectAllOrderBy(@Param("column") String column, @Param("order") String order);

// 调用：selectAllOrderBy("create_time", "DESC")
// 生成：SELECT * FROM sys_user ORDER BY create_time DESC
// 注意：column 与 order 必须在代码层做白名单校验，防止注入

易错点

  1. 该用 #{} 时误用 ${}：

    • 这是最常见也最危险的安全漏洞，会导致 SQL 注入
    • 默认规则：所有 WHERE 条件值、INSERT/UPDATE 值都用 #{}
    • 仅在动态表名、动态列名、动态排序方向时才考虑 ${}，且必须做白名单校验

  2. 多参数未加 @Param：

    • 单参数可以省略 @Param，MyBatis 自动按参数名绑定
    • 多参数必须用 @Param("name") 显式指定，否则报 Parameter 'xxx' not found
    // 错误：多参数无 @Param
@Select("... WHERE role = #{role} AND status = #{status}")
List<SysUser> select(String role, String status);  // 报错

// 正确：加 @Param
@Select("... WHERE role = #{role} AND status = #{status}")
List<SysUser> select(@Param("role") String role, @Param("status") String status);

  3. @Select 返回类型不匹配：

    • 查询单条用实体类：SysUser selectById(Long id)
    • 查询多条用 List：List<SysUser> selectAll()
    • 如果查询可能返回多条但方法返回单个实体，会抛 TooManyResultsException

  4. LIKE 模糊查询写法：

    • 错误：LIKE '%#{keyword}%'（#{} 在引号内不会被解析）
    • 错误：LIKE '%${keyword}%'（有注入风险）
    • 正确：LIKE CONCAT('%', #{keyword}, '%')（推荐，安全）
    • 正确：LIKE '%' #{keyword} '%'（空格分隔，MyBatis 支持）

  5. ${} 的动态排序不做白名单校验：

    • 危险：ORDER BY ${column} ${order} 不校验，攻击者传入 1; DROP TABLE sys_user --
    • 安全：代码层校验 column 必须在 ["id", "create_time", "username"] 中，order 必须是 "ASC" 或 "DESC"

  6. 注解 SQL 中写复杂动态 SQL 困难：

    • 注解 SQL 不支持 <if>、<where>、<foreach> 等动态标签
    • 需要动态 SQL 时用 @SelectProvider 或改用 XML SQL（K7-5）
    • 简单固定 SQL 用注解，复杂动态 SQL 用 XML

小结

注解 SQL 适合简单、固定的查询场景——一行 @Select 写在接口方法上，简洁直观。核心原则是永远优先使用 #{}，它通过预编译占位符从根本上防止 SQL 注入；${} 仅用于动态表名/列名/排序方向等无法参数化的场景，且必须做白名单校验。复杂动态 SQL 应改用 XML SQL 映射（K7-5）。SQL 注入是 OWASP Top 10 之首的安全风险，写错一行 ${} 可能导致整个数据库被拖走——这不是危言耸听，是每年都在真实发生的安全事故。

K7-5 XML SQL映射

定义

XML SQL 映射指把 SQL 语句写在独立的 XML 文件中（XxxMapper.xml），通过 namespace 与 Java Mapper 接口绑定的方式。相比注解 SQL，XML SQL 支持动态标签（<if>、<where>、<foreach>、<choose> 等），适合复杂的、动态的 SQL 场景。

XML 映射文件的核心要素：

  • namespace：命名空间，值为 Mapper 接口的全限定名，建立 XML 与接口的绑定
  • <select>/<insert>/<update>/<delete>：SQL 标签，id 属性对应接口方法名
  • resultMap：结果映射，处理字段名与属性名的复杂对应关系
  • parameterType：参数类型（可省略，MyBatis 会自动推断）

原理

MyBatis 启动时解析 mapper.xml 文件，根据 namespace 找到对应的 Mapper 接口，将 XML 中的 <select id="xxx"> 与接口方法 xxx 绑定。调用接口方法时，MyBatis 找到对应的 XML SQL 标签执行：

Mapper 接口方法  ←─ namespace 绑定 ─→  XML SQL 标签
       ↓                                      ↓
trainingProjectMapper.selectByStatus(1)
       ↓                                      ↓
       ↓           id="selectByStatus" 匹配
       ↓                                      ↓
MyBatis 拦截调用 → 找到 <select id="selectByStatus"> → 解析 SQL
       ↓                                      ↓
       ↓           #{status} 替换为 ? → 预编译执行
       ↓                                      ↓
       ↓           resultMap 映射结果
       ↓                                      ↓
返回 List<TrainingProject> ←──── 结果集自动映射

XML 文件位置约定：

  • 默认位置：src/main/resources/mapper/ 目录下
  • 文件名约定：XxxMapper.xml（与接口同名）
  • 配置扫描路径：application.yml 中 mybatis-plus.mapper-locations

问题/场景

场景：CTTS 项目需要"按状态查询实训项目列表"，且后续会扩展为多条件动态查询（按状态、教师、日期范围等）。这种动态查询用注解 SQL 难以表达（注解不支持 <if> 标签），应使用 XML SQL：

<!-- TrainingProjectMapper.xml -->
<select id="selectByStatus" resultMap="BaseResultMap">
    SELECT id, title, description, teacher_id, start_date, end_date, status, create_time
    FROM training_project
    WHERE status = #{status}
</select>

易错点

  1. namespace 写错：

    • namespace 必须等于 Mapper 接口的全限定名（含包名）
    • 错误：namespace="TrainingProjectMapper"（缺包名）
    • 错误：namespace="com.ctts.mapper.trainingProjectMapper"（类名大小写错）
    • 正确：namespace="com.ctts.mapper.TrainingProjectMapper"

  2. id 与接口方法名不一致：

    • XML 中 <select id="selectByStatus"> 必须与接口方法名 selectByStatus 完全一致
    • 不一致会报 BindingException: Invalid bound statement (not found)

  3. XML 文件未被扫描：

    • 默认扫描 classpath:mapper/*.xml，若 XML 放在 classpath:xml/ 下则扫描不到
    • 需在 application.yml 配置：mybatis-plus.mapper-locations: classpath:xml/*.xml
    • 或用通配符：classpath*:mapper/**/*.xml

  4. resultMap 与 resultType 混淆：

    • resultType：直接指定返回类型（如 resultType="com.ctts.entity.SysUser"），要求字段名与属性名一致（或驼峰映射）
    • resultMap：引用 <resultMap> 的 id，用于字段名与属性名不一致或复杂映射
    • 两者只能选一个，不能同时用

  5. <resultMap> 中 column 写错：

    • column 是 SQL 查询结果集的列名（数据库列名或别名），不是 Java 属性名
    • 例如 SELECT create_time FROM ...，则 column="create_time"（不是 createTime）

  6. parameterType 可以省略：

    • MyBatis 会根据接口方法参数类型自动推断，写错反而出问题
    • 教学时为清晰可显式写出，生产代码常省略

  7. XML 中 SQL 末尾不能加 ;：

    • 错误：SELECT * FROM sys_user WHERE id = #{id};
    • MyBatis 会把 ; 当作 SQL 一部分，部分数据库会报错
    • 正确：SELECT * FROM sys_user WHERE id = #{id}

  8. XML 注释不能用 <!-- --> 包含 --：

    • 错误：<!-- 这是 -- 注释 -->（-- 在 XML 注释中非法）
    • 正确：<!-- 这是注释 -->

小结

XML SQL 映射是 MyBatis 的传统写法，优势在于支持动态 SQL 标签（<if>、<where>、<foreach> 等），适合复杂查询场景。核心三要素：namespace 绑定接口全限定名、<select id="方法名"> 对应接口方法、resultMap 处理字段映射。简单的固定 SQL 用注解 @Select 更轻量，复杂的动态 SQL 用 XML 更清晰——两者可在同一 Mapper 接口中混用，CTTS 项目 SysUserMapper 用注解 SQL，TrainingProjectMapper 用 XML SQL，正是为了让同学们对比两种写法。

四、拓展阅读

1. MyBatis 动态代理原理

MyBatis 对 Mapper 接口的实现基于 JDK 动态代理：启动时为每个 Mapper 接口生成 MapperProxy 代理对象，调用接口方法时，MapperProxy.invoke() 拦截调用，根据方法名找到对应的 SQL（注解或 XML），执行后返回结果。这就是为什么 Mapper 接口不需要写实现类——框架用代理自动实现了。

2. resultMap 的高级用法

本次课只用了基础的 <result> 标签做字段映射。resultMap 还支持：

  • association：一对一关联映射（如用户关联部门）
  • collection：一对多关联映射（如教师关联其负责的所有项目）
  • discriminator：根据某字段值决定映射到不同类

这些高级用法在第19次课"多表关联业务"中详解。

3. MyBatis-Plus 的 @TableField 高级配置

// 自动填充：插入时自动赋值（需配合 MetaObjectHandler）
@TableField(fill = FieldFill.INSERT)
private LocalDateTime createTime;

// 自动填充：更新时自动赋值
@TableField(fill = FieldFill.INSERT_UPDATE)
private LocalDateTime updateTime;

// 乐观锁：版本号字段
@TableField(fill = FieldFill.INSERT)
@Version
private Integer version;

// 逻辑删除：标记删除字段
@TableLogic
@TableField(fill = FieldFill.INSERT)
private Integer deleted;

这些高级特性在第9次课"持久层综合实践"和后续课程中讲解。

4. 注解 SQL 的动态 SQL 方案

注解 SQL 本身不支持 <if> 标签，但可通过 @SelectProvider、@InsertProvider 等注解配合 Java 代码生成动态 SQL：

@SelectProvider(type = UserSqlProvider.class, method = "selectByCondition")
List<SysUser> selectByCondition(SysUser condition);

但企业实践中，复杂动态 SQL 通常直接用 XML 更清晰，@SelectProvider 使用较少。

5. SQL 注入的真实案例与防护

经典案例：某高校教务系统登录接口使用 SELECT * FROM user WHERE username='${username}' AND password='${password}'，攻击者输入用户名 ' OR '1'='1' --，密码任意，即可绕过登录获取全部学生信息。

防护原则：

  1. 永远使用 #{} 参数化查询（预编译 + 转义）
  2. 动态表名/列名用 ${} 时必须做白名单校验
  3. 数据库账号最小权限（应用账号不应有 DROP/ALTER 权限）
  4. 敏感数据加密存储（密码用 BCrypt）
  5. 启用 WAF（Web 应用防火墙）作为额外防线

OWASP Top 10：SQL 注入长期位列 Web 安全威胁榜首，掌握 #{} 防注入是后端工程师的基本素养。

六、复习思考题

  1. @Mapper 和 @MapperScan 有什么区别？项目里应该选哪个？

    提示：@Mapper 是接口级注解，逐个声明；@MapperScan 是类级注解，在启动类上批量扫描指定包。项目实践中推荐 @MapperScan，新增 Mapper 无需改注解。两者二选一，不要同时使用。

  2. 继承 BaseMapper 后，最少写多少代码就能完成单表 CRUD？请列举 5 个常用方法。

    提示：继承 BaseMapper<T> 即可，零 SQL。常用方法：insert、deleteById、updateById、selectById、selectList。

  3. @TableName、@TableId、@TableField 分别解决什么映射问题？

    提示：@TableName 映射表名（类名与表名不符时必须）；@TableId 映射主键及生成策略（AUTO/ASSIGN_ID 等）；@TableField 映射普通字段或标记非表字段（exist = false）。

  4. @TableField(exist = false) 用在什么场景？不加会怎样？

    提示：用于实体类中存在但数据库表中没有的字段（如 confirmPassword）。不加会导致 MyBatis-Plus 把它当表字段，查询时报 Unknown column 错误。

  5. #{} 和 ${} 的本质区别是什么？为什么 #{} 能防 SQL 注入？

    提示：#{} 是预编译占位符，被替换为 JDBC 的 ?，参数通过 PreparedStatement.setXxx() 绑定，会被自动转义，参数不参与 SQL 语法解析；${} 是字符串拼接，直接把参数值拼入 SQL 字符串，可被注入恶意 SQL。

  6. 什么场景下必须使用 ${}？使用时如何保证安全？

    提示：动态表名（FROM ${table}）、动态列名（ORDER BY ${column}）、动态排序方向（ORDER BY x ${order}）时必须用 ${}，因为这些不能作为 PreparedStatement 参数。安全做法：代码层做白名单校验，只允许预定义的合法值。

  7. 注解 SQL 和 XML SQL 各有什么优缺点？什么时候用哪个？

    提示：注解 SQL 简洁直观，适合简单固定 SQL，但不支持动态标签；XML SQL 支持 <if>/<where>/<foreach> 等动态标签，适合复杂动态 SQL，但文件较多。简单查询用注解，复杂动态查询用 XML，两者可在同一 Mapper 中混用。

  8. XML 映射文件中 namespace 的作用是什么？写错会怎样？

    提示：namespace 用于绑定 XML 与 Mapper 接口，值必须等于接口全限定名。写错会导致 MyBatis 无法将 XML 的 SQL 与接口方法关联，调用时报 BindingException: Invalid bound statement (not found)。

  9. resultMap 和 resultType 有什么区别？

    提示：resultType 直接指定返回类型，要求字段名与属性名一致（或驼峰映射），简单场景用；resultMap 引用 <resultMap> 定义，可处理字段名不一致、复杂关联映射，复杂场景用。两者只能选一个。

  10. 如果调用 Mapper 方法时报 Invalid bound statement (not found)，应该如何排查？

    提示：依次检查：①XML 文件是否被扫描（mapper-locations 配置）；②namespace 是否等于接口全限定名；③<select id="xxx"> 的 id 是否与方法名一致；④target/classes 下是否有编译后的 XML（mvn clean compile）。

  11. updateById 方法更新时，实体类中值为 null 的字段会被更新吗？为什么？

    提示：不会。MyBatis-Plus 默认策略是 null 字段不参与 UPDATE 语句拼接（FieldStrategy.NOT_NULL），避免误覆盖。若需更新为 null，用 UpdateWrapper.set("字段", null) 或 @TableField(updateStrategy = FieldStrategy.IGNORED)。

  12. 为什么实体类字段推荐用包装类型（Long/Integer）而不是基本类型（long/int）？

    提示：基本类型有默认值（int 默认 0），会被 MyBatis-Plus 误认为"有值"而参与更新，可能误覆盖数据库中的 null。包装类型默认 null，不参与更新，更安全。
