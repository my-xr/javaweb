知识点详解

K12-1 RESTful设计原则回顾

1.1 定义

REST（Representational State Transfer，表述性状态转移）是 Roy Fielding 在2000年博士论文中提出的一种网络应用架构风格。RESTful API 是符合REST架构约束的HTTP接口设计风格。

RESTful的六大核心原则（针对接口设计实践版）：

原则 含义 示例
① 资源用名词复数 URL表示资源，用名词复数 /users、/projects、/tasks
② HTTP方法表达操作 用方法语义表达对资源的操作 GET查询、POST创建、PUT更新、DELETE删除
③ ID用路径参数 定位具体资源用path /users/1、/projects/1/tasks/2
④ 无状态 每个请求自包含所有信息，服务器不保存会话状态 请求带Token，不依赖Session
⑤ 统一JSON响应 所有响应用JSON，结构统一 {"code":200,"message":"ok","data":{...}}
⑥ 版本管理 接口版本在路径或Header中体现 /api/v1/users

1.2 原理

REST的核心思想是 "资源 + 表述"：

图示 2：结构与流程重绘
客户端 ──HTTP方法──▶ 资源（URL） ──表述（JSON）──▶ 客户端

已由原 Markdown 字符图转换为网页图示，保留原有逻辑关系并优化阅读效果。

  • 资源：系统中可被命名的实体，如用户、项目、任务。每个资源有唯一URI。
  • 表述：资源在某一时刻的状态数据，通常用JSON表示。
  • 状态转移：通过HTTP方法对资源状态进行增删改查。

1.3 问题：为什么不推荐动词路径？

反例：

POST /api/getUserById?id=1
POST /api/createUser
POST /api/deleteUser?id=1
POST /api/updateUser

问题分析：

  1. 资源不清晰：URL里看不出操作的是什么资源。
  2. 方法语义浪费：所有操作都用POST，HTTP方法成了摆设。
  3. 无法缓存：POST不被缓存，GET可以。
  4. 难以扩展：新增操作就要新增URL，URL数量爆炸。

RESTful改写：

GET    /api/v1/users/1        # 查询
POST   /api/v1/users          # 创建
DELETE /api/v1/users/1        # 删除
PUT    /api/v1/users/1        # 全量更新
PATCH  /api/v1/users/1        # 部分更新

1.4 完整代码：HTTP方法与资源操作对照

package com.ctts.demo;

import org.springframework.web.bind.annotation.*;

/**
 * RESTful 方法语义演示（非真实业务，仅说明原则）
 */
@RestController
@RequestMapping("/api/v1/users")
public class RestDemoController {

    // ① GET /users —— 列表查询（安全、幂等、可缓存）
    @GetMapping
    public String list() {
        return "GET: 查询用户列表";
    }

    // ② GET /users/{id} —— 详情查询（安全、幂等、可缓存）
    @GetMapping("/{id}")
    public String getById(@PathVariable Long id) {
        return "GET: 查询用户 " + id;
    }

    // ③ POST /users —— 创建（非幂等）
    @PostMapping
    public String create(@RequestBody String userDTO) {
        return "POST: 创建用户 " + userDTO;
    }

    // ④ PUT /users/{id} —— 全量更新（幂等）
    @PutMapping("/{id}")
    public String update(@PathVariable Long id, @RequestBody String userDTO) {
        return "PUT: 全量更新用户 " + id;
    }

    // ⑤ PATCH /users/{id} —— 部分更新（幂等）
    @PatchMapping("/{id}")
    public String patch(@PathVariable Long id, @RequestBody String userDTO) {
        return "PATCH: 部分更新用户 " + id;
    }

    // ⑥ DELETE /users/{id} —— 删除（幂等）
    @DeleteMapping("/{id}")
    public String delete(@PathVariable Long id) {
        return "DELETE: 删除用户 " + id;
    }
}

1.6 易错点

易错点 错误示例 正确做法
URL含动词 /api/getUsers /api/users + GET方法
资源用单数 /api/user/1 /api/users/1
用POST做查询 POST /api/users/search GET /api/users?name=张三
用GET做创建 GET /api/users/create?name=张三 POST /api/users
操作写在路径 /api/users/1/delete DELETE /api/users/1
混用大小写 /api/Users/1 /api/users/1（全小写）

1.7 小结

RESTful的精髓是 "让HTTP方法干活，让URL安静地描述资源"。一句话口诀："名词复数表资源，方法动词表操作，ID定位用路径，统一JSON做响应"。

K12-2 接口路径设计

2.1 定义

接口路径设计是指为系统每个接口规划 URL结构，包括：

  • 资源命名：用什么名词表示资源
  • 嵌套资源：资源间的从属关系如何表达
  • 版本管理：接口演进时如何兼容旧版本

2.2 原理

资源命名规范：

  1. 用名词复数：/users、/projects、/tasks
  2. 全小写，多词用连字符：/user-profiles（不用驼峰、不用下划线）
  3. 名词要表达业务含义，避免技术名词：/users（√）而非 /tbl_user（×）

嵌套资源：

  • 表达从属关系：/projects/1/tasks 表示"项目1下的任务列表"
  • 层级一般不超过2层：/projects/1/tasks/2 可以，/projects/1/tasks/2/comments/3/users/4 太深
  • 深层关系用query或独立资源：/comments?taskId=2 优于 /projects/1/tasks/2/comments

版本管理：

  • URL版本（推荐）：/api/v1/users、/api/v2/users
  • Header版本：Accept: application/vnd.ctts.v1+json
  • Query版本：/api/users?version=1

三种方式对比：

方式 优点 缺点 推荐度
URL版本 /api/v1/ 直观、可缓存、易调试 URL变更需同步前端 ★★★
Header版本 URL干净 不可缓存、调试难 ★★
Query版本 简单 易忽略、不可缓存 ★

2.3 问题：嵌套层级过深会怎样？

反例：

GET /api/v1/projects/1/tasks/2/comments/3/users/4

问题：

  1. 可读性差：5层路径，含义难懂
  2. 耦合度高：任务删除后，这条URL就失效了
  3. 服务端实现复杂：要链式查询4张表
  4. 不符合REST：REST强调资源独立性，深层嵌套违背了"资源平级"思想

正确做法：

GET /api/v1/comments/3              # 直接查评论
GET /api/v1/tasks/2/comments        # 2层够用

2.7 小结

K12-3 请求参数设计

3.1 定义

请求参数设计是指为接口规划 参数的位置与类型。HTTP请求有四类参数位置：

位置 适用场景 Spring注解 示例
query 筛选、分页、排序 @RequestParam ?page=1&size=10&name=张三
path 定位具体资源 @PathVariable /users/1 中的 1
body 创建、更新复杂数据 @RequestBody POST/PUT的JSON体
header 认证、追踪、自定义 @RequestHeader Authorization: Bearer xxx

3.2 原理：四种参数位置的选择决策

图示 3：结构与流程重绘
┌─────────────────────────────────────────────┐ │ 参数位置选择决策树 │ ├─────────────────────────────────────────────┤ │ │ │ 是定位资源唯一标识吗？ │ │ ├─ 是 → path （/users/{id}） │ │ └─ 否 ↓ │ │ │ │ 是创建/更新的复杂对象吗？ │ │ ├─ 是 → body （@RequestBody） │ │ └─ 否 ↓ │ │ │ 是认证/追踪信息吗？ │ │ ├─ 是 → header（Authorization） │ │ └─ 否 ↓ │ │ │ │ → query（?page=1&name=xxx） │ │ │ └─────────────────────────────────────────────┘

3.3 问题：参数位置用错会怎样？

反例1：用query传ID

GET /api/v1/users?id=1     # ✗

问题：①不符合REST（ID应定位资源）；②无法被缓存（query参数变化触发新缓存）；③语义模糊（是查id=1还是筛选id=1？）

正确：GET /api/v1/users/1

反例2：用query传复杂对象

POST /api/v1/users?name=张三&email=zhangsan@ctts.com&role=STUDENT&phone=13800000000

问题：①URL过长浏览器截断；②参数类型复杂无法表达；③敏感信息暴露在URL

正确：POST /api/v1/users + body

{
  "name": "张三",
  "email": "zhangsan@ctts.com",
  "role": "STUDENT",
  "phone": "13800000000"
}

反例3：用body做查询

POST /api/v1/users/search
Body: {"name":"张三","role":"STUDENT"}

问题：①GET变POST，不可缓存；②违反REST（查询应用GET）

正确：GET /api/v1/users?name=张三&role=STUDENT

3.4 完整代码：四类参数的Controller示例

package com.ctts.controller;

import com.ctts.dto.*;
import com.ctts.vo.*;
import com.ctts.common.Result;
import com.ctts.common.PageResult;
import io.swagger.v3.oas.annotations.Operation;
import io.swagger.v3.oas.annotations.Parameter;
import io.swagger.v3.oas.annotations.tags.Tag;
import jakarta.validation.Valid;
import org.springframework.web.bind.annotation.*;

/**
 * 用户接口控制器 —— 演示四类参数位置
 */
@Tag(name = "用户管理", description = "用户的增删改查")
@RestController
@RequestMapping("/api/v1/users")
public class UserController {

    /**
     * ① path 参数：定位资源
     */
    @Operation(summary = "查询用户详情", description = "根据用户ID查询用户完整信息")
    @GetMapping("/{id}")
    public Result<UserVO> getById(
            @Parameter(description = "用户ID", required = true, example = "1")
            @PathVariable Long id) {
        return Result.success(new UserVO(id, "张三"));
    }

    /**
     * ② query 参数：筛选 + 分页
     */
    @Operation(summary = "分页查询用户", description = "支持按角色筛选、关键字搜索")
    @GetMapping
    public Result<PageResult<UserVO>> page(
            @Parameter(description = "角色：STUDENT/TEACHER/ADMIN", example = "STUDENT")
            @RequestParam(required = false) String role,

易错点 错误 正确

K12-4 响应数据设计

4.1 定义

响应数据设计是指为所有接口规划 统一的响应结构，包括：

  • 成功响应：统一 Result<T> 包装
  • 分页响应：PageResult<T> 含分页元信息
  • 错误响应：含错误码、消息、时间戳、路径

4.2 原理：为什么需要统一响应？

不统一的响应（反例）：

// 接口A 成功
{"id": 1, "name": "张三"}

// 接口B 成功
{"data": {"id": 1, "name": "张三"}, "success": true}

// 接口A 失败
{"error": "用户不存在"}

// 接口B 失败
{"code": 404, "msg": "User not found"}

问题：①前端要为每个接口写不同的解析逻辑；②错误处理混乱；③无法统一拦截。

统一响应（正例）：

// 成功
{"code": 200, "message": "ok", "data": {"id": 1, "name": "张三"}}

// 失败
{"code": 40401, "message": "用户不存在", "timestamp": "...", "path": "..."}

4.3 问题：业务码与HTTP状态码如何配合？

两种流派：

流派A：HTTP状态码 + 业务码（推荐）

  • HTTP状态码反映"传输层"结果：200成功、404未找到、500服务器错误
  • 业务码反映"业务层"结果：20001成功、40401用户不存在、40402项目不存在
HTTP 404
{"code": 40401, "message": "用户不存在"}

流派B：HTTP永远200 + 业务码

  • 所有响应HTTP都是200，只靠业务码区分
HTTP 200
{"code": 40401, "message": "用户不存在"}

CTTS采用流派A：让HTTP状态码发挥语义，业务码做细粒度区分。

① Result 统一响应类
package com.ctts.common;

import io.swagger.v3.oas.annotations.media.Schema;
import lombok.Data;
import lombok.AllArgsConstructor;
import lombok.NoArgsConstructor;

/**
 * 统一响应结构
 * @param <T> 业务数据类型
 */
@Data
@NoArgsConstructor
@AllArgsConstructor
@Schema(description = "统一响应结构")
public class Result<T> {

    @Schema(description = "业务码：200成功，其他为错误码", example = "200")
    private Integer code;

    @Schema(description = "提示信息", example = "ok")
    private String message;

    @Schema(description = "业务数据")
    private T data;

    /** 成功（无数据） */
    public static <T> Result<T> success() {
        return new Result<>(200, "ok", null);
    }

    /** 成功（带数据） */
    public static <T> Result<T> success(T data) {
        return new Result<>(200, "ok", data);
    }

    /** 成功（自定义消息+数据） */
    public static <T> Result<T> success(String message, T data) {
        return new Result<>(200, message, data);
    }

    /** 失败（自定义码+消息） */
    public static <T> Result<T> fail(Integer code, String message) {
        return new Result<>(code, message, null);
    }
}

package com.ctts.common;

import io.swagger.v3.oas.annotations.media.Schema;
import lombok.Data;
import lombok.AllArgsConstructor;
import lombok.NoArgsConstructor;

import java.util.Collections;
import java.util.List;

/**
 * 分页响应结构
 * @param <T> 列表元素类型
 */
@Data
@NoArgsConstructor
@AllArgsConstructor
@Schema(description = "分页响应结构")
public class PageResult<T> {

    @Schema(description = "当前页数据列表")
    private List<T> list;

    @Schema(description = "总记录数", example = "100")
    private Long total;

    @Schema(description = "当前页码", example = "1")
    private Integer page;

    @Schema(description = "每页条数", example = "10")
    private Integer size;

    @Schema(description = "总页数", example = "10")
    private Integer totalPages;

    /** 构造分页结果 */
    public static <T> PageResult<T> of(List<T> list, Long total, Integer page, Integer size) {
        PageResult<T> r = new PageResult<>();
        r.setList(list);
        r.setTotal(total);
        r.setPage(page);
        r.setSize(size);
        r.setTotalPages(size == 0 ? 0 : (int) Math.ceil((double) total / size));
        return r;
    }

    /** 空分页（便于测试） */
    public static <T> PageResult<T> empty() {
        return new PageResult<>(Collections.emptyList(), 0L, 1, 10, 0);
    }
}

4.6 易错点

易错点 错误 正确
data直接返回实体 Result<User> 泄露密码字段 Result<UserVO> 用VO过滤
分页无total 只返回list 必须含total/totalPages
错误无时间戳 只有code+message 加timestamp便于排查

4.7 小结

统一响应三件套："Result包成功，PageResult包分页，ErrorResponse包错误"。一句话："前端只认一种结构，后端只写一种结构"——这就是契约。

Knife4j 是基于 OpenAPI 3 的 Java MVC 框架增强文档工具，是 Swagger/SpringDoc 的"中文化增强版"。通过在Controller上加注解，即可自动生成可交互的在线接口文档，访问地址 http://localhost:8080/doc.html。

5.6 易错点

易错点 错误 正确
忘记加@Tag Controller无分组，全堆在default 每个Controller必加@Tag
summary过长 @Operation(summary="根据用户ID查询用户的完整信息包括姓名邮箱...") summary≤15字，详细放description
example缺失 @Parameter(description="用户ID") 加 example="1"
必填未标注 @Parameter(description="用户ID") required=true
DTO字段无@Schema 只有 private String name; @Schema(description="用户名", example="张三")
注解用错包 import io.swagger.annotations.*（Swagger2） import io.swagger.v3.oas.annotations.*（OpenAPI3）
生产环境未关闭文档 上线后doc.html可访问 配置 springdoc.api-docs.enabled=false

5.7 小结

Knife4j的精髓是 "注解即文档"——代码与文档同源，永远不会过时。一句话："写好注解，文档自来；不写注解，前端难猜"。

package com.ctts.controller;

import com.ctts.common.PageResult;
import com.ctts.common.Result;
import com.ctts.dto.*;
import com.ctts.vo.TaskVO;
import io.swagger.v3.oas.annotations.Operation;
import io.swagger.v3.oas.annotations.Parameter;
import io.swagger.v3.oas.annotations.tags.Tag;
import jakarta.validation.Valid;
import org.springframework.web.bind.annotation.*;

/**
 * 任务接口控制器
 * 嵌套资源：/projects/{projectId}/tasks
 */
@Tag(name = "任务管理", description = "项目下的任务增删改查、指派")
@RestController
@RequestMapping("/api/v1/projects/{projectId}/tasks")
public class TaskController {

    @Operation(summary = "创建任务", description = "在指定项目下创建任务")
    @PostMapping
    public Result<TaskVO> create(
            @Parameter(description = "项目ID", required = true, example = "1")
            @PathVariable Long projectId,
            @Valid @RequestBody TaskCreateDTO dto) {
        return Result.success(new TaskVO(1L, projectId, dto.getTitle()));
    }

    @Operation(summary = "查询任务详情")
    @GetMapping("/{id}")
    public Result<TaskVO> getById(
            @Parameter(description = "项目ID", required = true, example = "1")
            @PathVariable Long projectId,
            @Parameter(description = "任务ID", required = true, example = "2")
            @PathVariable Long id) {
        return Result.success(new TaskVO(id, projectId, "任务标题"));
    }

    @Operation(summary = "分页查询任务", description = "支持按状态、指派人筛选")
    @GetMapping
    public Result<PageResult<TaskVO>> page(
            @Parameter(description = "项目ID", required = true, example = "1")
            @PathVariable Long projectId,
            @Parameter(description = "任务状态", example = "TODO")
            @RequestParam(required = false) String status,
            @Parameter(description = "指派人ID", example = "5")
            @RequestParam(required = false) Long assigneeId,
            @Parameter(description = "页码", example = "1")
            @RequestParam(defaultValue = "1") Integer page,
            @Parameter(description = "每页条数", example = "10")
            @RequestParam(defaultValue = "10") Integer size) {
        return Result.success(PageResult.empty());
    }

    @Operation(summary = "更新任务")
    @PutMapping("/{id}")
    public Result<TaskVO> update(
            @PathVariable Long projectId,
            @Parameter(description = "任务ID", required = true, example = "2")
            @PathVariable Long id,
            @Valid @RequestBody TaskUpdateDTO dto) {
        return Result.success(new TaskVO(id, projectId, dto.getTitle()));
    }

    @Operation(summary = "删除任务")
    @DeleteMapping("/{id}")
    public Result<Void> delete(
            @PathVariable Long projectId,
            @Parameter(description = "任务ID", required = true, example = "2")
            @PathVariable Long id) {
        return Result.success();
    }

    @Operation(summary = "指派任务", description = "将任务指派给指定学生，部分更新")
    @PatchMapping("/{id}/assignee")
    public Result<Void> assign(
            @PathVariable Long projectId,
            @Parameter(description = "任务ID", required = true, example = "2")
            @PathVariable Long id,
            @Parameter(description = "被指派人ID", example = "5")
            @RequestBody Long assigneeId) {
        return Result.success();
    }
}

拓展阅读

拓展1：REST成熟度模型（Richardson Maturity Model）

Leonard Richardson 提出的REST成熟度4级模型：

级别 特征 示例
Level 0 一个端点，全用POST POST /api + body描述操作
Level 1 资源化，多端点 /users、/projects 但全用POST
Level 2 正确使用HTTP方法与状态码 GET/POST/PUT/DELETE + 200/201/404
Level 3 HATEOAS（超媒体） 响应中含可执行操作的链接

CTTS目标：达到Level 2。Level 3在企业级实际很少用，了解即可。

拓展2：gRPC与REST的对比

维度 REST gRPC
协议 HTTP/1.1 HTTP/2
数据格式 JSON（文本） Protobuf（二进制）
性能 一般 高（约5-10倍）
浏览器支持 原生 需gRPC-Web
文档 OpenAPI/Swagger proto文件
适用场景 对外API、前后端 微服务内部通信

拓展3：GraphQL——另一种API风格

GraphQL允许客户端"按需查询字段"，解决REST的"过度获取/获取不足"问题。例如：

query {
  user(id: 1) {
    name
    projects {
      name
      tasks(status: "TODO") {
        title
      }
    }
  }
}

但GraphQL学习成本高、缓存复杂，中小型项目仍以REST为主。

拓展4：OpenAPI 3 规范简介

OpenAPI 3 是Swagger的继任者，是RESTful API的描述规范。Knife4j底层就是OpenAPI 3。一个最小的OpenAPI 3 文档：

openapi: 3.0.1
info:
  title: CTTS API
  version: 1.0.0
paths:
  /api/v1/users/{id}:
    get:
      summary: 查询用户详情
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: integer
      responses:
        '200':
          description: 成功
