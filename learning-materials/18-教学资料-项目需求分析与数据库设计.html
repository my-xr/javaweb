一、学习导读

1.1 本课定位

本课是M7综合项目开发模块的第一课，标志从"零散知识点学习"转向"完整项目实战"。CTTS（Campus Training Task System，校园实训任务管理系统）将作为后续多次课的主线项目，贯穿数据库设计、后端接口开发、前后端联调、测试部署全流程。

本课聚焦项目需求分析与数据库设计——这是所有后端开发的起点。一个好的数据库设计，决定了系统未来3-5年的可维护性；一个糟糕的设计，会让后续编码、优化、扩展步步维艰。

1.2 学习目标

读完本资料后，你应当能够：

  1. 独立分析一个中等规模信息系统的功能需求与非功能需求。
  2. 识别实体及其关系，画出ER图并转化为符合第三范式的表结构。
  3. 编写规范的CREATE TABLE SQL，合理设置主键、外键、约束、注释、索引。
  4. 编写并执行数据库初始化脚本，插入测试数据并验证外键关系。
  5. 对他人表结构设计进行评审，提出建设性改进意见。

1.3 学习建议

  • 先理解业务再写代码：务必先读懂CTTS需求说明书，再进入表设计。
  • 动手验证：所有SQL请在MySQL中实际执行，观察结果。
  • 对比反思：尝试用不同的方式设计同一张表，比较优劣。
  • 团队视角：假设你是后端团队一员，你的表设计要能被同事看懂、用好。

1.4 前置知识

  • MySQL基本语法（CREATE/INSERT/SELECT/UPDATE/DELETE）。
  • 面向对象基础（类、属性、关系）。
  • 软件工程基本概念（需求、设计、实现）。

二、知识点详解

K18-1 需求分析

2.1.1 需求拆解方法

需求分析是软件开发的第一步，目标是将模糊的用户期望转化为清晰的系统行为描述。常用方法有两种：

方法 思路 适用场景
自顶向下 系统→模块→功能→用例 已有明确系统边界，从整体到细节
自底向上 用户故事→功能点→模块 需求零散，从用户场景聚合

CTTS采用自顶向下：系统分为5大模块（用户/项目/任务/提交/评审），每个模块再细化为具体功能点。

2.1.2 功能需求

功能需求描述系统"做什么"。CTTS功能需求如下：

模块1 用户管理

  • 注册：学生/教师/管理员注册账号。
  • 登录：账号密码登录，返回角色信息。
  • 权限控制：不同角色可访问的功能不同。

模块2 项目管理

  • 教师：创建/编辑/发布实训项目。
  • 学生：浏览已发布项目、查看详情。
  • 管理员：审核项目、下线项目。

模块3 任务管理

  • 教师：在项目下创建任务、设置截止时间与总分。
  • 学生：查看任务详情、下载任务附件。

模块4 提交管理

  • 学生：提交任务成果（文本+文件），支持多次提交。
  • 教师：查看提交列表。

模块5 评审管理

  • 教师：对学生提交打分、写评语。
  • 学生：查看评审结果。

2.1.3 非功能需求

非功能需求描述系统"做得多好"，常被初学者忽视，却直接决定用户体验。

维度 CTTS要求
安全 密码加密存储（BCrypt）、SQL注入防护、越权访问拦截
性能 列表查询响应<500ms、支持100并发用户
可用性 7×24可用、界面易用、操作不超过3步
可维护性 代码规范、注释完整、模块解耦
可扩展性 支持后续新增"小组任务""自动评测"等功能

2.1.4 用例图基础

用例图（Use Case Diagram）是UML的一种，用于描述参与者与系统功能的交互。

三要素：

  • 参与者（Actor）：人形图标，表示与系统交互的角色。
  • 用例（Use Case）：椭圆，表示系统提供的功能。
  • 关系：连线，参与者与用例的关联。

CTTS用例图简述：

  • 学生参与者 → 登录、浏览项目、查看任务、提交任务、查看评审
  • 教师参与者 → 登录、创建项目、创建任务、查看提交、评审提交
  • 管理员参与者 → 登录、用户管理、项目审核、系统管理

K18-2 数据库设计基础

2.2.1 ER图概念

ER图（Entity-Relationship Diagram，实体-关系图）是概念模型的核心工具，用于在设计阶段描述数据结构。

三要素：

  • 实体（Entity）：客观存在的事物，如用户、项目、任务。矩形表示。
  • 属性（Attribute）：实体的特征，如用户的姓名、角色。椭圆表示。
  • 关系（Relationship）：实体间的联系，如"教师-创建-项目"。菱形表示。

2.2.2 实体关系

实体间关系有三种基数：

关系 说明 CTTS示例
一对一（1:1） A对应一个B，B对应一个A 用户-用户详情（CTTS暂不涉及）
一对多（1:N） A对应多个B，B属于一个A 项目-任务、任务-提交、提交-评审
多对多（M:N） A对应多个B，B对应多个A 学生-任务（通过提交表转换）

重点：一对多关系在数据库中通过外键实现——在"多"的一方加外键引用"一"的一方主键。多对多关系通常拆解为两个一对多，引入中间表。

2.2.3 外键设计

外键（Foreign Key）是表间关系的保障，作用：

  1. 保证数据完整性：外键值必须引用已存在的主键。
  2. 明确业务语义：task_submission.user_id表示"提交者是谁"。
  3. 支持级联操作：可设置ON DELETE CASCADE级联删除。

CTTS外键设计原则：

  • 所有外键必须显式声明FOREIGN KEY约束。
  • 外键命名：fk_子表_引用表（如fk_task_project）。
  • 默认不级联删除，避免误删；按业务需要设置。

2.2.4 范式基础

范式（Normal Form, NF）是关系数据库设计的规范，目标是减少冗余、消除异常。

范式 要求 反例 正例
1NF 字段原子性，不可再分 项目信息="Java,Python" 拆为两行或单独表
2NF 非主属性完全依赖主键（针对复合主键） 主键(学号,课程)但姓名只依赖学号 拆分学生表与选课表
3NF 非主属性不传递依赖主键 表含学号→院系号→院系名 拆分学生表与院系表

CTTS范式分析：

  • 所有表均满足1NF：每个字段不可再分。
  • 所有表主键为单列id，天然满足2NF。
  • 通过外键拆分实体，避免传递依赖，满足3NF。例如：不在task表中冗余存储项目名称，而是通过project_id关联。

工程提示：实际项目中为查询性能可适度反范式（冗余字段），但需明确权衡。CTTS作为教学项目严格遵循3NF。

2.3.2 通用设计规范

  • 主键：id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY
  • 命名：小写+下划线，表名单数（sys_user例外，保留sys_前缀表示系统表）
  • 时间字段：create_time、update_time，DATETIME类型，默认CURRENT_TIMESTAMP
  • 字符集：utf8mb4（支持emoji），排序规则utf8mb4_general_ci
  • 存储引擎：InnoDB（支持事务与外键）
  • 每个字段必加COMMENT注释

2.3.3 字段设计原则

  • ID类：BIGINT，预留扩展空间。
  • 字符串短文本：VARCHAR(n)，按实际最大长度设。
  • 字符串长文本：TEXT。
  • 状态/角色类：TINYINT，注释说明取值含义。
  • 时间：DATETIME。
  • 分数：INT，按业务约束范围。

K18-4 索引基础

2.4.1 索引概念

索引是数据库中用于加速查询的数据结构（默认B+树）。类比书籍目录：通过目录快速定位章节，无需逐页翻阅。

代价：

  • 占用额外存储空间。
  • 写入（INSERT/UPDATE/DELETE）时需同步维护索引，拖慢写入。

2.4.2 索引类型

类型 关键字 特点 CTTS示例
主键索引 PRIMARY KEY 自动创建，唯一且非空 所有表的id
唯一索引 UNIQUE 列值唯一，允许一个NULL sys_user.username
普通索引 INDEX/KEY 加速查询，无唯一约束 sys_user.role、training_project.status

2.4.3 何时建索引

该建：

  • 经常作为WHERE条件的列（如role、status）。
  • 经常用于JOIN的列（外键列）。
  • 区分度高（取值多样）的列。
  • 经常用于ORDER BY/GROUP BY的列。

不该建：

  • 数据量小的表（全表扫描更快）。
  • 区分度低的列（如性别，只有男/女）。
  • 写入极频繁、查询少的列。
  • 频繁更新的列（索引维护成本高）。

2.4.4 CTTS索引方案

表 索引 类型 理由
sys_user username 唯一 登录按username查询，且需唯一
sys_user role 普通 按角色筛选用户
training_project teacher_id 普通 按教师查项目
training_project status 普通 按状态筛选项目
task project_id 普通 按项目查任务
task_submission task_id 普通 按任务查提交
task_submission user_id 普通 按学生查提交
task_review submission_id 普通 按提交查评审
task_review reviewer_id 普通 按教师查评审

K18-5 数据库初始化脚本

2.5.1 脚本编写规范

  • 文件头部注释：数据库名、版本、创建时间、作者。
  • 顺序：先建库→后建表（注意外键依赖顺序：被引用表先建）。
  • 每条语句以分号结尾，关键字大写。
  • INSERT语句列出全部字段名，避免隐式依赖。

2.5.2 执行流程

  1. CREATE DATABASE：创建数据库并指定字符集。
  2. CREATE TABLE：按依赖顺序创建5张表。
  3. INSERT：插入测试数据（注意外键约束，先插入被引用表的数据）。
  4. 验证：用SELECT JOIN查询确认数据正确关联。

2.5.3 建表依赖顺序

sys_user（无外键依赖）
  ↓
training_project（依赖sys_user）
  ↓
task（依赖training_project）
  ↓
task_submission（依赖task、sys_user）
  ↓
task_review（依赖task_submission、sys_user）

三、综合示例：CTTS完整设计

3.1 CTTS需求说明书

3.1.1 项目背景

高校实训是软件工程等专业的核心实践环节。传统实训管理依赖Excel表格+QQ群通知，存在任务下发混乱、提交进度不透明、评审结果难追溯等问题。CTTS系统旨在通过Web化、流程化的方式，实现实训项目的全生命周期管理。

3.1.2 角色定义

角色 标识 职责
学生 role=1 浏览项目/任务、提交任务成果、查看评审
教师 role=2 创建项目/任务、查看提交、评审打分
管理员 role=3 用户管理、项目审核、系统维护

3.1.3 功能需求清单

FR-01 用户管理

  • FR-01-1 用户注册（指定角色）
  • FR-01-2 用户登录（账号密码）
  • FR-01-3 用户信息查询/修改
  • FR-01-4 用户列表（管理员）

FR-02 项目管理

  • FR-02-1 教师创建实训项目
  • FR-02-2 教师编辑项目信息
  • FR-02-3 发布/下线项目
  • FR-02-4 学生浏览项目列表
  • FR-02-5 查看项目详情

FR-03 任务管理

  • FR-03-1 教师在项目下创建任务
  • FR-03-2 编辑任务
  • FR-03-3 设置截止时间与总分
  • FR-03-4 学生查看任务列表与详情

FR-04 提交管理

  • FR-04-1 学生提交任务（文本+文件URL）
  • FR-04-2 支持多次提交
  • FR-04-3 查看提交历史
  • FR-04-4 教师查看某任务全部提交

FR-05 评审管理

  • FR-05-1 教师对提交打分+评语
  • FR-05-2 支持多次评审（修订评分）
  • FR-05-3 学生查看评审结果
  • FR-05-4 按项目统计评审成绩

3.1.4 非功能需求清单

编号 维度 要求
NFR-01 安全 密码BCrypt加密、接口鉴权、SQL注入防护
NFR-02 性能 列表查询<500ms、详情查询<200ms

NFR-04 可维护性 代码符合阿里规约、注释完整

3.1.5 用例描述示例

用例：学生提交任务

  • 参与者：学生
  • 前置条件：学生已登录，任务处于开放状态
  • 主流程：
    1. 学生进入任务详情页
    2. 点击"提交任务"
    3. 填写提交内容、上传文件（获得file_url）
    4. 系统保存提交记录，状态=待评审
    5. 返回提交成功提示
  • 后置条件：提交记录可被教师查看与评审

用例：教师评审提交

  • 参与者：教师
  • 前置条件：教师已登录，存在待评审提交
  • 主流程：
    1. 教师进入提交列表
    2. 选择某条提交
    3. 填写评分（0~任务总分）、评语
    4. 系统保存评审记录，提交状态=已评审
    5. 返回评审成功提示
  • 后置条件：学生可查看评审结果

3.2 ER图文字描述

CTTS系统包含5个实体，关系如下：

  1. sys_user（用户）与 training_project（项目）：一对多。一个教师（role=2）可创建多个项目，一个项目由一个教师负责。training_project.teacher_id为外键。

  2. training_project（项目）与 task（任务）：一对多。一个项目包含多个任务，一个任务属于一个项目。task.project_id为外键。

  3. sys_user（学生）与 task_submission（提交）：一对多。一个学生有多次提交，一条提交属于一个学生。task_submission.user_id为外键。

  4. task（任务）与 task_submission（提交）：一对多。一个任务收到多条提交，一条提交针对一个任务。task_submission.task_id为外键。

  5. task_submission（提交）与 task_review（评审）：一对多。一条提交可被多次评审（支持修订），一条评审针对一条提交。task_review.submission_id为外键。

  6. sys_user（教师）与 task_review（评审）：一对多。一个教师可进行多次评审，一条评审由一个教师完成。task_review.reviewer_id为外键。

3.3 范式分析说明

CTTS五张表均满足第三范式（3NF），分析如下：

3.3.1 sys_user表

  • 1NF：每个字段（username、password、real_name等）不可再分。✓
  • 2NF：主键为单列id，所有非主属性完全依赖id。✓
  • 3NF：非主属性间无传递依赖（如role不依赖username）。✓

3.3.2 training_project表

  • 1NF：title、description等字段原子。✓
  • 2NF：单列主键id。✓
  • 3NF：不在表中冗余教师姓名（通过teacher_id关联sys_user获取），消除传递依赖。✓

3.3.3 task表

  • 1NF：✓
  • 2NF：✓
  • 3NF：不冗余项目名称（通过project_id关联），✓

3.3.4 task_submission表

  • 1NF：✓
  • 2NF：✓
  • 3NF：不冗余任务标题、学生姓名，均通过外键关联获取，✓

3.3.5 task_review表

  • 1NF：✓
  • 2NF：✓
  • 3NF：不冗余提交内容、教师姓名，✓

反例警示：若在task_submission中冗余存储"任务标题"，当task表更新标题时，submission中的冗余字段会与task表不一致，产生更新异常。这正是3NF要避免的。

DROP DATABASE IF EXISTS ctts;
CREATE DATABASE ctts DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;
USE ctts;

-- ------------------------------------------------------------
-- 步骤2：创建表（按外键依赖顺序）
-- ------------------------------------------------------------

-- ------------------------------------------------------------
-- 表1：sys_user 用户表
-- ------------------------------------------------------------
DROP TABLE IF EXISTS sys_user;
CREATE TABLE sys_user (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '用户ID',
    username    VARCHAR(50)  NOT NULL                COMMENT '登录用户名',
    password    VARCHAR(100) NOT NULL                COMMENT '密码（BCrypt加密）',
    real_name   VARCHAR(50)  NOT NULL                COMMENT '真实姓名',
    role        TINYINT      NOT NULL                COMMENT '角色：1学生 2教师 3管理员',
    phone       VARCHAR(20)           DEFAULT NULL   COMMENT '手机号',
    email       VARCHAR(100)          DEFAULT NULL   COMMENT '邮箱',
    status      TINYINT      NOT NULL DEFAULT 1      COMMENT '状态：1正常 0禁用',
    create_time DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    update_time DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (id),
    UNIQUE KEY uk_user_username (username),
    KEY idx_user_role (role),
    KEY idx_user_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';

-- ------------------------------------------------------------
-- 表2：training_project 实训项目表
-- ------------------------------------------------------------
DROP TABLE IF EXISTS training_project;
CREATE TABLE training_project (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '项目ID',
    title       VARCHAR(100) NOT NULL                COMMENT '项目标题',
    description VARCHAR(500)          DEFAULT NULL   COMMENT '项目描述',
    teacher_id  BIGINT UNSIGNED NOT NULL              COMMENT '负责教师ID（引用sys_user.id）',
    start_date  DATE          NOT NULL               COMMENT '开始日期',
    end_date    DATE          NOT NULL               COMMENT '结束日期',
    status      TINYINT       NOT NULL DEFAULT 1     COMMENT '状态：1待发布 2进行中 3已结束 4已下线',
    create_time DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    update_time DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (id),
    KEY idx_project_teacher (teacher_id),
    KEY idx_project_status (status),
    CONSTRAINT fk_project_teacher FOREIGN KEY (teacher_id) REFERENCES sys_user (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='实训项目表';

-- ------------------------------------------------------------
-- 表3：task 任务表
-- ------------------------------------------------------------
DROP TABLE IF EXISTS task;
CREATE TABLE task (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '任务ID',
    project_id  BIGINT UNSIGNED NOT NULL              COMMENT '所属项目ID（引用training_project.id）',
    title       VARCHAR(100) NOT NULL                COMMENT '任务标题',
    description VARCHAR(1000)         DEFAULT NULL   COMMENT '任务描述',
    deadline    DATETIME      NOT NULL               COMMENT '截止时间',
    total_score INT           NOT NULL DEFAULT 100   COMMENT '任务总分',
    create_time DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    update_time DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (id),
    KEY idx_task_project (project_id),
    CONSTRAINT fk_task_project FOREIGN KEY (project_id) REFERENCES training_project (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='任务表';

-- ------------------------------------------------------------
-- 表4：task_submission 提交表
-- ------------------------------------------------------------
DROP TABLE IF EXISTS task_submission;
CREATE TABLE task_submission (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '提交ID',
    task_id     BIGINT UNSIGNED NOT NULL              COMMENT '任务ID（引用task.id）',
    user_id     BIGINT UNSIGNED NOT NULL              COMMENT '提交学生ID（引用sys_user.id）',
    content     TEXT                  DEFAULT NULL   COMMENT '提交文本内容',
    file_url    VARCHAR(255)          DEFAULT NULL   COMMENT '附件URL',
    submit_time DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '提交时间',
    status      TINYINT       NOT NULL DEFAULT 1     COMMENT '状态：1待评审 2已评审',
    PRIMARY KEY (id),
    KEY idx_submission_task (task_id),
    KEY idx_submission_user (user_id),
    CONSTRAINT fk_submission_task FOREIGN KEY (task_id) REFERENCES task (id),
    CONSTRAINT fk_submission_user FOREIGN KEY (user_id) REFERENCES sys_user (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='任务提交表';

-- ------------------------------------------------------------
-- 表5：task_review 评审表
-- ------------------------------------------------------------
DROP TABLE IF EXISTS task_review;
CREATE TABLE task_review (
    id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '评审ID',
    submission_id BIGINT UNSIGNED NOT NULL            COMMENT '提交ID（引用task_submission.id）',
    reviewer_id   BIGINT UNSIGNED NOT NULL            COMMENT '评审教师ID（引用sys_user.id）',
    score         INT           NOT NULL             COMMENT '评分',
    comment       VARCHAR(500)          DEFAULT NULL  COMMENT '评审评语',
    review_time   DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '评审时间',
    PRIMARY KEY (id),
    KEY idx_review_submission (submission_id),
    KEY idx_review_reviewer (reviewer_id),
    CONSTRAINT fk_review_submission FOREIGN KEY (submission_id) REFERENCES task_submission (id),
    CONSTRAINT fk_review_reviewer   FOREIGN KEY (reviewer_id)   REFERENCES sys_user (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='任务评审表';

3.6 验证查询SQL

USE ctts;

-- 验证1：查询学生"张三"的所有提交及对应任务和项目
SELECT
    su.real_name        AS student_name,
    ts.submit_time,
    t.title             AS task_title,
    tp.title            AS project_title
FROM task_submission ts
JOIN sys_user su  ON ts.user_id  = su.id
JOIN task t        ON ts.task_id  = t.id
JOIN training_project tp ON t.project_id = tp.id
WHERE su.real_name = '张三';

-- 验证2：查询某次提交的评审结果
SELECT
    ts.id               AS submission_id,
    su.real_name        AS student_name,
    t.title             AS task_title,
    tr.score,
    tr.comment,
    tu.real_name        AS reviewer_name,
    tr.review_time
FROM task_submission ts
JOIN task_review tr  ON tr.submission_id = ts.id
JOIN sys_user tu      ON tr.reviewer_id   = tu.id
JOIN task t           ON ts.task_id       = t.id
JOIN sys_user su      ON ts.user_id       = su.id;

-- 验证3：统计每个项目的任务数
SELECT
    tp.title            AS project_title,
    COUNT(t.id)         AS task_count
FROM training_project tp
LEFT JOIN task t ON tp.id = t.project_id
GROUP BY tp.id, tp.title;

-- 验证4：统计学生各任务最终成绩
SELECT
    su.real_name        AS student_name,
    t.title             AS task_title,
    MAX(tr.score)       AS final_score
FROM task_submission ts
JOIN task_review tr ON tr.submission_id = ts.id
JOIN task t          ON ts.task_id       = t.id
JOIN sys_user su     ON ts.user_id       = su.id
GROUP BY su.real_name, t.title;

四、拓展阅读

4.1 数据库设计进阶

  • 反范式设计：在高并发读场景下，为减少JOIN，可适度冗余字段。例如在task_submission中冗余student_name，以空间换时间。需权衡一致性维护成本。
  • 分库分表：当单表数据超过千万级，考虑按时间或用户ID分表。CTTS作为教学项目暂不需要。
  • 软删除：实际项目中常用is_deleted字段逻辑删除，而非物理DELETE，以保留数据追溯能力。

4.2 索引进阶

  • 联合索引：对多列组合查询可建联合索引，遵循"最左前缀"原则。如idx(task_id, user_id)可加速"查某学生某任务提交"。
  • 执行计划：用EXPLAIN查看SQL是否走索引，是后端工程师必备技能。
  • 索引失效场景：函数操作列、隐式类型转换、LIKE '%xxx'、OR条件等可能导致索引失效。

4.3 工具推荐

  • Navicat / DBeaver：可视化数据库管理工具，支持ER图导出。
  • PowerDesigner / draw.io：专业ER图绘制工具。
  • 阿里Java开发手册（嵩山版）：数据库设计规约章节，必读。

4.4 思辨阅读

  • 《高性能MySQL》第3版——索引与查询优化经典。
  • 《数据密集型应用系统设计》——分布式数据系统设计思想。
