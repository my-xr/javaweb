K5-1 Apifox/Postman 接口调试

定义

Apifox 是一款国产一体化 API 开发协作工具，集接口文档、接口调试、接口测试、Mock 于一身，定位是 "Postman + Swagger + Mock"。Postman 是老牌 API 调试工具，功能强大但国内访问慢。本课统一使用 Apifox。

解析展示

HTTP 请求报文结构：

POST /api/task/list HTTP/1.1          ← 请求行（方法 URL 协议）
Host: localhost:8080                   ← 请求头
Content-Type: application/json
Authorization: Bearer xxx.yyy.zzz

问题/场景

场景：CTTS 项目已经实现了用户登录、任务列表、任务新增、任务删除等接口，前端同学还没开工，后端如何独立验证接口是否正确？

问题：浏览器地址栏只能发 GET 请求，且无法设置 Content-Type、Authorization 等请求头，必须使用专业 API 调试工具。

易错点

  1. URL 拼写错误：少了 /api 前缀、写成 /api/auth/login/（末尾多斜杠），导致 404
  2. 方法选错：登录接口是 POST，误选 GET，后端返回 405 Method Not Allowed
  3. 未启动后端：发送请求后长时间无响应或连接拒绝，先检查 Spring Boot 是否启动
  4. 端口错误：后端实际端口 8080，Apifox 写成 8081，连接被拒绝
  5. Body 格式未切换：默认是 form-data，发 JSON 必须切到 json，否则 415
  6. JSON 语法错误：多了逗号、少了引号、使用单引号，Apifox 会红色提示，需修正

小结

Apifox 是后端开发的"瑞士军刀"，掌握它的核心是理解 HTTP 请求四要素：方法、URL、请求头、请求体。发送前对照这四项检查一遍，能避免 80% 的低级错误。

K5-2 请求头设置

定义

请求头（Request Headers） 是 HTTP 请求中位于请求行之后、请求体之前的部分，以 Key: Value 形式向服务器传递附加信息。常见请求头有 Content-Type、Accept、Authorization、User-Agent 等。

原理

HTTP 请求头本质是键值对元数据，服务器根据这些元数据决定如何解析请求体、如何鉴权、返回什么格式。三类必会请求头：

请求头 作用 常见取值
Content-Type 告诉服务器请求体是什么格式 application/json、application/x-www-form-urlencoded、multipart/form-data
Accept 告诉服务器客户端希望接收什么格式 application/json、/
Authorization 携带身份凭证（Token） Bearer xxx、Basic xxx

Content-Type 对照表（重点）：

Content-Type 请求体示例 后端接收方式
application/json {"name":"张三"} @RequestBody UserDTO dto
application/x-www-form-urlencoded name=张三&age=20 @RequestParam String name 或对象
multipart/form-data 二进制分块 @RequestPart MultipartFile file
无（GET 请求） 无请求体 @RequestParam / @PathVariable

问题/场景

场景1：前端用 fetch/axios 发送 JSON，后端却收不到参数，控制台报 Required request body is missing。

原因：前端忘记设置 Content-Type: application/json，或设置了又被覆盖。

场景2：登录后调用任务列表接口，后端返回 401 Unauthorized。

原因：未携带 Authorization 头，或 Token 过期、格式错误（少了 Bearer 前缀）。

完整示例代码

Apifox 设置 Headers 的操作步骤：

  1. 打开接口 → 切换到"Headers"标签
  2. 在 Key 列输入 Content-Type，Value 列输入 application/json
  3. 回车确认，Apifox 会自动提示常用值
  4. 再加一行 Accept = application/json

CTTS 登录后调用任务列表的完整 Headers：

Content-Type: application/json
Accept: application/json
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJhZG1pbiIsImlhdCI6MTY5MDAwMDAwMCwiZXhwIjoxNjkwMDg2NDAwfQ.xxx

Apifox 全局 Token 配置（避免每个接口都粘贴）：

  1. 点击右上角"环境管理"→ 选中"本地"环境
  2. 在"环境变量"中添加：
    • 变量名：token，初始值留空
    • 变量名：baseUrl，初始值 http://localhost:8080
  3. 在登录接口的"后置操作"中添加"提取变量"：
    • 变量名：token，JSONPath：$.data.token
  4. 其他接口的 Header 中 Authorization 值写 Bearer {{token}}，自动引用

Spring Boot 后端接收不同 Content-Type 的代码对比：

// 接收 JSON（Content-Type: application/json）
@PostMapping("/save")
public Result save(@RequestBody TaskDTO dto) {
    return Result.success(taskService.save(dto));
}

// 接收表单（Content-Type: application/x-www-form-urlencoded）
@PostMapping("/saveForm")
public Result saveForm(@RequestParam String title,
                       @RequestParam String content) {
    return Result.success();
}

// 接收文件（Content-Type: multipart/form-data）
@PostMapping("/upload")
public Result upload(@RequestPart MultipartFile file) {
    return Result.success(file.getOriginalFilename());
}

说明请求方法、路径与协议版本。

请求头

说明内容类型、认证信息、客户端信息等。

请求体

提交 JSON 业务数据。

易错点

  1. Content-Type 与后端注解不匹配：前端 application/json，后端用 @RequestParam → 415 或参数为 null
  2. Authorization 少 Bearer 前缀：Spring Security 默认要求 Bearer 开头，否则解析失败
  3. Token 过期：JWT 默认有效期短，调试中途 401 先检查 Token 是否过期
  4. Content-Type 大小写：HTTP 头不区分大小写，但建议统一小写 application/json
  5. 多次设置 Content-Type：Apifox 若同时启用 Body 的 json 类型和 Headers 手动设置，可能冲突，以 Body 设置为准
  6. 中文乱码：极少数情况需加 charset=UTF-8，Spring Boot 默认 UTF-8 一般无需设置

小结

请求头是客户端与服务器的"沟通礼仪"：Content-Type 说"我给你的是 JSON"，Accept 说"我想要 JSON"，Authorization 说"我是 admin"。三者匹配，接口才能通畅。

K5-3 JSON 响应分析

定义

HTTP 响应 由状态行、响应头、响应体三部分组成。JSON 响应 指响应体为 JSON 格式的数据，是现代 RESTful 接口的事实标准。

原理

HTTP 响应报文结构：

HTTP/1.1 200 OK                       ← 状态行（协议 状态码 状态描述）
Content-Type: application/json         ← 响应头
Transfer-Encoding: chunked

{"code":200,"message":"success","data":{...}}  ← 响应体

HTTP 状态码分类（必背）：

分类 含义 常见状态码
2xx 成功 200 OK、201 Created、204 No Content
3xx 重定向 304 Not Modified
4xx 客户端错误 400 Bad Request、401 Unauthorized、403 Forbidden、404 Not Found、405 Method Not Allowed、415 Unsupported Media Type
5xx 服务端错误 500 Internal Server Error、502 Bad Gateway、503 Service Unavailable

CTTS 统一响应结构（回顾第4次课）：

{
  "code": 200,           // 业务状态码：200成功，非200失败
  "message": "success",  // 提示信息
  "data": {              // 业务数据，可为对象/数组/基本类型
    "id": 1,
    "title": "需求评审"
  }
}

问题/场景

场景：调用任务列表接口，返回 200，但 data 为 null，前端页面空白。

排查步骤：

  1. 查响应体 message 是否有提示
  2. 查后端控制台是否有异常日志
  3. 查数据库是否有数据
  4. 查 MyBatis-Plus SQL 日志，确认 SQL 执行结果

场景：返回 500，Apifox 显示一长串堆栈。

排查步骤：

  1. 看堆栈第一行异常类型：NullPointerException、SQLException、HttpMessageNotReadableException
  2. 看堆栈中 com.ctts 开头的行，定位到具体类和方法
  3. 看异常消息，结合代码分析

完整示例代码

Apifox 查看响应的操作：

  1. 发送请求后，下方"响应"区域自动展示
  2. 顶部显示：状态码 200 OK | 响应时间 87ms | 响应大小 256B

Apifox 断言校验（自动化测试）：

在"后置操作"中添加断言：

  • 断言状态码：pm.response.code === 200
  • 断言 JSON 字段：pm.response.json().code === 200
  • 断言字段不为空：pm.response.json().data.token != null

图示

图示 5：HTTP 响应状态码分类

2xx 成功

200 OK：标准成功
201 Created：创建成功
204 No Content：删除成功，无返回体

3xx 重定向

API 开发中较少主动使用，常见于浏览器跳转。

4xx 客户端错误

400 参数错误
401 未认证
403 无权限
404 路径不对
405 方法不允许
415 Content-Type 不对

5xx 服务端错误

500 代码异常
502 网关错误
503 服务不可用

易错点

  1. 只看 code 不看 HTTP 状态码：业务 code 200 但 HTTP 500，说明全局异常处理器捕获了异常但返回了错误 code，要看 HTTP 状态码定位
  2. 混淆 401 和 403：401 是"没登录"，403 是"登录了但没权限"
  3. 忽视响应头：Content-Type: application/json;charset=UTF-8 若是 text/html，可能是被全局异常拦截到了错误页
  4. 响应体被拦截器改写：Spring Security 默认 401 返回 HTML 错误页，需自定义处理器返回 JSON
  5. 嵌套层级判断错误：data.records vs data，分页结果是嵌套结构，提取数据要看准层级

小结

分析响应"三看"：一看状态码定位问题大类，二看 message 了解具体原因，三看 data 验证业务数据。调试时养成先看状态码的习惯，能快速缩小问题范围。

K5-4 Knife4j 集成

定义

Knife4j 是国人开源的 Swagger 增强 UI，基于 OpenAPI 3 规范，让 Java 项目自动生成可交互的 API 文档。访问路径 http://localhost:8080/doc.html，可在线查看文档并直接调试接口。

OpenAPI 3 是 OpenAPI Initiative 维护的 API 描述规范（前身 Swagger Specification），用 JSON/YAML 描述接口结构，实现"代码即文档"。

原理

Knife4j 工作原理：

1. Spring Boot 启动 → 扫描所有 @RestController 类和方法
        ↓
2. OpenAPI 库根据 @Tag/@Operation/@Parameter 注解
   生成 OpenAPI 3 规范的 JSON 文档（/v3/api-docs）
        ↓
3. Knife4j 前端 UI 加载该 JSON → 渲染成 doc.html 页面
        ↓
4. 用户访问 doc.html → 在线浏览/调试接口

Knife4j vs Swagger UI：

特性 Swagger UI Knife4j
规范 OpenAPI 3 OpenAPI 3
UI 风格 简陋 现代化、响应式
调试体验 一般 增强（类似 Postman）
文档导出 不支持 支持 Markdown/HTML/PDF
国产化 英文 中文友好

问题/场景

场景：CTTS 项目接口越来越多，前端同学每次问"登录接口怎么调、参数是什么"，后端疲于应付，需要一份"永远不过期"的文档。

解决：集成 Knife4j，接口代码改动后文档自动同步，前端访问 doc.html 即可查看最新文档并在线调试。

易错点

  1. 依赖版本错误：Spring Boot 2.x 用 knife4j-spring-boot-starter，Spring Boot 3.x 必须用 knife4j-openapi3-jakarta-spring-boot-starter，否则启动报错
  2. 包导入错误：@Tag 来自 io.swagger.v3.oas.annotations.tags.Tag，不要导成 Swagger 2 的 @Api
  3. 生产环境暴露文档：knife4j.production=true 必须在生产环境开启，否则泄露接口信息
  4. Spring Security 拦截 doc.html：需在 Security 配置中放行 /doc.html、/webjars/**、/v3/api-docs/**
  5. 分组 pathsToMatch 错误：写错路径前缀（如 /task/** 漏了 /api），导致分组为空
  6. @Parameter in 写错：path 参数必须 in = ParameterIn.PATH，query 参数默认 QUERY，写错导致文档显示位置错误
  7. 空指针异常：@Bean OpenAPI 没配置 Components，访问带 @SecurityRequirement 的接口文档报错

小结

Knife4j 三步集成：加依赖 → 写配置类 → 标注解。核心注解记住四个：@Tag（类分组）、@Operation（方法说明）、@Parameter（参数说明）、@Schema（DTO 字段说明）。集成完成后，文档与代码永远同步，前端自助查阅，后端省心省力。

K5-5 常见接口问题排查

定义

接口调试中会遇到各种错误，按 HTTP 状态码可分为 4xx 客户端错误和 5xx 服务端错误。本知识点梳理 CTTS 项目中最常见的 5 类问题及其排查方法。

原理

每个状态码背后都有典型根因，掌握"状态码 → 根因 → 排查动作"的映射，能快速定位问题：

状态码 含义 典型根因 排查动作
404 Not Found URL 路径不对、Controller 未注册、context-path 错误 对比 @RequestMapping 路径与请求 URL
400 Bad Request 参数类型不匹配、必填参数缺失、JSON 格式错误 查 message 提示、检查参数
401 Unauthorized 未带 Token、Token 过期、Token 格式错误 重新登录获取新 Token
403 Forbidden 已登录但权限不足 检查用户角色与接口权限要求
405 Method Not Allowed 请求方法与接口定义不符（GET vs POST） 检查 @GetMapping/@PostMapping
415 Unsupported Media Type Content-Type 与后端期望不符 检查 Headers 的 Content-Type
500 Internal Server Error 代码空指针、SQL 异常、数组越界等 看后端控制台堆栈
502/503 Bad Gateway/Service Unavailable 网关错误、服务未启动 检查后端是否启动、网关配置

问题/场景

场景1：404 Not Found

调用 http://localhost:8080/api/task/list 返回 404。

排查清单：

  • ✅ Spring Boot 是否启动成功？看控制台
  • ✅ context-path 配置是否正确？看 application.yml
  • ✅ Controller 是否被扫描？包名是否在 @ComponentScan 范围
  • ✅ @RequestMapping 路径是否拼写正确？/api/task/list vs /api/Task/list（大小写）
  • ✅ 末尾是否多了斜杠？/api/task/list/ ≠ /api/task/list

场景2：415 Unsupported Media Type

调用新增任务接口返回 415。

根因：Apifox Body 类型选了 form-data，但后端 @RequestBody 要求 application/json。

解决：Apifox Body 切到 json 选项卡，重新发送。

场景3：500 Internal Server Error

调用任务列表返回 500，Apifox 显示：

{
  "code": 500,
  "message": "服务器开小差了",
  "data": null
}

后端控制台堆栈：

java.lang.NullPointerException: Cannot invoke "com.ctts.entity.Task.getTitle()" because "task" is null
    at com.ctts.service.impl.TaskServiceImpl.formatTitle(TaskServiceImpl.java:45)
    at com.ctts.controller.TaskController.list(TaskController.java:38)
    ...

排查：从堆栈顶到底阅读，找到 com.ctts 开头的行 → 定位到 TaskServiceImpl.java:45 → 打断点调试 → 发现数据库返回 null 未判空 → 修复。

场景4：跨域 CORS 错误

前端 http://localhost:5173 调用 http://localhost:8080 接口，浏览器报：

Access to XMLHttpRequest at 'http://localhost:8080/api/task/list' from origin 'http://localhost:5173'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource.

根因：浏览器同源策略限制，不同端口视为跨域。

解决：后端添加全局 CORS 配置：

package com.ctts.config;

import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.config.annotation.CorsRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOriginPatterns("*")
                .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
                .allowedHeaders("*")
                .allowCredentials(true)
                .maxAge(3600);
    }
}

package com.ctts.config;

import com.ctts.vo.Result;
import jakarta.servlet.http.HttpServletRequest;
import lombok.extern.slf4j.Slf4j;
import org.springframework.http.HttpStatus;
import org.springframework.http.converter.HttpMessageNotReadableException;
import org.springframework.validation.BindException;
import org.springframework.validation.FieldError;
import org.springframework.web.HttpRequestMethodNotSupportedException;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.MissingServletRequestParameterException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.ResponseStatus;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.servlet.NoHandlerFoundException;

import java.util.stream.Collectors;

/**
 * 全局异常处理器
 * <p>统一处理各类异常并返回标准 JSON</p>
 */
@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler {

    /** 业务异常 */
    @ExceptionHandler(BusinessException.class)
    public Result<Void> handleBusiness(BusinessException e, HttpServletRequest req) {
        log.warn("[业务异常] {} - {}", req.getRequestURI(), e.getMessage());
        return Result.error(e.getCode(), e.getMessage());
    }

    /** 参数校验失败 @Valid @RequestBody */
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<Void> handleValid(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldErrors().stream()
                .map(fe -> fe.getField() + ":" + fe.getDefaultMessage())
                .collect(Collectors.joining(";"));
        log.warn("[参数校验失败] {}", msg);
        return Result.error(400, "参数校验失败：" + msg);
    }

    /** 参数校验失败 @Validated 表单 */
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    @ExceptionHandler(BindException.class)
    public Result<Void> handleBind(BindException e) {
        String msg = e.getBindingResult().getFieldErrors().stream()
                .map(FieldError::getDefaultMessage)
                .collect(Collectors.joining(";"));
        return Result.error(400, "参数校验失败：" + msg);
    }

    /** 必填参数缺失 */
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    @ExceptionHandler(MissingServletRequestParameterException.class)
    public Result<Void> handleMissingParam(MissingServletRequestParameterException e) {
        return Result.error(400, "缺少必填参数：" + e.getParameterName());
    }

    /** JSON 解析失败 / @RequestBody 缺失 */
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    @ExceptionHandler(HttpMessageNotReadableException.class)
    public Result<Void> handleJsonParse(HttpMessageNotReadableException e) {
        log.warn("[JSON解析失败] {}", e.getMessage());
        return Result.error(400, "请求体格式错误或为空");
    }

    /** 请求方法不支持 → 405 */
    @ResponseStatus(HttpStatus.METHOD_NOT_ALLOWED)
    @ExceptionHandler(HttpHttpRequestMethodNotSupportedException.class)
    public Result<Void> handleMethod(HttpHttpRequestMethodNotSupportedException e) {
        return Result.error(405, "请求方法不支持：" + e.getMethod());
    }

    /** 路径不存在 → 404 */
    @ResponseStatus(HttpStatus.NOT_FOUND)
    @ExceptionHandler(NoHandlerFoundException.class)
    public Result<Void> handleNotFound(NoHandlerFoundException e) {
        return Result.error(404, "接口不存在：" + e.getRequestURL());
    }

    /** 兜底：其他未捕获异常 → 500 */
    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    @ExceptionHandler(Exception.class)
    public Result<Void> handleException(Exception e, HttpServletRequest req) {
        log.error("[系统异常] {} - ", req.getRequestURI(), e);
        return Result.error(500, "服务器开小差了：" + e.getMessage());
    }
}

                │   ├─ 500 代码异常
                │   │   └─ 看控制台堆栈 → 定位代码行 → 断点调试
                │   └─ 502/503 服务未启动/网关问题
                │
                └─ 浏览器跨域错误（不是状态码）
                    └─ 后端加 CorsConfig

易错点

  1. 404 不抛异常返回默认页：未配置 throw-exception-if-no-handler-found: true，404 不会被全局异常处理器捕获
  2. 500 异常栈不打印：@ExceptionHandler(Exception.class) 中只 return Result.error(500, "...") 而忘记 log.error，导致无法定位
  3. CORS 配置失效：allowedOrigins("*") 与 allowCredentials(true) 不能同时使用，必须用 allowedOriginPatterns("*")
  4. 生产环境忘记关闭调试信息：异常 message 暴露 SQL/堆栈，给攻击者信息，生产环境应只返回通用提示
  5. 顺序错误：@ExceptionHandler 子类异常必须写在父类之前，否则永远走不到
  6. 跨域 OPTIONS 预检被拦截：Spring Security 拦截了 OPTIONS 请求，需在 Security 配置中 permitAll 放行

小结

排查接口问题口诀："看码定位类，看消息找原因，看堆栈定行号"。4xx 找客户端，5xx 查服务端，跨域配 CORS。养成先看状态码、再看消息、最后看堆栈的三步排查习惯。

4.1 OpenAPI 3 规范

  • 官网：https://swagger.io/specification/
  • 核心概念：Path Item、Operation、Parameter、RequestBody、Response、Schema、SecurityScheme
  • 优势：语言无关、机器可读、工具生态丰富（生成客户端 SDK、Mock 服务）

4.2 Knife4j 高级特性

特性 用法
接口排序 @Operation 加 extension 或 Operation.sort
接口分组 GroupedOpenApi 定义多分组
全局鉴权 OpenAPI.addSecurityItem + Components.addSecuritySchemes
文档导出 doc.html 页面右上角"离线文档" → Markdown/HTML/PDF
生产屏蔽 knife4j.production: true
Basic 认证 knife4j.basic.enable: true 访问 doc.html 需账号密码

4.3 Postman vs Apifox vs Knife4j 调试

工具 优势 劣势
Postman 老牌、生态成熟 国内访问慢、英文
Apifox 国产、协作强、Mock 一体 部分高级功能收费
Knife4j 调试 与代码同步、零配置 仅适合后端自测，不便协作
