二、知识点详解

知识点 K2-1：HTTP 协议与报文结构

定义

HTTP（HyperText Transfer Protocol，超文本传输协议） 是 Web 客户端与服务器之间通信的协议。它采用请求-响应模型：客户端发起请求，服务器返回响应。

原理

HTTP 是无状态协议（服务器不记录上一次请求的状态），基于 TCP，默认端口 80。通信过程：

图示 1：HTTP 请求-响应模型

客户端

浏览器、APP、Apifox 等发起请求。

→

服务器

接收并处理请求。

←

HTTP 响应

服务器把状态码、响应头、响应体返回客户端。

HTTP 请求报文结构（三部分）：

请求行        POST /api/tasks HTTP/1.1
请求头        Host: localhost:8080
              Content-Type: application/json
              Content-Length: 52
空行
请求体        {"title":"任务1","projectId":1}
部分 说明 示例
请求行 方法 + 路径 + 版本 POST /api/tasks HTTP/1.1
请求头 键值对，描述请求元信息 Content-Type: application/json
请求体 携带数据（GET 一般无，POST 有） {"title":"任务1"}

HTTP 响应报文结构（三部分）：

状态行        HTTP/1.1 200 OK
响应头        Content-Type: application/json
              Content-Length: 38
空行
响应体        {"code":200,"message":"success"}
部分 说明 示例
状态行 版本 + 状态码 + 原因短语 HTTP/1.1 200 OK
响应头 键值对，描述响应元信息 Content-Type: application/json
响应体 返回的数据（常为 JSON） {"code":200}

问题 / 场景

问：GET 请求有请求体吗？

  • 一般没有。GET 用于查询，参数放在 URL 的 query string 中。POST/PUT 才用请求体携带数据。

问：请求头和请求体之间为什么要有一个空行？

  • 空行是 HTTP 规范规定的分隔符，告诉服务器"请求头结束，后面是请求体"。

完整示例代码

一个完整的 HTTP 请求与响应（GET 查询任务列表）：

===== HTTP 请求 =====
GET /api/tasks?projectId=1 HTTP/1.1
Host: localhost:8080
Accept: application/json
User-Agent: Apifox/1.0

（GET 请求通常无请求体）


===== HTTP 响应 =====
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 156

[
  {"id":1,"title":"任务1","deadline":"2026-08-01"},
  {"id":2,"title":"任务2","deadline":"2026-08-10"}
]

一个完整的 HTTP 请求与响应（POST 新增任务）：

===== HTTP 请求 =====
POST /api/tasks HTTP/1.1
Host: localhost:8080
Content-Type: application/json
Content-Length: 52

{"title":"任务1","projectId":1,"deadline":"2026-08-01"}


===== HTTP 响应 =====
HTTP/1.1 201 Created
Content-Type: application/json

{"code":201,"message":"创建成功","data":{"id":101}}

图示

图示 2：HTTP 请求报文与响应报文结构
HTTP 请求报文
请求行GET /api/x HTTP/1.1
请求头Host: ...
Content-Type: ...
空行分隔头部与主体
请求体{"title":"..."}
HTTP 响应报文
状态行HTTP/1.1 200 OK
响应头Content-Type: application/json
空行分隔头部与主体
响应体{"code":200,...}

易错点

  1. ❌ 误认为 GET 请求有请求体。✅ GET 参数在 URL，一般无请求体。
  2. ❌ 误认为请求头和请求体之间没有空行。✅ 必须有空行分隔。
  3. ❌ 混淆请求行与请求头。✅ 请求行只有一行（方法+路径+版本），请求头是多行键值对。

小结

HTTP 报文分请求与响应，各三部分：请求=请求行+请求头+请求体，响应=状态行+响应头+响应体。空行分隔头部与体。

知识点 K2-2：URL 与请求方法

定义

URL（Uniform Resource Locator，统一资源定位符） 用于定位网络上的资源。

HTTP 请求方法表示对资源执行的操作类型。

原理

URL 组成：

图示 3：URL 各组成部分拆解
完整 URL
http://localhost:8080/api/tasks?projectId=1&status=进行中

协议

http

说明通信规则。

主机

localhost

说明访问哪台机器。

端口

8080

说明访问哪个服务入口。

路径

/api/tasks

说明访问哪个资源。

查询参数

projectId=1
status=进行中

说明筛选条件。

组成 说明 示例
协议 通信协议 http / https
主机 服务器地址 localhost / www.example.com
端口 服务端口 80（默认）/ 8080 / 443（https）
路径 资源位置 /api/tasks
查询参数 附带条件 ?projectId=1&status=进行中

HTTP 请求方法：

方法 语义 幂等性 示例
GET 查询资源 幂等 GET /api/tasks/1 查询 id=1 的任务
POST 新增资源 非幂等 POST /api/tasks 新增任务
PUT 更新资源（全量） 幂等 PUT /api/tasks/1 更新 id=1 的任务
DELETE 删除资源 幂等 DELETE /api/tasks/1 删除 id=1 的任务

幂等性：同一请求执行一次与执行多次效果相同。GET/PUT/DELETE 幂等，POST 非幂等（多次提交会创建多条数据）。

问题 / 场景

问：GET 和 POST 有什么区别？（面试经典题）

  1. 语义：GET 查询，POST 新增。
  2. 参数位置：GET 参数在 URL，POST 参数在请求体。
  3. 幂等性：GET 幂等，POST 非幂等。
  4. 安全性：GET 参数暴露在 URL，POST 相对隐蔽（但都不加密传输，https 才安全）。
  5. 长度限制：GET URL 长度有限制（浏览器限制），POST 请求体理论上无限制。

问：查询用 GET 还是 POST？

  • 查询用 GET。GET 语义就是"获取资源"，且参数在 URL 便于分享和缓存。

完整示例代码

RESTful 风格的 CRUD 接口（以 task 资源为例）：

查询所有任务：    GET    /api/tasks
查询单个任务：    GET    /api/tasks/5        （5 是任务 ID）
新增任务：       POST   /api/tasks           （请求体带数据）
更新任务：       PUT    /api/tasks/5         （请求体带数据）
删除任务：       DELETE /api/tasks/5

对比非 RESTful 写法（不推荐）：

查询所有任务：    GET /api/getAllTasks
查询单个任务：    GET /api/getTaskById?id=5
新增任务：       POST /api/addTask
更新任务：       POST /api/updateTask?id=5
删除任务：       GET /api/deleteTask?id=5    （用 GET 删除，不规范）

易错点

  1. ❌ 用 GET 执行删除操作。✅ 删除应使用 DELETE 方法，GET 应只用于查询（无副作用）。
  2. ❌ 把参数既放 URL 又放请求体。✅ GET 参数放 URL，POST/PUT 数据放请求体。
  3. ❌ 误认为 POST 比 GET 安全（加密意义）。✅ 两者都是明文传输，安全要靠 HTTPS。

小结

URL 定位资源，HTTP 方法表达操作。GET 查询、POST 新增、PUT 更新、DELETE 删除，遵循语义是 RESTful 的基础。

知识点 K2-3：HTTP 状态码

定义

HTTP 状态码是服务器返回的 3 位数字，表示请求的处理结果。

原理

状态码按首位数字分为 5 类：

分类 含义 常见状态码
1xx 信息性（请求已接收，继续处理） 较少使用
2xx 成功 200 OK、201 Created
3xx 重定向 302 Found、304 Not Modified
4xx 客户端错误 400、401、403、404
5xx 服务器错误 500、502、503

必须掌握的常用状态码：

状态码 含义 典型场景
200 OK 请求成功 查询/更新成功返回
201 Created 资源创建成功 POST 新增成功
400 Bad Request 请求参数错误 参数缺失、格式不对
401 Unauthorized 未认证（未登录） 没带 Token 或 Token 失效
403 Forbidden 无权限（已认证但禁止访问） 普通用户访问管理员接口
404 Not Found 资源不存在 查询的 ID 找不到
500 Internal Server Error 服务器内部错误 代码异常、数据库错误

问题 / 场景

问：401 和 403 有什么区别？（面试高频）

  • 401 Unauthorized：未认证——服务器不知道你是谁（没登录、没带 Token）。
  • 403 Forbidden：已认证但无权限——服务器知道你是谁，但你没权限做这件事。
  • 例：学生想删除任务 → 若没登录返回 401；若已登录但学生不能删任务返回 403。

问：实际项目中状态码怎么用？

  • 真实项目中，很多团队在 HTTP 层统一返回 200，在响应体的业务 code 字段中区分业务状态（如 {"code":4001,"message":"参数错误"}）。两种做法都存在，本课程后续会讲解统一响应结果设计。

完整示例代码

不同场景的状态码示例：

场景1：查询成功
HTTP/1.1 200 OK
{"code":200,"data":[...]}

场景2：新增成功
HTTP/1.1 201 Created
{"code":201,"message":"创建成功","data":{"id":101}}

场景3：未登录访问需认证接口
HTTP/1.1 401 Unauthorized
{"code":401,"message":"未登录或Token失效"}

场景4：学生访问管理员接口
HTTP/1.1 403 Forbidden
{"code":403,"message":"无权限"}

场景5：查询不存在的资源
HTTP/1.1 404 Not Found
{"code":404,"message":"任务不存在"}

场景6：服务器代码异常
HTTP/1.1 500 Internal Server Error
{"code":500,"message":"服务器内部错误"}

易错点

  1. ❌ 混淆 401 与 403。✅ 401=未认证（你是谁），403=无权限（你能干嘛）。
  2. ❌ 误认为 4xx 是服务器错误。✅ 4xx 是客户端错误（请求有问题），5xx 才是服务器错误。
  3. ❌ 误认为 404 只表示页面不存在。✅ 404 表示请求的资源不存在，包括接口、数据记录。

小结

状态码 5 类：2xx 成功、4xx 客户端错误、5xx 服务器错误。重点掌握 200/201/400/401/403/404/500，尤其区分 401 与 403。

知识点 K2-4：Header / Cookie / Session

定义

  • Header（报文头）：HTTP 请求和响应中的键值对，携带元信息（如 Content-Type、User-Agent）。
  • Cookie：服务器发给客户端的小段数据，由客户端保存，后续请求自动带上。
  • Session（会话）：服务器端保存的会话状态，通过 Session ID 标识用户。

原理

常见 Header：

Header 方向 说明
Content-Type 请求/响应 数据类型，如 application/json
Accept 请求 客户端能接受的类型
User-Agent 请求 客户端信息（浏览器类型）
Authorization 请求 认证信息（如 Bearer Token）
Set-Cookie 响应 服务器设置 Cookie

Cookie 与 Session 的关系：

图示 6：首次访问与后续访问中的 Cookie / Session
首次访问

客户端

请求服务器，暂时没有 Cookie。

→

服务器

创建 Session，生成 SessionID。

←

Set-Cookie

JSESSIONID=abc123 返回给客户端。

后续访问

客户端

请求携带 Cookie: JSESSIONID=abc123。

→

服务器

根据 SessionID 找到 Session，识别用户身份。

←

响应

返回个性化内容。

Cookie 与 Session 区别：

对比项 Cookie Session
存储位置 客户端（浏览器） 服务器端
安全性 较低（可被查看篡改） 较高（数据在服务器）
大小限制 单个约 4KB 无特别限制（受服务器内存）
生命周期 可设过期时间 默认会话结束失效，可配置

问题 / 场景

问：前后端分离项目为什么倾向用 Token 而非 Session？

  • Session 存在服务器，多服务器部署时需共享 Session（复杂）；Token（如 JWT）是无状态的，客户端携带即可，服务器不用存，便于扩展。这部分第 6 模块详讲。

问：Cookie 和 Session 哪个更安全？

  • Session 更安全，敏感数据存服务器，客户端只存 SessionID。Cookie 存客户端，可被查看篡改。

完整示例代码

请求头与响应头示例：

===== 请求头示例 =====
GET /api/tasks HTTP/1.1
Host: localhost:8080
Accept: application/json
User-Agent: Mozilla/5.0
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...   （Token 认证）
Cookie: JSESSIONID=abc123                         （带 Cookie）


===== 响应头示例 =====
HTTP/1.1 200 OK
Content-Type: application/json
Set-Cookie: JSESSIONID=abc123; Path=/; HttpOnly   （设置 Cookie）

图示

图示 7：Cookie / Session 工作流程

客户端

请求（无 Cookie）
保存 Set-Cookie: abc
请求携带 Cookie: abc
接收个性化响应

服务器

创建 Session(ID=abc)
通过 Set-Cookie 返回 ID
根据 ID 找 Session

易错点

  1. ❌ 误认为 Cookie 存在服务器。✅ Cookie 存客户端，Session 存服务器。
  2. ❌ 误认为 Session 不需要 Cookie。✅ 传统模式下 Session 依赖 Cookie 传递 SessionID（除非用 URL 重写）。
  3. ❌ 误认为前后端分离必须用 Session。✅ 前后端分离更倾向用 Token（无状态），第 6 模块详讲。

小结

Header 携带元信息；Cookie 存客户端、Session 存服务器；前后端分离倾向用 Token 替代 Session（第 6 模块）。

知识点 K2-5：JSON 数据格式

定义

JSON（JavaScript Object Notation） 是一种轻量级的数据交换格式，前后端分离后后端最常用的返回数据格式。

原理

JSON 支持的数据类型：

类型 说明 示例
对象（Object） 键值对集合，用 {} {"name":"张三","age":20}
数组（Array） 有序列表，用 [] [1,2,3] 或 [{"id":1},{"id":2}]
字符串（String） 用双引号 "hello"
数字（Number） 整数或浮点 20 或 3.14
布尔（Boolean） 真/假 true / false
null 空值 null

JSON 语法规则：

  1. 数据是键值对，键必须用双引号。
  2. 键值对用冒号 : 分隔。
  3. 多个键值对用逗号 , 分隔。
  4. 对象用 {}，数组用 []。
  5. 字符串必须用双引号（不能用单引号）。

问题 / 场景

问：JSON 的键能用单引号吗？

  • 不能。JSON 规范要求键和字符串都用双引号。{'name':'张三'} 不是合法 JSON（虽然 JS 中允许）。

问：JSON 能嵌套吗？

  • 能。对象里可以有数组，数组里可以有对象，多层嵌套。

完整示例代码

合法的 JSON 示例（描述一个学生提交任务的数据）：

{
  "student": {
    "id": 1001,
    "name": "张三",
    "className": "软件工程1班"
  },
  "task": {
    "id": 5,
    "title": "搭建Spring Boot项目",
    "deadline": "2026-08-01"
  },
  "submission": {
    "content": "已完成项目搭建，代码已提交GitHub",
    "submitTime": "2026-07-25T14:30:00",
    "status": "已提交"
  },
  "score": null,
  "isReviewed": false
}

JSON 数组示例（任务列表）：

[
  {"id": 1, "title": "任务1", "status": "进行中"},
  {"id": 2, "title": "任务2", "status": "已结束"},
  {"id": 3, "title": "任务3", "status": "未开始"}
]

常见错误 JSON（不合法）：

// 错误1：键用了单引号
{'name': '张三'}

// 错误2：字符串用了单引号
{"name": '张三'}

// 错误3：最后一个键值对多了逗号
{"name": "张三", "age": 20,}

// 错误4：键没有引号
{name: "张三"}

// 错误5：注释（JSON 不允许注释）
{"name": "张三"} // 这是学生姓名

数字：20

复合类型

对象：{ ... }

常见规则

属性名使用双引号；不能写注释；最后一项后面不能多逗号。

  "name": "张三",
  "age": 20,
  "active": true,
  "score": null,
  "courses": ["Java","DB"],

    "name": "李老师"
  }
}
类型标注
name字符串
age数字

scorenull

易错点

  1. ❌ 键或字符串用单引号。✅ JSON 必须用双引号。
  2. ❌ 最后一个键值对后加逗号。✅ JSON 不允许尾逗号。
  3. ❌ 在 JSON 中写注释。✅ JSON 不支持注释。
  4. ❌ 键不加引号。✅ 键必须用双引号包裹。

小结

JSON 是轻量级数据交换格式，支持对象/数组/字符串/数字/布尔/null。键和字符串必须用双引号，不支持注释和尾逗号。

知识点 K2-6：RESTful API 设计思想

定义

REST（Representational State Transfer，表现层状态转化） 是一种 Web 接口设计风格。遵循 REST 风格的 API 称为 RESTful API。它不是协议，而是一种设计约定。

原理

RESTful 核心原则：

  1. 资源用名词，路径用复数：URL 表示资源，用名词复数。

    • ✅ /api/tasks（任务资源）
    • ❌ /api/getTasks（动词，不推荐）

  2. 用 HTTP 方法表达操作：不在 URL 里写动词，用方法区分。

    • ✅ DELETE /api/tasks/5
    • ❌ GET /api/deleteTask?id=5

  3. 资源 ID 用路径参数：

    • ✅ /api/tasks/5（5 是 ID）
    • ❌ /api/tasks?id=5（查询特定资源应路径参数）

  4. 无状态：每个请求自带认证信息，服务器不保存客户端状态。

  5. 统一响应格式：返回 JSON，结构统一。

RESTful CRUD 设计标准（以 task 资源为例）：

操作 方法 路径 说明
查询列表 GET /api/tasks 获取所有任务
查询单个 GET /api/tasks/5 获取 id=5 的任务
新增 POST /api/tasks 请求体带新任务数据
更新 PUT /api/tasks/5 请求体带更新数据
删除 DELETE /api/tasks/5 删除 id=5 的任务

问题 / 场景

问：RESTful 必须严格遵守吗？

  • RESTful 是设计风格不是强制标准。实际项目中可灵活调整，但遵循 RESTful 能让接口更规范、可读、可维护。团队应有统一约定。

问：子资源怎么设计？

  • 如"查询项目 1 下的所有任务"：GET /api/projects/1/tasks（项目 1 的任务列表）。

完整示例代码

CTTS 系统 RESTful 接口设计示例：

=== 任务资源（task）===
GET    /api/tasks              查询任务列表（可带筛选参数）
GET    /api/tasks/5            查询 id=5 的任务
POST   /api/tasks              新增任务
PUT    /api/tasks/5            更新 id=5 的任务
DELETE /api/tasks/5            删除 id=5 的任务

=== 子资源：某项目下的任务 ===
GET    /api/projects/1/tasks   查询项目 1 下的所有任务

=== 提交资源（submission）===
GET    /api/submissions        查询提交列表
POST   /api/submissions        学生提交任务
GET    /api/submissions/50     查询 id=50 的提交

对比非 RESTful 设计（不推荐）：

GET  /api/getTaskList              ← 动词，应改为名词
GET  /api/getTaskById?id=5         ← 应用路径参数 /tasks/5
POST /api/addTask                  ← 动词
POST /api/updateTask               ← 应用 PUT
GET  /api/deleteTask?id=5          ← 应用 DELETE，且不该用 GET 删

图示

RESTful 设计三要素：
1. 资源用名词复数：/api/tasks
2. 操作用HTTP方法：GET查/POST增/PUT改/DELETE删
3. ID用路径参数：  /api/tasks/5

资源操作映射：
GET    /api/tasks     → 查全部
GET    /api/tasks/5   → 查一个
POST   /api/tasks     → 增一个
PUT    /api/tasks/5   → 改一个
DELETE /api/tasks/5   → 删一个

易错点

  1. ❌ URL 中写动词（如 /api/deleteTask）。✅ 资源用名词，操作用方法。
  2. ❌ 用 GET 执行删除/修改。✅ 删除用 DELETE，修改用 PUT。
  3. ❌ 查询单个资源用 query 参数（/api/tasks?id=5）。✅ 应用路径参数（/api/tasks/5）。

小结

RESTful 是接口设计风格：资源用名词复数、操作用 HTTP 方法、ID 用路径参数、无状态、统一 JSON 响应。遵循 RESTful 让接口规范、可读、可维护。

四、拓展阅读（选学）

  1. HTTPS：HTTP + TLS/SSL 加密，端口 443，保障传输安全。
  2. PUT 与 PATCH 的区别：PUT 全量更新，PATCH 部分更新。
