二、知识点详解

知识点 K15-1 注册登录流程

1. 定义

用户注册登录是系统识别"你是谁"的基础功能。注册是用户首次建立身份凭证的过程；登录是用户凭已有凭证换取系统访问凭证的过程；登出是主动放弃访问凭证的过程。

2. 原理（业务流程图）

注册流程：

图示 2：用户注册业务流程

客户端

{username,password,name}
接收 Result.ok()

服务端

@Valid 校验参数
根据 username 查询用户
若存在，抛“用户名已存在”
BCrypt 加密 password

数据库

查询 sys_user
返回是否存在

用户不存在则抛异常

3. 问题（常见疑问）

Q1：为什么注册时要做用户名唯一性校验？ A：用户名将作为登录的唯一标识，若允许重复则无法区分用户。虽然数据库层面可加 UNIQUE 约束兜底，但业务层应主动校验并给出友好提示，避免直接抛 SQLIntegrityConstraintViolationException。

Q2：注册和登录中"密码"分别以什么形式传输和存储？ A：传输层应由 HTTPS 保证加密（本课不展开）；应用层密码以明文形式从客户端 POST 到服务端（因为服务端要做 BCrypt 哈希），存储层必须以密文形式入库。任何情况下都不得在数据库中存储明文密码。

Q3：登录后为什么要返回 Token 而不是直接返回用户信息就完事？ A：HTTP 是无状态协议，下一次请求服务端并不知道"你是谁"。Token 是后续请求携带的身份凭证，相当于"入场手环"。

package com.ctts.exception;

import com.ctts.common.Result;
import jakarta.validation.ConstraintViolationException;
import lombok.extern.slf4j.Slf4j;
import org.springframework.validation.FieldError;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BusinessException.class)
    public Result<?> handleBusiness(BusinessException e) {
        log.warn("业务异常: {}", e.getMessage());
        return Result.error(e.getCode(), e.getMessage());
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<?> handleValid(MethodArgumentNotValidException e) {
        FieldError fe = e.getBindingResult().getFieldError();
        String msg = fe != null ? fe.getDefaultMessage() : "参数校验失败";
        return Result.error(400, msg);
    }

    @ExceptionHandler(ConstraintViolationException.class)
    public Result<?> handleConstraint(ConstraintViolationException e) {
        return Result.error(400, e.getMessage());
    }

    @ExceptionHandler(Exception.class)
    public Result<?> handleException(Exception e) {
        log.error("系统异常", e);
        return Result.error(500, "系统异常: " + e.getMessage());
    }
}

（10）UserService 注册登录实现（重点）

package com.ctts.service;

import com.baomidou.mybatisplus.core.conditions.query.LambdaQueryWrapper;
import com.ctts.dto.UserLoginDTO;
import com.ctts.dto.UserRegisterDTO;
import com.ctts.entity.User;
import com.ctts.exception.BusinessException;
import com.ctts.mapper.UserMapper;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Service;

import java.util.HashMap;
import java.util.Map;
import java.util.UUID;

@Slf4j
@Service
@RequiredArgsConstructor
public class UserService {

    private final UserMapper userMapper;
    private final PasswordEncoder passwordEncoder;

    /**
     * 注册
     * ① 用户名唯一性校验 ②BCrypt加密 ③入库
     */
    public void register(UserRegisterDTO dto) {
        // 1. 用户名唯一性校验
        Long count = userMapper.selectCount(
            new LambdaQueryWrapper<User>().eq(User::getUsername, dto.getUsername())
        );
        if (count > 0) {
            throw new BusinessException(400, "用户名已存在");
        }

        // 2. 构建 User，BCrypt 加密密码
        User user = new User();
        user.setUsername(dto.getUsername());
        user.setPassword(passwordEncoder.encode(dto.getPassword()));
        user.setName(dto.getName());
        user.setRole(dto.getRole());

        // 3. 入库
        userMapper.insert(user);
        log.info("用户注册成功: {}", dto.getUsername());
    }

    /**
     * 登录
     * ① 查用户 ②BCrypt校验密码 ③生成Token返回
     */
    public Map<String, Object> login(UserLoginDTO dto) {
        // 1. 根据用户名查用户
        User user = userMapper.selectOne(
            new LambdaQueryWrapper<User>().eq(User::getUsername, dto.getUsername())
        );
        if (user == null) {
            throw new BusinessException(400, "用户名或密码错误");
        }

        // 2. BCrypt 校验密码
        if (!passwordEncoder.matches(dto.getPassword(), user.getPassword())) {
            throw new BusinessException(400, "用户名或密码错误");
        }

        // 3. 生成简单 Token（UUID，下节课改用 JWT）
        String token = UUID.randomUUID().toString().replace("-", "");

        // 4. 封装返回结果（注意：不要返回 password）
        Map<String, Object> result = new HashMap<>();
        result.put("token", token);
        Map<String, Object> userInfo = new HashMap<>();
        userInfo.put("id", user.getId());
        userInfo.put("username", user.getUsername());
        userInfo.put("name", user.getName());
        userInfo.put("role", user.getRole());
        result.put("user", userInfo);

        log.info("用户登录成功: {}", dto.getUsername());
        return result;
    }
}

6. 易错点

易错点 现象 原因 解决方案
未配置 PasswordEncoder Bean 启动报 NoSuchBeanDefinitionException Spring 容器中无 PasswordEncoder 实例 写 SecurityConfig 配置类，@Bean 注入
引入 spring-boot-starter-security 后接口全 401 任何请求返回 401 Security 默认拦截所有请求 配置 permitAll() 或排除 SecurityAutoConfiguration
用 equals 比对密码 永远登录失败 BCrypt 每次加密结果不同 必须用 passwordEncoder.matches(明文,密文)
登录返回了 password 字段 安全漏洞 直接序列化整个 User 用 Map/VO 手动挑选字段，或 @JsonIgnore
用户名唯一校验时机错误 高并发下重复注册 业务校验与 INSERT 之间存在时间窗 数据库加 UNIQUE 约束兜底 + 捕获 DuplicateKeyException
@Valid 不生效 参数为空也不报错 漏写 @Valid 或未引入 spring-boot-starter-validation 检查注解和依赖
密码字段长度不够 入库报 Data too long BCrypt 密文 60 字符，字段太短 VARCHAR(100)

7. 小结

注册登录本质是"建立身份"与"换取凭证"。三个关键动作：校验（唯一性 + 参数格式）、加密（BCrypt）、凭证（Token）。安全的核心是密码绝不入库明文，校验必须用 matches 而非 equals。

知识点 K15-2 密码加密

1. 定义

密码加密是指将用户密码通过单向哈希函数转换为不可逆的密文后存储的过程。"单向"意味着无法从密文反推出明文，校验时只能将明文再次哈希后比对。

2. 原理

（1）明文存储的危害

  • 数据库泄漏 → 所有用户密码直接暴露。
  • 用户跨站复用密码 → 一个站泄漏导致多个站被攻破（撞库）。
  • 内部员工可查看所有用户密码。

（2）MD5 为什么不安全

  • MD5 是单向哈希，理论不可逆，但：
    • 彩虹表攻击：攻击者预先计算好大量明文→MD5 的对照表，查询即可反查。
    • MD5 计算太快：现代 GPU 每秒可计算数十亿次 MD5，暴力破解成本低。
    • 相同明文 MD5 相同：一旦一个站密码泄漏，相同密码的其他账户都被识别。

（3）BCrypt 为什么安全

  • 自带盐（salt）：每次加密自动生成随机盐，相同明文每次加密结果不同。
  • 慢哈希：成本因子（strength）可调，计算慢，暴力破解成本极高。
  • 盐嵌入密文：盐作为密文的一部分存储，无需单独维护盐字段。

成本因子，表示 2^10 轮。

Salt

每次生成不同盐，抵抗彩虹表。

Hash

最终哈希值，和盐一起存储。

（4）Spring Security PasswordEncoder Spring Security 提供 PasswordEncoder 接口统一抽象密码加密与校验：

public interface PasswordEncoder {
    String encode(CharSequence rawPassword);       // 加密
    boolean matches(CharSequence rawPassword,      // 校验
                    String encodedPassword);
    default boolean upgradeEncoding(String encodedPassword) {
        return false;
    }
}

BCryptPasswordEncoder 是其最常用的实现。

3. 问题

Q1：BCrypt 每次加密同一明文结果都不同，为什么还能正确校验？ A：因为盐被嵌入到密文中（前 22 位字符）。matches 时会从密文中解析出盐，用相同的盐和成本因子重新哈希明文，再与密文比对。所以即便每次加密结果不同，校验依然正确。

Q2：成本因子 strength 设多少合适？ A：默认 10（约 100ms/次）。生产环境推荐 10-12，每增加 1 计算时间翻倍。太高影响登录性能，太低不安全。

Q3：BCrypt 密文长度是多少？数据库字段怎么设计？ A：标准 BCrypt 密文 60 字符，建议 VARCHAR(100) 留余量。

Q4：为什么 MD5 + 盐也不推荐？ A：MD5 计算太快，即便加盐，攻击者拿到盐后仍可针对性暴力破解。BCrypt 的"慢"是它的优点而非缺点。

4. 完整代码

PasswordEncoder 配置类：

package com.ctts.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;

@Configuration
public class SecurityConfig {

    @Bean
    public PasswordEncoder passwordEncoder() {
        // strength=10 表示 2^10=1024 轮哈希，约 100ms
        return new BCryptPasswordEncoder(10);
    }
}

知识点 K15-3 Session 认证思路

1. 定义

Session 认证是服务器端有状态认证方案：服务器为每个登录用户创建一个 Session 对象存储用户信息，并通过 Cookie 将 SessionID 返回客户端，后续请求客户端自动携带 Cookie，服务器据此识别用户。

2. 原理

Session 认证流程：

图示 7：Session 认证流程

首次登录

Client POST /login，提交用户名和密码。

服务端校验

校验账号密码，创建 Session 并保存用户信息。

下发 Cookie

返回 Set-Cookie: JSESSIONID=xxx。

后续请求

浏览器自动携带 Cookie 请求业务接口。

服务端取身份

根据 SessionID 找到 Session，取出用户信息并处理业务。

3. 问题

Q1：Session 存在哪里？ A：默认存在服务器内存中（如 Tomcat 的 StandardManager），也可配置存 Redis 等外部存储。

Q2：SessionID 怎么传给客户端？ A：通过 HTTP 响应头 Set-Cookie: JSESSIONID=xxx，浏览器会自动保存并在后续同域请求中携带。

Q3：Session 认证的局限？ A：① 服务器需存储大量 Session，内存压力大；② 多服务器部署时需 Session 共享（粘性会话或 Redis）；③ 跨域时 Cookie 默认不携带，需配置 CORS + withCredentials；④ 移动端 App 不方便管理 Cookie。

4. 完整代码（Spring Session 简化演示，非本课项目重点）

// 本段仅为演示 Session 认证思路，CTTS 项目实际使用 Token 认证
@RestController
public class SessionLoginController {

    @PostMapping("/session-login")
    public Result<Void> login(@RequestBody UserLoginDTO dto, HttpSession session) {
        // 校验账号密码（伪代码）
        if (checkUser(dto)) {
            session.setAttribute("loginUser", dto.getUsername());
            return Result.ok();
        }
        return Result.error(400, "用户名或密码错误");
    }

    @GetMapping("/me")
    public Result<String> me(HttpSession session) {
        Object user = session.getAttribute("loginUser");
        if (user == null) {
            return Result.error(401, "未登录");
        }
        return Result.ok(user.toString());
    }
}

知识点 K15-4 Token 认证思路

1. 定义

Token 认证是客户端无状态认证方案：用户登录成功后服务器签发一个 Token（令牌）返回客户端，客户端自行存储 Token，后续请求通过 HTTP Header 携带 Token，服务器解析 Token 识别用户身份。

2. 原理

Token 认证流程：

图示 8：Token 认证流程

首次登录

Client POST /login，提交用户名和密码。

生成 Token

校验成功后生成 UUID/JWT，可选写入 Redis。

返回 Token

响应 200 { token: "xxx" }，客户端保存。

后续请求

Header: Authorization: Bearer xxx。

解析身份

服务端校验 Token，得到用户身份并处理业务。

3. 问题

Q1：Token 存在客户端哪里？ A：浏览器端通常存 localStorage（关闭浏览器仍在）或 sessionStorage（关闭即销毁）；移动端存本地存储。注意防范 XSS 攻击窃取 Token。

Q2：Token 怎么传给服务端？ A：约定通过 HTTP Header Authorization: Bearer <token> 携带，也可自定义 Header 如 X-Token。

Q3：Token 怎么失效？ A：① 服务端将 Token 存 Redis，登出时删除；② 使用 JWT 的过期时间字段 exp；③ 维护 Token 黑名单。

Q4：UUID Token 和 JWT 的区别？ A：UUID Token 是无意义的随机串，服务端必须查 Redis 才能知道属于谁；JWT 自包含用户信息（Payload），服务端解析即得用户身份，无需查库，但签发后难以主动失效。

4. 完整代码（本课使用 UUID Token，下节课改 JWT）

见上文流程图。

6. 易错点

易错点 说明
Token 存 localStorage 被 XSS 窃取 严格过滤用户输入，配置 CSP
Token 永不过期 必须设置过期时间或刷新机制
Header 名大小写敏感问题 HTTP Header 名不区分大小写，但建议统一规范
Token 主动失效难 UUID 方案配合 Redis 可解决；JWT 需黑名单

7. 小结

Token 认证是"客户端存、Header 传"的无状态方案。无状态、易扩展、跨域友好，是前后端分离架构的主流选择。

知识点 K15-5 认证方案选型

1. 定义

认证方案选型指在 Session 与 Token 两种认证机制之间，根据业务场景、架构特点、扩展需求进行权衡决策的过程。

2. 原理（对比分析）

维度 Session 认证 Token 认证
状态存储 服务端内存/Redis 客户端（localStorage）
传递方式 Cookie 自动携带 Header 手动携带
扩展性 多服务器需 Session 共享 无状态，天然支持分布式
跨域 Cookie 跨域复杂（CORS+withCredentials） Header 传 Token，跨域简单
前后端分离 不友好（移动端 App 难管 Cookie） 友好（统一 Header）
安全性 防 CSRF 需额外配置；防 XSS 同样需注意 防 XSS 需注意；JWT 防篡改靠签名
主动失效 简单（删除 Session） UUID+Redis 简单；JWT 需黑名单
移动端适配 不友好 友好

3. 问题

Q1：为什么前后端分离架构选 Token？ A：前后端分离后，前端可能是 Web/小程序/App，后端是独立的 RESTful API 服务。① 移动端不方便管理 Cookie；② 跨域请求 Cookie 携带复杂；③ Token 通过 Header 传递，与客户端类型无关；④ 无状态后端更容易横向扩展。

Q2：JWT 相比 UUID Token 的优势？ A：JWT 自包含用户信息，服务端解析即得身份，无需查 Redis；天然支持过期时间；签名防篡改。缺点是签发后难以主动失效。

Q3：Session 真的一无是处吗？ A：不是。传统同域 Web 应用（如 JSP/Thymeleaf 渲染）用 Session 简单高效；强安全性要求、需主动踢人下线的场景，Session+Redis 仍是好选择。

4.3 密码加密算法演进

  • DES/3DES：对称加密，可逆，不适用于密码存储。
  • SHA 系列：SHA-1 已不安全，SHA-256 仍可用但需加盐且计算快。
  • BCrypt/PBKDF2/scrypt/Argon2：慢哈希算法族，专门用于密码存储。Argon2 是 2015 年密码哈希竞赛冠军，是当前最推荐的选择。
