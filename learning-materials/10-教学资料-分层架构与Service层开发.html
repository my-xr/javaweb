二、知识点详解

K10-1 为什么分层

定义

分层架构（Layered Architecture）：将应用按照职责纵向切分为多个层次，每层只负责一类工作，层与层之间通过明确的接口调用，方向单一（上层调用下层，下层不反向依赖上层）。

原理

分层的核心思想是 关注点分离（Separation of Concerns, SoC）——把"不同性质的事情"交给"不同的人/层"去做。这一思想源于 Dijkstra 在 1968 年提出的"分层是组织复杂系统的基本手段"。

在 JavaWeb 后端，最经典的就是 三层架构：Controller / Service / Mapper（DAO）。三层之间的调用方向是单向的：

图示 2：三层架构单向调用链
请求

HTTP / JSON

前端发起业务请求。

→
Controller

接口层

参数接收、校验入口、响应封装。

→
Service

业务层

业务规则、事务边界、组合多个 Mapper。

→
Mapper

持久层

执行 SQL 或 BaseMapper 方法。

→
DB

数据库

保存和返回真实业务数据。

调用方向保持单向：Controller 不直接越过 Service 调 Mapper，Mapper 也不反向依赖业务层。

问题/场景：不分层会怎样？

来看一段 CTTS 中"不分层"的反例代码——ProjectController 直接调 ProjectMapper，业务逻辑全部塞在 Controller 里：

// ❌ 反例：Controller 直接调 Mapper，业务逻辑堆在 Controller
package com.ctts.controller;

import com.ctts.entity.Project;
import com.ctts.mapper.ProjectMapper;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.web.bind.annotation.*;

import java.time.LocalDateTime;
import java.util.List;

@RestController
@RequestMapping("/api/projects")
public class ProjectController {

    @Autowired
    private ProjectMapper projectMapper;   // 直接注入 Mapper

    @PostMapping
    public String addProject(@RequestBody Project project) {
        // 业务校验
        if (project.getTitle() == null || project.getTitle().trim().isEmpty()) {
            return "项目标题不能为空";
        }
        if (project.getTitle().length() > 100) {
            return "项目标题不能超过100字";
        }
        // 查重
        Project exist = projectMapper.selectByTitle(project.getTitle());
        if (exist != null) {
            return "项目标题已存在";
        }
        // 补全字段
        project.setStatus(0);
        project.setCreateTime(LocalDateTime.now());
        project.setUpdateTime(LocalDateTime.now());
        // 插入
        int rows = projectMapper.insert(project);
        if (rows != 1) {
            return "新增失败";
        }
        // 同时记录一条日志（假设有 logMapper）
        // logMapper.insert(new Log(...));   // 多步操作，没有事务！
        return "新增成功，ID=" + project.getId();
    }

    @PutMapping("/{id}/status")
    public String updateStatus(@PathVariable Long id, @RequestParam Integer status) {
        Project project = projectMapper.selectById(id);
        if (project == null) {
            return "项目不存在";
        }
        // 状态机校验
        if (project.getStatus() == 2 && status != 2) {
            return "已完成项目不能改状态";
        }
        project.setStatus(status);
        project.setUpdateTime(LocalDateTime.now());
        int rows = projectMapper.updateById(project);
        return rows == 1 ? "更新成功" : "更新失败";
    }

    @GetMapping
    public List<Project> list() {
        return projectMapper.selectList(null);
    }
}

这段反例代码有 6 个典型问题：

# 问题 后果
1 Controller 职责过重 既接请求、又写业务、又调 Mapper、又处理异常，方法动辄几十上百行
2 业务逻辑无法复用 "查重 + 补字段 + 插入" 这套逻辑只在 Controller 出现一次，别处想用得复制粘贴
3 无法单元测试 Controller 方法依赖 HTTP 请求，要测业务逻辑必须发 HTTP 请求，测试又慢又脆
4 事务边界不清晰 addProject 里既插 project 又想插 log，没有 @Transactional，一旦第二步失败数据不一致
5 不利于团队协作 前端调接口的同学、写业务的同学、写 SQL 的同学都改同一个 Controller 文件，冲突频繁
6 异常处理散落 每个方法都写"返回字符串提示"，没有统一异常处理，接口返回格式混乱

正例代码（三层架构改造后）：

// ✅ 正例：Controller 只接请求、调 Service、返回响应
package com.ctts.controller;

import com.ctts.entity.Project;
import com.ctts.service.ProjectService;
import lombok.RequiredArgsConstructor;
import org.springframework.web.bind.annotation.*;

import java.util.List;

@RestController
@RequestMapping("/api/projects")
@RequiredArgsConstructor
public class ProjectController {

    private final ProjectService projectService;   // 调 Service，不调 Mapper

    @PostMapping
    public String addProject(@RequestBody Project project) {
        Long id = projectService.createProject(project);
        return "新增成功，ID=" + id;
    }

    @PutMapping("/{id}/status")
    public String updateStatus(@PathVariable Long id, @RequestParam Integer status) {
        projectService.updateStatus(id, status);
        return "更新成功";
    }

    @GetMapping
    public List<Project> list() {
        return projectService.findAll();
    }
}

对比可见：Controller 从 40 行瘦身到 15 行，业务逻辑全部下沉到 Service。

易错点

# 易错点 说明
1 "分层 = 包多" 分层不是简单建几个包，而是职责的真正剥离。把业务逻辑原封不动从 Controller 移到 Service 才叫分层
2 "Controller 越薄越好，连参数校验都不要" 参数格式校验（@Valid）可以放 Controller；业务规则校验（如标题查重）必须放 Service
3 "Service 可以反向调 Controller" 违反单向依赖原则。Service 不应知道 Controller 的存在，更不能返回 HTTP 相关对象（如 ResponseEntity）
4 "Mapper 也可以做业务逻辑" Mapper 只负责数据访问，不能写业务。if/else 业务判断不应出现在 Mapper 或 XML 中
5 "分层会让性能变差" 方法调用纳秒级开销，可忽略。分层的可维护性收益远大于这点开销

小结

  • 分层的本质是 关注点分离，把不同性质的工作交给不同的层；
  • 三层架构的核心价值：可维护、可测试、可协作、避免臃肿；
  • 分层是 团队协作的契约，是对队友负责、对项目负责的工程规范；
  • 后续所有业务功能都将遵循"Controller → Service → Mapper"的标准链路。

K10-2 三层架构

定义

三层架构：将后端应用分为 Controller（表现层）、Service（业务层）、Mapper/DAO（数据访问层）三个层次，每层有明确的职责边界。

原理：三层职责划分

层 包名（CTTS 约定） 职责 关键词 厚薄
Controller com.ctts.controller 接收 HTTP 请求、参数绑定、调用 Service、封装响应 薄 薄层
Service com.ctts.service + com.ctts.service.impl 业务逻辑、事务管理、业务规则校验、组合多个 Mapper 调用 厚 厚层
Mapper com.ctts.mapper 数据访问，执行 SQL（CRUD、查询） 单一 数据层

调用方向（单向依赖）：

       ┌──────────────────────────────────────┐
       │           HTTP 请求 / 响应            │
       └────────────────┬─────────────────────┘
                        │
                        ▼
       ┌──────────────────────────────────────┐
       │   Controller（表现层 / 薄层）         │
       │   - @RestController / @RequestMapping │
       │   - 参数接收：@RequestParam/@PathVariable/@RequestBody
       │   - 调用 Service，不调 Mapper          │
       │   - 返回 JSON / 统一响应体             │
       └────────────────┬─────────────────────┘
                        │ 调用（单向）
                        ▼
       ┌──────────────────────────────────────┐
       │   Service（业务层 / 厚层）            │
       │   - @Service 注解                     │
       │   - 业务逻辑 / 规则校验                │
       │   - @Transactional 事务管理           │
       │   - 组合调用多个 Mapper               │
       └────────────────┬─────────────────────┘
                        │ 调用（单向）
                        ▼
       ┌──────────────────────────────────────┐
       │   Mapper（数据访问层）                │
       │   - @Mapper / BaseMapper<T>           │
       │   - 执行 SQL：insert/update/delete/select
       │   - 不含业务逻辑                      │
       └────────────────┬─────────────────────┘
                        │
                        ▼
                   ┌─────────┐
                   │  MySQL  │
                   └─────────┘

关键原则：

  1. 上层依赖下层，下层不依赖上层——Service 可以调 Mapper，Mapper 不能调 Service；
  2. 跨层调用禁止——Controller 不能直接调 Mapper（必须经过 Service）；
  3. 下层不感知上层——Mapper 不知道谁在调它，Service 不知道 Controller 的存在。

问题/场景：三层职责边界怎么判断？

判断一个代码该放哪一层，问三个问题：

问题 是 否
这段代码和 HTTP 请求/响应有关吗？ 放 Controller 继续问
这段代码涉及业务规则、事务、多表组合吗？ 放 Service 继续问
这段代码就是读写数据库吗？ 放 Mapper ——

典型例子（CTTS）：

代码片段 该放哪层 理由
@GetMapping("/api/projects") Controller HTTP 路由
@RequestBody Project project Controller 请求体反序列化
标题查重 selectByTitle Service（调 Mapper） 业务规则
project.setStatus(0) 补默认值 Service 业务逻辑
@Transactional 保证多表一致性 Service 事务边界

易错点

# 易错点 说明
1 Controller 直接 @Autowired Mapper 违反分层。即使业务再简单，也要经过 Service，保证一致性
2 Service 返回 ResponseEntity 或 HttpServletRequest Service 不应感知 Web 层。返回业务对象或业务结果，HTTP 相关交给 Controller
3 业务校验写在 Mapper XML 里（<if test="title != null">） XML 里的 <if> 是 SQL 拼接判断，不是业务校验。业务校验放 Service
4 一个 Controller 方法调多个 Service 多数情况应合并为一个 Service 方法（Service 可组合多个 Mapper）
5 Service 接口和实现类同名（都叫 ProjectService） 实现类应叫 ProjectServiceImpl，放 impl 子包
6 @Service 写在接口上 注解应写在实现类上。接口保持纯净，不依赖 Spring

小结

  • 三层架构 = Controller（薄）+ Service（厚）+ Mapper（数据）；
  • 调用方向 单向：Controller → Service → Mapper → DB；
  • 判断代码归属的三问法：HTTP 相关 → Controller；业务规则/事务 → Service；读写 DB → Mapper；
  • @Service 写在实现类上，接口放 service 包，实现类放 service/impl 子包。

K10-3 Service 层开发

定义

Service 层开发：在 Controller 与 Mapper 之间引入 Service 层，使用 @Service 注解将实现类注册为 Spring Bean，通过 接口 + 实现类 的形式对外提供业务能力。

原理

Spring Boot 启动时会扫描带 @Service 注解的类，把它们实例化为 Bean 放入 IoC 容器。当 Controller 需要某个 Service 时，Spring 根据类型自动注入。

启动扫描                 IoC 容器                  注入使用
   │                        │                         │
   ▼                        ▼                         ▼
@Service class              ┌──────────────────┐     @Autowired
ProjectServiceImpl   ──►   │ projectService:  │ ──► private ProjectService
                          │  ProjectServiceImpl│      projectService;
                          └──────────────────┘

接口与实现分离的意义：

  1. 面向接口编程：Controller 依赖 ProjectService 接口而非实现类，解耦；
  2. 便于切换实现：测试时可注入 mock 实现；将来换实现只改 @Service 类；
  3. 统一契约：接口即业务能力的契约文档。

问题/场景：如何为 ProjectController 创建 Service？

步骤 1：创建 Service 接口

package com.ctts.service.impl;

import com.ctts.entity.Project;
import com.ctts.mapper.ProjectMapper;
import com.ctts.service.ProjectService;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import org.springframework.util.StringUtils;

import java.time.LocalDateTime;
import java.util.List;

@Service                                  // ① 注册为 Spring Bean
@RequiredArgsConstructor                  // ② Lombok 生成构造器（构造器注入，见 K10-5）
public class ProjectServiceImpl implements ProjectService {

    private final ProjectMapper projectMapper;   // ③ 依赖 Mapper

    @Override
    public List<Project> findAll() {
        return projectMapper.selectList(null);
    }

    @Override
    public Project findById(Long id) {
        return projectMapper.selectById(id);
    }

    @Override
    public Long createProject(Project project) {
        // 业务校验
        if (!StringUtils.hasText(project.getTitle())) {
            throw new IllegalArgumentException("项目标题不能为空");
        }
        if (project.getTitle().length() > 100) {
            throw new IllegalArgumentException("项目标题不能超过100字");
        }
        // 查重
        Project exist = projectMapper.selectByTitle(project.getTitle());
        if (exist != null) {
            throw new IllegalStateException("项目标题已存在");
        }
        // 补默认值
        if (project.getStatus() == null) {
            project.setStatus(0);
        }
        project.setCreateTime(LocalDateTime.now());
        project.setUpdateTime(LocalDateTime.now());
        // 写入
        projectMapper.insert(project);
        return project.getId();
    }

    @Override
    public boolean updateProject(Project project) {
        project.setUpdateTime(LocalDateTime.now());
        return projectMapper.updateById(project) == 1;
    }

    @Override
    public boolean updateStatus(Long id, Integer status) {
        Project project = projectMapper.selectById(id);
        if (project == null) {
            throw new IllegalArgumentException("项目不存在");
        }
        // 状态机校验：已完成(2)不能改回其他状态
        if (project.getStatus() == 2 && status != 2) {
            throw new IllegalStateException("已完成项目不能改状态");
        }
        project.setStatus(status);
        project.setUpdateTime(LocalDateTime.now());
        return projectMapper.updateById(project) == 1;
    }

    @Override
    public boolean deleteById(Long id) {
        return projectMapper.deleteById(id) == 1;
    }
}

package com.ctts.service.impl;

import com.ctts.entity.Task;
import com.ctts.entity.TaskSubmission;
import com.ctts.mapper.TaskMapper;
import com.ctts.mapper.TaskSubmissionMapper;
import com.ctts.service.TaskService;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.util.StringUtils;

import java.time.LocalDateTime;
import java.util.List;

@Service
@RequiredArgsConstructor
public class TaskServiceImpl implements TaskService {

    private final TaskMapper taskMapper;
    private final TaskSubmissionMapper taskSubmissionMapper;

    @Override
    public List<Task> findAll() {
        return taskMapper.selectList(null);
    }

    @Override
    public Task findById(Long id) {
        return taskMapper.selectById(id);
    }

    /**
     * 学生提交任务：同时创建提交记录 + 更新任务状态
     * 涉及多表写操作，必须加事务
     */
    @Override
    @Transactional(rollbackFor = Exception.class)   // ★ 见 K10-4
    public Long submitTask(Long taskId, TaskSubmission submission) {
        // 1. 业务校验：任务必须存在
        Task task = taskMapper.selectById(taskId);
        if (task == null) {
            throw new IllegalArgumentException("任务不存在: " + taskId);
        }
        // 2. 业务校验：提交内容不能为空
        if (!StringUtils.hasText(submission.getContent())) {
            throw new IllegalArgumentException("提交内容不能为空");
        }
        // 3. 补全提交记录字段
        submission.setTaskId(taskId);
        submission.setStatus(1);                       // 已提交
        submission.setSubmitTime(LocalDateTime.now());
        submission.setCreateTime(LocalDateTime.now());
        submission.setUpdateTime(LocalDateTime.now());
        // 4. 写入提交记录
        taskSubmissionMapper.insert(submission);
        // 5. 更新任务状态为"进行中"（如果原来是未开始）
        if (task.getStatus() == 0) {
            task.setStatus(1);
            task.setUpdateTime(LocalDateTime.now());
            taskMapper.updateById(task);
        }
        // 6. 若以上任一步骤抛异常，整个事务回滚，提交记录与状态更新都不会落库
        return submission.getId();
    }

    @Override
    public boolean updateStatus(Long id, Integer status) {
        Task task = taskMapper.selectById(id);
        if (task == null) {
            throw new IllegalArgumentException("任务不存在");
        }
        task.setStatus(status);
        task.setUpdateTime(LocalDateTime.now());
        return taskMapper.updateById(task) == 1;
    }
}

易错点

# 易错点 说明
1 @Service 写在接口上 应写在实现类上。接口保持纯净，与 Spring 解耦
2 实现类不实现接口 直接 @Service class XxxService（无接口）虽能跑，但失去接口分离的优势。建议接口 + 实现
3 实现类放错包 实现类应放 service/impl 子包，不要和接口混放
4 Service 方法命名随意 应使用业务动词：createXxx / updateXxx / deleteXxx / findXxx / submitXxx，而非 insertXxx / updateDb（Mapper 风格）
5 Service 直接返回 Mapper 查询结果，未做业务处理 如果只是透传，说明这层 Service 价值不大；但即使透传，也保留 Service 层便于未来扩展
6 Controller 注入 ProjectServiceImpl（实现类） 应注入接口 ProjectService，面向接口编程
7 @RequiredArgsConstructor 未生效，构造器没生成 未引入 Lombok 依赖；或字段未加 final（只有 final 字段才进构造器）

小结

  • Service 层开发三件套：接口（service 包）+ 实现类（service/impl 子包，加 @Service）+ 构造器注入 Mapper；
  • 接口与实现分离 = 面向接口编程 + 便于切换实现 + 统一契约；
  • @Service 写在实现类上，Controller 依赖接口而非实现类；
  • 包结构约定：controller / service / service/impl / mapper / entity。

K10-4 事务管理

定义

事务（Transaction）：一组不可分割的操作序列，要么全部成功提交，要么全部失败回滚。事务具有 ACID 四大特性：

  • Atomicity 原子性：全部成功或全部失败；
  • Consistency 一致性：事务前后数据保持一致；
  • Isolation 隔离性：并发事务互不干扰；
  • Durability 持久性：提交后永久保存。

声明式事务：通过 @Transactional 注解让 Spring 自动管理事务，开发者只需声明"这个方法需要事务"，无需手写 commit / rollback。

原理

完整示例代码：@Transactional 详解

场景：学生提交任务时，同时创建提交记录并更新任务状态——两步写操作必须保证原子性。

@Service
@RequiredArgsConstructor
public class TaskServiceImpl implements TaskService {

    private final TaskMapper taskMapper;
    private final TaskSubmissionMapper taskSubmissionMapper;

    /**
     * 提交任务（事务方法）
     */
    @Override
    @Transactional(rollbackFor = Exception.class)   // ★ 关键注解
    public Long submitTask(Long taskId, TaskSubmission submission) {
        // 1. 校验任务存在
        Task task = taskMapper.selectById(taskId);
        if (task == null) {
            throw new IllegalArgumentException("任务不存在");
        }
        // 2. 补全字段
        submission.setTaskId(taskId);
        submission.setStatus(1);
        submission.setSubmitTime(LocalDateTime.now());
        // 3. 写入提交记录
        taskSubmissionMapper.insert(submission);
        // 4. 更新任务状态（若原状态为未开始）
        if (task.getStatus() == 0) {
            task.setStatus(1);
            taskMapper.updateById(task);   // 若此步抛异常，第3步的 insert 也会回滚
        }
        return submission.getId();
    }
}

@Transactional 注解核心属性：

属性 说明 常用值
rollbackFor 遇到哪些异常时回滚 Exception.class（推荐，覆盖所有异常）
noRollbackFor 遇到哪些异常时不回滚 特定业务异常
propagation 事务传播行为（见下文） REQUIRED（默认）/ REQUIRES_NEW
isolation 事务隔离级别 DEFAULT（默认，使用数据库隔离级别）
timeout 事务超时时间（秒） -1（默认，不超时）
readOnly 是否只读事务 false（默认）；纯查询可设 true 优化
transactionManager 指定事务管理器 多数据源时使用

为什么必须加 rollbackFor = Exception.class？

Spring 默认只对 RuntimeException 和 Error 回滚，对 受检异常（checked Exception） 不回滚。如果方法签名抛出 IOException、SQLException 等受检异常，默认不回滚，会导致数据不一致。

// ❌ 危险写法：默认只回滚 RuntimeException
@Transactional
public void doSomething() throws IOException {
    mapper.insert(a);
    if (xxx) {
        throw new IOException("文件读不到");   // 抛受检异常，默认不回滚！insert(a) 已落库
    }
}

// ✅ 安全写法：显式指定 rollbackFor
@Transactional(rollbackFor = Exception.class)
public void doSomething() throws IOException {
    mapper.insert(a);
    if (xxx) {
        throw new IOException("文件读不到");   // 回滚
    }
}

养成习惯：所有 @Transactional 都加 rollbackFor = Exception.class。

事务传播行为（Propagation）

传播行为：当一个事务方法被另一个事务方法调用时，如何处理事务边界。

传播行为 说明 使用场景
REQUIRED（默认） 当前有事务就加入，没有就新建 90% 的场景，最常用
REQUIRES_NEW 不管当前有没有事务，都新建一个独立事务；外层事务挂起 日志记录：无论主业务成功与否，日志都要落库
SUPPORTS 当前有事务就加入，没有就非事务运行 查询方法，可有可无事务
NOT_SUPPORTED 以非事务方式运行，当前事务挂起 不需要事务的耗时操作
NEVER 以非事务方式运行，如果当前有事务则抛异常 不允许在事务中运行的方法
MANDATORY 必须在事务中运行，否则抛异常 强制要求调用方提供事务
NESTED 嵌套事务，基于 savepoint 实现 部分回滚场景

重点对比：REQUIRED vs REQUIRES_NEW

场景：方法A（有事务）调用方法B

【REQUIRED】（默认）
  方法B加入方法A的事务，A和B在同一个事务中
  → B抛异常，A也回滚；A抛异常，B也回滚
  → 一荣俱荣，一损俱损

【REQUIRES_NEW】
  方法B新开一个独立事务，A的事务挂起
  → B提交后，A的事务恢复
  → B抛异常，B自己回滚，A可选择捕获继续或一起回滚
  → 互不影响

示例：
  submitTask() {                 // 事务A
      taskMapper.insert(...);
      logService.recordLog();    // REQUIRES_NEW，事务B
      taskMapper.update(...);    // 抛异常
  }
  → 事务A回滚：insert 和 update 都回滚
  → 事务B已独立提交：日志保留（这正是日志业务想要的）

示例代码：REQUIRES_NEW 用于日志

@Service
@RequiredArgsConstructor
public class TaskServiceImpl implements TaskService {

    private final TaskMapper taskMapper;
    private final LogService logService;   // 独立事务的日志服务

    @Override
    @Transactional(rollbackFor = Exception.class)
    public Long submitTask(Long taskId, TaskSubmission submission) {
        taskMapper.insert(...);
        logService.recordLog("submit", taskId);   // 即使主事务回滚，日志也保留
        taskMapper.update(...);
        return submission.getId();
    }
}

@Service
@RequiredArgsConstructor
public class LogServiceImpl implements LogService {

    private final LogMapper logMapper;

    @Override
    @Transactional(propagation = Propagation.REQUIRES_NEW, rollbackFor = Exception.class)
    public void recordLog(String action, Long taskId) {
        Log log = new Log();
        log.setAction(action);
        log.setTaskId(taskId);
        log.setCreateTime(LocalDateTime.now());
        logMapper.insert(log);
    }
}

事务失效的 7 大场景（面试高频）

# 失效场景 原因 解决方案
1 方法非 public Spring AOP 代理只拦截 public 方法 改为 public
2 类内部自调用 this.method() 不走代理，注解失效 通过注入自己（@Lazy）或拆到另一个 Service
3 异常被 try-catch 吞掉 Spring 通过异常判断是否回滚，异常被吞则认为正常 catch 后手动 throw，或用 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()
4 抛出受检异常但未配 rollbackFor 默认只回滚 RuntimeException 加 rollbackFor = Exception.class
5 数据库引擎不支持事务 MySQL 的 MyISAM 引擎不支持事务 用 InnoDB 引擎
6 @Transactional 加在 final/static 方法 代理无法重写 改为普通方法
7 多线程调用 事务绑定在线程上，新线程没有事务 避免在事务方法内开新线程，或用编程式事务

重点：类内部自调用导致事务失效

@Service
public class TaskServiceImpl implements TaskService {

    @Transactional(rollbackFor = Exception.class)
    public void methodA() {
        mapper.insert(a);
        this.methodB();    // ❌ 自调用，methodB 的事务注解失效！
        mapper.insert(c);
    }

    @Transactional(rollbackFor = Exception.class)
    public void methodB() {
        mapper.insert(b);
        throw new RuntimeException("error");
    }
}

原因：this.methodB() 是直接方法调用，不经过 Spring 代理对象，所以 methodB 上的 @Transactional 不会被拦截处理。整个 methodA 是一个事务（如果 methodA 有 @Transactional），methodB 的异常会导致整个事务回滚——但 methodB 自己声明的传播行为不会生效。

解决方案：把 methodB 拆到另一个 Service，或注入自己：

@Service
@RequiredArgsConstructor
public class TaskServiceImpl implements TaskService {

    private final TaskService self;   // 注入自己（需 @Lazy 避免循环依赖）

    @Transactional(rollbackFor = Exception.class)
    public void methodA() {
        mapper.insert(a);
        self.methodB();    // ✅ 通过代理调用，事务生效
        mapper.insert(c);
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW, rollbackFor = Exception.class)
    public void methodB() {
        mapper.insert(b);
    }
}

易错点

# 易错点 说明
1 @Transactional 加在 Controller 上 事务应加在 Service 层。Controller 不应感知事务
2 @Transactional 加在 private 方法上 代理不生效，注解无效
3 类内部自调用 见上文，最常见的失效场景
4 不加 rollbackFor 受检异常不回滚，数据不一致
5 在事务方法内 try-catch 吞异常 Spring 检测不到异常，不回滚
6 滥用 REQUIRES_NEW 性能开销大（多一个事务连接），仅在日志等独立场景使用
7 纯查询方法加 @Transactional 无意义，浪费事务资源。如需只读优化，用 @Transactional(readOnly = true)
8 把事务当作万能锁 事务不解决并发问题，并发需用乐观锁/悲观锁/隔离级别

小结

  • 事务保证 多步写操作的原子性，判断标准："方法内是否有多步写操作？"；
  • @Transactional 加在 Service 方法上，推荐 @Transactional(rollbackFor = Exception.class)；
  • 传播行为重点掌握 REQUIRED（默认，加入当前事务）和 REQUIRES_NEW（新开独立事务，用于日志）；
  • 事务失效 7 大场景：非 public、自调用、异常被吞、受检异常未配 rollbackFor、MyISAM、final/static 方法、多线程。

K10-5 依赖注入

定义

依赖注入（Dependency Injection, DI）：对象不再自己 new 它的依赖，而是由 Spring IoC 容器在运行时自动把依赖注入进去。

IoC 容器（Inversion of Control）：Spring 维护一个"对象池"，所有被 @Component / @Service / @Repository / @Controller 等注解标记的类，都会被实例化为 Bean 放入容器。需要时由容器注入。

原理：三种依赖注入方式

Spring 提供三种注入方式：

方式 1：字段注入（@Autowired）
@Service
public class ProjectServiceImpl implements ProjectService {

    @Autowired
    private ProjectMapper projectMapper;
}
  • 优点：写法简洁；
  • 缺点：
    • 字段无法声明为 final，对象可能被中途修改；
    • 脱离 Spring 容器后无法 new（依赖未注入）；
    • 循环依赖不易发现（Spring 用三级缓存解决，但隐藏设计问题）；
    • Spring 官方不推荐，IDE 会给出警告。
方式 2：构造器注入（推荐）
// 手动构造器写法
@Service
public class ProjectServiceImpl implements ProjectService {

    private final ProjectMapper projectMapper;

    public ProjectServiceImpl(ProjectMapper projectMapper) {
        this.projectMapper = projectMapper;
    }
}

// Lombok 简化写法（推荐）
@Service
@RequiredArgsConstructor
public class ProjectServiceImpl implements ProjectService {

    private final ProjectMapper projectMapper;   // Lombok 自动生成构造器
}
  • 优点：
    • 字段可声明为 final，不可变，线程安全；
    • 脱离 Spring 容器也能 new（可单元测试）；
    • 循环依赖在启动阶段就暴露（编译报错），避免运行时才发现；
    • Spring 官方推荐。
  • 缺点：依赖多时构造器参数多（但通常说明类职责过重，应拆分）。

@RequiredArgsConstructor 是 Lombok 注解，会为类中所有 final 字段生成构造器。这是企业项目最常用的写法。

方式 3：@Resource（JSR-250）
@Service
public class ProjectServiceImpl implements ProjectService {

    @Resource
    private ProjectMapper projectMapper;

    @Resource(name = "projectMapper")
    private ProjectMapper anotherMapper;
}
  • @Resource 是 JDK 提供的注解（javax.annotation.Resource），Spring 也支持；
  • 默认按 名称 注入，找不到再按类型；
  • 可通过 name 属性指定 Bean 名称；
  • 适用于需要按名称区分多个实现的场景。
三种方式对比
方式 写法 推荐度 不可变 可脱离容器 循环依赖检测
@Autowired 字段注入 简洁 ❌ 不推荐 否 否 运行时

Setter 注入 繁琐 ⭕ 可选（可选依赖） 否 是 运行时

问题/场景：什么时候用 @Autowired、什么时候用 @Resource？

  • 90% 场景：用构造器注入（@RequiredArgsConstructor + final），连 @Autowired 都不用写；
  • 多个实现类需要选择：用 @Qualifier("beanName") 配合构造器注入，或用 @Resource(name="beanName")；
  • 历史代码维护：如果原有代码用 @Autowired，可逐步迁移到构造器注入，不必一次性全改。

易错点

# 易错点 说明
1 @RequiredArgsConstructor 加了但字段未加 final 只有 final 字段才进构造器，未加 final 的字段不会被注入
2 引入了 @Resource 但用错包 @Resource 是 javax.annotation.Resource（JDK）或 jakarta.annotation.Resource（Spring Boot 3.x）。Spring Boot 3 用 jakarta
3 在 @Service 类中 new 另一个 @Service new 出来的对象不被 Spring 管理，其内部的 @Autowired 不生效。应注入
4 用 @Autowired 注入 Mapper 但 Mapper 未注册 Mapper 需加 @Mapper，或启动类加 @MapperScan("com.ctts.mapper")
5 多个实现类未指定选哪个 报 NoUniqueBeanDefinitionException。用 @Primary 或 @Qualifier 解决
6 在非 Spring 管理的类中用 @Autowired @Autowired 只在 Spring Bean 中生效。普通 new 出来的类中的 @Autowired 不生效
7 构造器注入 + @Value 配置属性混用 可以混用，@Value 注入配置值，final 字段注入 Bean

小结

  • 依赖注入 = 对象不自己 new 依赖，由 Spring IoC 容器注入；
  • 三种方式：@Autowired 字段注入（不推荐）、构造器注入（推荐）、@Resource（可选）；
  • 企业项目推荐：@RequiredArgsConstructor + final 字段，简洁且不可变；
  • Spring IoC 容器职责：扫描 → 实例化 → 注入 → 管理 Bean 生命周期；
  • 多个实现类用 @Primary 或 @Qualifier 选择。

3.3.2 ProjectServiceImpl 实现类

package com.ctts.service.impl;

import com.ctts.entity.Project;
import com.ctts.mapper.ProjectMapper;
import com.ctts.service.ProjectService;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import org.springframework.util.StringUtils;

import java.time.LocalDateTime;
import java.util.List;

@Service
@RequiredArgsConstructor
public class ProjectServiceImpl implements ProjectService {

    private final ProjectMapper projectMapper;

    @Override
    public List<Project> findAll() {
        return projectMapper.selectList(null);
    }

    @Override
    public Project findById(Long id) {
        return projectMapper.selectById(id);
    }

    @Override
    public Long createProject(Project project) {
        if (!StringUtils.hasText(project.getTitle())) {
            throw new IllegalArgumentException("项目标题不能为空");
        }
        if (project.getTitle().length() > 100) {
            throw new IllegalArgumentException("项目标题不能超过100字");
        }
        Project exist = projectMapper.selectByTitle(project.getTitle());
        if (exist != null) {
            throw new IllegalStateException("项目标题已存在");
        }
        if (project.getStatus() == null) {
            project.setStatus(0);
        }
        project.setCreateTime(LocalDateTime.now());
        project.setUpdateTime(LocalDateTime.now());
        projectMapper.insert(project);
        return project.getId();
    }

    @Override
    public boolean updateProject(Project project) {
        project.setUpdateTime(LocalDateTime.now());
        return projectMapper.updateById(project) == 1;
    }

    @Override
    public boolean updateStatus(Long id, Integer status) {
        Project project = projectMapper.selectById(id);
        if (project == null) {
            throw new IllegalArgumentException("项目不存在");
        }
        if (project.getStatus() == 2 && status != 2) {
            throw new IllegalStateException("已完成项目不能改状态");
        }
        project.setStatus(status);
        project.setUpdateTime(LocalDateTime.now());
        return projectMapper.updateById(project) == 1;
    }

    @Override
    public boolean deleteById(Long id) {
        return projectMapper.deleteById(id) == 1;
    }
}

3.3.5 TaskServiceImpl 实现类（含 @Transactional）

package com.ctts.service.impl;

import com.ctts.entity.Task;
import com.ctts.entity.TaskSubmission;
import com.ctts.mapper.TaskMapper;
import com.ctts.mapper.TaskSubmissionMapper;
import com.ctts.service.TaskService;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.util.StringUtils;

import java.time.LocalDateTime;
import java.util.List;

@Service
@RequiredArgsConstructor
public class TaskServiceImpl implements TaskService {

    private final TaskMapper taskMapper;
    private final TaskSubmissionMapper taskSubmissionMapper;

    @Override
    public List<Task> findAll() {
        return taskMapper.selectList(null);
    }

    @Override
    public Task findById(Long id) {
        return taskMapper.selectById(id);
    }

    /**
     * 学生提交任务：同时创建提交记录 + 更新任务状态
     * 涉及多表写操作，必须加事务
     */
    @Override
    @Transactional(rollbackFor = Exception.class)
    public Long submitTask(Long taskId, TaskSubmission submission) {
        // 1. 校验任务存在
        Task task = taskMapper.selectById(taskId);
        if (task == null) {
            throw new IllegalArgumentException("任务不存在: " + taskId);
        }
        // 2. 校验提交内容
        if (!StringUtils.hasText(submission.getContent())) {
            throw new IllegalArgumentException("提交内容不能为空");
        }
        // 3. 补全提交记录字段
        submission.setTaskId(taskId);
        submission.setStatus(1);
        submission.setSubmitTime(LocalDateTime.now());
        submission.setCreateTime(LocalDateTime.now());
        submission.setUpdateTime(LocalDateTime.now());
        // 4. 写入提交记录
        taskSubmissionMapper.insert(submission);
        // 5. 更新任务状态
        if (task.getStatus() == 0) {
            task.setStatus(1);
            task.setUpdateTime(LocalDateTime.now());
            taskMapper.updateById(task);
        }
        // 若 4 或 5 任一步骤抛异常，整个事务回滚，两步操作都不会落库
        return submission.getId();
    }

    @Override
    public boolean updateStatus(Long id, Integer status) {
        Task task = taskMapper.selectById(id);
        if (task == null) {
            throw new IllegalArgumentException("任务不存在");
        }
        task.setStatus(status);
        task.setUpdateTime(LocalDateTime.now());
        return taskMapper.updateById(task) == 1;
    }
}

三层架构是经典分层，随着业务复杂度提升，可演进为 DDD 四层架构：

层 职责 对应三层架构
Interface（接口层） HTTP / RPC 接口 Controller
Application（应用层） 编排业务流程，不含业务规则 Service（部分）
Domain（领域层） 业务规则、领域模型 Service（核心）+ Entity
Infrastructure（基础设施层） 数据访问、消息、缓存 Mapper

4.2 编程式事务

除了声明式事务（@Transactional），Spring 还支持 编程式事务，用 TransactionTemplate 手动控制：

@Service
@RequiredArgsConstructor
public class TaskServiceImpl implements TaskService {

    private final TransactionTemplate transactionTemplate;
    private final TaskMapper taskMapper;

    public void submitTask(Long taskId, TaskSubmission submission) {
        transactionTemplate.execute(status -> {
            try {
                taskMapper.insert(submission);
                taskMapper.update(...);
                return true;
            } catch (Exception e) {
                status.setRollbackOnly();
                return false;
            }
        });
    }
}

适用场景：事务边界需要精确控制（如只包裹部分代码）。

4.3 @Transactional 的 7 种传播行为完整列表

本课重点讲 REQUIRED 和 REQUIRES_NEW，其余 5 种了解即可：

传播行为 含义
REQUIRED（默认） 有事务加入，无事务新建
REQUIRES_NEW 总是新建独立事务，外层挂起
SUPPORTS 有事务加入，无事务非事务运行
NOT_SUPPORTED 非事务运行，外层挂起
NEVER 非事务运行，有事务则抛异常
MANDATORY 必须在事务中运行，无事务抛异常
NESTED 嵌套事务，基于 savepoint

4.4 Spring Boot 3.x 的 @Resource 包变化

Spring Boot 3.x（基于 Jakarta EE 9+）中，@Resource 的包从 javax.annotation.Resource 改为 jakarta.annotation.Resource。迁移时需注意 import。

五、小结与思维导图

5.1 核心要点回顾

  1. 为什么分层：关注点分离、可维护、可测试、可协作、避免臃肿；
  2. 三层架构：Controller（薄）→ Service（厚）→ Mapper（数据），单向依赖；
  3. Service 开发：接口（service 包）+ 实现类（service/impl 子包，@Service），构造器注入 Mapper；
  4. 事务管理：@Transactional(rollbackFor = Exception.class)，多步写操作必须加事务；
  5. 依赖注入：构造器注入（@RequiredArgsConstructor + final）推荐，@Autowired 字段注入不推荐。
