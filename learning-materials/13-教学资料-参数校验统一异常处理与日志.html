一、学习导读

1.1 本课定位

本课是 M5 模块（接口规范与工程规范）的第 1 课，是从"能跑的接口"到"能上线的接口"的关键一课。前面你已经能写出 CRUD 接口，但接口的"健壮性"还差得远：

  • 用户传个空字符串，后端直接存进数据库 → 脏数据；
  • 用户传个错误类型，后端返回一长串英文堆栈 → 信息泄露 + 体验差；
  • 线上接口报错，没有日志 → 无从排查。

本课的"三件套"——参数校验 + 统一异常处理 + 日志——就是解决这三个问题的标准答案，也是大厂后端接口的"标配"。

学完本课后，你应当能够：

  1. 为 DTO 添加合适的校验注解，并理解 @Valid 与 @Validated 的区别；
  2. 编写 GlobalExceptionHandler 全局异常处理器，统一返回 Result<T>；
  3. 设计 BusinessException 自定义业务异常，并在 Service 层抛出；
  4. 使用 @Slf4j 输出日志，并在 application.yml 配置日志级别与文件输出；
  5. 根据日志与堆栈信息排查空指针、类型不匹配、SQL 异常、404/500 等常见错误。

二、知识点详解

K13-1 参数校验

2.1.1 定义

参数校验是指在请求进入业务逻辑之前，对请求参数（DTO 字段、查询参数、路径参数）进行合法性验证的过程。Spring Boot 通过 JSR 380（Bean Validation 2.0）规范 + Hibernate Validator 实现来完成这件事。

为什么需要参数校验？

不校验的后果 校验的好处
脏数据进库（空名、负数 ID） 把好入口关，数据干净
业务逻辑里到处 if (name == null) 校验集中，代码清爽
异常难定位（NPE 在 Service 层爆） 在 Controller 入口就拦截，错误清晰
前端传错类型直接 500 返回 400 + 友好提示

2.1.2 原理

Spring MVC 处理请求时，如果方法参数上有 @Valid 或 @Validated，会调用 Validator 对目标对象进行校验：

  1. 请求到达 Controller，Spring 解析 @RequestBody 反序列化为 DTO 对象；
  2. 若参数标注了 @Valid，Spring 调用 Validator.validate(dto)；
  3. 校验失败时，Spring 收集所有 ConstraintViolation，封装为 MethodArgumentNotValidException（@RequestBody 场景）或 ConstraintViolationException（@RequestParam / @PathVariable 场景）抛出；
  4. 该异常若没有被 Controller 内部捕获，会被 @RestControllerAdvice 全局捕获。

2.1.3 常见问题

Q1：@Valid 和 @Validated 到底用哪个？

场景 推荐
@RequestBody DTO 校验 @Valid（或 @Validated 都行）
@RequestParam / @PathVariable 校验 @Validated（类上标注）
分组校验（新增/更新不同规则） @Validated(AddGroup.class)
嵌套校验（DTO 中包含 DTO） 字段上标 @Valid

Q2：@NotBlank / @NotNull / @NotEmpty 三者怎么区分？

  • @NotNull：只要不是 null 就行，空字符串 "" 也能过；
  • @NotEmpty：非 null 且长度/大小 > 0（String、Collection、Map、Array）；
  • @NotBlank：非 null 且去空格后非空（仅 String）。

一句话：@NotNull 最宽松，@NotEmpty 管集合，@NotBlank 管字符串最严。

Q3：校验失败后怎么拿到错误信息？

两种方式：

  • 方式一（不推荐）：在 Controller 方法参数加 BindingResult，手动处理。缺点是每个接口都要写一遍，冗余。
  • 方式二（推荐）：用全局异常处理器捕获 MethodArgumentNotValidException，统一处理。本课采用方式二。

package com.ctts.project.dto;

import jakarta.validation.constraints.*;
import lombok.Data;

import java.time.LocalDate;

/**
 * 项目 DTO（创建/更新项目用）
 */
@Data
public class ProjectDTO {

    /** 项目ID（更新时必传，新增时不传） */
    @NotNull(message = "项目ID不能为空", groups = UpdateGroup.class)
    private Long id;

    /** 项目名称 */
    @NotBlank(message = "项目名称不能为空")
    @Size(min = 2, max = 50, message = "项目名称长度需在2-50之间")

    /** 项目描述（可选） */
    @Size(max = 200, message = "项目描述不能超过200字")
    private String description;

    @NotNull(message = "负责人ID不能为空")
    @Min(value = 1, message = "负责人ID非法")
    private Long leaderId;

    /** 项目状态：0-筹备中 1-进行中 2-已结束 */
    @Min(value = 0, message = "状态值非法")
    @Max(value = 2, message = "状态值非法")
    private Integer status;

    /** 分组校验：新增 */
    public interface AddGroup {}
    /** 分组校验：更新 */
    public interface UpdateGroup {}
}

package com.ctts.project.controller;

import com.ctts.common.Result;
import com.ctts.project.dto.ProjectDTO;
import com.ctts.project.service.ProjectService;
import jakarta.validation.Valid;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.validation.annotation.Validated;
import org.springframework.web.bind.annotation.*;

/**
 * 项目控制器
 */
@Slf4j
@RestController
@RequestMapping("/api/projects")
@RequiredArgsConstructor
@Validated  // 类级别开启 @RequestParam/@PathVariable 校验
public class ProjectController {

    private final ProjectService projectService;

    /** 新增项目（默认校验） */
    @PostMapping
    public Result<Void> create(@Valid @RequestBody ProjectDTO dto) {
        log.info("收到新增项目请求: name={}", dto.getName());
        projectService.create(dto);
        return Result.success();
    }

    /** 更新项目（分组校验：UpdateGroup） */
    @PutMapping
    public Result<Void> update(@Validated(ProjectDTO.UpdateGroup.class) @RequestBody ProjectDTO dto) {
        log.info("收到更新项目请求: id={}", dto.getId());
        projectService.update(dto);
        return Result.success();
    }

    /** 查询项目详情（@PathVariable 校验） */
    @GetMapping("/{id}")
    public Result<ProjectVO> getById(@PathVariable @Min(value = 1, message = "ID必须大于0") Long id) {
        log.debug("查询项目详情: id={}", id);
        return Result.success(projectService.getById(id));
    }

    /** 分页查询（@RequestParam 校验） */
    @GetMapping
    public Result<PageVO<ProjectVO>> page(
            @RequestParam(defaultValue = "1") @Min(value = 1, message = "页码必须大于0") Integer page,
            @RequestParam(defaultValue = "10") @Min(value = 1, message = "每页条数必须大于0") Integer size) {
        return Result.success(projectService.page(page, size));
    }
}

2.1.6 易错点

  1. 忘记加 @Valid：DTO 上写了校验注解，但 Controller 参数没加 @Valid，校验不会触发。
  2. @NotBlank 用在非 String 类型：如 @NotBlank 用在 Integer 上，启动报错。@NotBlank 只能用于 String。
  3. @Size 用在数字类型上：@Size 只能用于 String / Collection / Map / Array，数字用 @Min / @Max。
  4. @Email 不校验非空：如果字段可为 null，@Email 不拦截 null；要非空必须配合 @NotBlank。
  5. 嵌套校验忘记加 @Valid：DTO 中有个 List<TaskDTO>，不加 @Valid 不会校验内部元素。
  6. 分组校验用错注解：分组校验必须用 @Validated(Group.class)，@Valid 不支持分组。
  7. @RequestParam 校验不生效：需要在 Controller 类上加 @Validated，方法参数上的注解才生效。

2.1.7 小结

  • 参数校验用 JSR 380 注解 + @Valid / @Validated 触发；
  • 三大非空注解：@NotNull（对象）/ @NotEmpty（集合）/ @NotBlank（字符串）；
  • @RequestBody 用 @Valid，@RequestParam / @PathVariable 用 @Validated（类上）；
  • 分组校验用 @Validated(Group.class)；
  • 校验失败交给全局异常处理器统一处理，不要在 Controller 用 BindingResult 手动处理。

K13-2 全局异常处理

2.2.1 定义

全局异常处理是指通过 @RestControllerAdvice + @ExceptionHandler 在一个集中位置统一捕获并处理整个应用抛出的异常，把异常转换为统一的 Result<T> 响应。

为什么不直接 try-catch？

方式 缺点
每个 Controller 方法 try-catch 代码冗余，重复劳动
Service 抛异常 Controller 接住 异常处理逻辑分散，难维护
全局异常处理器 集中处理，统一返回，一处修改全局生效 ✅

2.2.2 原理

Spring MVC 处理请求时若抛出异常，会交给 HandlerExceptionResolver 链处理。其中 ExceptionHandlerExceptionResolver 负责查找 @ExceptionHandler 方法：

  1. 先在当前 Controller 中查找 @ExceptionHandler；
  2. 再到全局 @RestControllerAdvice 中查找；
  3. 匹配规则：子类优先，最近优先；
  4. 都没匹配到，由 Spring 默认处理（返回 500 + 默认错误页）。

2.2.3 常见问题

Q1：为什么兜底要用 Exception.class 而不是 Throwable.class？

Throwable 包括 Error（如 OutOfMemoryError），这类是 JVM 级错误，应用层不该处理，让 JVM 自己处理。

Q2：异常处理方法返回 Result<Void> 还是 ResponseEntity<Result<Void>>？

  • 返回 Result<Void>：HTTP 状态码永远是 200，业务码在 body 里（推荐，前后端分离常用）；
  • 返回 ResponseEntity<Result<Void>>：可以设置 HTTP 状态码（如 400/500），更符合 HTTP 语义。

本课采用第一种，业务码通过 Result.code 表达。

Q3：异常处理方法能注入哪些参数？

参数类型 说明
异常对象本身 MethodArgumentNotValidException e
HttpServletRequest 获取请求信息
HandlerMethod 获取处理方法信息
WebRequest Spring 的请求抽象

不能注入 BindingResult（它只在 Controller 方法参数中存在）。

2.2.4 完整代码——GlobalExceptionHandler

package com.ctts.common.exception;

import com.ctts.common.Result;
import jakarta.validation.ConstraintViolation;
import jakarta.validation.ConstraintViolationException;
import lombok.extern.slf4j.Slf4j;
import org.springframework.http.converter.HttpMessageNotReadableException;
import org.springframework.validation.BindException;
import org.springframework.validation.FieldError;
import org.springframework.web.HttpRequestMethodNotSupportedException;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.MissingServletRequestParameterException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.method.annotation.MethodArgumentTypeMismatchException;

import java.util.stream.Collectors;

/**
 * 全局异常处理器
 * 统一捕获应用抛出的异常，转换为 Result<T> 返回前端
 */
@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler {

    /**
     * 1. @RequestBody 体校验失败（@Valid 触发）
     */
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<Void> handleMethodArgumentNotValid(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldErrors().stream()
                .map(fe -> fe.getField() + ": " + fe.getDefaultMessage())
                .collect(Collectors.joining("; "));
        log.warn("参数校验失败(Body): {}", msg);
        return Result.fail(400, msg);
    }

    /**
     * 2. 表单校验失败（@Validated + 表单提交）
     */
    @ExceptionHandler(BindException.class)
    public Result<Void> handleBindException(BindException e) {
        String msg = e.getBindingResult().getFieldErrors().stream()
                .map(fe -> fe.getField() + ": " + fe.getDefaultMessage())
                .collect(Collectors.joining("; "));
        log.warn("参数校验失败(Form): {}", msg);
        return Result.fail(400, msg);
    }

    /**
     * 3. @RequestParam / @PathVariable 校验失败（@Validated 类级触发）
     */
    @ExceptionHandler(ConstraintViolationException.class)
    public Result<Void> handleConstraintViolation(ConstraintViolationException e) {
        String msg = e.getConstraintViolations().stream()
                .map(ConstraintViolation::getMessage)
                .collect(Collectors.joining("; "));
        log.warn("参数校验失败(Param): {}", msg);
        return Result.fail(400, msg);
    }

    /**
     * 4. 缺少必填的 @RequestParam
     */
    @ExceptionHandler(MissingServletRequestParameterException.class)
    public Result<Void> handleMissingParam(MissingServletRequestParameterException e) {
        log.warn("缺少必填参数: {}", e.getParameterName());
        return Result.fail(400, "缺少必填参数: " + e.getParameterName());
    }

    /**
     * 5. 参数类型不匹配（如前端传 abc，后端要 Long）
     */
    @ExceptionHandler(MethodArgumentTypeMismatchException.class)
    public Result<Void> handleTypeMismatch(MethodArgumentTypeMismatchException e) {
        log.warn("参数类型不匹配: {} 需要 {}", e.getName(), e.getRequiredType());
        return Result.fail(400, "参数类型不匹配: " + e.getName());
    }

    /**
     * 6. 请求体不可读（JSON 格式错误 / body 为空）
     */
    @ExceptionHandler(HttpMessageNotReadableException.class)
    public Result<Void> handleNotReadable(HttpMessageNotReadableException e) {
        log.warn("请求体格式错误: {}", e.getMessage());
        return Result.fail(400, "请求体格式错误，请检查JSON");
    }

    /**
     * 7. 请求方法不支持（如 POST 接口用 GET 调）
     */
    @ExceptionHandler(HttpRequestMethodNotSupportedException.class)
    public Result<Void> handleMethodNotSupported(HttpRequestMethodNotSupportedException e) {
        log.warn("请求方法不支持: {}", e.getMethod());
        return Result.fail(405, "请求方法不支持: " + e.getMethod());
    }

    /**
     * 8. 业务异常（Service 抛出的 BusinessException）
     */
    @ExceptionHandler(BusinessException.class)
    public Result<Void> handleBusiness(BusinessException e) {
        log.warn("业务异常: code={}, msg={}", e.getCode(), e.getMessage());
        return Result.fail(e.getCode(), e.getMessage());
    }

    /**
     * 9. 兜底异常（所有未被上面匹配的异常）
     * 注意：不要把堆栈返回给前端，避免信息泄露
     */
    @ExceptionHandler(Exception.class)
    public Result<Void> handleException(Exception e) {
        log.error("系统异常", e);
        return Result.fail(500, "系统繁忙，请稍后重试");
    }
}

2.2.6 易错点

  1. 兜底异常返回堆栈：把 e.getMessage() 直接返回给前端，可能泄露数据库结构、SQL 语句等敏感信息。正确做法：只返回"系统繁忙"，堆栈记到日志。
  2. 异常处理顺序写错：@ExceptionHandler 的匹配是按类型精确匹配 + 子类优先，不是按代码顺序，但建议按"子类→父类"顺序写，便于阅读。
  3. 漏掉兜底 Exception.class：没有兜底的话，未预料的异常会返回 Spring 默认错误页，体验差。
  4. 异常处理方法返回类型不统一：有的返回 Result，有的返回 String，前端无法统一处理。所有 @ExceptionHandler 返回类型应统一为 Result<T>。
  5. 在异常处理方法中抛异常：异常处理方法本身又抛异常会导致死循环或默认错误页，处理方法内部必须 try-catch 严密。
  6. 业务异常被兜底吃掉：BusinessException 的 @ExceptionHandler 写在 Exception 之后，仍能正确匹配（子类优先），但容易让人误以为被兜底了。建议按顺序写清楚。

2.2.7 小结

  • 全局异常处理 = @RestControllerAdvice + @ExceptionHandler；
  • 至少处理 5 类异常：Body 校验、Param 校验、类型不匹配、业务异常、兜底 Exception；
  • 匹配规则：子类优先，最近优先；
  • 兜底异常只记日志，不返堆栈；
  • 所有异常返回统一 Result<T> 结构。

K13-3 自定义业务异常

2.3.1 定义

自定义业务异常是指为表达业务规则违反而专门设计的异常类，通常携带业务错误码（code）与友好提示信息（message），由 Service 层抛出，由全局异常处理器捕获并返回前端。

为什么不直接用 RuntimeException？

方式 问题
throw new RuntimeException("项目不存在") 无业务码，前端无法区分不同业务错误
返回 null 或 false 表示失败 调用方需要判断，容易漏判，不符合"异常即错误"思想
自定义 BusinessException(code, message) 携带业务码，表达清晰，全局统一处理 ✅

2.3.2 原理

自定义异常继承 RuntimeException（非受检异常），符合以下设计原则：

  1. 非受检异常：Service 方法签名不需要 throws BusinessException，调用链清爽；
  2. 携带业务码：code 字段让前端可以精确区分不同业务错误（如 40010 项目名重复、40011 负责人不存在）；
  3. 全局捕获：被 @ExceptionHandler(BusinessException.class) 统一捕获，返回 Result.fail(code, message)；
  4. 事务回滚：继承 RuntimeException 默认触发 Spring 事务回滚（@Transactional 默认对 RuntimeException 回滚）。

为什么继承 RuntimeException 而不是 Exception？

对比项 RuntimeException（非受检） Exception（受检）
方法签名 不需要 throws 必须 throws 或 try-catch
代码侵入性 低 高（每层都要处理）
Spring 事务回滚 默认回滚 默认不回滚（需配置 rollbackFor）
业务异常推荐 ✅ ✗

2.3.3 常见问题

Q1：业务异常码怎么设计？

推荐按模块分段，如：

码段 模块
40001-40099 通用业务错误（未登录、无权限）
40010-40019 项目模块
40020-40029 任务模块
40030-40039 用户模块
50000-50099 系统错误

Q2：业务异常要打印 ERROR 日志吗？

不需要。业务异常是预期内的错误（如"项目名重复"），属于正常业务流程，用 log.warn 即可。log.error 留给非预期的系统性异常（如 NPE、数据库连接失败）。

Q3：一个项目要定义多少个自定义异常？

通常 1 个 BusinessException 够用，通过 code 区分不同业务错误。也可以为每个模块定义子类（如 ProjectException、TaskException），但不要过度设计。

2.3.4 完整代码——BusinessException

package com.ctts.common.exception;

import lombok.Getter;

/**
 * 自定义业务异常
 * 用于表达业务规则违反，携带业务码 code 与友好提示 message
 */
@Getter
public class BusinessException extends RuntimeException {

    /** 业务错误码 */
    private final Integer code;

    /**
     * 构造器1：指定 code 和 message
     * @param code    业务码（如 40010）
     * @param message 友好提示（如 "项目名已存在"）
     */
    public BusinessException(Integer code, String message) {
        super(message);
        this.code = code;
    }

    /**
     * 构造器2：仅指定 message，code 默认 500
     * 用于无明确业务码的场景
     */
    public BusinessException(String message) {
        this(500, message);
    }

    /**
     * 构造器3：指定 code、message、cause
     * 用于包装底层异常
     */
    public BusinessException(Integer code, String message, Throwable cause) {
        super(message, cause);
        this.code = code;
    }
}

Service 层使用示例：

package com.ctts.project.service.impl;

import com.ctts.common.exception.BizCode;
import com.ctts.common.exception.BusinessException;
import com.ctts.project.dto.ProjectDTO;
import com.ctts.project.entity.Project;
import com.ctts.project.mapper.ProjectMapper;
import com.ctts.project.service.ProjectService;
import com.ctts.user.mapper.UserMapper;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.BeanUtils;
import org.springframework.stereotype.Service;

/**
 * 项目 Service 实现
 */
@Slf4j
@Service
@RequiredArgsConstructor
public class ProjectServiceImpl implements ProjectService {

    private final ProjectMapper projectMapper;
    private final UserMapper userMapper;

    @Override
    public void create(ProjectDTO dto) {
        log.debug("开始创建项目: {}", dto);

        // 1. 校验项目名是否重复
        if (projectMapper.existsByName(dto.getName())) {
            log.warn("项目名重复: {}", dto.getName());
            throw new BusinessException(BizCode.PROJECT_NAME_DUPLICATE, "项目名已存在");
        }

        // 2. 校验负责人是否存在
        if (!userMapper.existsById(dto.getLeaderId())) {
            log.warn("负责人不存在: leaderId={}", dto.getLeaderId());
            throw new BusinessException(BizCode.PROJECT_LEADER_INVALID, "负责人不存在");
        }

        // 3. 执行新增
        Project project = new Project();
        BeanUtils.copyProperties(dto, project);
        projectMapper.insert(project);
        log.info("创建项目成功: id={}, name={}", project.getId(), project.getName());
    }

    @Override
    public void delete(Long id) {
        Project project = projectMapper.selectById(id);
        if (project == null) {
            log.warn("删除失败，项目不存在: id={}", id);
            throw new BusinessException(BizCode.PROJECT_NOT_FOUND, "项目不存在");
        }
        projectMapper.deleteById(id);
        log.info("删除项目成功: id={}", id);
    }
}

2.3.6 易错点

  1. 继承 Exception 而非 RuntimeException：导致每个 Service 方法都要 throws BusinessException，代码冗余，且 Spring 事务默认不回滚。
  2. 业务异常打 log.error：业务异常是预期内的，打 ERROR 会污染告警（运维可能配置 ERROR 触发告警）。
  3. code 用 int 而非 Integer：int 默认 0，无法表达"未设置"；Integer 可为 null。不过本课用 int 也行，因为构造器强制传 code。
  4. 异常信息硬编码：throw new BusinessException(40011, "项目名已存在") 中文字符串散落各处，国际化困难。推荐用常量类 BizCode 集中管理。
  5. 构造器不调 super(message)：忘记调父类构造器，e.getMessage() 返回 null。
  6. 业务异常被 Exception 兜底吃掉：如果 BusinessException 的 @ExceptionHandler 漏写，会被兜底 Exception 捕获，返回 500"系统繁忙"，业务码丢失。一定要单独写 @ExceptionHandler(BusinessException.class)。

2.3.7 小结

  • 业务异常继承 RuntimeException，携带 code + message；
  • Service 层 throw new BusinessException(code, msg)；
  • 全局处理器 @ExceptionHandler(BusinessException.class) 捕获，返回 Result.fail(code, msg)；
  • 业务异常用 log.warn，不用 log.error；
  • 业务码用常量类集中管理。

K13-4 日志基础

2.4.1 定义

日志是程序运行过程中自动记录的事件信息，是生产环境排查问题的"黑匣子"。Java 生态主流方案是 SLF4J（门面）+ Logback（实现），Spring Boot 默认集成。

为什么不用 System.out.println？

对比项 System.out.println 日志框架
性能 同步阻塞，影响性能 异步可配，性能高
级别 无 TRACE/DEBUG/INFO/WARN/ERROR
输出目标 只控制台 控制台 + 文件 + 网络
格式 固定 可模板化（时间/线程/类名）
滚动 无 按大小/日期滚动
生产可用 ✗ ✅

2.4.2 原理

门面模式：SLF4J 是接口，Logback 是实现，业务代码只调 SLF4J 接口，切换实现无需改代码。

图示 6：结构与流程重绘
业务代码 → SLF4J 接口（门面） → Logback 实现 → 控制台 / 文件 ↑ 可替换为 Log4j2 等

日志级别从低到高：TRACE < DEBUG < INFO < WARN < ERROR

  • 设置某级别后，只输出该级别及以上的日志；
  • 如设置 INFO，则 TRACE / DEBUG 不输出，INFO / WARN / ERROR 输出。

Lombok @Slf4j 注解原理：

@Slf4j
@Service
public class ProjectService { ... }

编译后等价于：

@Service
public class ProjectService {
    private static final org.slf4j.Logger log = org.slf4j.LoggerFactory.getLogger(ProjectService.class);
    ...
}

省去手动声明 Logger，直接用 log.info() / log.warn() 等。

2.4.3 常见问题

Q1：日志级别怎么选？

级别 使用场景 举例
TRACE 极细粒度流程跟踪（极少用） 方法入参出参详细 dump
DEBUG 开发调试用，关键变量值 log.debug("dto={}", dto)
INFO 重要业务节点，上线默认级别 log.info("创建项目成功: id={}", id)
WARN 可恢复的异常，需关注但不致命 log.warn("项目名重复: {}", name)
ERROR 不可恢复的异常，影响业务 log.error("数据库连接失败", e)

口诀：INFO 记业务，WARN 记可恢复，ERROR 记不可恢复，DEBUG 只在开发开。

Q2：日志参数为什么用 {} 占位符而不是字符串拼接？

// ✗ 不推荐：字符串拼接，即使日志级别不输出也会拼接
log.debug("查询项目: " + project);

// ✅ 推荐：占位符，日志级别不输出时不拼接，性能高
log.debug("查询项目: {}", project);

Q3：异常堆栈怎么打印？

// ✗ 错误：只打 message，丢失堆栈
log.error("系统异常: " + e.getMessage());

// ✅ 正确：把异常对象作为最后一个参数，自动打印完整堆栈
log.error("系统异常", e);

Q4：日志文件怎么滚动？

通过 application.yml 配置 logging.logback.rollingpolicy：

  • max-file-size：单个日志文件最大大小，超过则滚动；
  • max-history：保留多少天的日志；
  • total-size-cap：所有日志文件总大小上限，超过则删除最旧的。

2.4.6 易错点

  1. 日志级别乱用 ERROR：业务异常、可恢复异常打 ERROR，导致告警泛滥。ERROR 只用于不可恢复的系统性异常。
  2. 字符串拼接而非占位符：log.debug("user=" + user) 即使 DEBUG 不输出，字符串也已拼接，浪费性能。
  3. 异常对象没作为参数：log.error("失败: " + e.getMessage()) 丢失堆栈，无法排查。正确：log.error("失败", e)。
  4. 日志里打印敏感信息：密码、身份证、银行卡号等不能打日志，避免泄露。
  5. 日志文件不滚动：单个文件无限增长，最终撑爆磁盘。必须配置 max-file-size 与 total-size-cap。
  6. 日志对象不用 @Slf4j 而手动声明：private static final Logger log = LoggerFactory.getLogger(Xxx.class); 冗余，用 Lombok @Slf4j 一行搞定。
  7. 在循环里打大量日志：循环里 log.info 可能产生海量日志，拖慢性能。循环内用 log.debug，必要时采样输出。

2.4.7 小结

  • SLF4J 是门面，Logback 是实现，Spring Boot 默认集成；
  • @Slf4j 注解自动注入 log 对象；
  • 级别：TRACE < DEBUG < INFO < WARN < ERROR，生产用 INFO，开发用 DEBUG；
  • 用 {} 占位符，不用字符串拼接；
  • 异常对象作为最后一个参数打印完整堆栈；
  • application.yml 配置级别 + 文件 + 滚动策略。

K13-5 常见后端错误排查

2.5.1 定义

后端错误排查是指根据 HTTP 状态码、控制台日志、异常堆栈等信息，定位并修复后端运行时错误的能力。这是工程师的核心素养，也是面试高频考点。

2.5.2 原理——HTTP 状态码分类

码段 含义 典型
1xx 信息 极少
2xx 成功 200 OK
3xx 重定向 302
4xx 客户端错误 400 参数错、401 未认证、403 无权限、404 找不到、405 方法不支持
5xx 服务端错误 500 内部错误、502 网关错误、503 服务不可用

排查口诀：先看状态码（4xx 客户端、5xx 服务端）→ 再看日志（级别 + 堆栈）→ 定位代码行 → 复现验证。

2.5.3 常见错误与排查

（1）空指针异常 NullPointerException

项 内容
现象 500 错误，堆栈含 NullPointerException
常见原因 查询结果为 null 直接用、对象未初始化、自动拆箱 null
排查步骤 1. 看堆栈第一行定位类:行号 → 2. 检查该行所有对象是否可能为 null → 3. 加判空或用 Optional
修复示例 if (project != null) { ... } 或 Optional.ofNullable(project).map(Project::getName).orElse("")

（2）参数类型不匹配 MethodArgumentTypeMismatchException

项 内容
现象 400 错误，日志含 MethodArgumentTypeMismatchException
常见原因 前端传 abc 后端要 Long、传 2024-13-45 日期格式错
排查步骤 1. 看日志异常类型 → 2. 看日志中的参数名与目标类型 → 3. 检查前端传值
修复示例 全局异常处理器返回友好提示，前端校验格式

（3）SQL 异常

项 内容
现象 500 错误，日志含 SQLException / DataAccessException
常见原因 字段名错、类型不匹配、唯一约束冲突、非空约束冲突、SQL 语法错
排查步骤 1. 看日志 SQL 与参数（MyBatis-Plus DEBUG 级别打印 SQL）→ 2. 对比表结构 → 3. 检查约束
修复示例 修正字段名、调整类型、处理唯一约束（业务层先查重）

（4）404 Not Found

项 内容
现象 404 错误
常见原因 URL 写错、Controller 缺 @RestController / @RequestMapping、启动类扫描不到、静态资源路径错
排查步骤 1. Postman 核对 URL（路径、大小写）→ 2. 看 Controller 注解 → 3. 看启动类 @SpringBootApplication 扫描包 → 4. 看是否有拦截器拦截
修复示例 补注解、调整包结构使启动类能扫描到

（5）500 Internal Server Error

项 内容
现象 500 错误
常见原因 业务异常未处理、NPE、数据库异常、空指针、数组越界
排查步骤 1. 看日志 ERROR 行 + 完整堆栈 → 2. 定位代码行 → 3. 复现请求验证假设 → 4. 修复
修复示例 加判空、补异常处理、修业务逻辑

2.5.5 易错点

  1. 不看日志直接猜：凭感觉改代码，效率低。正确：先看日志再动手。
  2. 只看 message 不看堆栈：e.getMessage() 可能 null 或信息不全，必须看完整堆栈定位行号。
  3. 修复不复现：改完不复现请求验证，可能没修对或引入新问题。
  4. 改了不重启：Spring Boot DevTools 热部署偶尔失效，改完没重启就测试，以为没修对。
  5. 日志级别太高排查困难：排查时 root: INFO 看不到 DEBUG 信息，临时调 com.ctts: DEBUG 排查。

2.5.6 小结

  • 先看状态码：4xx 客户端、5xx 服务端；
  • 再看日志：级别 + 堆栈 + 行号；
  • 定位代码行：复现 + 验证；
  • 常见错误：NPE 判空、类型不匹配、SQL 异常、404、500。

3.3.4 GlobalExceptionHandler.java

package com.ctts.common.exception;

import com.ctts.common.Result;
import jakarta.validation.ConstraintViolation;
import jakarta.validation.ConstraintViolationException;
import lombok.extern.slf4j.Slf4j;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.method.annotation.MethodArgumentTypeMismatchException;

import java.util.stream.Collectors;

@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<Void> handleValid(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldErrors().stream()
                .map(fe -> fe.getField() + ": " + fe.getDefaultMessage())
                .collect(Collectors.joining("; "));
        log.warn("参数校验失败: {}", msg);
        return Result.fail(400, msg);
    }

    @ExceptionHandler(ConstraintViolationException.class)
    public Result<Void> handleConstraint(ConstraintViolationException e) {
        String msg = e.getConstraintViolations().stream()
                .map(ConstraintViolation::getMessage)
                .collect(Collectors.joining("; "));
        log.warn("约束校验失败: {}", msg);
        return Result.fail(400, msg);
    }

    @ExceptionHandler(MethodArgumentTypeMismatchException.class)
    public Result<Void> handleTypeMismatch(MethodArgumentTypeMismatchException e) {
        log.warn("参数类型不匹配: {}", e.getName());
        return Result.fail(400, "参数类型不匹配: " + e.getName());
    }

    @ExceptionHandler(BusinessException.class)
    public Result<Void> handleBusiness(BusinessException e) {
        log.warn("业务异常: code={}, msg={}", e.getCode(), e.getMessage());
        return Result.fail(e.getCode(), e.getMessage());
    }

    @ExceptionHandler(Exception.class)
    public Result<Void> handleException(Exception e) {
        log.error("系统异常", e);
        return Result.fail(500, "系统繁忙，请稍后重试");
    }
}

package com.ctts.project.service.impl;

import com.ctts.common.exception.BizCode;
import com.ctts.common.exception.BusinessException;
import com.ctts.project.dto.ProjectDTO;
import com.ctts.project.entity.Project;
import com.ctts.project.mapper.ProjectMapper;
import com.ctts.project.service.ProjectService;
import com.ctts.user.mapper.UserMapper;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.BeanUtils;
import org.springframework.stereotype.Service;

@Slf4j
@Service
@RequiredArgsConstructor
public class ProjectServiceImpl implements ProjectService {

    private final ProjectMapper projectMapper;
    private final UserMapper userMapper;

    @Override
    public void create(ProjectDTO dto) {
        log.info("开始创建项目: name={}", dto.getName());

        if (projectMapper.existsByName(dto.getName())) {
            log.warn("项目名重复: {}", dto.getName());
            throw new BusinessException(BizCode.PROJECT_NAME_DUPLICATE, "项目名已存在");
        }

        if (!userMapper.existsById(dto.getLeaderId())) {
            log.warn("负责人不存在: leaderId={}", dto.getLeaderId());
            throw new BusinessException(BizCode.PROJECT_LEADER_INVALID, "负责人不存在");
        }

        Project project = new Project();
        BeanUtils.copyProperties(dto, project);
        projectMapper.insert(project);
        log.info("创建项目成功: id={}, name={}", project.getId(), project.getName());
    }

    @Override
    public Project getById(Long id) {
        Project project = projectMapper.selectById(id);
        if (project == null) {
            throw new BusinessException(BizCode.PROJECT_NOT_FOUND, "项目不存在");
        }
        return project;
    }

    @Override
    public void delete(Long id) {
        Project project = projectMapper.selectById(id);
        if (project == null) {
            throw new BusinessException(BizCode.PROJECT_NOT_FOUND, "项目不存在");
        }
        projectMapper.deleteById(id);
        log.info("删除项目成功: id={}", id);
    }
}

  1. 在 ProjectDTO / TaskDTO 字段上加 @NotBlank / @NotNull / @Size 等注解；
  2. 在 Controller 方法参数上加 @Valid（Body 校验）或类上加 @Validated（Param 校验）；
  3. 启动项目，用 Postman 传空值，验证是否返回 400 + 校验错误信息。

步骤2：创建全局异常处理器

  1. 在 com.ctts.common.exception 包下创建 GlobalExceptionHandler；
  2. 类上加 @RestControllerAdvice，方法上加 @ExceptionHandler；
  3. 至少实现 5 个 handler：Body 校验、Param 校验、类型不匹配、业务异常、兜底 Exception；
  4. 测试每种异常场景，验证返回统一 Result 结构。

步骤3：自定义业务异常

  1. 创建 BusinessException 继承 RuntimeException，含 code + message；
  2. 创建 BizCode 常量类集中管理业务码；
  3. 在 Service 层 throw new BusinessException(code, msg)；
  4. 测试业务异常场景，验证返回对应业务码。

步骤4：配置日志

  1. 在 application.yml 中配置 logging.level、logging.file.name、logging.logback.rollingpolicy；
  2. 在 Service / Controller 类上加 @Slf4j；
  3. 在关键节点输出 log.info / log.warn / log.error；
  4. 启动项目，查看控制台与 logs/ctts.log 文件，验证日志输出。

步骤5：测试各种异常场景

  1. 打开 Postman，按"测试场景与预期"表格逐个测试；
  2. 每个场景记录请求、响应、日志，验证是否符合预期；
  3. 对不符合预期的场景，按"错误排查决策树"排查。

步骤6：常见报错排查

  1. 故意制造 NPE（String s = null; s.length();），观察日志与响应；
  2. 故意制造类型不匹配（GET /api/projects/abc），观察日志与响应；
  3. 故意制造 SQL 异常（改字段名为不存在的列），观察日志与响应；
  4. 故意访问不存在的 URL，观察 404；
  5. 按"排查口诀"定位每个错误并修复。
