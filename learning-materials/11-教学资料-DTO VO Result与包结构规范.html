前10次课中，我们已经完成了CTTS项目的数据库设计（5张表）、Spring Boot工程搭建、MyBatis-Plus逆向、以及TrainingProject的基础CRUD接口。但你可能已经发现两个"不舒服"：

二、知识点详解

K11-1 PO/Entity/DTO/VO的区别与职责

1. 定义

在Java后端开发中，"对象"并非只有一个身份。同一个"用户"概念，在数据库里、在请求参数里、在响应数据里，可能需要不同的Java类来承载。业界将它们划分为：

缩写 全称 中文 职责 所在层
PO Persistent Object 持久化对象 对应数据库中的一条记录，强调"持久化"语义。在MyBatis-Plus中，Entity类实际充当PO角色 dao/mapper层
Entity Entity 实体类 对应数据库表结构，字段与表列一一映射。在MyBatis-Plus中Entity≈PO entity包
DTO Data Transfer Object 数据传输对象 用于接收请求参数或服务层之间传递数据，常带JSR-303校验注解 controller/service层
VO View Object / Value Object 视图对象 用于返回给前端展示的数据，可聚合多表字段、脱敏敏感字段 controller层
BO Business Object 业务对象 服务层内部的业务模型（本课不深入，了解即可） service层

💡 关键认知：在Spring Boot + MyBatis-Plus项目中，Entity类一身二职——既映射数据库表（PO属性），又被BaseMapper操作。所以我们通常把Entity放在entity包，不再单独建PO包。PO更多是一个"概念"，而非物理类。

2. 原理

为什么要把对象分这么多类？核心是职责分离原则（SRP）：

图示 2：DTO、Entity、VO 在请求与响应中的位置
请求入库方向

→

→

  • 数据库结构变化不应影响前端 → Entity与VO解耦
  • 前端请求字段与数据库列不完全一致 → DTO与Entity解耦
  • 敏感字段（password、deleted）不应返回前端 → VO按需裁剪

3. 问题/场景

场景A：直接返回Entity的灾难 sys_user表有password字段。若UserController.list()直接返回List<SysUser>，前端拿到的每个用户都带密码哈希——安全隐患！

场景B：新增接口接收Entity的尴尬 training_project表的id、create_time、update_time由数据库自动生成。若新增接口接收TrainingProject，前端可能误传这些字段导致脏数据。用DTO只暴露应填字段，干净利落。

场景C：跨表聚合展示 任务列表需展示"任务名+创建人姓名+所属项目名"，但这3个字段分属3张表。Entity做不到，VO可以聚合。

6. 易错点

易错点 说明 正确做法
❌ DTO/VO混用 小项目图省事用一个类既接收又返回，导致敏感字段暴露或字段污染 即便省事，至少VO不能含password，DTO不能含id(新增时)
❌ VO里塞业务方法 把VO当Service用，写入业务逻辑 VO只做数据载体，不加业务方法
❌ DTO字段与Entity完全照搬 把deleted、createTime也放进DTO，前端可伪造 DTO只暴露"前端应填"字段
❌ 在DTO/VO里加@TableName 把持久化注解混入传输对象 @TableName只在Entity上
❌ 一对多关系直接用Entity返回 SysUser含List<Task>导致序列化死循环 用VO裁剪，或用@JsonIgnore

7. 小结

一句话记忆：DTO管进、VO管出、Entity管库、PO是概念。前端永远不直接接触Entity。

K11-2 统一响应Result设计

1. 定义

Result 是后端给前端的所有接口响应的统一外壳。无论成功还是失败，无论返回的是单个对象还是列表还是分页，HTTP响应体都遵循同一结构：

{
  "code": 200,
  "message": "操作成功",
  "data": { ... }
}

其中 T 是泛型，表示 data 字段的具体类型——可能是 ProjectVO、List<ProjectVO>、PageVO<ProjectVO> 等。

2. 原理

设计动机：

  1. 前端解析统一：前端封装一个axios拦截器，只判断code===200即可决定成功失败，无需每个接口写不同逻辑。
  2. 错误信息标准化：业务错误（如"项目不存在"）通过HTTP 200+业务code返回，避免前端误以为是网络错误。
  3. 扩展性：未来加timestamp、traceId字段不影响既有接口。
  4. 文档友好：Knife4j展示的响应结构统一，便于联调。

为什么用泛型T而不用Object？

  • 编译期类型安全：Result<ProjectVO> 取data时无需强转
  • Knife4j能正确生成data的Schema文档
  • IDE智能提示能识别data的字段

3. 问题/场景

场景：错误码管理 随着接口增多，错误码会爆炸式增长。硬编码fail(50001, "项目不存在")不可维护。应配套设计ResultCode枚举：

public enum ResultCode {
    SUCCESS(200, "操作成功"),
    PARAM_ERROR(400, "参数错误"),
    UNAUTHORIZED(401, "未登录或token失效"),
    FORBIDDEN(403, "无权限"),
    NOT_FOUND(404, "资源不存在"),
    SERVER_ERROR(500, "服务器内部错误"),
    PROJECT_NOT_FOUND(50001, "项目不存在"),
    PROJECT_NAME_EXISTS(50002, "项目名称已存在");

    private final int code;
    private final String message;
    // 构造器、getter 省略
}

4. 完整示例代码

完整Result类：

package com.ctts.common;

import io.swagger.v3.oas.annotations.media.Schema;
import lombok.Data;
import lombok.experimental.Accessors;

import java.io.Serializable;

/**
 * 统一响应结果类
 * @param <T> data字段的具体类型
 */
@Data
@Accessors(chain = true)   // 开启链式setter
@Schema(description = "统一响应结果")
public class Result<T> implements Serializable {

    @Schema(description = "业务状态码：200成功，非200失败")
    private int code;

    @Schema(description = "提示信息")
    private String message;

    @Schema(description = "响应数据")
    private T data;

    // ===== 无参构造 =====
    public Result() {}

    // ===== 全参构造（供MapStruct等工具使用）=====
    public Result(int code, String message, T data) {
        this.code = code;
        this.message = message;
        this.data = data;
    }

    // ===== 成功静态方法 =====
    public static <T> Result<T> ok() {
        return new Result<>(ResultCode.SUCCESS.getCode(), ResultCode.SUCCESS.getMessage(), null);
    }

    public static <T> Result<T> ok(T data) {
        return new Result<>(ResultCode.SUCCESS.getCode(), ResultCode.SUCCESS.getMessage(), data);
    }

    public static <T> Result<T> ok(String message, T data) {
        return new Result<>(ResultCode.SUCCESS.getCode(), message, data);
    }

    // ===== 失败静态方法 =====
    public static <T> Result<T> fail() {
        return new Result<>(ResultCode.SERVER_ERROR.getCode(), ResultCode.SERVER_ERROR.getMessage(), null);
    }

    public static <T> Result<T> fail(String message) {
        return new Result<>(ResultCode.SERVER_ERROR.getCode(), message, null);
    }

    public static <T> Result<T> fail(int code, String message) {
        return new Result<>(code, message, null);
    }

    public static <T> Result<T> fail(ResultCode resultCode) {
        return new Result<>(resultCode.getCode(), resultCode.getMessage(), null);
    }

    public static <T> Result<T> fail(ResultCode resultCode, String message) {
        return new Result<>(resultCode.getCode(), message, null);
    }

    // ===== 链式调用示例（也可由@Accessors(chain=true)自动生成）=====
    // Result<ProjectVO> r = Result.ok(vo).setMessage("自定义成功消息");
}

配套ResultCode枚举：

package com.ctts.common;

import lombok.AllArgsConstructor;
import lombok.Getter;

/**
 * 业务状态码枚举
 * 约定：200成功，4xx客户端错误，5xx服务端错误，5xxxx业务错误
 */
@Getter
@AllArgsConstructor
public enum ResultCode {

    SUCCESS(200, "操作成功"),
    PARAM_ERROR(400, "参数错误"),
    UNAUTHORIZED(401, "未登录或token失效"),
    FORBIDDEN(403, "无权限"),
    NOT_FOUND(404, "资源不存在"),
    SERVER_ERROR(500, "服务器内部错误"),

    // ===== 实训项目业务码 50001-50099 =====
    PROJECT_NOT_FOUND(50001, "项目不存在"),
    PROJECT_NAME_EXISTS(50002, "项目名称已存在"),
    PROJECT_STATUS_ERROR(50003, "项目状态不允许此操作"),

    // ===== 任务业务码 50101-50199 =====
    TASK_NOT_FOUND(50101, "任务不存在"),
    TASK_NOT_IN_PROJECT(50102, "任务不属于该项目"),

    // ===== 任务提交业务码 50201-50299 =====
    SUBMISSION_DUPLICATE(50201, "重复提交"),
    SUBMISSION_DEADLINE_PASSED(50202, "已超过截止时间");

    private final int code;
    private final String message;
}

6. 易错点

易错点 说明 正确做法
❌ code用HTTP状态码 把HTTP 200/404/500直接当code，与业务码混淆 HTTP永远返回200（除非网络层错误），业务code独立
❌ 静态方法不写泛型 public static Result ok() 丢失T，导致链式调用类型退化 public static <T> Result<T> ok()
❌ fail不返回data 业务失败时data为null但前端访问data.xxx报错 前端先判code再取data；后端fail时data置null
❌ 用Object代替T Result<Object> 导致类型丢失 用泛型T，保留编译期检查
❌ 把Result做成单例 Result有状态（每次data不同），不能单例 每次new新对象，静态方法已保证

7. 小结

一句话记忆：code管成败、message管提示、data管数据、泛型T管类型安全。静态方法ok()/fail()是入口。

K11-3 对象转换

1. 定义

对象转换指在DTO↔︎Entity↔︎VO之间复制属性值的过程。因为它们字段高度重合（如projectName、description），手写vo.setProjectName(entity.getProjectName())繁琐易错，于是有了转换工具。

主流方案：

  • BeanUtils.copyProperties：运行期反射拷贝，Spring/Apache各一套
  • MapStruct：编译期生成转换代码，性能高、类型安全

2. 原理

BeanUtils（Spring版）原理： 运行时通过反射获取source和target的所有属性，按属性名+类型匹配，逐个调用setter。源码入口：org.springframework.beans.BeanUtils.copyProperties(Object source, Object target)。

MapStruct原理： 编译期（maven compile阶段）读取@Mapper接口，根据方法签名生成xxxMapperImpl.java实现类，里面是纯new + setter代码，无反射。类似于你手写的转换代码，但自动生成。

性能对比（参考量级，10万次转换）： | 方案 | 耗时 | 说明 | |------|------|------| | 手写setter | ~5ms | 基准 | | MapStruct | ~6ms | 接近手写 | | Spring BeanUtils | ~300ms | 反射开销 | | Apache BeanUtils | ~3000ms | 反射+类型转换，最慢 |

3. 问题/场景

场景A：属性名不一致 TrainingProject.creatorId ↔︎ ProjectVO.creatorId 同名可拷贝；但若VO字段叫creatorUserId，则拷贝不到，需手动补全。

场景B：类型不一致 Entity的createTime是LocalDateTime，VO的createTime是String，BeanUtils不会自动转换，直接跳过该字段。MapStruct则可自定义转换方法。

场景C：嵌套对象 Entity含SysUser creator，VO想展平为String creatorName。BeanUtils无法自动展平，需手动处理；MapStruct可配@Mapping(source="creator.username", target="creatorName")。

4. 完整示例代码

方案一：Spring BeanUtils（推荐入门）

package com.ctts.utils;

import com.ctts.dto.ProjectDTO;
import com.ctts.entity.TrainingProject;
import com.ctts.vo.ProjectVO;
import org.springframework.beans.BeanUtils;

/**
 * 对象转换工具类
 */
public class ConvertUtils {

    /**
     * ProjectDTO -> TrainingProject Entity
     */
    public static TrainingProject dtoToEntity(ProjectDTO dto) {
        TrainingProject entity = new TrainingProject();
        BeanUtils.copyProperties(dto, entity);  // source在前，target在后
        return entity;
    }

    /**
     * TrainingProject Entity -> ProjectVO
     */
    public static ProjectVO entityToVO(TrainingProject entity) {
        ProjectVO vo = new ProjectVO();
        BeanUtils.copyProperties(entity, vo);
        // creatorName 需单独查询补全（BeanUtils拷贝不到）
        // vo.setCreatorName(sysUserService.getById(entity.getCreatorId()).getUsername());
        return vo;
    }

    /**
     * List<Entity> -> List<VO>
     */
    public static List<ProjectVO> entityListToVOList(List<TrainingProject> list) {
        return list.stream()
                .map(ConvertUtils::entityToVO)
                .collect(Collectors.toList());
    }
}

6. 易错点

易错点 说明 正确做法
❌ Spring BeanUtils参数写反 copyProperties(target, source)导致拷贝无效 牢记：source在前，target在后
❌ 用Apache BeanUtils 性能极差，且异常处理繁琐 统一用Spring的org.springframework.beans.BeanUtils
❌ 期望BeanUtils转换日期格式 LocalDateTime→String不会自动转 手动处理或用MapStruct自定义方法
❌ 拷贝后忘记补全聚合字段 creatorName为null却以为拷贝成功 BeanUtils后手动set聚合字段
❌ MapStruct+Lombok冲突 Lombok先生成getter，MapStruct找不到 pom中annotationProcessorPaths把两个都配上
❌ 修改source波及target 浅拷贝，引用类型字段共享 基本类型无忧；引用对象需深拷贝或new

7. 小结

一句话记忆：小项目用Spring BeanUtils（source在前target在后），大项目上MapStruct（编译期生成、性能好、类型安全）。聚合字段都要手动补。

K11-4 项目包结构规范

1. 定义

包结构规范指Java项目中package的划分约定。Spring Boot企业级项目通常按"分层"+"功能"混合划分，以分层为主：

图示 5：规范包结构与职责边界
  • com.ctts/
  • CttsApplication.java # 启动类
  • controller/ # 表现层，接收请求、返回响应
  • service/ 与 service/impl/ # 业务接口与实现
  • mapper/ # MyBatis-Plus Mapper 接口
  • entity/ # 数据库表实体，充当 PO
  • dto/ # 请求入参对象
  • vo/ # 响应视图对象
  • common/ config/ utils/ exception/ # 公共、配置、工具与异常

2. 原理

为什么service要分接口和impl？

  • 解耦：Controller依赖ProjectService接口，不依赖ProjectServiceImpl实现，便于替换实现类（如Mock测试）
  • 代理：Spring AOP（事务@Transactionall）基于接口动态代理（JDK Proxy）更自然
  • 规范：阿里规范要求"service层必须先定义接口"

为什么不把所有类放一个包？

  • 可维护性：500个类堆一起，找一个要翻半天
  • 职责清晰：改Entity不会动到Controller
  • 团队协作：前端联调看controller，DBA看entity，互不干扰

3. 问题/场景

场景：包结构混乱的反面教材

图示 6：不规范包结构反例
  • com.ctts/

  • ProjectMapper.java # 持久层直接散落根包
  • ProjectService.java / ProjectServiceImpl.java # 接口与实现混在一起
  • 问题：职责边界不清，后续扩展 DTO、VO、异常与配置时会越来越乱

20个类时还能忍，200个类时找类全靠Ctrl+N，且无法一眼看出类的角色。

/**
 * 通用分页VO
 */
@Data
@Schema(description = "分页结果")
public class PageVO<T> {

    @Schema(description = "当前页码")
    private Long current;

    @Schema(description = "每页大小")
    private Long size;

    @Schema(description = "总记录数")
    private Long total;

    @Schema(description = "总页数")
    private Long pages;

    @Schema(description = "当前页数据列表")
    private List<T> records;

    public static <T> PageVO<T> of(Long current, Long size, Long total, List<T> records) {
        PageVO<T> page = new PageVO<>();
        page.setCurrent(current);
        page.setSize(size);
        page.setTotal(total);
        page.setPages((total + size - 1) / size);
        page.setRecords(records);
        return page;
    }
}

K11-5 Lombok常用注解

1. 定义

Lombok是通过编译期注解处理器，在class文件中自动生成getter/setter/构造器/toString等模板代码的工具。一个@Data注解就能省去几十行样板代码。

2. 原理

Lombok在编译期（javac阶段）拦截AST（抽象语法树），根据注解向AST中插入getter/setter等方法节点。生成的是字节码，源码不变。所以反编译class能看到方法，但.java文件里没有。

IDEA配置要点：

  1. 安装Lombok插件（IDEA 2020.3+已内置，无需安装）
  2. 开启 Settings → Build → Compiler → Annotation Processors → Enable annotation processing
  3. 引入Maven依赖

3. 问题/场景

场景A：@Builder与@NoArgsConstructor冲突

@Builder
@NoArgsConstructor
public class User { ... }

编译报错：User does not have an accessible constructor()。因为@Builder会生成全参私有构造器，与无参冲突。解决：再加@AllArgsConstructor。

场景B：链式setter 默认setter返回void，无法链式。用@Accessors(chain=true)让setter返回this：

user.setName("张三").setAge(20);

4. 完整示例代码

Lombok依赖：

    <groupId>org.projectlombok</groupId>

</dependency>

6. 易错点

易错点 说明 正确做法
❌ IDEA未开Annotation Processing 编译报错"找不到符号" Settings开启注解处理
❌ @Builder单独用导致无参构造丢失 反序列化JSON失败（Jackson需要无参构造） @Builder + @NoArgsConstructor + @AllArgsConstructor 三件套
❌ @Data用在Entity上导致@EqualsAndHashCode循环 一对多关系下equals递归 单独用@Getter/@Setter，或加@EqualsAndHashCode(exclude="关联字段")
❌ 把Lombok依赖scope写成compile 打进jar浪费空间 scope=provided
❌ @Slf4j后仍手写Logger 重复 @Slf4j已注入log变量，直接用log.info()

一句话记忆：@Data最常用、@Builder三件套（+无参+全参）、@Accessors链式、@Slf4j日志。IDEA记得开Annotation Processing。

package com.ctts.service.impl;

import com.ctts.dto.ProjectDTO;
import com.ctts.entity.TrainingProject;
import com.ctts.mapper.ProjectMapper;
import com.ctts.service.ProjectService;
import com.ctts.vo.ProjectVO;
import com.ctts.utils.ConvertUtils;
import org.springframework.beans.BeanUtils;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Service;

import java.util.List;
import java.util.stream.Collectors;

@Service
public class ProjectServiceImpl implements ProjectService {

    @Autowired
    private ProjectMapper projectMapper;

    @Override
    public List<ProjectVO> list() {
        List<TrainingProject> list = projectMapper.selectList(null);
        return list.stream()
                .map(e -> {
                    ProjectVO vo = new ProjectVO();
                    BeanUtils.copyProperties(e, vo);
                    return vo;
                })
                .collect(Collectors.toList());
    }

    @Override
    public ProjectVO getById(Long id) {
        TrainingProject entity = projectMapper.selectById(id);
        if (entity == null) {
            throw new RuntimeException("项目不存在");  // 第12次课改为BusinessException
        }
        ProjectVO vo = new ProjectVO();
        BeanUtils.copyProperties(entity, vo);
        return vo;
    }

    @Override
    public Long add(ProjectDTO dto) {
        TrainingProject entity = new TrainingProject();
        BeanUtils.copyProperties(dto, entity);
        projectMapper.insert(entity);
        return entity.getId();
    }

    @Override
    public boolean update(ProjectDTO dto) {
        TrainingProject entity = new TrainingProject();
        BeanUtils.copyProperties(dto, entity);
        return projectMapper.updateById(entity) > 0;
    }

    @Override
    public boolean delete(Long id) {
        return projectMapper.deleteById(id) > 0;
    }
}

四、拓展阅读

4.1 DTO/VO合并还是分离？

小项目（接口少、字段简单）可以合并为DTO（既接收又返回）。但出现以下信号就该拆分：

  • 返回字段明显多于请求字段（如 createTime、creatorName）
  • 返回字段需脱敏（如 password、deleted）
  • 同一Entity有多个不同视图（如列表页只显示5字段，详情页显示全字段）

经验法则：接口数 > 10 或 字段数 > 15 时，必拆DTO和VO。

4.2 Result的进阶设计

大型项目可考虑：

  • 链式调用：Result.ok().setCode(200).setMessage("ok").setData(vo)
  • 链路追踪：加traceId字段，便于日志关联
  • 时间戳：加timestamp字段，便于排查时序问题
  • 分页封装：Result<PageVO<ProjectVO>> 嵌套分页

4.3 MapStruct高级特性

  • @Mapping(target="xxx", expression="java(dto.getField().toUpperCase())") 自定义表达式
  • @Mapping(target="createTime", dateFormat="yyyy-MM-dd HH:mm:ss") 日期格式化
  • @Mapping(target="status", qualifiedByName="statusStr") 调用自定义方法
  • @AfterMapping 注解在方法上，转换后回调，用于补全聚合字段

五、小结与思维导图

5.1 一页纸小结

图示 10：第 11 次课核心知识地图

DTO

接收请求参数，配合校验注解保护入口数据。

VO

控制响应字段，只返回前端需要展示的数据。

Result

统一响应结构，承载 code、message、data。

包结构

按 controller、service、mapper、entity、dto、vo 分层组织。

转换边界

Controller 处理 DTO/VO，Service 处理业务与实体转换。

5.2 思维导图（文字版）

图示 11：DTO、VO、Result 与包结构规范总览

请求入口

前端 JSON → DTO → Controller 参数校验。

业务处理

Service 使用 Entity/PO 完成业务逻辑和持久化。

响应出口

Entity/聚合结果 → VO → Result.success(data)。

工程组织

包结构让对象流向和职责边界在代码目录中可见。
