知识点详解

K19-1 多表关联查询

定义

多表关联查询是指通过 SQL 的 JOIN 子句，根据表之间的逻辑关系（通常是外键），将两张或多张表的数据按指定条件连接成一个结果集的查询方式。

原理

1. JOIN 的分类与区别

JOIN 类型 含义 结果特点
INNER JOIN（内连接） 只返回两表中满足连接条件的行 交集，不匹配的行被丢弃
LEFT JOIN（左连接） 返回左表所有行，右表不匹配的行填 NULL 以左表为准，右表可能为 NULL
RIGHT JOIN（右连接） 返回右表所有行，左表不匹配的行填 NULL 以右表为准（实际开发少用）
CROSS JOIN（交叉连接） 返回两表的笛卡尔积 行数 = 左表行数 × 右表行数

2. 为什么多表业务场景多用 LEFT JOIN？

以"教师查看某项目下所有任务及提交情况"为例：一个任务可能还没有任何提交（新发布的任务），如果用 INNER JOIN，这些"零提交"的任务会从结果中消失——教师看不到它们。LEFT JOIN 能保证所有任务都出现，没有提交时提交相关字段为 NULL，符合业务预期。

3. 多表 JOIN 的执行过程（数据库层面）

FROM task t                          -- 1. 确定驱动表（左表）
LEFT JOIN task_submission ts         -- 2. 关联第二张表
       ON t.id = ts.task_id          --    指定连接条件
LEFT JOIN sys_user u                 -- 3. 关联第三张表
       ON ts.user_id = u.id          --    继续指定连接条件
WHERE t.project_id = #{projectId}    -- 4. 过滤条件
ORDER BY t.create_time, ts.submit_time  -- 5. 排序

数据库执行时：先取驱动表一行，去被连接表中找匹配行，找不到则填 NULL，逐行累加得到最终结果集。

问题

问题 1：列名歧义 多张表中常有同名列（如 id、create_time、name），直接写列名会报错 "Column 'id' in field list is ambiguous"。

问题 2：连接条件写错或遗漏 忘记写 ON 条件，会变成笛卡尔积，数据量爆炸。

问题 3：LEFT JOIN 与 INNER JOIN 选错 该用 LEFT JOIN 时用了 INNER JOIN，导致"无提交的任务"丢失。

完整代码

示例：查询某项目下所有任务及提交情况（三表 LEFT JOIN）

-- 查询项目 ID 为 1 的所有任务及其提交情况（含提交人姓名）
SELECT
    t.id              AS task_id,
    t.title           AS task_title,
    t.description     AS task_description,
    t.project_id      AS task_project_id,
    t.create_time     AS task_create_time,
    ts.id             AS submission_id,
    ts.content        AS submission_content,
    ts.submit_time    AS submission_submit_time,
    u.id              AS user_id,
    u.username        AS user_username,
    u.real_name       AS user_real_name
FROM task t
LEFT JOIN task_submission ts ON t.id = ts.task_id
LEFT JOIN sys_user u         ON ts.user_id = u.id
WHERE t.project_id = 1
ORDER BY t.create_time ASC, ts.submit_time DESC;

关键要点说明：

  • 使用表别名 t、ts、u，所有列都带别名前缀，避免列名歧义。
  • 对重名列使用 AS 重命名（如 t.id AS task_id），让结果集列名唯一，方便 MyBatis 映射。
  • LEFT JOIN 保证"零提交"的任务也出现在结果中。

易错点

  1. 列名歧义报错：SELECT id FROM task t LEFT JOIN task_submission ts ON ... 会报错，因为两张表都有 id 列。正确做法：所有列加表别名前缀，如 t.id、ts.id。
  2. LEFT JOIN 误用 INNER JOIN：导致无子记录的父记录丢失。判断原则：业务上"父记录必须出现"就用 LEFT JOIN。
  3. ON 条件遗漏：LEFT JOIN task_submission ts 后忘记 ON t.id = ts.task_id，会报语法错误或产生笛卡尔积。
  4. WHERE 中过滤右表字段导致 LEFT JOIN 失效：如 WHERE ts.submit_time > '2024-09-01'，会让"零提交"任务因 NULL 不满足条件而被过滤。正确做法：右表过滤条件放到 ON 子句中，或用 WHERE ts.submit_time > '...' OR ts.submit_time IS NULL。

小结

  • 多表关联查询通过 JOIN 子句实现，INNER JOIN 取交集，LEFT JOIN 保留左表全部。
  • 业务场景中"主记录必须出现，子记录可有可无"的多用 LEFT JOIN。
  • 编写多表 SQL 的三个习惯：表别名、列加前缀、重名列重命名。

K19-2 MyBatis多表映射

定义

MyBatis 多表映射是指将 JOIN 查询返回的"扁平结果集"映射为"嵌套 Java 对象结构"的机制，核心是通过 ResultMap 配置表间关系。MyBatis 提供两种配置方式：注解 @Results（适合简单场景）和 XML ResultMap（适合复杂嵌套场景）。

原理

1. 扁平结果集 vs 嵌套对象

数据库返回的是扁平的行：

task_id | task_title | submission_id | submission_content | user_real_name
   1    | 任务A      | 10            | 提交1              | 张三
   1    | 任务A      | 11            | 提交2              | 李四
   2    | 任务B      | 12            | 提交3              | 张三

Java 需要的是嵌套对象：

Task {
    id: 1, title: "任务A",
    submissions: [
        Submission { id: 10, content: "提交1", user: { realName: "张三" } },
        Submission { id: 11, content: "提交2", user: { realName: "李四" } }
    ]
}

ResultMap 的职责就是完成这个"扁平 → 嵌套"的转换。

2. association 与 collection 的区别

元素 用途 关系 典型场景
association 映射一对一/多对一关系 Java 中是一个对象 提交 → 提交人（一个提交对应一个用户）
collection 映射一对多关系 Java 中是一个 List 任务 → 提交列表（一个任务对应多个提交）

3. ResultMap 嵌套映射的执行原理

MyBatis 处理 JOIN 结果集时，按"主表 id"分组：相同 task_id 的行合并成一个 Task 对象，其 submissions 集合中追加不同的 submission_id 对应的 Submission 对象。关键：必须正确标注 <id> 列，MyBatis 才知道如何分组。

问题

问题 1：<id> 列标注错误导致分组失败 如果没有正确标注 task_id 为 <id>，MyBatis 会把每一行都当成一个新 Task 对象，导致一对多关系丢失，集合中只有一个元素。

问题 2：列名映射错位 SQL 中 SELECT t.id 没有重命名，Java 实体中 task 和 submission 都有 id 字段，MyBatis 会把同一个列值映射到两个对象，造成数据错乱。

问题 3：嵌套结果集与嵌套 select 混淆 association/collection 有两种用法：嵌套结果（resultMap 属性，一次 JOIN 查询）和嵌套 select（select 属性，触发额外 SQL，是 N+1 问题根源）。初学者容易混淆。

完整代码

方式一：注解 @Results（适合简单一对一场景）

package com.ctts.mapper;

import com.baomidou.mybatisplus.core.mapper.BaseMapper;
import com.ctts.entity.TaskSubmission;
import com.ctts.vo.SubmissionSimpleVO;
import org.apache.ibatis.annotations.*;

import java.util.List;

public interface TaskSubmissionMapper extends BaseMapper<TaskSubmission> {

    /**
     * 简单一对一关联：查询提交记录及提交人姓名（注解方式）
     * 适合单层关联，复杂嵌套不推荐用注解
     */
    @Select("SELECT ts.id, ts.task_id, ts.content, ts.submit_time, " +
            "       u.id AS user_id, u.username, u.real_name " +
            "FROM task_submission ts " +
            "LEFT JOIN sys_user u ON ts.user_id = u.id " +
            "WHERE ts.task_id = #{taskId}")
    @Results({
        @Result(column = "id", property = "id"),
        @Result(column = "task_id", property = "taskId"),
        @Result(column = "content", property = "content"),
        @Result(column = "submit_time", property = "submitTime"),
        // 一对一：用 @Result + one = @One
        @Result(column = "user_id", property = "user",
                one = @One(select = "com.ctts.mapper.SysUserMapper.selectById"))
    })
    List<SubmissionSimpleVO> selectSubmissionsWithUserByTaskId(Long taskId);
}

方式二：XML ResultMap 嵌套映射（本课重点，适合一对多复杂场景）

TaskMapper.xml：

<?xml version="1.0" encoding="UTF-8" ?>
<!DOCTYPE mapper PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
        "http://mybatis.org/dtd/mybatis-3-mapper.dtd">
<mapper namespace="com.ctts.mapper.TaskMapper">

    <!-- ========== 一对多嵌套映射：任务 + 提交列表 + 提交人 ========== -->
    <resultMap id="taskWithSubmissionMap" type="com.ctts.vo.TaskWithSubmissionVO">
        <!-- 主表（task）字段：必须正确标注 id，MyBatis 据此分组 -->
        <id column="task_id" property="taskId"/>
        <result column="task_title" property="taskTitle"/>
        <result column="task_description" property="taskDescription"/>
        <result column="task_project_id" property="projectId"/>
        <result column="task_create_time" property="createTime"/>

        <!-- 一对多：collection 嵌套结果，property 对应 VO 中的 List 字段 -->
        <collection property="submissions"
                    ofType="com.ctts.vo.SubmissionDetailVO">
            <id column="submission_id" property="submissionId"/>
            <result column="submission_content" property="content"/>
            <result column="submission_submit_time" property="submitTime"/>

            <!-- 一对一：提交 → 提交人 -->
            <association property="user"
                         javaType="com.ctts.vo.UserSimpleVO">
                <id column="user_id" property="userId"/>
                <result column="user_username" property="username"/>
                <result column="user_real_name" property="realName"/>
            </association>
        </collection>
    </resultMap>

    <!-- 多表关联查询 SQL -->
    <select id="selectTasksWithSubmissionsByProjectId" resultMap="taskWithSubmissionMap">
        SELECT
            t.id              AS task_id,
            t.title           AS task_title,
            t.description     AS task_description,
            t.project_id      AS task_project_id,
            t.create_time     AS task_create_time,
            ts.id             AS submission_id,
            ts.content        AS submission_content,
            ts.submit_time    AS submission_submit_time,
            u.id              AS user_id,
            u.username        AS user_username,
            u.real_name       AS user_real_name
        FROM task t
        LEFT JOIN task_submission ts ON t.id = ts.task_id
        LEFT JOIN sys_user u         ON ts.user_id = u.id
        WHERE t.project_id = #{projectId}
        ORDER BY t.create_time ASC, ts.submit_time DESC
    </select>

</mapper>

对应 Mapper 接口：

package com.ctts.mapper;

import com.baomidou.mybatisplus.core.mapper.BaseMapper;
import com.ctts.entity.Task;
import com.ctts.vo.TaskWithSubmissionVO;
import org.apache.ibatis.annotations.Mapper;
import org.apache.ibatis.annotations.Param;

import java.util.List;

@Mapper
public interface TaskMapper extends BaseMapper<Task> {

    /**
     * 多表关联查询：根据项目 ID 查询该项目下所有任务及其提交情况
     * 一次 JOIN 查询，ResultMap 嵌套映射组装结果，无 N+1 问题
     */
    List<TaskWithSubmissionVO> selectTasksWithSubmissionsByProjectId(@Param("projectId") Long projectId);
}

易错点

  1. <id> 列漏标或标错：<id> 是 MyBatis 分组的依据，漏标会导致一行一个对象，一对多失效。经验：主表主键、每个子表的主键都要标 <id>。
  2. ofType vs javaType 混淆：collection 用 ofType（集合元素类型），association 用 javaType（对象类型）。写反会报错。
  3. property 写成列名：property 是 Java 字段名，column 是 SQL 列名（AS 后的别名），两者不能混。
  4. SQL 列别名与 column 不一致：SQL 中 AS task_id，ResultMap 中 column="taskId"，映射失败（NULL）。校验习惯：写完对照一遍。
  5. 嵌套 select 误用导致 N+1：<collection select="..."> 会触发额外 SQL，本课场景应使用嵌套结果（resultMap 属性或内联配置），一次 JOIN 查询完成。

小结

  • ResultMap 嵌套映射实现"扁平结果集 → 嵌套对象"的转换。
  • association 处理一对一，collection 处理一对多。
  • 正确标注 <id> 是分组的关键；嵌套结果（一次 JOIN）优于嵌套 select（避免 N+1）。

K19-3 业务对象组装

定义

业务对象组装是指根据接口返回需要，将多张表的数据组合成一个面向前端的复合对象（VO，View Object）的过程。VO 不对应单张表，而是为接口"量身定制"的数据结构。

原理

1. 为什么需要 VO？

场景 不用 VO（直接返回实体） 用 VO
数据来源 只能来自单表 可来自多表组装
字段控制 暴露实体所有字段（可能含密码等敏感字段） 按需定义，安全可控
嵌套结构 实体间无嵌套 可包含子对象列表
接口语义 与表结构耦合 与接口语义对齐

2. VO 设计原则

  • 按接口设计，不按表设计：一个接口一个 VO，不要一个 VO 通吃所有接口。
  • 字段命名面向前端：用 taskTitle 而非 title，避免前端混淆。
  • 敏感字段不出现：密码、手机号等不放进 VO（或脱敏）。
  • 嵌套结构清晰：一对多用 List<子VO>，一对一用子 VO 对象。

3. Service 层组装的两种方式

方式 做法 优点 缺点
方式 A：Mapper 直接返回 VO JOIN SQL + ResultMap 直接映射成 VO 一次查询，性能好 ResultMap 配置复杂
方式 B：Service 层二次组装 先分别查多表，再在 Service 中拼装 逻辑清晰，易维护 多次查询，需注意 N+1

本课推荐方式 A（一次 JOIN 查询 + ResultMap 映射），性能最优。

问题

问题 1：VO 字段与实体字段混用 有人图省事让 VO 继承实体，导致 VO 暴露实体所有字段。建议：VO 独立定义，不复用实体。

问题 2：Service 层循环调用单表查询（N+1 雏形）

// 反例：每个任务再查一次提交
List<Task> tasks = taskMapper.selectByProjectId(projectId);
for (Task task : tasks) {
    List<Submission> subs = submissionMapper.selectByTaskId(task.getId()); // N 次！
    ...
}

这是 N+1 问题的典型写法，将在 K19-4 详述。

问题 3：VO 命名混乱 TaskVO、TaskInfo、TaskDTO 含义不清。规范：XXVO 面向前端返回，XXDTO 面向接收参数，XXBO 面向业务层内部传递。

import com.ctts.entity.TrainingProject;
import com.ctts.mapper.TaskMapper;
import com.ctts.mapper.TrainingProjectMapper;

public class TaskService {

    @Autowired
    private TaskMapper taskMapper;

    @Autowired
    private TrainingProjectMapper trainingProjectMapper;

    /**
     * 查询某项目下所有任务及提交情况
     * 方式 A：Mapper 一次 JOIN 查询直接返回 VO，Service 直接透传
     */
    public List<TaskWithSubmissionVO> getTasksWithSubmissionsByProjectId(Long projectId) {
        return taskMapper.selectTasksWithSubmissionsByProjectId(projectId);
    }

    /**
     * 综合接口：查询项目信息 + 项目下所有任务及提交情况
     * Service 层二次组装：项目信息单查，任务列表 JOIN 查询，组合返回
     */
    public ProjectTaskVO getProjectWithTasks(Long projectId) {
        // 1. 查询项目信息（单表）
        TrainingProject project = trainingProjectMapper.selectById(projectId);
        if (project == null) {
            throw new RuntimeException("项目不存在");
        }

        // 2. 查询项目下所有任务及提交情况（多表 JOIN，一次查询）
        List<TaskWithSubmissionVO> tasks = taskMapper.selectTasksWithSubmissionsByProjectId(projectId);

        // 3. 组装 ProjectTaskVO
        ProjectTaskVO vo = new ProjectTaskVO();
        BeanUtils.copyProperties(project, vo);  // 复制项目基础字段
        vo.setTasks(tasks);

        return vo;
    }
}

易错点

  1. VO 字段名与 ResultMap property 不一致：ResultMap 中 property="taskTitle"，VO 中写成 tasktitle，映射失败。校验：Lombok @Data 生成 getter/setter 时按驼峰，注意大小写。
  2. BeanUtils.copyProperties 字段名不一致：源对象（实体）与目标对象（VO）字段名不同时不会复制。如实体 title、VO taskTitle，需手动 set。
  3. VO 中集合未初始化导致 NPE：private List<SubmissionDetailVO> submissions; 默认 null，ResultMap 映射时会自动 new ArrayList，但 Service 手动组装时要小心。建议：声明时初始化 = new ArrayList<>() 或确保 Mapper 返回非 null。
  4. VO 与 DTO 混用：接收前端参数用 VO，导致校验注解与返回字段混杂。规范：接收用 XxxDTO，返回用 XxxVO。

小结

  • VO 按接口设计，不复用实体，不含敏感字段。
  • 一对多用 List<子VO>，一对一用子 VO 对象。
  • Service 组装优先用"Mapper 一次 JOIN 返回 VO"，性能最优。
  • 命名规范：VO 返回、DTO 接收、BO 内部传递。

K19-4 N+1查询问题

定义

N+1 查询问题是指在循环中执行 1 次主查询获取 N 条主记录，再对每条主记录执行 1 次子查询获取关联数据，总共执行 N+1 次 SQL 的性能问题。这是 ORM 框架中最常见的性能陷阱。

原理

1. N+1 问题的产生过程

以"查询项目下所有任务及提交情况"为例：

// 第 1 次查询：查询项目下所有任务（1 次）
List<Task> tasks = taskMapper.selectList(
    new LambdaQueryWrapper<Task>().eq(Task::getProjectId, projectId)
);

for (Task task : tasks) {
    // 第 2~N+1 次查询：每个任务查一次提交（N 次）
    List<Submission> subs = submissionMapper.selectList(
        new LambdaQueryWrapper<Submission>().eq(Submission::getTaskId, task.getId())
    );
    // ...组装
}

假设项目下有 10 个任务，总共执行 1 + 10 = 11 次 SQL。如果项目下有 100 个任务，就是 101 次 SQL。

2. N+1 的危害

危害维度 具体表现
数据库压力 SQL 执行次数暴增，数据库 CPU、连接池被占满
网络开销 每次 SQL 都有网络往返延迟，N 次累积显著
响应时间 接口耗时线性增长，100 条记录可能从 10ms 涨到 1000ms
系统稳定性 高并发下连接池耗尽，服务雪崩

3. 解决方案对比

方案 做法 SQL 次数 适用场景
方案 A：JOIN 一次查询 LEFT JOIN + ResultMap 嵌套映射 1 次 关联层级少（1-2 层），推荐首选
方案 B：批量查询 先查主表，收集 ID，用 <foreach> 一次性查子表，再内存分组 2 次 关联层级多，或子查询条件复杂
方案 C：延迟加载 MyBatis lazyLoadEnabled，按需触发子查询 1 + 实际访问数 按需加载场景，仍可能 N+1

问题

问题 1：N+1 问题隐蔽性强 代码层面看是"先查列表，再循环查详情"，逻辑清晰，初学者很难意识到这是性能问题。识别方法：看是否有"循环内调用 Mapper"。

问题 2：MyBatis 嵌套 select 默认就是 N+1

<!-- 这是 N+1 写法：每个 task 触发一次 selectSubmissionsByTaskId -->
<collection property="submissions"
            column="task_id"
            select="com.ctts.mapper.SubmissionMapper.selectSubmissionsByTaskId"/>

改造：改用嵌套结果（一次 JOIN + 内联 ResultMap）。

问题 3：批量查询方案中 <foreach> 写错 <foreach> 的 collection、item、open、close、separator 配置错误导致 SQL 语法错误。

完整代码

反例：N+1 查询（性能差，课堂互动代码阅读素材）

package com.ctts.service;

import com.baomidou.mybatisplus.core.conditions.query.LambdaQueryWrapper;
import com.ctts.entity.Task;
import com.ctts.entity.TaskSubmission;
import com.ctts.mapper.TaskMapper;
import com.ctts.mapper.TaskSubmissionMapper;
import com.ctts.vo.SubmissionDetailVO;
import com.ctts.vo.TaskWithSubmissionVO;
import com.ctts.vo.UserSimpleVO;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Service;

import java.util.ArrayList;
import java.util.List;

@Service
public class TaskServiceBad {

    @Autowired
    private TaskMapper taskMapper;

    @Autowired
    private TaskSubmissionMapper submissionMapper;

    @Autowired
    private SysUserMapper userMapper;

    /**
     * 【反例】N+1 查询：查询项目下所有任务及提交情况
     * 假设项目下有 N 个任务，总共执行 SQL 次数：
     *   1（查任务列表）+ N（每个任务查提交）+ N（每个提交查用户）= 2N + 1 次
     * 10 个任务 → 21 次 SQL；100 个任务 → 201 次 SQL
     */
    public List<TaskWithSubmissionVO> getTasksBad(Long projectId) {
        // 第 1 次 SQL：查询项目下所有任务
        List<Task> tasks = taskMapper.selectList(
            new LambdaQueryWrapper<Task>().eq(Task::getProjectId, projectId)
        );

        List<TaskWithSubmissionVO> result = new ArrayList<>();
        for (Task task : tasks) {
            TaskWithSubmissionVO vo = new TaskWithSubmissionVO();
            vo.setTaskId(task.getId());
            vo.setTaskTitle(task.getTitle());
            vo.setTaskDescription(task.getDescription());
            vo.setProjectId(task.getProjectId());
            vo.setCreateTime(task.getCreateTime());

            // 第 2~N+1 次 SQL：每个任务查一次提交（N 次查询！）
            List<TaskSubmission> subs = submissionMapper.selectList(
                new LambdaQueryWrapper<TaskSubmission>()
                    .eq(TaskSubmission::getTaskId, task.getId())
            );

            List<SubmissionDetailVO> subVOs = new ArrayList<>();
            for (TaskSubmission sub : subs) {
                SubmissionDetailVO subVO = new SubmissionDetailVO();
                subVO.setSubmissionId(sub.getId());
                subVO.setContent(sub.getContent());
                subVO.setSubmitTime(sub.getSubmitTime());

                // 第 N+2~2N+1 次 SQL：每个提交查一次用户（又是 N 次！）
                SysUser user = userMapper.selectById(sub.getUserId());
                if (user != null) {
                    UserSimpleVO userVO = new UserSimpleVO();
                    userVO.setUserId(user.getId());
                    userVO.setUsername(user.getUsername());
                    userVO.setRealName(user.getRealName());
                    subVO.setUser(userVO);
                }
                subVOs.add(subVO);
            }
            vo.setSubmissions(subVOs);
            result.add(vo);
        }
        return result;
    }
}

// Service 层批量查询组装（2 次 SQL）
public List<TaskWithSubmissionVO> getTasksBatch(Long projectId) {
    // 第 1 次 SQL：查询所有任务
    List<Task> tasks = taskMapper.selectList(
        new LambdaQueryWrapper<Task>().eq(Task::getProjectId, projectId)
    );
    if (tasks.isEmpty()) return new ArrayList<>();

    // 收集所有 task_id
    List<Long> taskIds = tasks.stream().map(Task::getId).toList();

    // 第 2 次 SQL：一次性查询所有任务的提交（IN 批量查询）
    List<SubmissionDetailVO> allSubs = submissionMapper.selectSubmissionsByTaskIds(taskIds);

    // 按 task_id 分组（内存分组）
    Map<Long, List<SubmissionDetailVO>> subMap = allSubs.stream()
        .collect(Collectors.groupingBy(SubmissionDetailVO::getTaskId));

    // 组装 VO
    List<TaskWithSubmissionVO> result = new ArrayList<>();
    for (Task task : tasks) {
        TaskWithSubmissionVO vo = new TaskWithSubmissionVO();
        vo.setTaskId(task.getId());
        vo.setTaskTitle(task.getTitle());
        vo.setTaskDescription(task.getDescription());
        vo.setProjectId(task.getProjectId());
        vo.setCreateTime(task.getCreateTime());
        vo.setSubmissions(subMap.getOrDefault(task.getId(), new ArrayList<>()));
        result.add(vo);
    }
    return result;
}

易错点

  1. 识别盲区：循环里调 Mapper 是 N+1 的典型特征，但初学者常以为是"正常写法"。口诀："Mapper 调用出现在 for 循环里，警惕 N+1"。
  2. MyBatis 嵌套 select 默认 N+1：<collection select="..."> 是 N+1 写法，需改用嵌套结果 <collection resultMap="..."> 或内联配置。
  3. 批量查询 <foreach> 漏写 open/close/separator：导致 IN 1,2,3 缺括号，SQL 语法错误。
  4. 过度优化：简单一对一关联也强制改成批量查询，增加代码复杂度。原则：能用 JOIN 一次查询的优先 JOIN。

小结

  • N+1 = 1 次主查询 + N 次循环子查询，是 ORM 常见性能陷阱。
  • 识别特征：循环内调用 Mapper。
  • 解决方案：JOIN 一次查询（首选）、批量查询（次选）、避免嵌套 select。

K19-5 多表业务接口实现

定义

多表业务接口实现是指将多表 JOIN 查询、ResultMap 嵌套映射、VO 组装串联起来，从 Controller 接收请求到 Service 处理到 Mapper 查询数据库，最终返回结构化 JSON 的完整链路实现。

原理

1. Controller-Service-Mapper 分层职责

层 职责 本课体现
Controller 接收请求、参数校验、调用 Service、返回统一结果 接收 projectId，调用 Service，返回 Result<ProjectTaskVO>
Service 业务逻辑、数据组装、事务控制 调用 Mapper 获取多表数据，组装 VO
Mapper 数据访问、SQL 执行 执行多表 JOIN 查询，ResultMap 映射

2. 统一返回结构

{
    "code": 200,
    "message": "success",
    "data": {
        "projectId": 1,
        "projectName": "2024春季实训",
        "tasks": [...]
    }
}

完整代码

1. 统一返回结果类 Result（复用既有）

package com.ctts.common;

import lombok.Data;

@Data
public class Result<T> {
    private Integer code;
    private String message;
    private T data;

    public static <T> Result<T> success(T data) {
        Result<T> r = new Result<>();
        r.setCode(200);
        r.setMessage("success");
        r.setData(data);
        return r;
    }

    public static <T> Result<T> error(Integer code, String message) {
        Result<T> r = new Result<>();
        r.setCode(code);
        r.setMessage(message);
        return r;
    }
}

@Service
public class TaskService {

    @Autowired
    private TaskMapper taskMapper;

    @Autowired
    private TrainingProjectMapper trainingProjectMapper;

    /**
     * 接口 1 实现：查询项目下所有任务及提交情况（一次 JOIN 查询）
     */
    public List<TaskWithSubmissionVO> getTasksWithSubmissionsByProjectId(Long projectId) {
        return taskMapper.selectTasksWithSubmissionsByProjectId(projectId);
    }

    /**
     * 接口 2 实现：查询项目信息 + 任务及提交情况（Service 层组装）
     */
    public ProjectTaskVO getProjectWithTasks(Long projectId) {
        TrainingProject project = trainingProjectMapper.selectById(projectId);
        if (project == null) {
            throw new RuntimeException("项目不存在: " + projectId);
        }
        List<TaskWithSubmissionVO> tasks = taskMapper.selectTasksWithSubmissionsByProjectId(projectId);

        ProjectTaskVO vo = new ProjectTaskVO();
        vo.setProjectId(project.getId());
        vo.setProjectName(project.getName());
        vo.setProjectDescription(project.getDescription());
        vo.setCreateTime(project.getCreateTime());
        vo.setTasks(tasks);
        return vo;
    }
}

易错点

  1. Controller 直接调 Mapper：跳过 Service 层，破坏分层架构。规范：Controller 只调 Service。
  2. Service 抛异常未处理：throw new RuntimeException 会导致前端收到 500 错误。规范：配合全局异常处理器（第13次课内容）。
  3. @PathVariable 名字不匹配：方法参数名 projectId 与路径 {projectId} 必须一致，否则需 @PathVariable("projectId") 显式指定。
  4. 接口路径冲突：/project/{projectId} 与 /project/{projectId}/detail 不冲突，但 /project/{id} 与 /project/detail 会冲突（detail 被当成 id 解析）。

小结

  • 完整链路：Controller 接收 → Service 组装 → Mapper 多表查询 → ResultMap 映射 → VO 返回。
  • 严格分层：Controller 不调 Mapper，Service 编排业务，Mapper 只管数据。
  • 测试验证：用 Postman 验证返回结构，特别是零提交任务的 submissions: []。

拓展阅读

1. MyBatis 延迟加载（Lazy Loading）

本课使用"嵌套结果"一次 JOIN 查询完成映射。MyBatis 还支持"延迟加载"：主对象加载时不查关联数据，访问关联属性时才触发 SQL。配置 mybatis.configuration.lazy-load-enabled=true 开启。延迟加载适合"部分场景才需要关联数据"的情况，但滥用仍会触发 N+1。参考：MyBatis 官方文档 - 延迟加载。

2. MyBatis-Plus 多表查询的局限

MyBatis-Plus 的 BaseMapper、QueryWrapper 主要面向单表操作，多表关联查询仍需手写 XML SQL。社区有 mybatis-plus-join 扩展库提供链式多表 API，但灵活性不如原生 XML，企业项目中多表查询推荐直接写 XML。

3. 数据库执行计划（EXPLAIN）

判断 SQL 性能的终极工具。在 JOIN SQL 前加 EXPLAIN，查看数据库执行计划：访问类型（type）、扫描行数（rows）、是否用索引（key）。发现 type=ALL（全表扫描）时需加索引优化。本课的三表 JOIN 应在 task.project_id、task_submission.task_id、task_submission.user_id 上建索引。

4. DTO vs VO vs BO vs PO 实体规范

  • PO（Persistent Object）：持久化对象，对应数据库表，如 Task。
  • DTO（Data Transfer Object）：数据传输对象，用于接收前端参数。
  • VO（View Object）：视图对象，用于返回前端展示。
  • BO（Business Object）：业务对象，Service 内部传递用。 大型项目会严格区分，中小项目常合并为 DTO/VO 两类。

5. 课堂思政延伸：性能与责任

一次 N+1 查询，在测试环境（10 条数据）几乎无感；上线后数据量增长到 1000 条，接口耗时从 10ms 涨到 10s，数据库连接池被占满，整个服务雪崩。某互联网公司曾因一个 N+1 查询导致线上事故，直接经济损失百万级。工程师对每一行 SQL 的性能负责，就是对用户、对团队、对服务器资源负责。低效查询不是"小问题"，而是对资源的浪费，是工程素养的缺失。培养性能意识，从拒绝 N+1 开始。
