二、知识点详解

K23-1 Maven打包

1. 定义

Maven打包是指使用Maven构建工具，将项目源码、资源文件、依赖库整合为可分发产物的过程。对于Spring Boot项目，打包产物是一个可执行jar（fat jar），包含内嵌Tomcat和所有依赖，可通过java -jar直接运行。

2. 原理

2.1 Maven生命周期

Maven的生命周期由多个阶段（phase）组成，与打包相关的阶段：

阶段 作用
clean 删除target目录
compile 编译主代码src/main/java → target/classes
test 编译并运行测试用例
package 打包成jar/war，输出到target/
install 将jar安装到本地仓库~/.m2/repository

关键命令：

mvn clean package          # 清理并打包（执行测试）
mvn clean package -DskipTests  # 清理并打包（跳过测试执行）
mvn clean package -Dmaven.test.skip=true  # 跳过测试编译和执行

启动流程：

  1. java -jar读取MANIFEST.MF中的Main-Class
  2. 执行JarLauncher.main()
  3. 加载BOOT-INF/classes和BOOT-INF/lib
  4. 通过反射调用应用主类（Start-Class）的main方法
  5. 启动内嵌Tomcat，加载Spring上下文

3. 问题

Q：为什么IDE能运行，打包后启动失败？

常见原因：

  1. pom.xml缺少spring-boot-maven-plugin：生成的jar不含启动器，无法java -jar运行
  2. 测试失败导致打包中断：使用-DskipTests跳过
  3. 主类未配置：插件未正确识别Start-Class
  4. 依赖缺失：<scope>provided</scope>的依赖不会打入jar

Q：-DskipTests和-Dmaven.test.skip=true的区别？

参数 编译测试代码 执行测试
-DskipTests ✅ 编译 ❌ 跳过
-Dmaven.test.skip=true ❌ 跳过 ❌ 跳过

生产打包通常用-DskipTests（保留测试代码编译，确保代码无语法错误）。

6. 易错点

易错点 说明 解决方案
❌ 忘记配置spring-boot-maven-plugin 生成的jar无法java -jar运行 pom.xml必须配置该插件
❌ finalName与版本号混淆 ctts-1.0.0.jar不利于部署脚本 用<finalName>ctts</finalName>固定名称
❌ 误用<scope>provided</scope> 依赖不会打入jar，运行时缺失 Spring Boot项目一般不用provided
❌ 主类位置错误 插件找不到启动类 显式配置<mainClass>
❌ 资源文件未打包 application.yml等丢失 检查<resources>配置
❌ 测试代码编译失败 即使-DskipTests也可能失败 用-Dmaven.test.skip=true
❌ Lombok未排除 增加jar体积 插件配置<excludes>排除lombok

7. 小结

Maven打包是项目交付的第一步。核心要点：

  1. 命令：mvn clean package -DskipTests
  2. 插件：spring-boot-maven-plugin的repackage目标生成可执行jar

K23-2 Spring Boot jar运行

1. 定义

Spring Boot jar运行是指通过java -jar命令启动可执行jar，由内嵌Tomcat承载Web应用，无需独立部署应用服务器。可通过命令行参数动态覆盖配置。

2. 原理

2.1 内嵌Tomcat机制

Spring Boot默认内嵌Tomcat（spring-boot-starter-web自动引入）：

  • 启动时创建Tomcat实例
  • 注册DispatcherServlet
  • 监听指定端口（默认8080）
  • 无需外部Tomcat，jar即应用

对比传统部署：

图示 9：传统：WAR包 → 部署到外部Tomcat → 启动Tomcat

传统：WAR包

→

java -jar启动

→

2.2 命令行参数机制

Spring Boot支持多种方式传递配置参数，命令行参数优先级最高：

方式1：--key=value形式

java -jar ctts.jar --server.port=9090
java -jar ctts.jar --spring.profiles.active=prod
java -jar ctts.jar --server.port=9090 --spring.profiles.active=prod

方式2：JVM系统属性-Dkey=value

java -Dserver.port=9090 -jar ctts.jar

注意：-D参数放在-jar之前，--参数放在-jar之后。

2.3 后台运行机制

前台运行：终端关闭则进程终止

java -jar ctts.jar

后台运行（Linux）：

nohup java -jar ctts.jar > ctts.log 2>&1 &
组成 作用
nohup 忽略SIGHUP信号，终端关闭后进程不退出
> ctts.log 标准输出重定向到文件
2>&1 标准错误也重定向到标准输出（即同一文件）
& 放入后台执行

Windows后台运行（了解）：

start /b java -jar ctts.jar > ctts.log 2>&1

3. 问题

Q：为什么启动后立即Ctrl+C会停止？

前台运行时，进程绑定在当前终端的会话上，Ctrl+C发送SIGINT信号导致进程退出。生产环境必须用nohup ... &后台运行。

Q：如何优雅停止Spring Boot应用？

Spring Boot支持优雅关闭（graceful shutdown），配置：

server:
  shutdown: graceful  # 默认immediate
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s  # 等待处理中的请求

停止时使用kill -15 PID（SIGTERM），应用会处理完当前请求后退出。kill -9 PID（SIGKILL）是强制终止，不推荐。

Q：-D和--参数的区别？

参数形式 位置 示例 说明
-Dkey=value -jar之前 java -Dserver.port=9090 -jar ctts.jar JVM系统属性
--key=value -jar之后 java -jar ctts.jar --server.port=9090 Spring Boot参数

两者都能覆盖配置，但Spring Boot官方推荐--形式。

#!/bin/bash
# CTTS启动脚本

#!/bin/bash
# CTTS停止脚本

PID_FILE=$APP_DIR/$APP_NAME.pid

if [ ! -f $PID_FILE ]; then
    echo "[$APP_NAME] 未运行（PID文件不存在）"
    exit 0

if ps -p $PID > /dev/null; then
    echo "[$APP_NAME] 正在停止，PID=$PID"

    sleep 5

    echo "[$APP_NAME] 已停止"
else
    echo "[$APP_NAME] 进程不存在"
fi

K23-3 配置文件管理

1. 定义

配置文件管理是指通过多环境配置文件（application-{profile}.yml）和spring.profiles.active机制，实现开发、测试、生产环境的配置隔离与灵活切换。Spring Boot支持外部配置文件覆盖机制，便于运维修改。

2. 原理

2.1 多环境配置机制

Spring Boot支持按profile组织配置文件：

图示 11：项目内多环境配置文件
  • src/main/resources/
  • application.yml # 公共配置与默认 profile
  • application-dev.yml # 开发环境
  • application-prod.yml # 生产环境
  • application-test.yml # 测试环境，可选

激活方式：

  • 主配置中：spring.profiles.active=dev
  • 命令行：--spring.profiles.active=prod
  • 环境变量：export SPRING_PROFILES_ACTIVE=prod

加载顺序：先加载application.yml，再加载application-{active}.yml，后者覆盖前者同名配置。

2.2 配置优先级（高→低）

Spring Boot配置加载遵循严格的优先级，高优先级覆盖低优先级：

1. 命令行参数 (--server.port=9090)
2. SPRING_APPLICATION_JSON 环境变量中的JSON
3. ServletConfig/ServletContext 初始化参数
4. JNDI 属性
5. Java系统属性 (-Dserver.port=9090)
6. 操作系统环境变量 (SERVER_PORT=9090)
7. jar包外部application-{profile}.yml (jar同目录/config/)
8. jar包内部application-{profile}.yml
9. jar包外部application.yml
10. jar包内部application.yml
11. @PropertySource注解指定的文件
12. 默认值

常用重点：命令行 > 环境变量 > 外部配置文件 > 内部配置文件 > 默认值

2.3 外部配置文件

将application.yml或application-{profile}.yml放在jar同目录或jar同目录的config/子目录下，会覆盖jar内同名配置：

图示 12：服务器外部配置目录
  • /opt/ctts/
  • ctts.jar
  • application.yml # 外部配置覆盖 jar 内配置
  • application-prod.yml # 生产配置
  • config/application.yml # config 目录优先级更高

优势：运维修改配置无需重新打包，直接修改外部文件重启即可。

3. 问题

Q：开发环境打印SQL，生产环境关闭，如何配置？

在application-dev.yml开启SQL日志，application-prod.yml关闭：

  configuration:
    log-impl: org.apache.ibatis.logging.stdout.StdOutImpl  # 打印SQL

# application-prod.yml

logging:
  level:
    root: info  # 生产环境只保留info级别

Q：生产环境数据库密码如何避免硬编码在配置文件中？

方案1：环境变量

spring:
  datasource:
    password: ${DB_PASSWORD:defaultPassword}

启动：export DB_PASSWORD=realpassword && java -jar ctts.jar

方案2：命令行参数

java -jar ctts.jar --spring.datasource.password=realpassword

方案3：外部配置文件（不打入jar，文件权限控制）

Q：jar内配置和外部配置同名，哪个生效？

外部配置生效。优先级：config/application.yml > application.yml(jar同目录) > jar内application.yml。

K23-4 数据库初始化脚本

1. 定义

数据库初始化脚本是指用于在新环境创建数据库表结构和预置初始数据的SQL脚本，包括schema.sql（建表）和data.sql（初始数据）。Spring Boot支持自动执行这些脚本，也支持手动执行。

2. 原理

2.1 脚本组织
图示 15：数据库初始化脚本组织
  • src/main/resources/
  • schema.sql # 建表 DDL
  • data.sql # 初始数据 DML
  • schema-mysql.sql / schema-postgresql.sql # 按数据库区分
  • data-dev.sql / data-prod.sql # 按环境区分
2.2 Spring Boot自动执行机制

Spring Boot可通过配置自动执行SQL脚本：

spring:
  sql:
    init:
      mode: always              # always | never | embedded
      schema-locations: classpath:schema.sql
      data-locations: classpath:data.sql
      continue-on-error: false
      separator: ;
mode值 说明
always 总是执行
never 不执行
embedded 仅嵌入式数据库（H2）执行

执行时机：在DataSource初始化后、应用启动完成前执行。

注意：生产环境强烈建议用mode: never，改为手动执行，避免：

  • 每次启动都执行（虽然有CREATE IF NOT EXISTS保护）
  • 误覆盖已有数据
  • 性能开销
2.3 手动执行SQL
# 执行建表脚本
mysql -u root -p < schema.sql

# 执行初始数据脚本
mysql -u root -p ctts < data.sql

# 或进入MySQL后执行
mysql -u root -p
mysql> CREATE DATABASE ctts DEFAULT CHARACTER SET utf8mb4;
mysql> USE ctts;
mysql> SOURCE /path/to/schema.sql;
mysql> SOURCE /path/to/data.sql;

3. 问题

Q：为什么生产环境不建议自动执行schema.sql？

  1. 数据安全：DROP TABLE会清空数据，即使有IF EXISTS保护也存在风险
  2. 幂等性：脚本可能不支持重复执行
  3. 性能：每次启动都检查/执行SQL，增加启动时间
  4. 审计：生产环境数据库变更应有审计记录，自动执行绕过了审计

推荐做法：开发环境mode: always（方便），生产环境mode: never + 手动执行 + 变更审计。

Q：如何让脚本支持重复执行（幂等）？

-- 建表用 IF NOT EXISTS
CREATE TABLE IF NOT EXISTS user (...);

-- 建库用 IF NOT EXISTS
CREATE DATABASE IF NOT EXISTS ctts;

-- 插入数据用 INSERT IGNORE 或 ON DUPLICATE KEY UPDATE
INSERT IGNORE INTO sys_user VALUES (1, 'admin', ...);

Q：初始数据包括哪些？

CTTS系统初始数据：

  • 管理员账号（默认admin/123456，生产环境强制修改）
  • 角色权限数据
  • 字典数据（任务状态、优先级等）
  • 菜单数据

6. 易错点

易错点 说明 解决方案
❌ 生产环境mode: always 每次启动执行SQL，可能覆盖数据 生产环境配置mode: never
❌ 脚本不含IF NOT EXISTS 重复执行报错 建表加IF NOT EXISTS
❌ 字符集不统一 中文乱码 数据库、表、连接均用utf8mb4
❌ 初始密码明文 安全风险 存储BCrypt加密后的密码
❌ 外键约束顺序错误 建表失败 按依赖顺序建表，或先禁用外键检查
❌ 忘记USE ctts 数据建到错误的库 脚本开头明确USE ctts;
❌ DROP TABLE在生产执行 清空数据 生产环境删除DROP TABLE语句

7. 小结

数据库初始化是部署的前置条件。核心要点：

  1. 脚本组织：schema.sql（DDL）+ data.sql（DML）
  2. 自动执行：spring.sql.init.mode=always（开发环境）
  3. 手动执行：mysql -u root -p < schema.sql（生产环境）
  4. 幂等性：建表用IF NOT EXISTS，插入用INSERT IGNORE
  5. 生产安全：mode: never + 手动执行 + 审计

3. 问题

Q：为什么部署后无法访问？

排查清单：

  1. 应用是否启动：ps -ef | grep ctts.jar
  2. 端口是否监听：netstat -tlnp | grep 8080
  3. 防火墙是否放行：firewall-cmd --list-ports
  4. 安全组是否配置（云服务器）：检查云平台安全组规则
  5. 数据库是否连通：mysql -u ctts_user -p -h 127.0.0.1 ctts
  6. 日志是否有报错：tail -100f /opt/ctts/ctts.log

Q：云服务器的安全组和防火墙有什么区别？

层次 控制方 说明
安全组 云平台 云平台层面的网络隔离，需在控制台配置
防火墙 操作系统 Linux系统层面的端口控制（firewalld/iptables）

两者都需要配置，缺一不可。

Q：Nginx反向代理后，Spring Boot如何获取真实客户端IP？

配置Nginx转发头：

proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

Spring Boot配置：

server:
  forward-headers-strategy: native  # 信任X-Forwarded-*头

6. 易错点

易错点 说明 解决方案
❌ 云服务器安全组未配置 浏览器无法访问 在云平台控制台开放80/8080端口
❌ 防火墙未开放端口 本机可访问，外部不可访问 firewall-cmd --add-port
❌ MySQL用户权限不足 应用连接数据库失败 GRANT ALL ON ctts.* TO 'ctts_user'@'localhost'
❌ MySQL只允许localhost 远程连接失败 CREATE USER 'user'@'%'（不推荐生产）
❌ Nginx配置proxy_pass带不带/ 路径转发错误 location /api/ + proxy_pass http://x:8080/api/;
❌ Nginx未设置转发头 后端获取IP错误 配置X-Real-IP和X-Forwarded-For
❌ 日志目录不存在 启动报错 mkdir -p /opt/ctts/logs
❌ 外部配置文件路径错误 配置未生效 放在jar同目录或config/子目录
❌ 端口冲突 8080被占用 --server.port=9090或kill占用进程

7. 小结

服务器部署是项目交付的最终环节。核心要点：

  1. 流程：打包 → 上传 → 装环境 → 初始化DB → 配置 → 启动 → 防火墙 → Nginx → 验证
  2. 环境：JDK 17 + MySQL 8 + Nginx
  3. 启动：nohup java -jar ctts.jar --spring.profiles.active=prod &
  4. 网络：防火墙开放80/443，Nginx反向代理80→8080
  5. 验证：ps + netstat + curl + 浏览器访问

# 4. 检查配置文件
cat /opt/ctts/application-prod.yml | grep -A5 datasource

  • 用户名/密码错误
  • 数据库名错误
  • MySQL不允许该用户连接

问题2：外部无法访问——防火墙问题

现象：服务器本机curl正常，外部浏览器无法访问

排查步骤：

# 1. 检查防火墙

# 2. 检查云平台安全组（如为云服务器）
# 登录云平台控制台 → 安全组 → 入方向规则

# 3. 检查Nginx
systemctl status nginx
netstat -tlnp | grep 80

问题3：Nginx 502 Bad Gateway

现象：Nginx正常，但访问返回502

排查步骤：

# 1. 检查后端应用是否运行
ps -ef | grep ctts.jar
netstat -tlnp | grep 8080

# 2. 检查Nginx错误日志
tail -50 /var/log/nginx/ctts.error.log

curl http://127.0.0.1:8080/api/auth/test

常见原因：

  • 后端应用未启动或已崩溃
  • 后端端口不是8080（检查--server.port）
  • Nginx配置的proxy_pass端口错误
