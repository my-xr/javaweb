一、单项选择题（30 题）

10-D-01 ★

后端分层架构的核心思想是？

  • A. 代码越多越好
  • B. 关注点分离
  • C. 一个类干所有事
  • D. 只用 Controller 层

答案：B 解析： 分层的本质是关注点分离（SoC），把不同性质的工作交给不同的层。Dijkstra 在 1968 年提出分层是组织复杂系统的基本手段。A、C 与分层理念相反；D 是不分层的反例。

10-D-02 ★★

下列哪一项 不是 分层架构带来的好处？

  • A. 可维护性提升
  • B. 可测试性提升
  • C. 运行时性能大幅提升
  • D. 团队协作更顺畅

答案：C 解析： 分层带来的是可维护性、可测试性、团队协作的改善。方法调用的开销是纳秒级，可忽略，不会"大幅提升性能"。把"性能提升"作为分层理由是常见误区。

10-D-03 ★

"Controller 直接调 Mapper，业务逻辑堆在 Controller" 的主要问题是？

  • A. 编译不过
  • B. Controller 职责过重，业务逻辑无法复用、无法单元测试
  • C. Mapper 不能被 Controller 调用
  • D. Spring 不允许这样写

答案：B 解析： Controller 直接调 Mapper 在技术上可行（能编译能运行），但会导致职责过重、业务无法复用、无法脱离 Web 容器做单元测试、事务边界不清。这是工程规范问题，不是技术限制。

10-D-04 ★★

关于分层架构中"调用方向"的描述，正确的是？

  • A. Mapper 可以调用 Service
  • B. Service 可以调用 Controller
  • C. Controller 调用 Service，Service 调用 Mapper，单向依赖
  • D. 各层之间可以相互调用

答案：C 解析： 三层架构严格单向依赖：Controller → Service → Mapper。下层不感知上层，更不能反向调用。这保证了依赖关系的清晰和层次的独立。

10-D-05 ★★

下列代码片段应该放在哪一层？if (project.getStatus() == 2 && status != 2) { throw new IllegalStateException("已完成项目不能改状态"); }

  • A. Controller
  • B. Service
  • C. Mapper
  • D. Entity

答案：B 解析： 这是业务规则校验（状态机检查），属于 Service 层职责。Controller 只做 HTTP 参数校验（如 @NotBlank），Mapper 只做数据访问，Entity 只是数据载体。

10-D-06 ★

CTTS 项目中，Service 接口应放在哪个包下？

  • A. com.ctts.controller
  • B. com.ctts.service
  • C. com.ctts.service.impl
  • D. com.ctts.mapper

答案：B 解析： Service 接口放 service 包，实现类放 service/impl 子包。这是行业通用约定，便于区分接口与实现。

10-D-07 ★★

关于三层架构中各层的"厚薄"，下列说法正确的是？

  • A. Controller 是厚层，Service 是薄层
  • B. Mapper 是厚层，Service 是薄层
  • C. Controller 是薄层，Service 是厚层
  • D. 三层一样厚

答案：C 解析： Controller 是薄层（只接请求、调 Service、返回响应），Service 是厚层（业务逻辑、事务、组合多个 Mapper 调用）。Mapper 是单一职责的数据访问层。

10-D-08 ★★

关于 Service 层的异常处理，下列做法 最合理 的是？

  • A. Service 捕获所有异常并返回字符串提示给 Controller
  • B. Service 抛出业务异常，由全局异常处理器统一处理
  • C. Service 不处理任何异常，直接 throw
  • D. Service 把异常包装成 RuntimeException 再抛

答案：B 解析： Service 层应抛出有业务含义的异常（如 IllegalArgumentException、自定义业务异常），由 @RestControllerAdvice 全局异常处理器统一处理。A 让 Service 返回字符串与 HTTP 耦合；C 太粗放；D 丢失异常语义。

10-D-09 ★★

下列哪种代码应该放在 Mapper 层？

  • A. 业务规则校验
  • B. 事务管理
  • C. SQL 查询与数据持久化
  • D. HTTP 请求参数绑定

答案：C 解析： Mapper 层是数据访问层，只负责执行 SQL（CRUD）。业务校验在 Service；事务在 Service；HTTP 参数在 Controller。Mapper XML 中的 <if> 是 SQL 拼接判断，不是业务校验。

10-D-10 ★★

判断代码归属的"三问法"顺序，正确的是？

  • A. 是否读写 DB → 是否 HTTP 相关 → 是否业务规则
  • B. 是否 HTTP 相关 → 是否业务规则/事务 → 是否读写 DB
  • C. 是否业务规则 → 是否 HTTP 相关 → 是否读写 DB
  • D. 是否读写 DB → 是否业务规则 → 是否 HTTP 相关

答案：B 解析： 三问法：① HTTP 相关 → Controller；② 业务规则/事务/多表组合 → Service；③ 读写 DB → Mapper。先排除上层，再归到下层。

10-D-11 ★

三层架构中，跨层调用（如 Controller 直接调 Mapper）为什么不被推荐？

  • A. 编译会报错
  • B. 违反分层原则，破坏职责分离，Service 层形同虚设
  • C. Mapper 会被 Spring 销毁
  • D. 性能会下降

答案：B 解析： 技术上 Controller 可以直接调 Mapper，但这样 Service 层就被绕过，分层失去意义，业务逻辑又堆回 Controller。分层是工程规范，不是技术限制。

10-D-12 ★

@Service 注解应该写在？

  • A. Service 接口上
  • B. Service 实现类上
  • C. Controller 上
  • D. Mapper 上

答案：B 解析： @Service 写在实现类上，让 Spring 扫描并注册为 Bean。接口保持纯净，不依赖 Spring。这也是"面向接口编程"的体现。

10-D-13 ★★

关于 Service 接口与实现类分离的好处，下列说法 错误 的是？

  • A. 便于切换实现（如 mock 测试）
  • B. 面向接口编程，降低耦合
  • C. 提高运行时性能
  • D. 统一业务能力的契约文档

答案：C 解析： 接口与实现分离带来的是解耦、可切换、契约清晰等设计层面好处，与运行时性能无关。A、B、D 都是正确描述。

10-D-14 ★

CTTS 项目中，ProjectServiceImpl 应该放在哪个包下？

  • A. com.ctts.service
  • B. com.ctts.service.impl
  • C. com.ctts.controller
  • D. com.ctts.mapper

答案：B 解析： 实现类放 service/impl 子包，接口放 service 包。ProjectServiceImpl implements ProjectService，类上加 @Service 注解。

10-D-15 ★★

Controller 注入 Service 时，应该依赖？

  • A. Service 实现类（如 ProjectServiceImpl）
  • B. Service 接口（如 ProjectService）
  • C. Mapper
  • D. Entity

答案：B 解析： Controller 应依赖 Service 接口而非实现类，这是面向接口编程的体现。Spring 会自动注入实现类的实例。依赖接口便于切换实现、解耦。

10-D-16 ★

@RequiredArgsConstructor 是哪个库提供的注解？

  • A. Spring
  • B. MyBatis-Plus
  • C. Lombok
  • D. JUnit

答案：C 解析： @RequiredArgsConstructor 是 Lombok 提供，会为类中所有 final 字段生成构造器。配合 Spring 的构造器注入，写法简洁。

10-D-17 ★★

使用 @RequiredArgsConstructor 时，被注入的字段必须声明为？

  • A. static
  • B. private
  • C. final
  • D. volatile

答案：C 解析： @RequiredArgsConstructor 只为 final 字段（或 @NonNull 字段）生成构造器。未加 final 的字段不会进构造器，也就不会被注入。

10-D-18 ★★

下列 Service 方法命名，最规范 的是？

  • A. insertProject()
  • B. doProject()
  • C. createProject()
  • D. projectDb()

答案：C 解析： Service 方法应用业务动词命名：createXxx / updateXxx / deleteXxx / findXxx / submitXxx。insertProject 是 Mapper 风格（数据访问语义），doProject 语义模糊，projectDb 不规范。

10-D-19 ★★

事务的 ACID 特性中，"全部成功或全部失败"指的是？

  • A. 原子性（Atomicity）
  • B. 一致性（Consistency）
  • C. 隔离性（Isolation）
  • D. 持久性（Durability）

答案：A 解析： 原子性指事务内操作不可分割，要么全部成功提交，要么全部失败回滚。一致性指事务前后数据保持一致；隔离性指并发事务互不干扰；持久性指提交后永久保存。

10-D-20 ★

判断一个 Service 方法是否需要加 @Transactional，核心标准是？

  • A. 方法是否超过 10 行
  • B. 方法内是否包含多步写操作（insert/update/delete）
  • C. 方法是否返回 List
  • D. 方法是否被 Controller 调用

答案：B 解析： 事务的本质是保证多步写操作的原子性。单步查询不需要事务；单步写操作可加可不加；多步写操作必须加事务。方法长度、返回类型、调用方都与事务判断无关。

10-D-21 ★★

Spring 默认情况下，@Transactional 会对哪些异常回滚？

  • A. 所有异常
  • B. 只有 RuntimeException 和 Error
  • C. 只有受检异常（checked Exception）
  • D. 只有 IOException

答案：B 解析： Spring 默认只对 RuntimeException 和 Error 回滚，对受检异常（如 IOException、SQLException）不回滚。因此推荐显式指定 @Transactional(rollbackFor = Exception.class) 覆盖所有异常。

10-D-22 ★★

@Transactional 注解推荐写法是？

  • A. @Transactional
  • B. @Transactional(rollbackFor = Exception.class)
  • C. @Transactional(noRollbackFor = Exception.class)
  • D. @Transactional(readOnly = true)

答案：B 解析： 推荐加 rollbackFor = Exception.class，让受检异常也回滚，避免数据不一致。A 是默认行为，只回滚 RuntimeException；C 是反向配置；D 是只读事务，用于查询优化。

10-D-23 ★★★

@Transactional 的传播行为 REQUIRED（默认）的含义是？

  • A. 总是新建独立事务
  • B. 当前有事务就加入，没有就新建
  • C. 以非事务方式运行
  • D. 必须在事务中运行，否则抛异常

答案：B 解析： REQUIRED 是默认传播行为：当前有事务就加入（与外层共享同一事务），没有就新建一个。90% 的场景用 REQUIRED。A 是 REQUIRES_NEW；C 是 NOT_SUPPORTED/SUPPORTS；D 是 MANDATORY。

10-D-24 ★★★

@Transactional 的传播行为 REQUIRES_NEW 的典型使用场景是？

  • A. 查询方法
  • B. 日志记录：无论主业务成功与否，日志都要落库
  • C. 单步查询
  • D. 只读事务

答案：B 解析： REQUIRES_NEW 总是新建独立事务，外层事务挂起。典型场景是日志记录——主业务回滚不影响日志落库，便于排查问题。查询方法用 SUPPORTS 或不加事务；只读用 readOnly=true。

10-D-25 ★★★

下列哪种情况 不会 导致 @Transactional 失效？

  • A. 方法是 private
  • B. 类内部自调用（this.method()）
  • C. 方法是 public 且通过 Spring 代理调用
  • D. 异常被 try-catch 吞掉

答案：C 解析： C 是正常情况，事务生效。A（private 方法）Spring AOP 代理不拦截；B（自调用）不经过代理对象；D（异常被吞）Spring 检测不到异常不回滚。这三种都是事务失效的常见场景。

10-D-26 ★★

Spring 官方推荐的依赖注入方式是？

  • A. @Autowired 字段注入
  • B. 构造器注入
  • C. @Resource 字段注入
  • D. Setter 注入

答案：B 解析： Spring 官方文档明确推荐构造器注入。优点：字段可声明为 final（不可变）、脱离 Spring 容器也能 new（可单元测试）、循环依赖在启动时就暴露。@Autowired 字段注入虽简洁但不推荐。

10-D-27 ★★

关于构造器注入的优势，下列说法 错误 的是？

  • A. 字段可声明为 final，保证不可变
  • B. 脱离 Spring 容器也能 new 出对象
  • C. 循环依赖在运行时才暴露
  • D. 符合 Spring 官方推荐

答案：C 解析： 构造器注入的循环依赖在**启动阶段（或编译阶段）**就暴露，启动失败报 BeanCurrentlyInCreationException，比字段注入的运行时 NPE 更早发现。C 说反了。

10-D-28 ★★

@Resource 注解默认按什么方式注入？

  • A. 按类型
  • B. 按名称
  • C. 按 ID
  • D. 随机

答案：B 解析： @Resource 是 JSR-250 规范，默认按名称注入，找不到再按类型。@Autowired 默认按类型注入。可通过 @Resource(name="beanName") 显式指定名称。

10-D-29 ★★★

Spring Boot 3.x 中，@Resource 注解的包路径是？

  • A. javax.annotation.Resource
  • B. jakarta.annotation.Resource
  • C. org.springframework.annotation.Resource
  • D. java.lang.Resource

答案：B 解析： Spring Boot 3.x 基于 Jakarta EE 9+，所有 javax.* 包改为 jakarta.*。@Resource 从 javax.annotation.Resource 变为 jakarta.annotation.Resource。迁移时需注意 import。

10-D-30 ★★★

当一个 Service 接口有多个实现类时，如何指定注入哪一个？

  • A. 在某个实现类上加 @Primary，或用 @Qualifier("beanName") 指定
  • B. 删除多余的实现类
  • C. 用 @Autowired 即可
  • D. 改用 @Resource 即可，不需要名称

答案：A 解析： 多个实现类时 Spring 会报 NoUniqueBeanDefinitionException。解决方案：①在某个实现类上加 @Primary 标记为默认；②用 @Qualifier("beanName") 精确指定。B 太粗暴；C、D 不指定名称无法区分。

二、多项选择题（10 题）

10-M-01 ★★

分层架构带来的好处有？（多选）

  • A. 关注点分离
  • B. 可维护性提升
  • C. 可测试性提升
  • D. 团队协作更顺畅
  • E. 运行时性能大幅提升

答案：ABCD 解析： 分层带来关注点分离、可维护性、可测试性、团队协作的好处。运行时性能不会大幅提升（方法调用开销可忽略），E 错误。性能不是分层的理由。

10-M-02 ★★

三层架构中，属于 Service 层职责的有？（多选）

  • A. 业务规则校验
  • B. 事务管理
  • C. 组合调用多个 Mapper
  • D. HTTP 请求参数绑定
  • E. 执行 SQL 查询

答案：ABC 解析： Service 层负责业务规则校验、事务管理、组合调用多个 Mapper。D 是 Controller 职责；E 是 Mapper 职责。Service 是"厚层"，承载主要业务逻辑。

10-M-03 ★★

关于 @Service 注解，下列说法正确的有？（多选）

  • A. 应该写在实现类上
  • B. 应该写在接口上
  • C. Spring 启动时扫描并注册为 Bean
  • D. 注解的 value 属性可指定 Bean 名称
  • E. 一个接口只能有一个 @Service 实现类

10-J-01 ★

Controller 层应该尽量薄，业务逻辑应放在 Service 层。

答案：✓ 解析： Controller 是薄层，只负责接收请求、调用 Service、返回响应。业务逻辑放在 Service 层是分层架构的基本原则。

Mapper 层可以写少量业务逻辑，只要 SQL 不太复杂就行。

答案：✗ 解析： Mapper 层只负责数据访问，不能写任何业务逻辑。Mapper XML 中的 <if> 是 SQL 拼接判断，不是业务校验。业务逻辑必须放 Service 层。

10-J-03 ★★

分层架构的调用方向是单向的，Service 不能调用 Controller。

答案：✓ 解析： 三层架构严格单向依赖：Controller → Service → Mapper。下层不感知上层，Service 不能反向调用 Controller，更不能返回 HTTP 相关对象。

10-J-04 ★★

Service 层返回 ResponseEntity 是合理的做法。

答案：✗ 解析： ResponseEntity 是 HTTP 响应对象，属于 Web 层。Service 不应感知 Web 层，应返回业务对象或业务结果。HTTP 相关封装由 Controller 完成。

10-J-05 ★★

如果一个 Service 方法只是简单调用一个 Mapper 方法（如 findAll），那这个 Service 层就没必要存在。

答案：✗ 解析： 即使当前只是透传，也保留 Service 层。原因：①保持分层一致性；②未来扩展业务逻辑时有地方放；③便于单元测试；④统一团队规范。分层是长期投资。

10-J-06 ★

@Service 注解可以写在接口上，也可以写在实现类上。

答案：✗ 解析： @Service 只能写在实现类上。接口保持纯净，不依赖 Spring。Spring 扫描的是带 @Service 的实现类，将其注册为 Bean，类型为接口类型。

10-J-07 ★★

Service 接口与实现类分离的好处之一是便于切换实现，例如测试时注入 mock 实现。

答案：✓ 解析： 接口与实现分离的核心价值之一就是可切换性。单元测试时可注入 mock 实现（实现同一接口），无需修改调用方代码。

10-J-08 ★★

Controller 注入 Service 时，应该依赖实现类（如 ProjectServiceImpl），这样能直接调用其方法。

答案：✗ 解析： 应该依赖接口（ProjectService）而非实现类。这是面向接口编程的体现，便于切换实现、降低耦合。Spring 会自动注入实现类的实例。

10-J-09 ★★

@RequiredArgsConstructor 会为类中所有字段生成构造器。

答案：✗ 解析： @RequiredArgsConstructor 只为 final 字段（或 @NonNull 字段）生成构造器。未加 final 的字段不会进构造器，不会被构造器注入。

10-J-10 ★★

在 Service 实现类中，可以用 new 创建另一个 Service 实例来调用其方法。

答案：✗ 解析： new 出来的对象不被 Spring 管理，其内部的 @Autowired 注入不生效，会导致 NPE。应通过构造器注入其他 Service。

10-J-11 ★★

事务的 ACID 特性中，"原子性"指的是事务内操作要么全部成功，要么全部失败。

答案：✓ 解析： 原子性（Atomicity）的准确含义：事务是不可分割的操作序列，全部成功提交或全部失败回滚。这是事务最基础的特性。

10-J-12 ★★

单步查询方法也需要加 @Transactional，否则会报错。

答案：✗ 解析： 单步查询不需要事务，不加 @Transactional 也不会报错。事务的本质是保证多步写操作的原子性。查询方法可加 @Transactional(readOnly = true) 做只读优化，但非必需。

10-J-13 ★★

@Transactional 加在 Service 方法上，如果方法内抛出 RuntimeException，事务会回滚。

答案：✓ 解析： Spring 默认对 RuntimeException 和 Error 回滚。但受检异常（如 IOException）默认不回滚，需配置 rollbackFor = Exception.class。

10-J-14 ★★

@Transactional 加在 private 方法上也能生效。

答案：✗ 解析： Spring AOP 代理只拦截 public 方法，private 方法上的 @Transactional 不生效。事务方法必须是 public。

10-J-15 ★★★

类内部自调用（this.method()）会导致 @Transactional 失效，因为不经过 Spring 代理对象。

答案：✓ 解析： this.method() 是直接方法调用，不经过 Spring 代理对象，@Transactional 注解不会被拦截处理。这是事务失效的最常见场景之一。解决方案：注入自己（@Lazy）或拆到另一个 Service。

10-J-16 ★★★

REQUIRES_NEW 传播行为会让当前方法新开一个独立事务，外层事务挂起，直到新事务结束。

答案：✓ 解析： REQUIRES_NEW 总是新建独立事务，外层事务挂起。新事务提交或回滚后，外层事务恢复。典型场景：日志记录，主业务回滚不影响日志落库。

10-J-17 ★★

@Autowired 字段注入是 Spring 官方最推荐的注入方式。

答案：✗ 解析： Spring 官方推荐构造器注入，不推荐 @Autowired 字段注入。字段注入的缺点：字段无法 final、脱离容器无法 new、循环依赖不易发现。IDE 也会给出警告。

10-J-18 ★★

构造器注入可以让循环依赖在启动阶段就暴露，而不是运行时才发现。

答案：✓ 解析： 构造器注入下，A 依赖 B、B 依赖 A 会在启动时实例化失败，报 BeanCurrentlyInCreationException。而字段注入借助三级缓存可能运行时才出 NPE，更难排查。

10-J-19 ★★

Spring IoC 容器负责扫描、实例化、注入、管理 Bean 的生命周期。

答案：✓ 解析： IoC 容器的核心职责：①扫描带注解的类；②实例化为 Bean；③按依赖关系注入；④管理 Bean 的生命周期（初始化、销毁）。ApplicationContext 是 IoC 容器的具体实现。

10-J-20 ★★

Spring Boot 3.x 中，@Resource 的包路径从 javax.annotation.Resource 变为 jakarta.annotation.Resource。

答案：✓ 解析： Spring Boot 3.x 基于 Jakarta EE 9+，所有 javax.* 包改为 jakarta.*。@Resource 也跟着变化。从 Spring Boot 2.x 迁移到 3.x 时需注意 import 修改。

10-S-02 ★★★

请详细说明 @Transactional 事务注解的核心属性、传播行为（重点对比 REQUIRED 与 REQUIRES_NEW）、回滚规则，并列举至少 5 种事务失效的场景。

参考答案：

核心属性：

属性 说明 常用值
rollbackFor 遇到哪些异常时回滚 Exception.class（推荐）
noRollbackFor 遇到哪些异常时不回滚 特定业务异常
propagation 事务传播行为 REQUIRED（默认）/ REQUIRES_NEW
isolation 事务隔离级别 DEFAULT（默认）
timeout 事务超时时间（秒） -1（不超时）
readOnly 是否只读事务 false（默认）；查询可设 true
transactionManager 指定事务管理器 多数据源时使用

传播行为对比：

传播行为 含义 使用场景
REQUIRED（默认） 当前有事务就加入，没有就新建 90% 场景，最常用
REQUIRES_NEW 总是新建独立事务，外层事务挂起 日志记录：无论主业务成功与否，日志都要落库

对比示例：方法 A（有事务）调用方法 B：

  • REQUIRED：B 加入 A 的事务，一荣俱荣，一损俱损；
  • REQUIRES_NEW：B 新开独立事务，A 挂起；B 提交后 A 恢复；B 回滚不影响 A，A 回滚不影响已提交的 B。

回滚规则：

  • Spring 默认只对 RuntimeException 和 Error 回滚；
  • 对 受检异常（如 IOException、SQLException）默认不回滚；
  • 推荐显式配置 @Transactional(rollbackFor = Exception.class)，让所有异常都回滚，避免数据不一致。

事务失效的 7 大场景：

  1. 方法非 public：Spring AOP 代理只拦截 public 方法，private/protected 上的注解无效；
  2. 类内部自调用：this.method() 不经过代理对象，注解失效；
  3. 异常被 try-catch 吞掉：Spring 检测不到异常，认为正常，不回滚；
  4. 抛出受检异常但未配 rollbackFor：默认不回滚受检异常；
  5. 数据库引擎不支持事务：MySQL 的 MyISAM 引擎不支持事务，需用 InnoDB；
  6. @Transactional 加在 final/static 方法：代理无法重写，注解无效；
  7. 多线程调用：事务绑定在线程上，新线程没有事务。

  • 核心属性列举 4 个以上（2 分）
  • REQUIRED 与 REQUIRES_NEW 对比准确（3 分）
  • 回滚规则说明（含受检异常问题）（2 分）
  • 事务失效场景列举 5 个以上（5 分，每个 1 分）

10-S-03 ★★

三种注入方式对比：

方式 写法 优点 缺点 推荐度
@Autowired 字段注入 @Autowired private XxxMapper mapper; 写法简洁 字段无法 final；脱离容器无法 new；循环依赖不易发现；IDE 警告 ❌ 不推荐

  1. 不可变性：字段可声明为 final，对象创建后依赖不可修改，线程安全；
  2. 可测试性：脱离 Spring 容器也能 new XxxServiceImpl(mockMapper)，便于单元测试；
  3. 循环依赖早暴露：A 依赖 B、B 依赖 A 在启动阶段就报错（BeanCurrentlyInCreationException），而非运行时 NPE；
  4. 明确依赖：构造器参数列表明确展示类的所有依赖，依赖过多时一眼看出类职责过重（代码坏味道）；
  5. 避免字段注入的隐藏问题：字段注入借助三级缓存可能"掩盖"循环依赖，运行时才暴雷。

示例：

@Service
@RequiredArgsConstructor

    private final ProjectMapper projectMapper;  // final 不可变
}

// 不推荐：字段注入
@Service
public class ProjectServiceImpl implements ProjectService {
    @Autowired
    private ProjectMapper projectMapper;  // 非 final，可被修改
}

package com.ctts.service.impl;

import com.ctts.entity.Task;
import com.ctts.entity.TaskSubmission;
import com.ctts.mapper.TaskMapper;
import com.ctts.mapper.TaskSubmissionMapper;
import com.ctts.service.TaskService;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.util.StringUtils;

import java.time.LocalDateTime;
import java.util.List;

@Service
@RequiredArgsConstructor
public class TaskServiceImpl implements TaskService {

    private final TaskMapper taskMapper;
    private final TaskSubmissionMapper taskSubmissionMapper;

    @Override
    public List<Task> findAll() {
        return taskMapper.selectList(null);
    }

    @Override
    public Task findById(Long id) {
        return taskMapper.selectById(id);
    }

    @Override
    @Transactional(rollbackFor = Exception.class)
    public Long submitTask(Long taskId, TaskSubmission submission) {
        // 1. 校验任务存在
        Task task = taskMapper.selectById(taskId);
        if (task == null) {
            throw new IllegalArgumentException("任务不存在: " + taskId);
        }
        // 2. 校验提交内容
        if (!StringUtils.hasText(submission.getContent())) {
            throw new IllegalArgumentException("提交内容不能为空");
        }
        // 3. 补全提交记录字段
        submission.setTaskId(taskId);
        submission.setStatus(1);
        submission.setSubmitTime(LocalDateTime.now());
        submission.setCreateTime(LocalDateTime.now());
        submission.setUpdateTime(LocalDateTime.now());
        // 4. 写入提交记录
        taskSubmissionMapper.insert(submission);
        // 5. 若任务原状态为未开始(0)，更新为进行中(1)
        if (task.getStatus() == 0) {
            task.setStatus(1);
            task.setUpdateTime(LocalDateTime.now());
            taskMapper.updateById(task);
        }
        return submission.getId();
    }

    @Override
    public boolean updateStatus(Long id, Integer status) {
        Task task = taskMapper.selectById(id);
        if (task == null) {
            throw new IllegalArgumentException("任务不存在");
        }
        task.setStatus(status);
        task.setUpdateTime(LocalDateTime.now());
        return taskMapper.updateById(task) == 1;
    }
}
