一、单项选择题（30题）

19-单选-01（★，K19-1）

在 SQL 多表关联查询中，INNER JOIN 的特点是？

  • A
    返回左表所有行，右表不匹配填 NULL
  • B
    返回两表中满足连接条件的行（交集）
  • C
    返回右表所有行，左表不匹配填 NULL
  • D
    返回两表的笛卡尔积

答案：B 解析：INNER JOIN（内连接）只返回两表中满足 ON 连接条件的行，不匹配的行被丢弃。A 是 LEFT JOIN，C 是 RIGHT JOIN，D 是 CROSS JOIN。

19-单选-02（★，K19-1）

查询"某项目下所有任务及提交情况"时，希望"零提交的任务"也出现在结果中，应使用哪种 JOIN？

  • A
    INNER JOIN
  • B
    LEFT JOIN
  • C
    RIGHT JOIN
  • D
    CROSS JOIN

答案：B 解析：LEFT JOIN 保留左表（task）所有行，右表（task_submission）不匹配时填 NULL，保证零提交任务不丢失。INNER JOIN 会丢失零提交任务。

19-单选-03（★★，K19-1）

执行 SELECT t.id, ts.id FROM task t LEFT JOIN task_submission ts ON t.id = ts.task_id 时报错 "Column 'id' is ambiguous"，原因是？

  • A
    表别名写错
  • B
    SELECT 中 id 未指定表别名前缀，数据库不知取哪张表的 id
  • C
    ON 条件写错
  • D
    LEFT JOIN 应改为 INNER JOIN

答案：B 解析：task 和 task_submission 都有 id 列，直接写 id 会列名歧义。正确写法是 t.id, ts.id，加表别名前缀。

19-单选-04（★，K19-1）

多表 JOIN 时，连接条件应写在哪个子句中？

  • A
    WHERE
  • B
    ON
  • C
    GROUP BY
  • D
    HAVING

答案：B 解析：JOIN 的连接条件写在 ON 子句中。WHERE 用于结果集过滤。虽然旧式 SQL 可用 WHERE 写连接条件（隐式连接），但标准写法是 ON。

19-单选-05（★★，K19-1）

关于 LEFT JOIN 中过滤右表字段的条件，下列说法正确的是？

  • A
    写在 WHERE 中和写在 ON 中效果完全相同
  • B
    写在 WHERE 中会使"左表无匹配的行"也被过滤掉，LEFT JOIN 等效于 INNER JOIN
  • C
    写在 ON 中会影响左表所有行的返回
  • D
    必须写在 GROUP BY 中

答案：B 解析：右表过滤条件写在 WHERE 中时，"零提交任务"的右表字段为 NULL，不满足 WHERE 条件会被过滤，LEFT JOIN 退化成 INNER JOIN。要保留左表全部，右表过滤应写在 ON 中。

19-单选-06（★，K19-1）

表别名的作用是？

  • A
    给列重命名
  • B
    简化表名书写并消除列名歧义
  • C
    改变表的真实名称
  • D
    提高查询速度

答案：B 解析：表别名用 AS 或空格定义，如 task t，简化 SQL 书写并通过 t.id 形式消除多表同名列歧义。不会改变表真实名称。

19-单选-07（★★，K19-1）

三表关联查询 task t LEFT JOIN task_submission ts LEFT JOIN sys_user u，下列 ON 条件正确的是？

  • A
    ON t.id = ts.task_id AND ts.user_id = u.id
  • B
    ON t.id = ts.task_id 紧跟第一个 JOIN，ON ts.user_id = u.id 紧跟第二个 JOIN
  • C
    所有 ON 条件都写在最后一个 JOIN 后
  • D
    三表关联不需要 ON 条件

答案：B 解析：每个 JOIN 后紧跟自己的 ON 条件，写法清晰。A 把两个 ON 合并写法不规范且某些数据库不支持。C、D 错误。

19-单选-12（★★★，K19-2）

MyBatis ResultMap 嵌套映射中，<id> 标签的作用是？

  • B
    标记非主键列
  • C
    标记外键列
  • D

19-单选-13（★★★，K19-2）

一对多 ResultMap 映射后，发现集合中只有一个元素，最可能的原因是？

19-单选-16（★★，K19-2）

关于 MyBatis 嵌套结果与嵌套 select，下列说法正确的是？

  • A
    嵌套 select 性能更好
  • B
    嵌套结果（一次 JOIN 查询）性能更好，且不会产生 N+1 问题
  • C
    两者性能完全相同
  • D
    嵌套 select 不会产生 N+1 问题

答案：B 解析：嵌套结果是一次 JOIN 查询后映射，SQL 只执行 1 次。嵌套 select 是对每条主记录触发额外 SQL，会产生 N+1 问题。优先用嵌套结果。

19-单选-21（★，K19-4）

N+1 查询问题是指？

  • A
    一次查询获取 N 条记录
  • B
    1 次主查询获取 N 条主记录，再对每条主记录执行 1 次子查询，共 N+1 次 SQL
  • C
    N 张表关联查询
  • D
    1 条 SQL 查询 N+1 个字段

答案：B 解析：N+1 问题：1 次主查询 + N 次循环子查询 = N+1 次 SQL。是 ORM 常见性能陷阱。

19-单选-22（★★，K19-4）

下列代码哪种写法是 N+1 问题的典型特征？

  • A
    Mapper 中写 JOIN SQL
  • B
    Service 中 for 循环内调用 Mapper
  • C
    Controller 直接返回 VO
  • D
    使用 ResultMap 嵌套映射

答案：B 解析：循环内调用 Mapper 是 N+1 的典型特征——每次循环触发一次 SQL。识别口诀："Mapper 调用出现在 for 循环里，警惕 N+1"。

19-单选-23（★★，K19-4）

下列哪种方式不能解决 N+1 问题？

  • A
    使用 JOIN 一次查询 + ResultMap 嵌套映射

19-单选-24（★★，K19-4）

N+1 问题中，若主查询返回 100 条记录，每条记录再查 1 次子查询，总共执行多少次 SQL？

三、判断题（20题）

19-判断-01（★，K19-1）

INNER JOIN 会返回两表中所有满足连接条件的行，不满足条件的行被丢弃。

答案：正确 解析：INNER JOIN 取交集，只返回满足 ON 条件的行，不匹配的行被丢弃。

19-判断-02（★，K19-1）

LEFT JOIN 中，右表不匹配的行会被自动丢弃。

答案：错误 解析：LEFT JOIN 保留左表所有行，右表不匹配时填 NULL，不会丢弃。INNER JOIN 才会丢弃。

19-判断-03（★★，K19-1）

多表 JOIN 时，所有列必须加表别名前缀以避免歧义。

答案：正确 解析：多表常有同名列（如 id、create_time），加表别名前缀（t.id、ts.id）避免 "ambiguous" 报错，是好习惯。

19-判断-04（★★，K19-1）

LEFT JOIN 的 ON 条件中可以写右表的过滤条件，不会影响左表全部行的返回。

答案：正确 解析：ON 中的右表过滤条件只影响右表的匹配，左表全部行仍返回（右表字段为 NULL）。若写在 WHERE 中则会使 LEFT JOIN 退化成 INNER JOIN。

19-判断-05（★，K19-2）

MyBatis ResultMap 中 association 用于一对一关系映射。

答案：正确 解析：association 映射 Java 单个对象，对应一对一/多对一。一对多用 collection。

19-判断-06（★，K19-2）

MyBatis ResultMap 中 collection 用于一对多关系映射。

答案：正确 解析：collection 映射 Java List 集合，对应一对多。

19-判断-07（★★，K19-2）

ResultMap 中 collection 用 javaType 指定集合元素类型。

答案：错误 解析：collection 用 ofType 指定集合元素类型。javaType 用于 association 指定对象类型。

19-判断-08（★★★，K19-2）

ResultMap 嵌套映射中，<id> 标签可以省略，不影响一对多分组。

答案：错误 解析：<id> 是 MyBatis 分组对象的依据，省略会导致每行一个对象，一对多关系失效。必须正确标注主表和子表主键。

19-判断-09（★★，K19-2）

SQL 中 SELECT t.id AS task_id，ResultMap 中 column="taskId" 能正确映射。

答案：错误 解析：SQL 别名是 task_id（下划线），ResultMap 的 column 必须是 task_id 与之一致。写成 taskId（驼峰）会映射失败（NULL）。

19-判断-10（★★★，K19-2）

MyBatis <collection select="..."> 嵌套 select 写法会产生 N+1 问题。

答案：正确 解析：嵌套 select 对每条主记录触发一次子查询 SQL，产生 N+1。应改用嵌套结果 <collection resultMap="..."> 一次 JOIN 查询。

19-判断-11（★，K19-3）

VO 对象应该按接口需要设计，而不是按数据库表结构设计。

答案：正确 解析：VO 是视图对象，面向接口返回，按需设计字段。与表结构解耦。

19-判断-12（★★，K19-3）

VO 可以继承实体类以减少重复代码。

答案：错误 解析：不推荐 VO 继承实体，会导致 VO 暴露实体所有字段（含敏感字段）。VO 应独立定义。

19-判断-13（★★，K19-3）

DTO 用于接收前端请求参数，VO 用于返回前端展示数据。

答案：正确 解析：DTO（Data Transfer Object）接收参数，VO（View Object）返回展示。规范项目中两者分离。

19-判断-14（★，K19-4）

N+1 问题是指 1 次主查询加 N 次子查询，共 N+1 次 SQL。

答案：正确 解析：N+1 问题的标准定义。主查询 1 次获取 N 条主记录，循环对每条主记录查询 1 次，共 N+1 次。

19-判断-15（★★，K19-4）

在 for 循环内调用 Mapper 是 N+1 问题的典型特征。

答案：正确 解析：循环内调 Mapper 意味着每次循环触发一次 SQL，是 N+1 的典型特征。识别口诀："循环内调 Mapper，警惕 N+1"。

19-判断-16（★★★，K19-4）

JOIN 一次查询 + ResultMap 嵌套映射可以解决 N+1 问题。

答案：正确 解析：一次 JOIN 查询 SQL 只执行 1 次，ResultMap 嵌套映射完成"扁平→嵌套"转换，无 N+1。是首选方案。

19-判断-17（★，K19-5）

Controller 层可以直接调用 Mapper 层，跳过 Service 层。

答案：错误 解析：严格分层中 Controller 只调 Service，不直接调 Mapper。Service 编排业务，Mapper 只管数据。

19-判断-18（★★，K19-5）

@PathVariable 用于接收 URL 路径中的变量。

答案：正确 解析：@PathVariable 接收 /project/{projectId} 中的 projectId。@RequestParam 接收查询参数，@RequestBody 接收请求体。

19-判断-19（★★★，K19-5）

多表关联查询接口返回的 JSON 中，零提交任务的 submissions 字段应为空数组 [] 而非 null。

答案：正确 解析：LEFT JOIN 保证零提交任务出现，ResultMap 的 collection 会映射为空集合（MyBatis 默认 new ArrayList）。返回 [] 便于前端处理，避免 null 判断。

19-判断-20（★★，K19-4）

N+1 问题在测试环境（少量数据）下往往难以察觉，上线后数据量增大才暴露。

答案：正确 解析：N+1 的隐蔽性——10 条数据时 11 次 SQL 几乎无感，1000 条时 1001 次 SQL 接口耗时暴增。需在开发阶段主动识别。

19-简答-01（★★，K19-1）

简述 INNER JOIN 与 LEFT JOIN 的区别，并结合"查询某项目下所有任务及提交情况"的场景说明应选择哪种 JOIN 及原因。

参考答案：

  • INNER JOIN：内连接，只返回两表中满足 ON 连接条件的行，不匹配的行被丢弃，结果是两表的交集。
  • LEFT JOIN：左连接，返回左表所有行，右表不匹配的行填 NULL，保证左表完整。
  • 场景选择：在"查询某项目下所有任务及提交情况"场景中，应选择 LEFT JOIN。原因：一个任务可能还没有任何提交（如刚发布的任务），使用 INNER JOIN 会让这些"零提交任务"从结果中消失，教师无法看到完整任务列表。LEFT JOIN 保证所有任务都出现，没有提交时提交相关字段为 NULL，符合"教师查看全部任务进度"的业务预期。

评分标准（满分 10 分）：

  • INNER JOIN 含义正确：3 分
  • LEFT JOIN 含义正确：3 分
  • 场景选择正确（LEFT JOIN）：1 分
  • 原因说明清晰（零提交任务不丢失）：3 分

19-简答-02（★★★，K19-2）

详细说明 MyBatis ResultMap 嵌套映射中 <id> 标签的作用，并解释漏标 <id> 会导致一对多映射出现什么问题及原因。

参考答案：

  • <id> 标签的作用：<id> 标签用于标记结果集的主键列，是 MyBatis 进行对象分组的依据。在处理 JOIN 查询的扁平结果集时，MyBatis 根据相同 <id> 列值的行合并成同一个 Java 对象。
  • 漏标 <id> 的问题：一对多映射中，若主表主键漏标 <id>，MyBatis 会把每一行都当成一个新对象，导致一对多关系丢失——本应合并到一个对象的多个子记录，被分散到多个对象中，每个对象的 collection 集合中只有一个元素（或为空）。
  • 原因：MyBatis 分组逻辑依赖 <id> 判断"当前行是否属于上一个对象"。无 <id> 时，MyBatis 默认每行是新对象，无法合并。正确做法是主表主键和每个子表主键都标 <id>，如 <id column="task_id"/> 和 <id column="submission_id"/>。
  • 示例：4 行结果集（task_id=1 两行、task_id=2 一行、task_id=3 一行），正确标注后得到 3 个 Task 对象（第 1 个 submissions 含 2 元素）；漏标 task_id 的 <id> 会得到 4 个 Task 对象，每个 submissions 只含 1 元素。

评分标准（满分 12 分）：

  • <id> 作用说明（分组依据）：3 分
  • 漏标问题现象描述（一对多失效）：3 分
  • 原因解释（MyBatis 分组逻辑）：4 分
  • 给出正确做法或示例：2 分

19-简答-03（★★★，K19-4）

什么是 N+1 查询问题？请描述其产生原因、危害，并说明两种解决方案的原理与 SQL 执行次数。

参考答案：

  • 定义：N+1 查询问题是指在循环中执行 1 次主查询获取 N 条主记录，再对每条主记录执行 1 次子查询获取关联数据，总共执行 N+1 次 SQL 的性能问题。
  • 产生原因：代码层面在 for 循环内调用 Mapper（如 for (Task t : tasks) { submissionMapper.selectByTaskId(t.getId()); }），或 MyBatis 配置使用了 <collection select="..."> 嵌套 select。
  • 危害：
    1. SQL 执行次数暴增，数据库 CPU、连接池被占满；
    2. 每次 SQL 有网络往返延迟，N 次累积显著；
    3. 接口响应时间线性增长（100 条记录可能从 10ms 涨到 1000ms）；
    4. 高并发下连接池耗尽，服务雪崩。
  • 解决方案：
    • 方案 A：JOIN 一次查询。用 LEFT JOIN 一次查询获取所有数据，通过 ResultMap 嵌套映射组装成嵌套对象。SQL 执行 1 次。适合关联层级少（1-2 层）的场景，首选。
    • 方案 B：批量查询。先查主表获取 N 条记录，收集主键 ID 列表，用 <foreach> IN 一次性查询所有子记录，再在内存按 ID 分组组装。SQL 执行 2 次。适合关联层级多或子查询条件复杂的场景。
  • 识别口诀：Mapper 调用出现在 for 循环里，警惕 N+1。

评分标准（满分 12 分）：

  • 定义正确：2 分
  • 产生原因（循环调 Mapper / 嵌套 select）：2 分
  • 危害（至少答出 3 点）：3 分
  • 方案 A 原理与 SQL 次数：2 分
  • 方案 B 原理与 SQL 次数：2 分
  • 识别口诀或补充说明：1 分

19-简答-04（★★★，K19-3/K19-5）

请说明 VO 对象的设计原则，并简述 Service 层组装多表数据的两种方式及各自的优缺点。

参考答案：

  • VO 设计原则：
    1. 按接口设计，不按表设计——一个接口一个 VO，不通吃；
    2. 不复用实体类——VO 独立定义，避免暴露实体所有字段；
    3. 不含敏感字段——密码、手机号等不出现或脱敏；
    4. 字段命名面向前端——如 taskTitle 而非 title；
    5. 嵌套结构清晰——一对多用 List<子VO>，一对一用子 VO 对象。
  • Service 组装两种方式：
    • 方式 A：Mapper 直接返回 VO。JOIN SQL + ResultMap 嵌套映射，Mapper 一次查询直接返回组装好的 VO。优点：一次 SQL，性能最优。缺点：ResultMap 配置复杂，SQL 与映射耦合。
    • 方式 B：Service 层二次组装。先分别查多表（单表查询），在 Service 中用 BeanUtils 或手动 set 拼装 VO。优点：逻辑清晰，易维护。缺点：多次 SQL，需注意 N+1（应用批量查询优化）。
  • 推荐：关联层级少时优先方式 A（一次 JOIN）；关联层级多或需复杂业务逻辑时用方式 B + 批量查询。

评分标准（满分 12 分）：

  • VO 设计原则（至少答出 4 点）：4 分
  • 方式 A 描述及优缺点：3 分
  • 方式 B 描述及优缺点：3 分
  • 推荐场景说明：2 分

<?xml version="1.0" encoding="UTF-8" ?>
<!DOCTYPE mapper PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
        "http://mybatis.org/dtd/mybatis-3-mapper.dtd">
<mapper namespace="com.ctts.mapper.TaskMapper">

    <resultMap id="taskWithSubmissionMap" type="com.ctts.vo.TaskWithSubmissionVO">
        <id column="task_id" property="taskId"/>
        <result column="task_title" property="taskTitle"/>
        <result column="task_description" property="taskDescription"/>
        <result column="task_project_id" property="projectId"/>
        <result column="task_create_time" property="createTime"/>

        <collection property="submissions" ofType="com.ctts.vo.SubmissionDetailVO">
            <id column="submission_id" property="submissionId"/>
            <result column="submission_content" property="content"/>
            <result column="submission_submit_time" property="submitTime"/>

                <id column="user_id" property="userId"/>
                <result column="user_username" property="username"/>
                <result column="user_real_name" property="realName"/>
            </association>
        </collection>
    </resultMap>

    <select id="selectTasksWithSubmissionsByProjectId" resultMap="taskWithSubmissionMap">
        SELECT
            t.id           AS task_id,
            t.title        AS task_title,
            t.description  AS task_description,
            t.project_id   AS task_project_id,
            t.create_time  AS task_create_time,
            ts.id          AS submission_id,
            ts.content     AS submission_content,
            ts.submit_time AS submission_submit_time,
            u.id           AS user_id,
            u.username     AS user_username,
            u.real_name    AS user_real_name
        FROM task t
        LEFT JOIN task_submission ts ON t.id = ts.task_id
        LEFT JOIN sys_user u         ON ts.user_id = u.id
        WHERE t.project_id = #{projectId}
        ORDER BY t.create_time ASC, ts.submit_time DESC
    </select>

3. XML SQL + ResultMap

<?xml version="1.0" encoding="UTF-8" ?>
<!DOCTYPE mapper PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
        "http://mybatis.org/dtd/mybatis-3-mapper.dtd">
<mapper namespace="com.ctts.mapper.TaskSubmissionMapper">

    <!-- 嵌套映射：提交 → 任务（一对一） → 项目（一对一） -->
    <resultMap id="studentSubmissionMap" type="com.ctts.vo.StudentSubmissionVO">
        <id column="submission_id" property="submissionId"/>
        <result column="submission_content" property="content"/>
        <result column="submission_submit_time" property="submitTime"/>

        <!-- 一对一：提交 → 任务 -->
        <association property="task" javaType="com.ctts.vo.TaskSimpleVO">
            <id column="task_id" property="taskId"/>
            <result column="task_title" property="taskTitle"/>
            <result column="task_description" property="taskDescription"/>

            <!-- 一对一嵌套：任务 → 项目 -->
            <association property="project" javaType="com.ctts.vo.ProjectSimpleVO">
                <id column="project_id" property="projectId"/>
                <result column="project_name" property="projectName"/>
                <result column="project_create_time" property="createTime"/>
            </association>
        </association>
    </resultMap>

    <select id="selectSubmissionsWithTaskByUserId" resultMap="studentSubmissionMap">
        SELECT
            ts.id           AS submission_id,
            ts.content      AS submission_content,
            ts.submit_time  AS submission_submit_time,
            t.id            AS task_id,
            t.title         AS task_title,
            t.description   AS task_description,
            p.id            AS project_id,
            p.name          AS project_name,
            p.create_time   AS project_create_time
        FROM task_submission ts
        INNER JOIN task t             ON ts.task_id = t.id
        INNER JOIN training_project p ON t.project_id = p.id
        WHERE ts.user_id = #{userId}
        ORDER BY ts.submit_time DESC
    </select>

</mapper>

6. 避免 N+1 问题的说明： 本接口通过"JOIN 一次查询 + ResultMap 嵌套映射"避免 N+1 问题。SQL 一次 LEFT/INNER JOIN 三表（task_submission + task + training_project）获取所有数据，MyBatis ResultMap 通过嵌套 <association> 将扁平结果集映射为嵌套对象（提交→任务→项目）。整个接口只执行 1 次 SQL，避免了循环内调用 Mapper 产生的 N+1 问题。相比"先查提交列表，再循环查任务、循环查项目"的 N+1 写法（1 + N + N 次 SQL），性能显著提升。
