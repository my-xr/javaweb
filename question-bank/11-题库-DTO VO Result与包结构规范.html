一、单项选择题（30题，每题2分，共60分）

11-单选-01（★）

关于PO（Persistent Object），下列说法正确的是： A. PO必须实现Serializable接口才能入库 B. PO是持久化对象，对应数据库中的一条记录 C. PO只能用于接收前端请求参数 D. PO和VO是同一个概念

答案：B 解析：PO（Persistent Object）持久化对象，对应数据库中的一条记录，强调持久化语义。在MyBatis-Plus中Entity类充当PO角色。PO不一定要实现Serializable（除非需要缓存/序列化），也不是接收请求参数（那是DTO），更不等同于VO。

11-单选-02（★）

在Spring Boot + MyBatis-Plus项目中，以下哪个类通常充当PO的角色？ A. ProjectController B. ProjectDTO C. ProjectVO D. TrainingProject（Entity）

答案：D 解析：Entity类对应数据库表，在MyBatis-Plus中由BaseMapper操作，实际充当PO（持久化对象）角色。Controller是表现层，DTO是入参，VO是出参，都不充当PO。

11-单选-03（★）

DTO的主要职责是： A. 对应数据库表结构 B. 接收请求参数并在层间传输数据 C. 返回给前端展示的数据 D. 处理业务逻辑

答案：B 解析：DTO（Data Transfer Object）数据传输对象，主要用于接收前端请求参数，以及服务层之间传递数据。A是Entity的职责，C是VO的职责，D是Service的职责。

11-单选-04（★）

VO（View Object）的主要用途是： A. 接收前端请求参数 B. 对应数据库表 C. 返回给前端展示的数据，可脱敏和聚合 D. 承载业务逻辑

答案：C 解析：VO（View Object）视图对象，用于返回给前端展示，可聚合多表字段、脱敏敏感字段（如隐藏password）。A是DTO，B是Entity，D是Service。

11-单选-05（★★）

下列哪种场景最适合使用VO而非直接返回Entity？ A. 列表查询返回所有字段 B. 返回的数据包含password等敏感字段 C. 简单的单表查询 D. 内部服务间调用

答案：B 解析：当返回数据包含敏感字段（如password、deleted）时，必须用VO裁剪脱敏，避免泄露。A、C场景简单时可返回Entity（虽然不推荐），D场景多用DTO。

11-单选-06（★）

统一响应Result中，泛型T的作用是： A. 限制code的类型 B. 表示data字段的具体类型 C. 限制message的长度 D. 表示HTTP方法类型

答案：B 解析：Result中T是data字段的类型，如Result表示data是ProjectVO类型。这样既保证编译期类型安全，又便于Knife4j生成准确文档。

11-单选-07（★）

Result的静态方法ok()返回的类型是： A. Result B. Result C. T D. void

答案：B 解析：ok()定义为public static <T> Result<T> ok()，返回Result。注意静态方法需自带泛型声明<T>，否则会丢失类型信息。

11-单选-08（★★）

以下Result的fail方法定义，正确的是： A. public static Result fail(int code, String msg) B. public static <T> Result<T> fail(int code, String msg) C. public <T> Result<T> fail(int code, String msg) D. public static Result<T> fail(int code, String msg)

答案：B 解析：静态方法需要自带泛型声明<T>放在static之后、返回类型之前，即public static <T> Result<T> fail(...)。A丢失泛型，C不是静态方法，D缺少方法级泛型声明会编译报错。

11-单选-09（★）

Spring的BeanUtils.copyProperties方法的参数顺序是： A. (target, source) B. (source, target) C. (key, value) D. (targetClass, sourceClass)

答案：B 解析：Spring的BeanUtils.copyProperties(Object source, Object target)是source在前、target在后。这是高频易错点，Apache的BeanUtils则相反。

11-单选-10（★★）

关于Spring BeanUtils.copyProperties，下列说法错误的是： A. 基于反射实现，运行期执行 B. 按属性名和类型匹配进行拷贝 C. 能自动将LocalDateTime转为String D. 属性名不一致的字段不会被拷贝

答案：C 解析：BeanUtils不会自动做类型转换，LocalDateTime和String类型不一致时该字段会被跳过，不会自动转换。A、B、D均正确。

11-单选-11（★★）

MapStruct相比BeanUtils的主要优势是： A. 使用更简单，无需配置 B. 基于编译期生成代码，性能接近手写 C. 不需要引入任何依赖 D. 支持所有Java版本

答案：B 解析：MapStruct在编译期（maven compile阶段）生成转换实现类，内部是纯new+setter代码，无反射，性能接近手写。A错误（需配annotation processor），C错误（需引入依赖），D错误（需Java 8+）。

11-单选-12（★）

MapStruct的@Mapper注解中，componentModel="spring"的作用是： A. 标识这是一个Spring配置类 B. 让生成的实现类成为Spring Bean，可被@Autowired注入 C. 启用Spring事务管理 D. 指定Spring Boot版本

答案：B 解析：@Mapper(componentModel = "spring")让MapStruct生成的XxxConverterImpl类上加@Component注解，从而可被Spring容器管理，通过@Autowired注入使用。

11-单选-13（★）

CTTS项目的标准包结构中，Controller类应放在： A. com.ctts.entity B. com.ctts.controller C. com.ctts.service D. com.ctts.dto

答案：B 解析：Controller是表现层，放在com.ctts.controller包下。entity放实体，service放业务接口，dto放数据传输对象。

11-单选-14（★）

关于service和serviceImpl的分离，下列说法正确的是： A. service接口和impl实现必须放在同一个包 B. service放接口定义，service/impl放实现类，体现分层解耦 C. 小项目可以不写service接口，直接写实现类 D. service接口主要是为了减少代码量

答案：B 解析：阿里规范要求service层先定义接口再实现，接口放service包，实现放service/impl子包。这样Controller依赖接口而非实现，便于解耦、替换实现、AOP代理。C、D说法错误。

11-单选-15（★）

Spring Boot项目的启动类应放在： A. com.ctts.controller包下 B. 任意包都可以 C. com.ctts根包下 D. resource目录下

答案：C 解析：启动类应放在根包com.ctts下，这样@SpringBootApplication的默认扫描范围能覆盖所有子包（controller/service/mapper等）。放子包会导致其他包扫描不到。

11-单选-16（★）

Lombok的@Data注解不包含以下哪个： A. @Getter B. @Setter C. @NoArgsConstructor D. @ToString

答案：C 解析：@Data = @Getter + @Setter + @ToString + @EqualsAndHashCode + @RequiredArgsConstructor。它包含的是@RequiredArgsConstructor（仅final字段构造），不包含@NoArgsConstructor（无参构造）。需要无参构造要单独加。

11-单选-17（★）

Lombok的@Builder注解单独使用可能导致的问题是： A. 编译报错找不到getter B. 类失去无参构造，影响JSON反序列化 C. 自动生成太多构造器 D. 与@Data冲突

答案：B 解析：@Builder会生成全参私有构造器，导致类没有无参构造。Jackson反序列化JSON时需要无参构造，会报错。解决方法是同时加@NoArgsConstructor和@AllArgsConstructor。

11-单选-18（★）

开启Lombok链式setter（如user.setName("x").setAge(20)）的注解是： A. @Data B. @Builder C. @Accessors(chain = true) D. @Slf4j

答案：C 解析：@Accessors(chain = true)让setter返回this而非void，从而支持链式调用。@Data生成的setter默认返回void。

11-单选-19（★★）

在IDEA中使用Lombok，除了引入依赖，还必须： A. 安装Lombok插件并开启Annotation Processing B. 重启电脑 C. 升级JDK到21 D. 关闭防火墙

答案：A 解析：IDEA需安装Lombok插件（2020.3+已内置）并在Settings → Build → Compiler → Annotation Processors中开启Enable annotation processing，否则编译报"找不到符号"。

11-单选-20（★）

Result类中code字段表示： A. HTTP状态码 B. 业务状态码，200表示成功 C. 接口耗时毫秒数 D. 数据条数

答案：B 解析：Result中的code是业务状态码，约定200成功、4xx客户端错误、5xx服务端错误、5xxxx业务错误。它与HTTP状态码独立，HTTP层通常恒返回200。

11-单选-21（★★）

下列关于HTTP状态码与业务code的说法，正确的是： A. 业务错误时应返回HTTP 500 B. HTTP状态码和业务code应保持一致 C. 业务错误时HTTP仍返回200，通过Result.code区分 D. 前端只需判断HTTP状态码

答案：C 解析：统一响应规范下，HTTP层恒返回200（除非网络层错误），业务成败通过Result.code区分。这样前端只需解析JSON的code字段，逻辑统一。A会导致前端误判为网络错误。

11-单选-22（★）

ProjectDTO中给projectName字段添加"不能为空"校验的注解是： A. @NotNull B. @NotBlank C. @NotEmpty D. @Size

答案：B 解析：@NotBlank用于String类型，校验非null且去除首尾空格后长度>0。@NotNull只校验非null（空字符串能过），@NotEmpty校验非null且非空（但允许纯空格），@Size校验长度。字符串用@NotBlank最严格。

11-单选-23（★）

在Controller方法参数上启用DTO校验，需要加的注解是： A. @Valid B. @Validated C. @RequestBody D. @Param

答案：A 解析：在@RequestBody参数前加@Valid（或@Validated）才会触发JSR-303校验。@RequestBody只负责反序列化，不做校验。@Validated是Spring扩展，支持分组校验。

11-单选-24（★★）

CTTS项目中，全局异常处理类GlobalExceptionHandler通常放在： A. com.ctts.controller B. com.ctts.exception C. com.ctts.config D. com.ctts.utils

答案：B 解析：自定义异常类、业务异常类、全局异常处理器统一放在com.ctts.exception包。config放配置类，utils放工具类，controller放控制器。

11-单选-25（★）

Lombok的@Slf4j注解的作用是： A. 生成toString方法 B. 注入一个名为log的Logger实例 C. 配置日志级别 D. 输出SQL日志

答案：B 解析：@Slf4j在类中注入private static final Logger log = LoggerFactory.getLogger(Xxx.class);，直接用log.info()/log.error()即可，无需手写Logger声明。

11-单选-26（★★）

关于Entity、DTO、VO的命名约定，下列最规范的是： A. User、UserDTO、UserVO B. UserEntity、UserDto、UserView C. SysUser、SysUserDTO、SysUserVO D. user、userDto、userVo

答案：C 解析：命名应体现业务含义+角色后缀。SysUser（Entity，对应sys_user表）、SysUserDTO（入参）、SysUserVO（出参）最规范。A的User不够业务化，B后缀不统一，D类名首字母小写违反Java规范。

11-单选-27（★）

Result类实现Serializable接口的主要原因是： A. 必须实现才能被Spring管理 B. 便于分布式/缓存场景下的序列化 C. 提升性能 D. Knife4j要求

答案：B 解析：Serializable是标识接口，便于在分布式（RPC）、缓存（Redis）、会话持久化等场景序列化。非必须，但企业项目通常加上以备扩展。

11-单选-28（★★）

下列哪种情况会导致BeanUtils.copyProperties拷贝失败（字段为null）？ A. source和target属性名相同且类型相同 B. source字段为private C. source和target属性名相同但类型不同（如LocalDateTime vs String） D. target有无参构造

答案：C 解析：BeanUtils按属性名+类型匹配，类型不一致时（如LocalDateTime和String）会跳过该字段不拷贝。A是正常拷贝，B不影响（反射能访问private），D是必要条件不影响。

11-单选-29（★）

包名com.ctts.controller的命名风格是： A. 大驼峰 B. 小驼峰 C. 全小写 D. 下划线

答案：C 解析：Java包名约定全小写，避免与类名/关键字冲突。com.ctts.controller全小写符合规范。大驼峰用于类名，小驼峰用于变量/方法名。

11-单选-30（★★）

项目中Result和ResultCode通常放在： A. com.ctts.controller B. com.ctts.common C. com.ctts.entity D. com.ctts.dto

答案：B 解析：Result和ResultCode是全项目共用的基础设施类，放在com.ctts.common包。common包专门放跨层共享的公共类。

二、多项选择题（10题，每题2分，共20分；少选得1分，多选/错选不得分）

11-多选-01（★）

下列属于"数据载体"类的有： A. Entity B. DTO C. VO D. Controller E. Service

答案：ABC 解析：Entity、DTO、VO都是承载数据的对象。Controller是控制器，Service是业务逻辑层，都不是数据载体。

11-多选-02（★）

统一响应Result的标准三字段是： A. code B. message C. data D. timestamp E. traceId

答案：ABC 解析：标准Result包含code（业务码）、message（提示信息）、data（数据）三字段。timestamp和traceId是可选扩展字段，非标准三字段。

11-多选-03（★★）

Lombok的@Data注解包含以下哪些注解的功能？ A. @Getter B. @Setter C. @ToString D. @EqualsAndHashCode E. @RequiredArgsConstructor F. @NoArgsConstructor

答案：ABCDE 解析：@Data = @Getter + @Setter + @ToString + @EqualsAndHashCode + @RequiredArgsConstructor。不包含@NoArgsConstructor，需单独加。

11-多选-04（★★）

关于Spring BeanUtils.copyProperties的说法，正确的有： A. source在前，target在后 B. 基于反射实现，有性能开销 C. 按属性名+类型匹配 D. 类型不一致会自动转换 E. 嵌套对象是浅拷贝（引用共享）

答案：ABCE 解析：A、B、C、E均正确。D错误，BeanUtils不会自动转换类型，类型不一致时跳过该字段。

11-多选-05（★★）

下列哪些是MapStruct相比BeanUtils的优势？ A. 编译期生成代码，性能高 B. 类型安全，编译期就能发现错误 C. 支持字段映射自定义（@Mapping） D. 无需引入任何依赖 E. 生成代码可调试查看

答案：ABCE 解析：A、B、C、E都是MapStruct优势。D错误，MapStruct需引入mapstruct和mapstruct-processor依赖。

11-多选-06（★）

CTTS项目的标准包结构包含以下哪些包？ A. controller B. service C. mapper D. entity E. dto F. vo G. config H. exception

答案：ABCDEFGH 解析：CTTS标准包结构包含controller、service（含impl）、mapper、entity、dto、vo、common、config、utils、exception，八个均正确。

11-多选-07（★★）

关于service接口与serviceImpl实现分离的好处，正确的有： A. Controller依赖接口而非实现，降低耦合 B. 便于Spring AOP基于接口做动态代理 C. 便于单元测试时Mock实现 D. 减少代码总量 E. 符合阿里Java开发规范

答案：ABCE 解析：A解耦、B利于AOP代理、C便于Mock测试、E符合阿里规范。D错误，分离反而增加代码量（多一个接口文件），但换来可维护性。

11-多选-08（★★）

下列哪些注解可用于DTO的字段校验？ A. @NotBlank B. @NotNull C. @NotEmpty D. @Size E. @JsonFormat F. @Schema

答案：ABCD 解析：A、B、C、D都是JSR-303校验注解。@JsonFormat是Jackson的日期格式化注解，@Schema是Knife4j/SpringDoc的文档注解，都不做校验。

11-多选-09（★★）

使用Lombok时，在IDEA中需要做哪些配置？ A. 安装Lombok插件（2020.3+已内置） B. 开启Annotation Processing C. 引入lombok的Maven依赖 D. 升级JDK到17 E. 配置lombok.config文件

答案：ABC 解析：A（插件）、B（注解处理开关）、C（依赖）是必需三件套。D非必需（Lombok支持JDK 8+），E非必需（仅高级配置时才用lombok.config）。

11-多选-10（★★★）

关于Result的设计，下列做法合理的有： A. code用业务码，HTTP恒返回200 B. 用ResultCode枚举管理错误码 C. 静态方法ok()/fail()作为统一入口 D. data字段类型用泛型T E. 把业务逻辑写在Result类中 F. Result做成单例

答案：ABCD 解析：A、B、C、D都是标准设计。E错误，Result只做数据载体不含业务逻辑。F错误，Result有状态（data每次不同）不能单例。

11-论述-01（8分，★★）

请详细说明PO、Entity、DTO、VO四类对象的定义、职责与区别，并各举一个CTTS项目中的具体例子。

评分标准：

  • 四类对象定义准确（每类1分，共4分）
  • 职责区别说明清晰（2分）
  • CTTS举例恰当（2分）

参考答案：

  • PO（Persistent Object）持久化对象：对应数据库中的一条记录，强调持久化语义。在MyBatis-Plus中Entity充当PO。例：TrainingProject被ProjectMapper操作时即为PO。
  • Entity实体类：对应数据库表结构，字段与表列一一映射。例：TrainingProject对应training_project表，含id/projectName/creatorId等字段。
  • DTO数据传输对象：接收前端请求参数，带JSR-303校验注解，只暴露前端应填字段。例：ProjectDTO接收新增项目请求，含projectName(@NotBlank)/startTime(@NotNull)等，不含id/createTime。
  • VO视图对象：返回给前端展示的数据，可脱敏敏感字段、聚合多表字段。例：ProjectVO返回项目列表，含creatorName（聚合自sys_user表），不含deleted字段。

区别：Entity对应表结构（全字段），DTO管"进"（裁剪+校验），VO管"出"（脱敏+聚合），PO是Entity在持久化层的角色概念。

11-论述-02（8分，★★）

请说明为什么Controller不应直接返回Entity，而要用VO包装并配合Result统一响应？请至少列出4条理由。

评分标准：

  • 每条理由2分，列满4条得8分（理由合理即可）
  • 理由不充分或重复酌情扣分

参考答案：

  1. 敏感字段泄露风险：Entity含password、deleted等敏感字段，直接返回会暴露给前端。如SysUser的password字段必须用VO裁剪。
  2. 返回格式不统一：直接返回Entity/List/String导致前端解析逻辑分散，每个接口都要单独处理。用Result统一外壳，前端拦截器只判code===200。
  3. 无法聚合多表字段：Entity对应单表，但前端常需展示关联数据（如项目的创建人姓名），VO可聚合多表查询结果。
  4. 数据库结构变更耦合前端：Entity字段随表结构变化，直接返回会导致前端接口契约不稳定。VO作为中间层解耦。
  5. 错误信息标准化：业务出错时直接抛异常前端无法解析，Result.fail(code,msg)统一错误格式，便于前端友好提示。
  6. 文档不清晰：Knife4j直接展示Entity会暴露所有字段，VO+Result让文档准确反映接口契约。

11-论述-03（8分，★★）

请比较Spring BeanUtils.copyProperties与MapStruct两种对象转换方案的原理、性能、适用场景。

评分标准：

  • 原理对比（3分）
  • 性能对比（2分）
  • 适用场景（3分）

参考答案： 原理：

  • Spring BeanUtils：运行期通过反射获取source/target属性，按属性名+类型匹配调用setter。无代码生成。
  • MapStruct：编译期（maven compile）读取@Mapper接口，生成XxxImpl.java纯setter代码，运行期无反射。

性能（10万次转换参考）：

  • 手写setter ~5ms（基准）
  • MapStruct ~6ms（接近手写）
  • Spring BeanUtils ~300ms（反射开销）
  • Apache BeanUtils ~3000ms（最差）

适用场景：

  • BeanUtils：小项目、转换少、字段简单、快速开发。优点是零配置、灵活；缺点是性能差、类型不安全（运行期才发现问题）。
  • MapStruct：大项目、转换频繁、字段复杂、追求性能与类型安全。优点是性能好、编译期检查、支持@Mapping自定义；缺点是需配annotation processor、学习成本略高。

结论：CTTS这种教学项目用BeanUtils足够；企业级生产项目推荐MapStruct。

11-论述-04（8分，★★★）

请画出（或文字描述）CTTS项目的标准包结构树，并说明service为什么要分接口和impl。

评分标准：

  • 包结构树完整准确（4分，每漏1个核心包扣0.5分）
  • service分离理由（4分，每条1分）

参考答案： 包结构树：

com.ctts
├── CttsApplication.java
├── controller          // 表现层
├── service             // 业务接口
│   └── impl            // 业务实现
├── mapper              // 持久层
├── entity              // 实体（PO）
├── dto                 // 请求参数
├── vo                  // 响应数据
├── common              // 公共类（Result/ResultCode）
├── config              // 配置类
├── utils               // 工具类
└── exception           // 异常处理

service分接口和impl的理由：

  1. 解耦：Controller依赖ProjectService接口而非ProjectServiceImpl实现，替换实现类不影响Controller。
  2. AOP代理：Spring基于接口做JDK动态代理更自然，事务@Transactionall等AOP功能更顺畅。
  3. 便于Mock测试：单元测试时可Mock接口，不依赖具体实现和数据库。
  4. 规范要求：阿里Java开发手册明确要求"service层必须先定义接口再实现"。
  5. 多实现扩展：未来若有多套实现（如不同租户不同逻辑），接口统一规范。
