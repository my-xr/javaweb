一、单项选择题（30题）

16-D-01 ★

JWT 的全称是（ ） A. Java Web Token B. JSON Web Token C. JavaScript Web Token D. JSON Web Transfer

答案：B 解析：JWT 全称 JSON Web Token，是一种基于 JSON 的开放标准（RFC 7519），用于在网络应用各方之间以紧凑、自包含的方式安全传递声明。

16-D-02 ★

JWT 由几段组成，用什么符号连接？（ ） A. 两段，用 : 连接 B. 三段，用 . 连接 C. 三段，用 - 连接 D. 四段，用 . 连接

答案：B 解析：JWT 由 Header、Payload、Signature 三段组成，每段 Base64URL 编码后用 . 连接，形如 xxxxx.yyyyy.zzzzz。

16-D-03 ★

JWT 三段中，描述令牌类型与签名算法的是哪一段？（ ） A. Header B. Payload C. Signature D. Claim

答案：A 解析：Header 头部包含 alg（签名算法，如 HS256）和 typ（类型，固定为 JWT）两个字段。

16-D-04 ★

JWT 的 Payload 中通常不包含以下哪个字段？（ ） A. userId B. username C. role D. password

答案：D 解析：Payload 仅做 Base64URL 编码，任何人可解码读取，绝不能放密码等敏感信息。通常放 userId、username、role、exp、iat 等声明。

16-D-05 ★

JWT 默认推荐的签名算法是（ ） A. MD5 B. SHA-256 C. HS256 D. RS256

答案：C 解析：HS256（HMAC-SHA-256）是对称签名算法，签发与校验用同一密钥，是最常用的默认算法。MD5 已不安全；SHA-256 是哈希函数不是签名算法；RS256 是非对称算法，适用于微服务场景。

16-D-06 ★★

关于 JWT 三段编码方式，下列说法正确的是（ ） A. Header 和 Payload 都加密，Signature 不加密 B. Header 加密，Payload 不加密，Signature 加密 C. Header 和 Payload 都是 Base64URL 编码（可逆），Signature 是 HMAC-SHA256（需密钥） D. 三段都加密

答案：C 解析：Header 和 Payload 用 Base64URL 编码（可逆，任何人可解码），不是加密；Signature 是用密钥计算的 HMAC-SHA256，没有密钥无法伪造。这是常见误区——Payload 不是加密的。

16-D-07 ★★

JWT 使用 Base64URL 编码而非标准 Base64，主要原因是（ ） A. Base64URL 编码更短 B. Base64URL 编码更安全 C. 标准 Base64 中的 +、/、= 在 URL/Header 中有特殊含义 D. Base64URL 编码速度更快

答案：C 解析：标准 Base64 中 + 可能被解析为空格、/ 是路径分隔符、= 是参数分隔符，在 URL/HTTP Header 中不安全。Base64URL 用 - 替换 +、_ 替换 /、去掉 = 填充。

16-D-08 ★★

HS256 签名算法的"对称"体现在（ ） A. 加密与解密用同一密钥 B. 签发与验证用同一密钥 C. Token 字符串左右对称 D. 算法可逆

答案：B 解析：HS256 是 HMAC-SHA-256，签发 Token 和验证 Token 使用同一个密钥，故称"对称"。与之相对，RS256 是非对称，私钥签发、公钥验证。

16-D-09 ★★

JWT 能防止 Token 被篡改的根本原因是（ ） A. Payload 是加密的 B. Header 是加密的 C. Signature 用密钥计算，篡改者无法生成正确签名 D. Token 字符串很长

答案：C 解析：Signature = HMAC-SHA256(base64(header) + "." + base64(payload), secret)。攻击者篡改 Payload 后，由于没有密钥无法生成匹配的 Signature，服务端验签失败。Payload 本身不加密。

16-D-10 ★

下列哪个不是 JWT 的标准注册声明（registered claims）？（ ） A. iss（签发者） B. exp（过期时间） C. sub（主题） D. userId（用户ID）

答案：D 解析：标准注册声明包括 iss、sub、aud、exp、nbf、iat、jti。userId 是私有声明（private claim），由业务自定义。

16-D-11 ★

jjwt 0.12.x 中，生成 Token 的入口 API 是（ ） A. Jwts.create() B. Jwts.builder() C. Jwts.generate() D. Jwts.token()

答案：B 解析：jjwt 0.12.x 用 Jwts.builder() 返回 JwtBuilder，链式调用 .claims().signWith().compact() 生成 Token。

16-D-12 ★

jjwt 0.12.x 中，解析 Token 的正确写法是（ ） A. Jwts.parser().setSigningKey(key).parseClaimsJws(token) B. Jwts.parserBuilder().verifyWith(key).build().parseSignedClaims(token) C. Jwts.parser().verifyWith(key).build().parseSignedClaims(token) D. Jwts.parse(token).verifyWith(key)

答案：C 解析：0.12.x 新 API：Jwts.parser().verifyWith(key).build().parseSignedClaims(token)。A 是 0.11.x 旧 API（setSigningKey/parseClaimsJws）。B 中 parserBuilder() 已废弃。

16-D-13 ★★

jjwt 依赖拆成三个 artifact，其中编译期需要、运行期不需要的是（ ） A. jjwt-api B. jjwt-impl C. jjwt-jackson D. 三个都编译期需要

答案：A 解析：jjwt-api 是 API 接口，编译期需要，scope 为默认 compile；jjwt-impl 与 jjwt-jackson 是运行期实现，scope 设为 runtime，不参与编译。

16-D-14 ★★

HS256 算法要求密钥的最短长度是（ ） A. 16 字节（128 位） B. 24 字节（192 位） C. 32 字节（256 位） D. 64 字节（512 位）

答案：C 解析：HS256 = HMAC-SHA-256，要求密钥至少 256 位 = 32 字节。若密钥过短，jjwt 启动时会抛 WeakKeyException。

16-D-15 ★★

jjwt 0.12.x 中，获取解析后 Claims 的方法是（ ） A. jws.getBody() B. jws.getPayload() C. jws.getClaims() D. jws.getData()

答案：B 解析：0.12.x 用 parseSignedClaims(token).getPayload() 获取 Claims。0.11.x 旧 API 是 getBody()，已废弃。

16-D-16 ★

HandlerInterceptor 接口中，在 Controller 方法执行前调用的方法是（ ） A. preHandle B. postHandle C. afterCompletion D. beforeHandle

答案：A 解析：preHandle 在 Controller 方法执行前调用，返回 true 放行、false 拦截。postHandle 在 Controller 返回后、视图渲染前调用；afterCompletion 在请求结束时调用。

16-D-17 ★★

HandlerInterceptor.preHandle 的返回值含义是（ ） A. 返回 true 表示请求处理成功 B. 返回 true 表示放行继续执行，false 表示拦截 C. 返回 false 表示请求失败 D. 返回值无意义

答案：B 解析：preHandle 返回 true 放行请求到 Controller，返回 false 拦截请求不再继续。返回 false 时需自己写响应，否则客户端收空响应。

16-D-18 ★★

下列哪个不是 HandlerInterceptor 的方法？（ ） A. preHandle B. postHandle C. afterCompletion D. beforeCompletion

答案：D 解析：HandlerInterceptor 接口有三个方法：preHandle、postHandle、afterCompletion。没有 beforeCompletion。

16-D-19 ★★

HTTP 请求中携带 JWT Token 的 Header 名称通常是（ ） A. Token B. Auth C. Authorization D. X-Token

答案：C 解析：标准做法是 Authorization: Bearer <token>。Authorization 是 HTTP 标准认证头（RFC 7235），Bearer 表示持有者方案。

16-D-20 ★

Authorization Header 中，Bearer Token 的正确格式是（ ） A. Bearer<token>（无空格） B. Bearer <token>（一个空格） C. bearer <token>（小写） D. token=<token>

答案：B 解析：格式为 Bearer <token>，"Bearer" 与 token 之间用一个空格分隔。服务端用 substring(7) 剥离 "Bearer " 前缀（7 个字符）。注意大小写敏感，应为 "Bearer"。

16-D-21 ★★

HandlerInterceptor.afterCompletion 的典型用途是（ ） A. 修改 Controller 返回值 B. 渲染视图 C. 清理资源（如 ThreadLocal.remove） D. 校验 Token

答案：C 解析：afterCompletion 在请求结束时（无论是否抛异常）调用，适合清理资源。最典型用途是 ThreadLocal.remove()，防止线程池复用导致用户串号。

16-D-22 ★★

Spring MVC 中，注册拦截器应实现哪个接口？（ ） A. WebMvcConfigurer B. WebSecurityConfigurer C. ServletContextInitializer D. FilterRegistrationBean

答案：A 解析：实现 WebMvcConfigurer 的 addInterceptors(InterceptorRegistry registry) 方法注册拦截器。配置类需加 @Configuration。

16-D-23 ★★

WebMvcConfig.addInterceptors 中，addPathPatterns("/**") 表示（ ） A. 拦截根路径 B. 拦截所有路径 C. 拦截单级路径 D. 不拦截任何路径

答案：B 解析：/** 是 Ant 风格通配符，匹配任意多级路径。/* 只匹配单级。

16-D-24 ★★

下列路径在登录拦截器中通常不需要放行的是（ ） A. /api/auth/login B. /api/auth/register C. /doc.html D. /api/users（获取用户列表）

答案：D 解析：登录、注册、接口文档（Knife4j/Swagger）等路径需放行。/api/users 是受保护接口，必须校验 Token。

16-D-25 ★★

关于 addPathPatterns 与 excludePathPatterns 的优先级，正确的是（ ） A. addPathPatterns 优先 B. excludePathPatterns 优先 C. 按配置顺序执行 D. 随机

答案：B 解析：excludePathPatterns 优先于 addPathPatterns。即先匹配排除列表，命中则不拦截，无论 addPathPatterns 是否包含。

16-D-26 ★★★

关于 ThreadLocal 在拦截器中的使用，下列说法错误的是（ ） A. 在 preHandle 中 set 当前用户 B. 在 Controller 中可通过 get 取出当前用户 C. 在 afterCompletion 中应 remove 防止内存泄漏 D. ThreadLocal 会随请求结束自动清理，无需手动 remove

答案：D 解析：ThreadLocal 不会自动清理。Spring Boot 用 Tomcat 线程池，线程被复用，若不 remove，下一个请求复用该线程时会读到上一个用户的数据，导致"用户串号"事故。必须在 afterCompletion 手动 remove。

16-D-27 ★★

JWT Token 过期时，jjwt 抛出的异常是（ ） A. JwtException B. ExpiredJwtException C. SignatureException D. IllegalArgumentException

答案：B 解析：ExpiredJwtException 是 JwtException 的子类，专门表示 Token 过期。签名不匹配抛 SignatureException，Token 为空或格式错抛 IllegalArgumentException。

16-D-28 ★★

@Configuration 注解的配置类与 @Component 的关键区别是（ ） A. @Configuration 不能用于 WebMvcConfig B. @Configuration 用 CGLIB 代理，保证 @Bean 方法间依赖调用走容器单例 C. @Component 才能用 CGLIB 代理 D. 两者完全等价

答案：B 解析：@Configuration 是全模式配置类，Spring 用 CGLIB 代理，@Bean 方法间相互调用时返回容器单例。WebMvcConfigurer 实现类推荐用 @Configuration。

16-D-29 ★★

在 LoginInterceptor.preHandle 中，handler 参数的实际类型通常是（ ） A. HttpServletRequest B. HandlerMethod C. Controller D. Method

答案：B 解析：handler 是 HandlerMethod 对象，封装了要执行的 Controller 方法。可用于读取方法注解（如 @RequireRole）。注意静态资源请求时 handler 可能是 ResourceHttpRequestHandler，需 instanceof 判断。

16-D-30 ★★★

关于 JWT 与 Session 认证的对比，下列说法错误的是（ ） A. JWT 是无状态的，服务端不存会话信息；Session 是有状态的，服务端存 Session B. JWT 适合分布式/微服务；Session 需解决跨服务共享问题 C. JWT 一旦签发无法主动吊销；Session 可随时销毁 D. JWT 比 Session 更安全，因为 Payload 是加密的

答案：D 解析：D 错误。JWT 的 Payload 仅 Base64 编码，不是加密，任何人可读。JWT 的安全性来自签名防篡改，而非加密。两者安全性各有取舍：JWT 难以主动吊销，Session 需共享存储。

二、多项选择题（10题）

16-M-01 ★

下列属于 JWT 三段结构的有（ ） A. Header B. Payload C. Signature D. Cookie E. Session

答案：ABC 解析：JWT 由 Header（头部）、Payload（载荷）、Signature（签名）三段组成。Cookie 和 Session 不是 JWT 的组成部分。

16-M-02 ★★

JWT Payload 中常见的标准注册声明（registered claims）有（ ） A. iss（签发者） B. sub（主题） C. exp（过期时间） D. iat（签发时间） E. userId（用户ID）

答案：ABCD 解析：标准注册声明包括 iss、sub、aud、exp、nbf、iat、jti。userId 是私有声明，不是标准声明。

16-M-03 ★★

jjwt 0.12.x 的三个依赖 artifact 是（ ） A. jjwt-api B. jjwt-impl C. jjwt-jackson D. jjwt-core E. jjwt-impl-jackson

答案：ABC 解析：jjwt 0.12.x 拆为 jjwt-api（API 接口，编译期）、jjwt-impl（运行时实现）、jjwt-jackson（JSON 序列化）。后两者 scope 为 runtime。

16-M-04 ★★

HandlerInterceptor 接口的方法有（ ） A. preHandle B. postHandle C. afterCompletion D. beforeHandle E. afterHandle

答案：ABC 解析：HandlerInterceptor 接口有三个方法：preHandle（Controller 前）、postHandle（Controller 后视图前）、afterCompletion（请求结束）。默认实现都是空方法。

16-M-05 ★★

WebMvcConfig 中配置登录拦截器时，通常需要放行（excludePathPatterns）的路径有（ ） A. /api/auth/login B. /api/auth/register C. /doc.html D. /v3/api-docs/** E. /error

答案：ABCDE 解析：登录、注册本身不需 Token；Knife4j/Swagger 文档路径需放行（/doc.html、/v3/api-docs/**、/webjars/**）；/error 是 Spring Boot 错误转发路径，不放行会导致错误页 401。

16-M-06 ★★

关于 ThreadLocal 在登录拦截器中的使用，下列做法正确的有（ ） A. 在 preHandle 中 set 当前用户信息 B. 在 Controller 中通过 get 取出当前用户 C. 在 afterCompletion 中 remove D. 在 postHandle 中 remove E. 依赖 JVM 自动清理，无需手动 remove

答案：ABC 解析：preHandle 存入、Controller 取用、afterCompletion 移除是标准做法。afterCompletion 无论是否抛异常都执行，是清理的可靠位置。不能依赖 JVM 自动清理，否则线程池复用导致用户串号。

16-M-07 ★★

下列属于 JWT 相比 Session 认证优势的有（ ） A. 无状态，服务端不存会话信息，易于水平扩展 B. 自包含，Token 本身携带用户信息，减少数据库查询 C. 跨域支持好，适合前后端分离 D. 可主动吊销单个 Token E. 天然防 CSRF 攻击（不依赖 Cookie）

答案：ABCE 解析：JWT 无状态、自包含、跨域好、不依赖 Cookie 故不受 CSRF 攻击。D 是 JWT 的劣势——一旦签发难以主动吊销（需引入黑名单牺牲无状态性）。

16-M-08 ★★

LoginInterceptor.preHandle 中处理 Token 校验的步骤包括（ ） A. 从 Authorization Header 取值 B. 校验是否以 Bearer 开头并剥离前缀 C. 调用 JwtUtil.parseToken 解析校验 D. 将用户信息存入 CurrentUserContext E. 返回 true 放行或返回 false 并写 401 响应

答案：ABCDE 解析：完整流程：取 Header → 校验 Bearer 前缀 → 剥离得到纯 Token → 解析校验 → 存 ThreadLocal → 放行/拒绝。

16-M-09 ★★

CTTS 系统中，三角色（学生/教师/管理员）的权限矩阵正确的有（ ） A. 学生可查看自己的任务 B. 教师可发布任务 C. 管理员可创建用户 D. 学生可删除任意任务 E. 教师可创建用户

答案：ABC 解析：CTTS 中学生只能查看自己的任务，不能删除任意任务（D 错）；教师可发布任务但不能创建用户（E 错）；管理员可创建用户。遵循权限最小化原则。

16-M-10 ★★★

下列关于 JWT 安全的说法，正确的有（ ） A. 密钥不能硬编码在代码中，应放配置文件并使用环境变量覆盖 B. Payload 中不能放密码、身份证号等敏感信息 C. 应设置合理的过期时间，不宜过长 D. 生产环境应使用 HTTPS 防止 Token 被中间人窃听 E. JWT 的 Payload 是加密的，可以放心放敏感数据

答案：ABCD 解析：E 错误，JWT Payload 仅 Base64 编码不是加密，任何人可解码。密钥管理、Payload 内容、过期时间、HTTPS 传输都是 JWT 安全要点。

三、判断题（20题）

16-P-01 ★

JWT 的 Payload 是加密的，任何人无法读取其中的内容。

答案：错误 解析：Payload 仅做 Base64URL 编码，是可逆的，任何人都能解码读取。绝不能放敏感信息。JWT 的安全性来自 Signature 防篡改，而非 Payload 加密。

16-P-02 ★

JWT 由 Header、Payload、Signature 三段组成，用 . 连接。

答案：正确 解析：JWT 标准结构为 header.payload.signature，三段均 Base64URL 编码后用 . 连接。

16-P-03 ★

HS256 是一种非对称签名算法，签发用私钥，验证用公钥。

答案：错误 解析：HS256 是对称算法（HMAC-SHA-256），签发与验证使用同一密钥。RS256 才是非对称算法。

16-P-04 ★★

JWT 的 Header 和 Payload 都使用 Base64URL 编码，目的是保证在 URL/Header 中安全传输。

答案：正确 解析：Base64URL 用 - 替换 +、_ 替换 /、去掉 =，避免在 URL/HTTP Header 中被特殊字符干扰。

16-P-05 ★

jjwt 0.12.x 中，生成 Token 使用 Jwts.builder() 方法。

答案：正确 解析：Jwts.builder() 返回 JwtBuilder，链式调用 .claims().signWith(key).compact() 生成 Token。

16-P-06 ★★

jjwt 0.12.x 中，Jwts.parserBuilder() 是解析 Token 的推荐写法。

答案：错误 解析：0.12.x 中 parserBuilder() 已废弃，推荐用 Jwts.parser().verifyWith(key).build().parseSignedClaims(token)。

16-P-07 ★★

HS256 算法要求密钥至少 32 字节（256 位），否则会抛 WeakKeyException。

答案：正确 解析：HS256 = HMAC-SHA-256，密钥长度需 ≥ 256 位 = 32 字节。jjwt 会在启动时校验密钥长度。

16-P-08 ★

HandlerInterceptor.preHandle 返回 false 时，请求继续到达 Controller。

答案：错误 解析：返回 false 拦截请求，不会到达 Controller。返回 true 才放行。

16-P-09 ★★

HandlerInterceptor.afterCompletion 无论 Controller 是否抛异常都会执行。

答案：正确 解析：afterCompletion 在请求结束时调用，无论 Controller 是否抛异常。这是清理资源（如 ThreadLocal.remove）的可靠位置。

16-P-10 ★

HTTP 请求中携带 JWT 的 Header 名称是 Token。

答案：错误 解析：标准 Header 名称是 Authorization，值为 Bearer <token>。Token 不是标准名称。

16-P-11 ★★

Bearer 前缀与 token 之间不需要空格，直接拼接即可。

答案：错误 解析：Bearer 与 token 之间必须有一个空格，即 Bearer <token>。服务端用 substring(7) 剥离前 7 个字符 "Bearer "。

16-P-12 ★★

Spring MVC 拦截器在 DispatcherServlet 之前执行。

答案：错误 解析：Filter 在 DispatcherServlet 之前执行；HandlerInterceptor 在 DispatcherServlet 之后、Controller 之前执行。

16-P-13 ★★

WebMvcConfig 配置类应该加 @Configuration 注解，而不是 @Component。

答案：正确 解析：@Configuration 是全模式配置类，用 CGLIB 代理保证 @Bean 方法间依赖调用走容器单例。WebMvcConfigurer 实现类推荐用 @Configuration。

16-P-14 ★★

excludePathPatterns 优先于 addPathPatterns，即排除路径命中后不再拦截。

答案：正确 解析：Spring MVC 先匹配 excludePathPatterns，命中则跳过拦截器，无论 addPathPatterns 是否包含该路径。

16-P-15 ★★

ThreadLocal 会随请求结束自动清理，无需在拦截器中手动 remove。

答案：错误 解析：ThreadLocal 不会自动清理。Spring Boot 用 Tomcat 线程池，线程被复用，若不手动 remove，下一个请求复用该线程时会读到上一个用户的数据，导致用户串号。必须在 afterCompletion 手动清理。

16-P-16 ★★

JWT 一旦签发，在过期前一直有效，服务端难以主动吊销。

答案：正确 解析：JWT 是无状态的，服务端不存 Token 列表，无法主动吊销。若需吊销需引入黑名单（牺牲无状态性）或缩短过期时间。

16-P-17 ★★

LoginInterceptor 中 handler 参数一定是 HandlerMethod 类型，可直接强转。

答案：错误 解析：handler 不一定是 HandlerMethod，静态资源请求时可能是 ResourceHttpRequestHandler。强转前必须 instanceof 判断，否则 ClassCastException。

16-P-18 ★★

@RequireRole 注解放在 Controller 方法上，拦截器通过 HandlerMethod.getMethodAnnotation 读取。

答案：正确 解析：自定义注解可用于方法级或类级权限控制。拦截器在 preHandle 中通过 hm.getMethodAnnotation(RequireRole.class) 读取方法注解，类注解用 hm.getBeanType().getAnnotation()。

16-P-19 ★★

多个拦截器配置时，preHandle 按注册顺序执行，afterCompletion 按逆序执行。

答案：正确 解析：拦截器执行是栈结构。preHandle 按注册顺序（order 小的先）执行；afterCompletion 按逆序执行。可用 registry.addInterceptor(x).order(n) 指定顺序。

16-P-20 ★★

JWT 适合前后端分离架构，因为 Token 可放在 Authorization Header 中，不依赖 Cookie。

答案：正确 解析：JWT 不依赖 Cookie，通过 Header 传递，天然支持跨域和前后端分离。Session 认证依赖 Cookie，跨域需额外配置。

五、论述简答题（4题）

16-S-01 ★★

请阐述 JWT 的三段结构，并说明 JWT 是如何防止 Token 被篡改的。

参考答案：

JWT 由三段组成，用 . 连接：

  1. Header（头部）：JSON 对象，包含 alg（签名算法，如 HS256）和 typ（类型，固定 JWT），Base64URL 编码。
  2. Payload（载荷）：JSON 对象，存放声明（claims），如 userId、username、role、exp、iat，Base64URL 编码。注意 Payload 仅编码不加密，任何人可读。
  3. Signature（签名）：HMACSHA256(base64UrlEncode(header) + "." + base64UrlEncode(payload), secret)，用密钥计算，Base64URL 编码。

防篡改原理：

  • Signature 由 Header、Payload 和密钥共同决定。
  • 攻击者修改 Payload（如把 role 从 STUDENT 改成 ADMIN）后，由于没有密钥，无法生成正确的 Signature。
  • 服务端用密钥重新计算签名，与 Token 中的 Signature 对比，不匹配则校验失败。
  • 因此 JWT 的防篡改能力来自"密钥保密 + HMAC 算法"，而非 Payload 加密。

评分标准（满分 10 分）：

  • 三段结构正确说出名称与内容（4 分，每段 1 分 + 编码方式 1 分）
  • 防篡改原理说清"密钥 + HMAC"（4 分）
  • 提到 Payload 不加密（1 分）
  • 表述清晰、逻辑连贯（1 分）

16-S-02 ★★

请描述 HandlerInterceptor 接口三个方法的执行时机与典型用途，并说明为什么要在 afterCompletion 中调用 ThreadLocal.remove()。

参考答案：

HandlerInterceptor 三个方法：

  1. preHandle(request, response, handler)：在 Controller 方法执行前调用。返回 true 放行，false 拦截。典型用途：登录校验、权限校验、日志记录。登录拦截器在此校验 Token 并存入 ThreadLocal。
  2. postHandle(request, response, handler, modelAndView)：在 Controller 返回后、视图渲染前调用。典型用途：修改 ModelAndView、统一添加响应头。
  3. afterCompletion(request, response, handler, ex)：在请求结束时调用，无论 Controller 是否抛异常。典型用途：清理资源、异常统计。

为什么 afterCompletion 要 ThreadLocal.remove()：

  • Spring Boot 默认用 Tomcat 线程池处理请求，线程会被复用。
  • 若不 remove，当前用户的数据残留在 ThreadLocal 中。
  • 线程复用给下一个请求时，若该请求未走登录拦截器（如静态资源）或异常中断，ThreadLocal 仍残留上一个用户数据。
  • Controller 或 Service 读取 CurrentUserContext.get() 会拿到错误用户，导致"用户串号"——A 看到 B 的数据，是严重安全事故。
  • afterCompletion 无论是否抛异常都执行，是清理 ThreadLocal 的可靠位置。

评分标准（满分 10 分）：

  • 三方法执行时机正确（3 分，每个 1 分）
  • 各方法典型用途（2 分）
  • ThreadLocal 不清理的后果——用户串号（3 分）
  • afterCompletion 可靠性说明（1 分）
  • 表述清晰（1 分）

16-S-03 ★★

请完整描述 JWT 登录认证的流程（从用户登录到访问受保护接口），并说明拦截器配置时哪些路径必须放行及原因。

参考答案：

JWT 登录认证完整流程：

  1. 登录：客户端 POST /api/auth/login，提交用户名密码。

  4. 返回 Token：服务端返回 {token: "xxx.yyy.zzz", ...}。
  5. 客户端保存：客户端将 Token 存入 LocalStorage 或内存。
  6. 携带 Token 访问：后续请求在 Authorization: Bearer xxx Header 中携带 Token。

16-S-04 ★★★

请对比 JWT 认证与 Session 认证的优劣，并说明在前后端分离架构中为何通常选择 JWT。若 Token 被盗，应如何应对？

参考答案：

JWT vs Session 对比：

维度 Session JWT
状态存储 服务端（内存/Redis） Token 中（自包含）
凭证传递 Cookie（SessionID） Authorization Header
扩展性 需共享 Session 存储 共享密钥即可，天然支持分布式
跨域 需配置 CORS + Cookie Header 传递，跨域友好
CSRF 易受 CSRF 攻击 不依赖 Cookie，免疫 CSRF
主动吊销 容易（删 Session 即可） 困难（需黑名单）
安全性 SessionID 不含业务信息 Payload 可读（不放敏感信息）
大小 SessionID 短 Token 较长（含 Payload）

前后端分离选 JWT 的原因：

  1. 跨域友好：前后端分离常跨域，JWT 通过 Header 传递不受 Cookie 跨域限制。
  2. 无状态：服务端不存会话，多实例只需共享密钥，无需 Redis 共享 Session。
  3. 移动端适配：App 不便管理 Cookie，Header 传递更通用。
  4. 免疫 CSRF：不依赖 Cookie，攻击者无法构造伪造请求。

Token 被盗的应对：

  1. 使用 HTTPS：防止中间人窃听，是最基础也最有效的措施。
  2. 缩短过期时间：如 Access Token 设 2 小时，降低被盗后窗口期。
  3. Refresh Token 机制：短期 Access Token + 长期 Refresh Token，Access Token 过期后用 Refresh Token 换新。
  4. 关键操作二次验证：支付、改密等敏感操作要求短信/邮箱二次验证。
  5. Token 黑名单：服务端维护已吊销 Token 列表（牺牲无状态性），用户登出或异常时加入黑名单。
  6. 客户端安全存储：Web 端 Token 存内存（vuex/redux）+ Refresh Token 存 HttpOnly Cookie，避免 XSS 读取。
  7. 监控异常：检测 Token 使用 IP/UA 突变，强制重新登录。

评分标准（满分 10 分）：

  • 对比维度至少 5 个（3 分）
  • 前后端分离选 JWT 原因至少 3 条（3 分）
  • Token 被盗应对至少 4 种（3 分）
  • 表述清晰、逻辑严密（1 分）

public class JwtUtil {

    private static final Logger log = LoggerFactory.getLogger(JwtUtil.class);

    public static final String CLAIM_USER_ID = "userId";
    public static final String CLAIM_USERNAME = "username";
    public static final String CLAIM_ROLE = "role";

    @Value("${ctts.jwt.secret}")
    private String secret;

    @Value("${ctts.jwt.expiration}")
    private long expiration;

    private SecretKey key;

    @PostConstruct
    public void init() {
        byte[] keyBytes = secret.getBytes(StandardCharsets.UTF_8);
        if (keyBytes.length < 32) {
            throw new IllegalStateException(
                "JWT secret 长度不足 32 字节，当前 " + keyBytes.length + " 字节");
        }
        this.key = Keys.hmacShaKeyFor(keyBytes);
        log.info("JwtUtil 初始化完成，密钥长度 {} 字节", keyBytes.length);
    }

    public String generateToken(Long userId, String username, String role) {
        Date now = new Date();
        Map<String, Object> claims = new HashMap<>();
        claims.put(CLAIM_USER_ID, userId);
        claims.put(CLAIM_USERNAME, username);
        claims.put(CLAIM_ROLE, role);
        return Jwts.builder()
                .claims(claims)
                .subject(username)
                .issuedAt(now)
                .expiration(new Date(now.getTime() + expiration))
                .signWith(key)
                .compact();
    }

    public Claims parseToken(String token) {
        return Jwts.parser()
                .verifyWith(key)
                .build()
                .parseSignedClaims(token)
                .getPayload();
    }

    public boolean validateToken(String token) {
        try {
            parseToken(token);
            return true;
        } catch (ExpiredJwtException e) {
            log.warn("Token 已过期: {}", e.getMessage());
        } catch (JwtException e) {
            log.warn("Token 无效: {}", e.getMessage());
        } catch (IllegalArgumentException e) {
            log.warn("Token 为空或格式错误: {}", e.getMessage());
        }
        return false;
    }

    public Long getUserId(String token) {
        return parseToken(token).get(CLAIM_USER_ID, Long.class);
    }

    public String getRole(String token) {
        return parseToken(token).get(CLAIM_ROLE, String.class);
    }
}

评分标准（满分 15 分）：

1. LoginInterceptor

package com.ctts.common.interceptor;

import com.ctts.common.context.CurrentUserContext;
import com.ctts.common.context.LoginUser;
import com.ctts.common.jwt.JwtUtil;
import com.fasterxml.jackson.databind.ObjectMapper;
import io.jsonwebtoken.Claims;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.http.HttpStatus;
import org.springframework.http.MediaType;
import org.springframework.stereotype.Component;
import org.springframework.web.servlet.HandlerInterceptor;

import java.nio.charset.StandardCharsets;
import java.util.HashMap;
import java.util.Map;

@Component
public class LoginInterceptor implements HandlerInterceptor {

    private static final String BEARER = "Bearer ";
    private static final ObjectMapper MAPPER = new ObjectMapper();

    @Autowired
    private JwtUtil jwtUtil;

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response,
                             Object handler) throws Exception {
        String authHeader = request.getHeader("Authorization");
        if (authHeader == null || !authHeader.startsWith(BEARER)) {
            return write401(response, "未携带 Token 或格式错误");
        }
        String token = authHeader.substring(BEARER.length()).trim();
        try {
            Claims claims = jwtUtil.parseToken(token);
            Long userId = claims.get(JwtUtil.CLAIM_USER_ID, Long.class);
            String username = claims.get(JwtUtil.CLAIM_USERNAME, String.class);
            String role = claims.get(JwtUtil.CLAIM_ROLE, String.class);
            CurrentUserContext.set(new LoginUser(userId, username, role));
            return true;
        } catch (Exception e) {
            return write401(response, "Token 无效或已过期");
        }
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response,
                                Object handler, Exception ex) {
        CurrentUserContext.remove();
    }

    private boolean write401(HttpServletResponse response, String msg) throws Exception {
        response.setStatus(HttpStatus.UNAUTHORIZED.value());
        response.setContentType(MediaType.APPLICATION_JSON_VALUE);
        response.setCharacterEncoding(StandardCharsets.UTF_8.name());
        Map<String, Object> body = new HashMap<>();
        body.put("code", 401);
        body.put("message", msg);
        response.getWriter().write(MAPPER.writeValueAsString(body));
        return false;
    }
}

package com.ctts.common.config;

import com.ctts.common.interceptor.LoginInterceptor;
import org.springframework.beans.factory.annotation.Autowired;

import org.springframework.web.servlet.config.annotation.InterceptorRegistry;

@Configuration
public class WebMvcConfig implements WebMvcConfigurer {

    @Autowired
    private LoginInterceptor loginInterceptor;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(loginInterceptor)
                .addPathPatterns("/**")
                .excludePathPatterns(
                        "/api/auth/login",
                        "/api/auth/register",
                        "/doc.html",
                        "/swagger-ui/**",
                        "/v3/api-docs/**",
                        "/webjars/**",
                        "/favicon.ico",
                        "/error"
                );
    }
}

3. AuthController 登录接口

package com.ctts.controller;

import com.ctts.common.jwt.JwtUtil;
import com.ctts.common.response.Result;
import com.ctts.dto.LoginDTO;
import com.ctts.entity.User;
import com.ctts.service.UserService;
import jakarta.validation.Valid;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.web.bind.annotation.*;

import java.util.HashMap;
import java.util.Map;

@RestController
@RequestMapping("/api/auth")
public class AuthController {

    @Autowired
    private UserService userService;

    @Autowired
    private JwtUtil jwtUtil;

    @PostMapping("/login")
    public Result<Map<String, Object>> login(@Valid @RequestBody LoginDTO dto) {
        User user = userService.findByUsername(dto.getUsername());
        if (user == null || !userService.checkPassword(dto.getPassword(), user.getPassword())) {
            return Result.fail(401, "用户名或密码错误");
        }
        if (user.getStatus() != 1) {
            return Result.fail(403, "账号已被禁用");
        }
        String token = jwtUtil.generateToken(user.getId(), user.getUsername(), user.getRole());
        Map<String, Object> data = new HashMap<>();
        data.put("token", token);
        data.put("userId", user.getId());
        data.put("username", user.getUsername());
        data.put("role", user.getRole());
        return Result.success(data);
    }
}
