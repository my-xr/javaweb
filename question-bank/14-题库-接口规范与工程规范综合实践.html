一、单选题（30题）

14-单选-1（★）

关于RESTful API设计，下列说法错误的是？

  • A. GET请求用于查询资源，不应修改服务器状态
  • B. POST请求用于新建资源
  • C. PUT请求用于完整更新资源
  • D. DELETE请求的请求体必须非空

答案：D 解析：DELETE请求通常不需要请求体，要删除的资源ID通过URL路径传递（如 DELETE /api/users/1）。RESTful规范中DELETE请求体一般为空。

14-单选-2（★）

在SpringBoot中，用于校验 @RequestBody 参数的注解是？

  • A. @Validated
  • B. @Valid
  • C. @Validated（类上）
  • D. @Validation

答案：B 解析：@Valid 用于校验 @RequestBody 标注的DTO对象参数。@Validated 加在类上用于校验 @RequestParam/@PathVariable 参数，也可用于分组校验。

14-单选-3（★）

校验字符串"非null且非空白（去除首尾空格后非空）"的注解是？

  • A. @NotNull
  • B. @NotEmpty
  • C. @NotBlank
  • D. @NonNull

答案：C 解析：@NotBlank 校验CharSequence类型，要求非null且trim()后长度大于0。@NotNull 仅校验非null（空字符串""可通过）。@NotEmpty 校验非null且非空（""不通过，但" "可通过）。

14-单选-4（★）

统一响应类 Result<T> 中，泛型T的作用是？

  • A. 限制code的类型
  • B. 限制message的类型
  • C. 限制data字段的类型
  • D. 限制timestamp的类型

答案：C 解析：Result<T> 中T表示data字段的类型。如 Result<User> 中data为User类型，Result<Void> 表示无数据返回，Result<List<Task>> 中data为任务列表。

14-单选-5（★）

Knife4j文档注解 @Tag 应该添加在？

  • A. Controller方法上
  • B. Controller类上
  • C. DTO字段上
  • D. Service类上

答案：B 解析：@Tag(name="模块名", description="描述") 用于Controller类上，对接口分组。@Operation 用于方法上，@Parameter 用于参数上，@Schema 用于DTO类或字段上。

14-单选-6（★）

@Operation 注解的作用是？

  • A. 描述接口分组
  • B. 描述接口摘要和详细说明
  • C. 描述请求参数
  • D. 描述响应结果

答案：B 解析：@Operation(summary="接口摘要", description="详细描述") 用于Controller方法上，生成接口文档的摘要和说明。分组用@Tag，参数用@Parameter，响应用@ApiResponses。

14-单选-7（★★）

在 GlobalExceptionHandler 中，处理 @RequestBody 参数校验失败应捕获的异常类型是？

  • A. ConstraintViolationException
  • B. MethodArgumentNotValidException
  • C. BindException
  • D. IllegalArgumentException

答案：B 解析：@RequestBody + @Valid 校验失败抛 MethodArgumentNotValidException。@RequestParam/@PathVariable + @Validated 校验失败抛 ConstraintViolationException。表单绑定校验失败抛 BindException。

14-单选-8（★★）

@RestControllerAdvice 注解的作用是？

  • A. 声明RESTful控制器
  • B. 全局异常处理 + 响应体增强
  • C. 配置跨域
  • D. 配置拦截器

答案：B 解析：@RestControllerAdvice = @ControllerAdvice + @ResponseBody，用于全局异常处理（配合@ExceptionHandler）和全局响应体增强（配合@InitBinder等）。捕获异常后返回的对象会被序列化为JSON。

14-单选-9（★★）

下列哪种异常应该用 log.error 记录？

  • A. 用户名已存在
  • B. 密码错误
  • C. NullPointerException
  • D. 参数格式错误

答案：C 解析：系统异常（NullPointerException等）用 log.error 记录并打印堆栈。业务异常（用户名已存在、密码错误）用 log.warn。正常流程用 log.info。参数错误用 log.warn。

14-单选-10（★）

Lombok提供用于简化日志的注解是？

  • A. @Data
  • B. @Slf4j
  • C. @Log
  • D. @Logger

答案：B 解析：@Slf4j 由Lombok提供，自动在类中生成 private static final Logger log = LoggerFactory.getLogger(类名.class);，可直接使用 log.info() 等方法。

14-单选-11（★★）

校验手机号格式"1开头，第二位3-9，共11位数字"的正则注解是？

  • A. @Pattern(regexp = "^1\d{10}$")
  • B. @Pattern(regexp = "^1[3-9]\d{9}$")
  • C. @Pattern(regexp = "1[3-9]\d{9}")
  • D. @Pattern(regexp = "\d{11}")

答案：B 解析：^1[3-9]\d{9}$ 中，^1 以1开头，[3-9] 第二位3-9，\d{9} 后9位数字，$ 结束。Java字符串中反斜杠需转义，所以写 ^1[3-9]\\d{9}$。

14-单选-12（★）

@Size(min=2, max=50) 注解可以校验的类型是？

  • A. 仅String
  • B. String、Collection、Map、Array
  • C. 仅数字类型
  • D. 仅日期类型

答案：B 解析：@Size 可校验CharSequence（字符串长度）、Collection（集合大小）、Map（键值对数量）、Array（数组长度）。

14-单选-13（★★）

关于 @Valid 和 @Validated 的区别，下列说法正确的是？

  • A. @Valid支持分组校验，@Validated不支持
  • B. @Validated支持分组校验，@Valid不支持
  • C. 两者完全相同
  • D. @Valid用于类上，@Validated用于参数上

答案：B 解析：@Validated 是Spring扩展注解，支持分组校验（如Add/Update分组）；@Valid 是JSR303标准注解，不支持分组。@Valid 用于 @RequestBody 参数；@Validated 用于类上以启用对 @RequestParam/@PathVariable 的校验。

14-单选-14（★★）

在Controller中，处理业务失败的最佳实践是？

  • A. 手动返回 Result.error(500, "失败")
  • B. 抛出 BusinessException，由全局异常处理器统一处理
  • C. 返回null
  • D. 抛出RuntimeException

答案：B 解析：业务失败应抛出 BusinessException，由 GlobalExceptionHandler 统一捕获并转换为 Result。这样Controller代码更简洁，异常处理逻辑集中，避免到处手写Result.error。

14-单选-15（★★）

@ExceptionHandler(Exception.class) 在GlobalExceptionHandler中的作用是？

  • A. 处理所有业务异常
  • B. 处理所有校验异常
  • C. 兜底处理所有未明确捕获的异常
  • D. 处理HTTP异常

答案：C 解析：@ExceptionHandler(Exception.class) 捕获Exception及其所有子类，作为兜底处理。应放在最后，避免提前拦截具体异常。具体异常（如BusinessException）的处理器应优先匹配。

14-单选-16（★）

Apifox导入SpringBoot接口文档的地址是？

  • A. /swagger-ui.html
  • B. /doc.html
  • C. /v3/api-docs
  • D. /api-docs.json

答案：C 解析：OpenAPI3的JSON文档地址是 /v3/api-docs，Apifox通过该地址导入接口。/doc.html 是Knife4j的HTML文档页面，/swagger-ui.html 是原生Swagger UI页面。

14-单选-17（★★）

下列哪个注解用于标注DTO字段的文档说明？

  • A. @ApiModelProperty
  • B. @Schema
  • C. @ApiModel
  • D. @Parameter

答案：B 解析：OpenAPI3（Knife4j 4.x）使用 @Schema(description="说明", example="示例") 描述DTO字段。@ApiModelProperty/@ApiModel 是Swagger2的旧注解，已不推荐。

14-单选-18（★★）

@ResponseStatus(HttpStatus.BAD_REQUEST) 注解的作用是？

  • A. 设置HTTP响应状态码为400
  • B. 设置HTTP响应状态码为200
  • C. 设置HTTP响应状态码为500
  • D. 设置HTTP响应状态码为404

答案：A 解析：HttpStatus.BAD_REQUEST 对应HTTP状态码400，表示请求参数错误。用于在@ExceptionHandler方法上设置响应状态码，使HTTP层状态码与业务语义一致。

14-单选-19（★★）

关于日志级别，从低到高的正确顺序是？

  • A. DEBUG < INFO < WARN < ERROR
  • B. INFO < DEBUG < WARN < ERROR
  • C. ERROR > WARN > INFO > DEBUG
  • D. WARN < INFO < DEBUG < ERROR

答案：A 解析：日志级别从低到高为 TRACE < DEBUG < INFO < WARN < ERROR < FATAL。级别越高，输出越少。配置INFO级别时，DEBUG及以下不输出。

14-单选-20（★★）

在 @PathVariable 参数上添加 @NotNull 注解不生效，原因是？

  • A. 注解写错
  • B. Controller类上未加@Validated
  • C. 参数前未加@Valid
  • D. @PathVariable不支持校验

答案：B 解析：@PathVariable/@RequestParam 参数的校验需在Controller类上加 @Validated，否则校验注解不生效。@Valid 仅用于 @RequestBody 参数。

14-单选-21（★★）

校验"截止时间必须是未来时间"的注解是？

  • A. @Past
  • B. @Future
  • C. @FutureOrPresent
  • D. @After

答案：B 解析：@Future 校验日期/时间必须在未来（当前时间之后）。@Past 校验必须在过去。@FutureOrPresent 校验为当前或未来。

14-单选-22（★★）

Result<Void> 中的 Void 表示？

  • A. 返回void类型
  • B. data字段为null，无具体数据返回
  • C. 方法无返回值
  • D. 编译错误

答案：B 解析：Result<Void> 表示统一响应中data字段为null，用于增删改等无需返回数据的接口。Void 是包装类型，data字段声明为 Void 时实际值为null。

14-单选-23（★★）

在全局异常处理器中，多个 @ExceptionHandler 的匹配规则是？

  • A. 按方法声明顺序匹配
  • B. 按异常类型的最具体子类优先匹配
  • C. 随机匹配
  • D. 按方法名字母顺序

答案：B 解析：Spring会优先匹配最具体的异常类型。如抛出BusinessException（继承RuntimeException），会优先匹配 @ExceptionHandler(BusinessException.class) 而非 @ExceptionHandler(Exception.class)。

14-单选-24（★★★）

下列哪种情况会导致 HttpMessageNotReadableException？

  • A. 请求参数缺失
  • B. 请求体JSON格式错误
  • C. 请求方法不支持
  • D. 参数类型不匹配

答案：B 解析：HttpMessageNotReadableException 在请求体无法被反序列化时抛出，如JSON格式错误、字段类型不匹配等。参数缺失抛 MissingServletRequestParameterException，方法不支持抛 HttpRequestMethodNotSupportedException，类型不匹配抛 MethodArgumentTypeMismatchException。

14-单选-25（★★★）

在CTTS项目中，@Positive 注解用于校验？

  • B. 数字为正数
  • C. 集合非空
  • D. 日期为未来

答案：B 解析：@Positive 校验数字为正数（>0），常用于ID字段，确保传入的ID为正数。@PositiveOrZero 校验为非负（≥0）。

14-单选-26（★★★）

下列关于 @RequestBody 和 @RequestParam 的说法，错误的是？

  • A. @RequestBody用于接收JSON请求体，@RequestParam用于接收URL查询参数
  • B. @RequestBody校验用@Valid，@RequestParam校验需类上加@Validated

答案：D 解析：一个方法只能有一个 @RequestBody 参数（请求体只能被读取一次）。但可以同时使用 @RequestBody 和多个 @RequestParam/@PathVariable。

14-单选-27（★★★）

在GlobalExceptionHandler中，处理 ConstraintViolationException 的场景是？

  • B. @RequestParam/@PathVariable参数校验失败

  • D. 业务异常

答案：B 解析：ConstraintViolationException 在 @Validated + @RequestParam/@PathVariable 校验失败时抛出。@RequestBody 校验失败抛 MethodArgumentNotValidException。

14-单选-28（★★★）

Knife4j注解 @Parameter 的 requiredMode 属性取值为 Schema.RequiredMode.REQUIRED 表示？

  • A. 参数可选

14-单选-29（★★★）

下列哪种做法符合"统一返回Result"规范？

  • A. 查询接口返回 Result.success(user)
  • B. 新增接口返回 "success" 字符串

答案：A 解析：所有接口应统一返回 Result<T>。查询返回 Result.success(data)，增删改返回 Result.success()，异常由全局处理器转换为 Result.error()。返回字符串、Map、裸对象都不符合规范。

14-单选-30（★★★）

关于交叉审查（代码互查），下列说法正确的是？

  • B. 交叉审查只检查功能实现，不检查规范

  • D. 交叉审查只需检查一次

答案：C 解析：交叉审查（Code Review）是工程实践的重要环节，有助于发现个人盲区、传播最佳实践、提升团队代码质量。审查不仅检查功能，更检查规范遵循情况（命名、注释、异常处理等）。

二、多选题（10题）

14-多选-1（★）

下列属于JSR303校验注解的有？

  • A. @NotBlank
  • B. @NotNull
  • C. @Size
  • D. @Email
  • E. @Data

答案：ABCD 解析：@NotBlank、@NotNull、@Size、@Email 都是JSR303（Jakarta Bean Validation）校验注解。@Data是Lombok注解，用于生成getter/setter/toString等方法，非校验注解。

14-多选-2（★）

下列属于Knife4j（OpenAPI3）注解的有？

  • A. @Tag
  • B. @Operation
  • C. @Parameter
  • D. @Schema
  • E. @ApiModel

答案：ABCD 解析：@Tag、@Operation、@Parameter、@Schema 是OpenAPI3注解（Knife4j 4.x使用）。@ApiModel 是Swagger2旧注解，OpenAPI3中已被@Schema取代。

14-多选-3（★★）

GlobalExceptionHandler应该处理的异常类型有？

  • A. BusinessException（业务异常）
  • B. MethodArgumentNotValidException（参数校验异常）
  • C. HttpRequestMethodNotSupportedException（方法不支持）
  • D. Exception（兜底异常）
  • E. IOException（IO异常，一般不处理）

答案：ABCD 解析：全局异常处理器应处理业务异常、参数校验异常、方法不支持异常等，并提供Exception兜底。IOException一般由Spring框架处理，不强制在GlobalExceptionHandler中处理。

14-多选-4（★★）

下列符合RESTful接口设计规范的有？

  • A. GET /api/users/1 查询用户
  • B. POST /api/users 新增用户
  • C. PUT /api/users 更新用户
  • D. DELETE /api/users/1 删除用户
  • E. POST /api/deleteUser?id=1 删除用户

答案：ABCD 解析：RESTful使用HTTP方法表达操作语义：GET查询、POST新增、PUT更新、DELETE删除。URL是资源路径，不应包含动词（如deleteUser）。E选项不符合RESTful。

14-多选-5（★★）

统一响应 Result<T> 应包含的字段有？

  • A. code（状态码）
  • B. message（提示信息）
  • C. data（响应数据）
  • D. timestamp（时间戳）
  • E. stackTrace（异常堆栈）

答案：ABCD 解析：统一响应通常包含code、message、data、timestamp。异常堆栈stackTrace不应返回给前端（暴露系统结构，有安全风险），仅在日志中记录。

14-多选-6（★★）

关于日志记录规范，下列说法正确的有？

14-简答-3（★★★）

题目：结合CTTS项目，论述统一响应格式 Result<T> 的设计意义，并说明如何配合全局异常处理器实现"Controller只关心成功流程"。

答案要点：

  1. Result的设计意义：

    • 统一响应结构：所有接口返回 {code, message, data, timestamp}，前端无需适配多种格式。
    • 语义清晰：code表示业务状态码，message提供提示信息，data承载业务数据。
    • 泛型支持：Result<User>、Result<List<Task>>、Result<Void> 类型安全。
    • 便于拦截：前端拦截器统一根据code判断是否登录失效、权限不足等。
    • 便于文档：Knife4j可基于Result结构生成统一响应文档。

  2. Controller只关心成功流程的实现：

    • Controller中成功时返回 Result.success(data) 或 Result.success()。
    • 业务失败时抛 BusinessException，不手动返回 Result.error()。
    • 系统异常由GlobalExceptionHandler兜底，转换为 Result.error(ResultCode.SYSTEM_ERROR)。
    • 参数校验失败由GlobalExceptionHandler捕获校验异常，转换为 Result.error(ResultCode.PARAM_VALIDATE_FAILED, message)。

  3. 示例对比：

    // 不规范：Controller中手写错误处理
@GetMapping("/{id}")
public Result<User> getById(@PathVariable Long id) {
    User user = userService.getById(id);
    if (user == null) {
        return Result.error(404, "用户不存在");  // 不推荐
    }
    return Result.success(user);
}

// 规范：Controller只关心成功流程，失败抛异常
@GetMapping("/{id}")
public Result<User> getById(@PathVariable Long id) {
    User user = userService.getById(id);
    if (user == null) {
        throw new BusinessException(ResultCode.NOT_FOUND, "用户不存在");
    }
    return Result.success(user);
}

  • Result设计意义（5分，至少3点）
  • Controller只关心成功流程的实现思路（5分）
  • 异常处理器配合说明（3分）
  • 代码示例（2分）

答案：5处不符合规范的问题及修改建议：

    userService.register(dto);
    return Result.success();

    }
    return Result.success(user);

    @DeleteMapping("/{id}")
@Operation(summary = "删除用户")
public Result<Void> delete(@PathVariable @NotNull Long id) {
    userService.removeById(id);
    return Result.success();
}

  6. getById中使用log但类上未加@Slf4j：编译报错，应在类上加 @Slf4j。

  7. 缺少@Validated：@PathVariable参数校验需类上加 @Validated。

题目：为CTTS系统的UserController设计并实现"根据ID查询用户详情"接口，要求：

  2. @PathVariable校验id非空
  3. 用户不存在时抛BusinessException（ResultCode.NOT_FOUND）

  5. 添加Knife4j文档注解
  6. 添加日志记录（请求、不存在、成功）
  7. 同时写出GlobalExceptionHandler中处理BusinessException的方法

请写出： （1）UserController的getById方法完整代码（含类注解） （2）GlobalExceptionHandler中处理BusinessException的方法

答案：

（1）UserController的getById方法：

@Slf4j
@Validated
@RestController
@RequestMapping("/api/users")
@RequiredArgsConstructor
@Tag(name = "用户管理", description = "用户的注册、登录、查询、更新等接口")
public class UserController {

    private final UserService userService;

    @GetMapping("/{id}")
    @Operation(summary = "查询用户详情", description = "根据用户ID查询用户信息")
    public Result<User> getById(
            @Parameter(description = "用户ID", required = true, example = "1")
            @PathVariable @NotNull(message = "用户ID不能为空") Long id) {
        log.info("查询用户详情请求：id={}", id);
        User user = userService.getById(id);
        if (user == null) {
            log.warn("用户不存在：id={}", id);
            throw new BusinessException(ResultCode.NOT_FOUND, "用户不存在");
        }
        log.info("查询用户详情成功：id={}", id);
        return Result.success(user);
    }
}

（2）GlobalExceptionHandler中处理BusinessException的方法：

@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BusinessException.class)
    public Result<Void> handleBusinessException(BusinessException e) {
        log.warn("业务异常：code={}, message={}", e.getCode(), e.getMessage());
        return Result.error(e.getCode(), e.getMessage());
    }
}

说明：

  • @ExceptionHandler(BusinessException.class) 捕获业务异常
  • 用 log.warn 记录（业务异常是预期内的，非系统错误）
  • 返回 Result.error(e.getCode(), e.getMessage())，使用异常中携带的code和message
  • 不加 @ResponseStatus，HTTP状态码默认200，业务状态码通过Result.code传递（这是常见做法；也可设置为HttpStatus.OK）
