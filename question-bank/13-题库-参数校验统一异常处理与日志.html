一、单选题（30 题）

13-单选-01 ★

关于 @Valid 和 @Validated，下列说法正确的是？ A. 两者完全等价，可以互换使用 B. @Valid 是 Spring 提供的注解，@Validated 是 JSR 380 标准注解 C. @Validated 支持分组校验，@Valid 不支持 D. @Valid 可以用在 @RequestParam 上触发校验，@Validated 不能

答案：C 解析：@Valid 是 JSR 380 标准注解，不支持分组校验；@Validated 是 Spring 扩展注解，支持分组校验。两者都可用于 @RequestBody 体校验，但 @RequestParam / @PathVariable 校验需要在类上加 @Validated。A 错误，两者不等价；B 错误，来源说反了；D 错误，@Validated 才是用于类级触发 Param 校验。

13-单选-02 ★

在 Spring Boot 3.x 中，使用 Bean Validation 校验需要引入的依赖是？ A. spring-boot-starter-web B. spring-boot-starter-validation C. hibernate-validator D. javax.validation-api

答案：B 解析：Spring Boot 2.3 之后，spring-boot-starter-web 不再自动包含校验依赖，需要单独引入 spring-boot-starter-validation，它内部已经包含 hibernate-validator 和 jakarta.validation-api。Spring Boot 3.x 使用 Jakarta EE 命名空间（jakarta.validation.），不是 javax.。

13-单选-03 ★

下列注解中，只能用于 String 类型的是？ A. @NotNull B. @NotEmpty C. @NotBlank D. @Size

答案：C 解析：@NotBlank 只能用于 String 类型，校验非 null 且去空格后非空。@NotNull 可用于任意类型；@NotEmpty 可用于 String / Collection / Map / Array；@Size 可用于 String / Collection / Map / Array。

13-单选-04 ★

@NotEmpty 注解可以用于下列哪种类型？ A. Integer B. Long C. List<String> D. LocalDate

答案：C 解析：@NotEmpty 用于 String / Collection / Map / Array，校验非 null 且长度/大小 > 0。Integer 和 Long 是数字类型，用 @NotNull / @Min / @Max；LocalDate 用 @NotNull / @Past / @Future。

13-单选-05 ★

校验"项目名称长度在 2-50 之间"，应使用哪个注解？ A. @Min(2) + @Max(50) B. @Size(min = 2, max = 50) C. @Length(min = 2, max = 50) D. @Range(min = 2, max = 50)

答案：B 解析：字符串长度校验用 @Size(min, max)。@Min / @Max 用于数值；@Length 是 Hibernate Validator 扩展，非标准；@Range 也是 Hibernate 扩展且用于数值。标准注解优先选 @Size。

13-单选-06 ★

校验"年龄必须大于 0"，应使用哪个注解？ A. @NotBlank B. @Size(min = 1) C. @Min(1) D. @NotEmpty

答案：C 解析：年龄是数值类型，用 @Min(1) 校验最小值为 1。@NotBlank 用于 String；@Size 用于字符串/集合长度；@NotEmpty 用于集合/字符串非空。

13-单选-07 ★

校验"手机号格式正确"，应使用哪个注解？ A. @Email B. @Pattern(regexp = "...") C. @Size D. @NotBlank

答案：B 解析：手机号需要正则匹配，用 @Pattern(regexp = "^1[3-9]\\d{9}$")。@Email 只校验邮箱；@Size 只校验长度；@NotBlank 只校验非空。@Pattern 内部用正则表达式，可自定义任意格式。

13-单选-08 ★

校验"截止日期必须晚于今天"，应使用哪个注解？ A. @Past B. @PastOrPresent C. @Future D. @FutureOrPresent

答案：C 解析：@Future 校验日期必须是未来的。@Past 校验过去的日期；@PastOrPresent 校验过去或现在；@FutureOrPresent 校验未来或现在。题目要求"晚于今天"，即严格未来，用 @Future。

13-单选-09 ★★

关于 @Valid 嵌套校验，下列说法正确的是？ A. 在 DTO 类上加 @Valid 即可触发嵌套校验 B. 在 DTO 的字段上加 @Valid 即可触发嵌套校验 C. 嵌套校验需要配合 @Validated 使用 D. 嵌套校验只能有一层

答案：B 解析：嵌套校验是在 DTO 的字段上标注 @Valid，表示对该字段对象内部的注解也进行校验。例如 ProjectDTO 中有 private List<@Valid TaskDTO> tasks;，会级联校验每个 TaskDTO 的字段。A 错误，类上加 @Valid 无效；C 错误，嵌套校验用 @Valid 即可；D 错误，可多层嵌套。

13-单选-10 ★★

@RequestBody 体校验失败时，抛出的异常类型是？ A. ConstraintViolationException B. MethodArgumentNotValidException C. BindException D. MethodArgumentTypeMismatchException

答案：B 解析：@RequestBody + @Valid 校验失败抛 MethodArgumentNotValidException。ConstraintViolationException 是 @RequestParam / @PathVariable 校验失败（类上加 @Validated）抛出的；BindException 是表单提交校验失败抛出的；MethodArgumentTypeMismatchException 是参数类型不匹配抛出的。

13-单选-11 ★★

@RequestParam 校验失败时，抛出的异常类型是？ A. ConstraintViolationException B. MethodArgumentNotValidException C. BindException D. MissingServletRequestParameterException

答案：A 解析：Controller 类上加 @Validated，方法参数上加 @Min 等注解，校验失败抛 ConstraintViolationException。B 是 Body 校验失败；C 是表单校验失败；D 是缺少必填参数（不是校验失败）。

13-单选-12 ★

@RestControllerAdvice 注解等价于？ A. @ControllerAdvice + @RequestMapping B. @ControllerAdvice + @ResponseBody C. @Component + @ExceptionHandler D. @Service + @Controller

答案：B 解析：@RestControllerAdvice 是组合注解，等于 @ControllerAdvice + @ResponseBody，表示全局异常处理类的返回值自动序列化为 JSON。A 错误，不是 @RequestMapping；C 错误，@ExceptionHandler 是方法级注解，不能加在类上；D 错误。

13-单选-13 ★★

关于 @ExceptionHandler 的异常匹配规则，下列说法正确的是？ A. 按代码声明顺序匹配，先声明的优先 B. 按异常类型精确匹配，父类异常优先于子类异常 C. 按异常类型精确匹配，子类异常优先于父类异常 D. 所有异常都会被 Exception.class 的 handler 处理

答案：C 解析：@ExceptionHandler 匹配规则是"子类优先，最近优先"。子类异常会优先匹配到精确类型的 handler，只有未被精确匹配的异常才会落到父类（如 Exception）兜底。A 错误，与声明顺序无关；B 错误，是子类优先；D 错误，有精确匹配的就不会落到兜底。

13-单选-14 ★★

自定义业务异常 BusinessException 应该继承哪个类？ A. Exception B. RuntimeException C. Throwable D. Error

答案：B 解析：业务异常应继承 RuntimeException（非受检异常），避免在 Service 方法签名上到处 throws，且 Spring 事务默认对 RuntimeException 回滚。继承 Exception（受检）会导致代码冗余；Throwable 和 Error 不适合业务异常。

13-单选-15 ★★

自定义业务异常继承 RuntimeException 的好处不包括？ A. 不需要在方法签名上声明 throws B. Spring 事务默认会回滚 C. 可以被 @ExceptionHandler 捕获 D. 编译器强制要求调用方处理

答案：D 解析：RuntimeException 是非受检异常，编译器不强制要求调用方处理（不强制 try-catch 或 throws）。A、B、C 都是继承 RuntimeException 的好处。D 是受检异常（Exception 子类）的特性，不是 RuntimeException 的。

13-单选-16 ★

SLF4J 与 Logback 的关系是？ A. SLF4J 是 Logback 的实现 B. Logback 是 SLF4J 的实现 C. 两者是同一个东西 D. 两者没有关系

答案：B 解析：SLF4J 是日志门面（接口），Logback 是 SLF4J 的实现。业务代码调用 SLF4J 接口，底层由 Logback 实现具体输出。这种门面模式的好处是切换日志实现（如换成 Log4j2）无需改业务代码。

13-单选-17 ★

Lombok 的 @Slf4j 注解的作用是？ A. 自动配置日志级别 B. 自动注入 log 对象 C. 自动输出日志 D. 自动生成日志文件

答案：B 解析：@Slf4j 注解在编译时自动为类注入一个 private static final Logger log = LoggerFactory.getLogger(Xxx.class); 字段，开发者直接用 log.info() 等方法即可。A、C、D 都不是 @Slf4j 的作用。

13-单选-18 ★

日志级别从低到高排列，正确的是？ A. TRACE < DEBUG < INFO < WARN < ERROR B. DEBUG < TRACE < INFO < WARN < ERROR C. ERROR < WARN < INFO < DEBUG < TRACE D. INFO < DEBUG < TRACE < WARN < ERROR

答案：A 解析：日志级别从低到高：TRACE < DEBUG < INFO < WARN < ERROR。设置某级别后，只输出该级别及以上的日志。如设置 INFO，则 TRACE / DEBUG 不输出，INFO / WARN / ERROR 输出。

13-单选-19 ★

生产环境通常使用的日志级别是？ A. TRACE B. DEBUG C. INFO D. ERROR

答案：C 解析：生产环境通常用 INFO，既能记录关键业务节点，又不会产生过多日志。TRACE / DEBUG 日志量太大，影响性能；只用 ERROR 会丢失重要业务信息。INFO 是生产环境的"黄金级别"。

13-单选-20 ★★

下列日志写法中，推荐的是？ A. log.debug("用户信息: " + user); B. log.error("失败: " + e.getMessage()); C. log.info("创建项目成功: id={}", id); D. log.warn("项目名重复:" + name);

答案：C 解析：推荐用 {} 占位符而非字符串拼接（A、D 错误），即使日志级别不输出也不会拼接字符串，性能更好。B 错误，异常日志应该把异常对象作为最后一个参数（log.error("失败", e)），才能打印完整堆栈，而不是 e.getMessage()（可能为 null 且丢失堆栈）。

13-单选-21 ★★

打印异常堆栈的正确写法是？ A. log.error("异常: " + e.getMessage()); B. log.error("异常: {}", e.getMessage()); C. log.error("异常", e); D. log.error("异常: " + e);

答案：C 解析：异常对象应作为日志方法的最后一个参数，SLF4J 会自动打印完整堆栈。A、D 是字符串拼接，丢失堆栈；B 只打印 message，丢失堆栈；C 正确，e 作为最后一个参数，自动打印堆栈。

13-单选-22 ★★

在 application.yml 中配置 com.ctts 包的日志级别为 DEBUG，正确的写法是？ A.

logging:
  level:
    com.ctts: DEBUG

B.

logging:
  com.ctts: DEBUG

C.

log:
  level:
    com.ctts: DEBUG

D.

logging:
  level.com.ctts: DEBUG

答案：A 解析：Spring Boot 日志级别配置在 logging.level 下，包名作为 key，级别作为 value。B、C 结构错误；D 虽然在某些情况下能工作，但标准写法是 A 的层级结构。

13-单选-23 ★★

配置日志文件输出到 logs/ctts.log，正确的 application.yml 配置是？ A.

logging:
  file: logs/ctts.log

B.

logging:
  file:
    name: logs/ctts.log

C.

logging:
  path: logs/ctts.log

D.

log:
  file: logs/ctts.log

答案：B 解析：Spring Boot 2.x 之后推荐用 logging.file.name 配置日志文件名（含路径）。logging.file.path 是配置日志目录（不含文件名，默认名为 spring.log）。A 的 logging.file 是旧写法已废弃；C 的 logging.path 同样废弃；D 顶层 key 错误。

13-单选-24 ★★

日志文件滚动策略中，max-file-size 的作用是？ A. 单个日志文件最大大小，超过则滚动 B. 所有日志文件总大小上限 C. 保留日志的天数 D. 日志文件数量上限

答案：A 解析：max-file-size 配置单个日志文件的最大大小，超过则创建新文件（滚动）。total-size-cap 是所有日志文件总大小上限；max-history 是保留天数；日志文件数量上限不是直接配置项。

13-单选-25 ★★

关于全局异常处理器的兜底异常，下列说法正确的是？ A. 兜底异常处理方法返回堆栈信息有助于前端调试 B. 兜底异常应该把完整堆栈返回给前端 C. 兜底异常应返回友好提示，堆栈记到日志 D. 不需要兜底异常处理方法

答案：C 解析：兜底异常（Exception.class）应该返回友好提示（如"系统繁忙，请稍后重试"），堆栈用 log.error 记录到日志，便于排查。把堆栈返回给前端会泄露敏感信息（数据库结构、SQL 等），A、B 错误；没有兜底会返回 Spring 默认错误页，体验差，D 错误。

13-单选-26 ★★

下列哪种异常不应该用 log.error 记录？ A. 数据库连接失败 B. 业务异常（如"项目名重复"） C. 空指针异常 D. 文件 IO 异常

答案：B 解析：业务异常是预期内的错误（如"项目名重复"），属于正常业务流程，用 log.warn 即可。log.error 用于不可恢复的系统性异常（如数据库连接失败、NPE、IO 异常），这些才是真正需要告警的。

13-单选-27 ★★★

关于分组校验，下列代码正确的是？ A.

@Valid(AddGroup.class) @RequestBody ProjectDTO dto

B.

@Validated(AddGroup.class) @RequestBody ProjectDTO dto

C.

@Valid @RequestBody(AddGroup.class) ProjectDTO dto

D.

@Validated @RequestBody ProjectDTO dto, @Group AddGroup.class

答案：B 解析：分组校验用 @Validated(Group.class)，指定校验分组。@Valid 不支持分组；@RequestBody 不接分组参数；D 语法不正确。正确写法是在 @Validated 中指定分组接口的 Class 对象。

13-单选-28 ★★

下列哪种方式可以让 @RequestParam 上的 @Min 注解生效？ A. 在方法参数上加 @Valid B. 在 Controller 类上加 @Validated C. 在方法上加 @Validated D. 在 DTO 字段上加 @Valid

答案：B 解析：@RequestParam / @PathVariable 校验需要在 Controller 类上加 @Validated，方法参数上的 @Min / @Max / @Pattern 等注解才会生效。方法参数上加 @Valid 用于 @RequestBody 体校验，不用于单个参数；C、D 语法不正确。

13-单选-29 ★★

下列关于日志级别设置的描述，错误的是？ A. root: INFO 设置全局默认级别为 INFO B. com.ctts: DEBUG 设置 ctts 包的级别为 DEBUG C. org.springframework: WARN 降低 Spring 框架日志噪音 D. 级别设置后不可在运行时动态调整

答案：D 解析：Spring Boot Actuator 提供了 /loggers 端点，可以在运行时动态调整日志级别，无需重启应用。A、B、C 都正确。D 错误。

13-单选-30 ★★★

关于 Spring Boot 3.x 中的校验，下列说法错误的是？ A. 校验注解的包名是 jakarta.validation.constraints.* B. @Valid 的包名是 jakarta.validation.Valid C. Spring Boot 3.x 仍然支持 javax.validation.* 包名 D. Spring Boot 3.x 基于 Jakarta EE 9+，包名从 javax 改为 jakarta

答案：C 解析：Spring Boot 3.x 基于 Jakarta EE 9+，所有 javax.* 包名改为 jakarta.*，不再支持 javax.validation.*。A、B、D 都正确；C 错误。从 Spring Boot 2.x 迁移到 3.x 时，需要把所有 import javax.validation.* 改为 import jakarta.validation.*。

二、多选题（10 题）

13-多选-01 ★

下列注解中，可以用于校验"非空"的有？ A. @NotNull B. @NotEmpty C. @NotBlank D. @Size E. @Min

答案：A、B、C 解析：@NotNull（任意类型非 null）、@NotEmpty（集合/字符串非空）、@NotBlank（字符串去空格后非空）都是非空校验。@Size 是长度校验；@Min 是数值最小值校验。

13-多选-02 ★★

13-论述-02 ★★

简述全局异常处理器 @RestControllerAdvice + @ExceptionHandler 的工作原理，并说明异常匹配规则。

答案要点：

工作原理：

  1. Spring MVC 处理请求时若抛出异常，交给 HandlerExceptionResolver 链处理；
  2. ExceptionHandlerExceptionResolver 负责查找 @ExceptionHandler 方法；
  3. 先在当前 Controller 中查找，再到全局 @RestControllerAdvice 中查找；
  4. 找到匹配的 handler 方法后，执行该方法，返回值作为响应体（@ResponseBody 自动序列化为 JSON）。

异常匹配规则：

  1. 子类优先：子类异常优先匹配到精确类型的 handler，如 BusinessException 优先于 Exception；
  2. 最近优先：Controller 内的 @ExceptionHandler 优先于全局 @RestControllerAdvice；
  3. 兜底：未被精确匹配的异常会落到 @ExceptionHandler(Exception.class) 兜底处理。

建议的 handler 顺序：

  1. MethodArgumentNotValidException（Body 校验）
  2. ConstraintViolationException（Param 校验）
  3. MethodArgumentTypeMismatchException（类型不匹配）
  4. BusinessException（业务异常）
  5. Exception（兜底）

评分标准（满分 10 分）：

  • 工作原理（4 分）
  • 匹配规则（3 分）
  • handler 顺序建议（3 分）

13-论述-03 ★★

自定义业务异常为什么要继承 RuntimeException 而不是 Exception？请从代码侵入性、事务回滚、异常处理三个角度分析。

答案要点：

1. 代码侵入性角度：

  • Exception 是受检异常，方法签名必须 throws 或调用方必须 try-catch，每层都要处理，代码冗余；
  • RuntimeException 是非受检异常，方法签名不需要 throws，调用链清爽，代码侵入性低。

2. 事务回滚角度：

  • Spring 的 @Transactional 默认只对 RuntimeException（及其子类）和 Error 回滚，对受检 Exception 不回滚；
  • 业务异常通常需要回滚事务（如"项目名重复"时，前面的操作要回滚），继承 RuntimeException 默认触发回滚；
  • 如果继承 Exception，需要额外配置 @Transactional(rollbackFor = Exception.class) 才能回滚。

3. 异常处理角度：

  • RuntimeException 可以被 @ExceptionHandler(BusinessException.class) 正常捕获，与继承 Exception 无区别；
  • 但 RuntimeException 不强制调用方处理，更符合"业务异常可预期、由全局处理器统一处理"的设计思路。

结论：业务异常应继承 RuntimeException，代码侵入性低、事务默认回滚、由全局异常处理器统一捕获。

评分标准（满分 10 分）：

  • 代码侵入性分析（3 分）
  • 事务回滚分析（4 分）
  • 异常处理分析（2 分）
  • 结论（1 分）

13-论述-04 ★★★

在生产环境中，日志应该如何规范配置？请从日志级别、日志文件、滚动策略、敏感信息、性能五个方面论述。

答案要点：

1. 日志级别：

  • root: INFO 全局默认 INFO，平衡信息量与性能；
  • com.ctts: INFO 业务包 INFO，记录关键业务节点；
  • org.springframework: WARN 框架日志降级，减少噪音；
  • 排查问题时临时调 com.ctts: DEBUG，排查完调回 INFO；
  • 可用 Actuator /loggers 端点运行时动态调整。

2. 日志文件：

  • 必须输出到文件，不能只输出控制台（生产环境没有控制台）；
  • 配置 logging.file.name: logs/ctts.log；
  • 日志文件至少保留 15 天（阿里规约），重要系统保留 30 天以上。

  • max-file-size: 10MB 单个文件最大 10MB，超过则滚动；
  • max-history: 30 保留 30 天；
  • total-size-cap: 1GB 所有日志文件总大小上限 1GB，超过则删除最旧的；
  • 避免单个文件无限增长撑爆磁盘。

4. 敏感信息：

  • 日志中不能打印密码、身份证、银行卡号等敏感信息；

5. 性能：

  • 用 {} 占位符，不用字符串拼接；
  • 异常对象作为最后一个参数；
  • 避免在循环中打大量日志；
  • 高并发场景考虑异步日志（AsyncAppender）；
  • ERROR 日志要节制，避免告警泛滥。

  • 日志级别（2 分）
  • 日志文件（2 分）
  • 滚动策略（2 分）
  • 敏感信息（2 分）

13-编程-02 ★★★

题目：为 CTTS 编写完整的全局异常处理器 GlobalExceptionHandler 和自定义业务异常 BusinessException，要求：

  1. BusinessException 继承 RuntimeException，包含 code（Integer）和 message，提供两个构造器；
  2. GlobalExceptionHandler 使用 @RestControllerAdvice，处理以下 5 类异常：
    • MethodArgumentNotValidException（Body 校验失败，返回 400）
    • ConstraintViolationException（Param 校验失败，返回 400）
    • MethodArgumentTypeMismatchException（类型不匹配，返回 400）
    • BusinessException（业务异常，返回 e.getCode()）
    • Exception（兜底，返回 500）
  3. 所有异常返回统一 Result<T> 结构；
  4. 校验异常用 log.warn，业务异常用 log.warn，兜底异常用 log.error 并打印完整堆栈；
  5. 兜底异常返回"系统繁忙，请稍后重试"，不返回堆栈。

答案：

package com.ctts.common.exception;

import lombok.Getter;

/**
 * 自定义业务异常
 */
@Getter
public class BusinessException extends RuntimeException {

    /** 业务错误码 */
    private final Integer code;

    /** 构造器1：指定 code 和 message */
    public BusinessException(Integer code, String message) {
        super(message);
        this.code = code;
    }

    /** 构造器2：仅指定 message，code 默认 500 */
    public BusinessException(String message) {
        this(500, message);
    }
}
package com.ctts.common.exception;

import com.ctts.common.Result;
import jakarta.validation.ConstraintViolation;
import jakarta.validation.ConstraintViolationException;
import lombok.extern.slf4j.Slf4j;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.method.annotation.MethodArgumentTypeMismatchException;

import java.util.stream.Collectors;

/**
 * 全局异常处理器
 */
@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler {

    /** 1. @RequestBody 体校验失败 */
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<Void> handleValid(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldErrors().stream()
                .map(fe -> fe.getField() + ": " + fe.getDefaultMessage())
                .collect(Collectors.joining("; "));
        log.warn("参数校验失败: {}", msg);
        return Result.fail(400, msg);
    }

    /** 2. @RequestParam/@PathVariable 校验失败 */
    @ExceptionHandler(ConstraintViolationException.class)
    public Result<Void> handleConstraint(ConstraintViolationException e) {
        String msg = e.getConstraintViolations().stream()
                .map(ConstraintViolation::getMessage)
                .collect(Collectors.joining("; "));
        log.warn("约束校验失败: {}", msg);
        return Result.fail(400, msg);
    }

    /** 3. 参数类型不匹配 */
    @ExceptionHandler(MethodArgumentTypeMismatchException.class)
    public Result<Void> handleTypeMismatch(MethodArgumentTypeMismatchException e) {
        log.warn("参数类型不匹配: {}", e.getName());
        return Result.fail(400, "参数类型不匹配: " + e.getName());
    }

    /** 4. 业务异常 */
    @ExceptionHandler(BusinessException.class)
    public Result<Void> handleBusiness(BusinessException e) {
        log.warn("业务异常: code={}, msg={}", e.getCode(), e.getMessage());
        return Result.fail(e.getCode(), e.getMessage());
    }

    /** 5. 兜底异常 */
    @ExceptionHandler(Exception.class)
    public Result<Void> handleException(Exception e) {
        log.error("系统异常", e);
        return Result.fail(500, "系统繁忙，请稍后重试");
    }
}

package com.ctts.common;

import lombok.Data;

@Data
public class Result<T> {
    private Integer code;
    private String message;
    private T data;

    private Result(Integer code, String message, T data) {
        this.code = code;
        this.message = message;
        this.data = data;
    }

    public static <T> Result<T> success() {
        return new Result<>(200, "success", null);
    }

    public static <T> Result<T> success(T data) {
        return new Result<>(200, "success", data);
    }

    public static <T> Result<T> fail(Integer code, String message) {
        return new Result<>(code, message, null);
    }
}
