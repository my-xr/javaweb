    likeLeft
  • B

  • D

20-单选-02 ★

题目：以下 QueryWrapper 代码生成的 WHERE 子句是？

wrapper.eq("status", 2)
       .like("name", "张三")
       .or().eq("name", "李四");
  • A
    WHERE status = 2 AND name LIKE '%张三%' AND name = '李四'
  • B
    WHERE (status = 2 AND name LIKE '%张三%') OR name = '李四'
  • C
    WHERE status = 2 AND (name LIKE '%张三%' OR name = '李四')
  • D
    WHERE status = 2 AND name LIKE '%张三%' OR name = '李四'

答案：D 解析：or() 只改变下一个条件的连接符为 OR，不会自动加括号。SQL 中 AND 优先级高于 OR，所以生成 status=2 AND name LIKE '%张三%' OR name='李四'。注意 D 与 B 语义相同，但 D 是 SQL 原样输出形式。如果要得到 C 的语义，必须用 wrapper.and(w -> w.like("name","张三").or().eq("name","李四"))。

20-单选-03 ★★

题目：要实现"查询状态为2，且姓名是张三或李四的记录"，以下写法正确的是？

  • A
    wrapper.eq("status",2).like("name","张三").or().eq("name","李四")
  • B
    wrapper.eq("status",2).and(w -> w.eq("name","张三").or().eq("name","李四"))
  • C
    wrapper.eq("status",2).or(w -> w.eq("name","张三").eq("name","李四"))
  • D
    wrapper.and(w -> w.eq("status",2)).or().eq("name","张三").eq("name","李四")

答案：B 解析：and(lambda) 会对 lambda 内的条件整体加括号，生成 status=2 AND (name='张三' OR name='李四')，符合需求。A 丢括号导致优先级错乱；C 用 or(lambda) 把最外层改成 OR；D 整体语义错。

20-单选-07 ★★

  • B

20-单选-08 ★★

题目：以下哪种事务传播行为表示"当前有事务就加入，没有就新建"？

  • A
    REQUIRES_NEW
  • B
    NESTED
  • C
    REQUIRED
  • D
    SUPPORTS

答案：C 解析：REQUIRED 是默认传播行为，当前有事务则加入，没有则新建。REQUIRES_NEW 总是新建独立事务；NESTED 在当前事务内建保存点；SUPPORTS 有则加入，无则非事务执行。

20-单选-09 ★★★

题目：以下代码的事务是否会生效？

@Service
public class FooService {
    public void outer() {
        this.inner();
    }
    @Transactional(rollbackFor = Exception.class)
    public void inner() { ... }
}
  • A
    生效，因为 @Transactional 注解正确
  • B
    不生效，因为 this 调用绕过了 AOP 代理
  • C
    生效，因为 Spring 会自动处理自调用
  • D
    不生效，因为方法名不是 startTransaction

答案：B 解析：Spring 声明式事务基于 AOP 代理，this.inner() 是对象内部直接调用，不经过代理对象，所以 @Transactional 失效。解决方法：注入自己（@Autowired @Lazy private FooService self;）或用 ApplicationContext.getBean() 取代理。

题目：以下代码事务是否会回滚？

@Transactional

    回滚，因为抛了异常

  • D
    不回滚，因为方法没有返回值

答案：B 解析：@Transactional 默认 rollbackFor = RuntimeException.class，IOException 是受检异常，不会触发回滚。必须写 @Transactional(rollbackFor = Exception.class)。

20-单选-11 ★★

题目：以下代码事务是否会回滚？

@Transactional(rollbackFor = Exception.class)
public void submit() {
    try {
        mapper.insert(...);
        throw new RuntimeException("模拟异常");
    } catch (Exception e) {
        log.error("出错", e);
    }
}
  • A
    回滚，因为抛了 RuntimeException
  • B
    不回滚，因为异常被 catch 吞掉，Spring 看不到异常
  • C
    回滚，因为 rollbackFor = Exception.class
  • D
    不回滚，因为方法没有 throws

答案：B 解析：Spring AOP 通过捕获方法抛出的异常来决定是否回滚。异常被 catch 后没有 rethrow，AOP 看到方法正常返回，不触发回滚。解决方法：catch 后 rethrow，或调用 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()。

题目：以下哪种方式能让"日志记录"操作不受主业务事务回滚影响？

20-单选-16 ★★★

题目：关于 REQUIRES_NEW 和 NESTED 的区别，以下说法正确的是？

  • A
    两者完全相同
  • B
    REQUIRES_NEW 开启物理独立事务，NESTED 在当前事务内建保存点
  • C
    NESTED 开启物理独立事务，REQUIRES_NEW 建保存点

题目：MyBatis-Plus 的 QueryWrapper.eq("name", null) 会拼接 name = NULL。 答案：错误 解析：eq 不带 condition 参数时，value 为 null 也会拼成 name = NULL，但这在 SQL 中永远为 false（NULL 比较要用 IS NULL）。动态条件应使用 eq(value != null, ...)。

20-论述-02 ★★

题目：请对比 Spring 事务的三种传播行为 REQUIRED、REQUIRES_NEW、NESTED 的区别，并分别给出适用场景。

答案要点：

传播行为 当前有事务 当前无事务 是否独立 适用场景
REQUIRED 加入当前事务 新建事务 否 99% 业务方法，保证整体原子性
REQUIRES_NEW 挂起当前事务，新建独立事务 新建事务 是 日志、审计、通知等需要独立保留的操作
NESTED 在当前事务内建保存点 新建事务 部分 子操作可独立回滚但不影响主事务，如批量操作中单条失败回滚到保存点继续

区别：

  • REQUIRED 与主事务同生共死，主回滚子也回滚，子回滚主也回滚。
  • REQUIRES_NEW 完全独立，主回滚不影响子，子回滚不影响主。
  • NESTED 是嵌套，子回滚只回滚到保存点不影响主，但主回滚会连带回滚子。

适用场景：

  • REQUIRED：业务核心写入（如提交任务+更新状态）。
  • REQUIRES_NEW：操作日志、审计记录、异常通知。
  • NESTED：批量处理中单条失败不影响其他条目，但整批仍想作为一个事务。

评分标准（满分 10 分）：

  • 三种行为各自描述 2 分（共 6 分）
  • 区别对比清晰 2 分
  • 适用场景正确 2 分

20-论述-03 ★★

题目：什么是业务状态机？请结合 CTTS 提交任务的状态流转，说明为什么要用状态机校验，并给出实现要点。

答案要点：

业务状态机定义：用一个状态字段记录业务对象当前所处阶段，通过规则约束状态之间的合法转换路径。三要素：状态（State）、事件（Event）、转换（Transition）。

CTTS 提交任务状态机：

  • 状态：未开始(0) → 进行中(1) → 已提交(2) → 已评审(3)
  • 合法转换：
    • 未开始 →进行中（学生开始）
    • 进行中 →已提交（学生提交）
    • 已提交 →已评审（教师评审）
    • 已提交 →进行中（退回修改）
  • 终态：已评审（不可回退）

为什么用状态机校验：

  1. 防止非法流转（如未开始直接跳到已提交），保证业务流程正确。
  2. 防止重复提交覆盖已评审成绩。
  3. 防止已评审记录被再次"提交"导致状态不一致。
  4. 集中管理转换规则，避免散落各处的 if-else。

实现要点：

  1. 状态字段用 TINYINT，配套枚举类（SubmissionStatus）。
  2. 状态机规则集中到 SubmissionStateMachine 类，用 EnumMap<Status, Set<Status>> 定义合法转换。
  3. 提供 canTransit(from, to) 判断和 check(from, to) 校验方法。
  4. 每次更新状态前调用 check，非法流转抛 IllegalStateException。
  5. 终态（已评审）的转换集合为空，禁止任何回退。

评分标准（满分 10 分）：

  • 状态机定义 2 分
  • CTTS 状态列举 2 分
  • 必要性论述 3 分
  • 实现要点 3 分

题目：课程思政——为什么说"事务是业务正确性的保障"？请结合 CTTS"成绩统计错乱"案例，谈一谈工程师对数据一致性负有什么责任。

答案要点：

案例背景：某校实训成绩统计因事务缺失，导致"评审记录已插入"但"提交状态未更新"，统计查询时这部分数据被遗漏，200 条成绩错乱，影响学生评优。

事务是业务正确性的保障：

  1. 事务的 ACID 特性中，原子性保证多步操作要么全成功要么全回滚，一致性保证执行前后数据满足约束。
  2. 在 CTTS 评审场景中，"插入评审记录 + 更新提交状态"必须原子，否则会出现"有评审无状态"或"有状态无评审"的脏数据。
  3. 一行 @Transactional 背后是"对数据负责的承诺"，不是技术装饰。

工程师的责任：

  1. 识别事务边界：哪些操作必须原子，哪些可以独立。
  2. 正确使用事务：指定 rollbackFor、避免失效场景、合理选择传播行为。
  3. 防御性设计：状态机校验、异常处理、回滚验证。
  4. 职业操守：数据正确性关乎用户切身利益（如学生成绩），工程师应把"跑得对"置于"跑得通"之上。
  5. 系统思维：局部正确 ≠ 全局正确，要从业务链整体设计事务边界。

结论：事务不是注解的游戏，而是对数据负责的承诺。一行 @Transactional，写的是技术，守的是信任。

package com.ctts.enums;
import lombok.AllArgsConstructor;
import lombok.Getter;

@Getter
@AllArgsConstructor
public enum SubmissionStatus {

    REVIEWED(3, "已评审");

// 2. 状态机
package com.ctts.enums;
import java.util.EnumMap;
import java.util.Map;
import java.util.Set;

public class SubmissionStateMachine {
    private static final Map<SubmissionStatus, Set<SubmissionStatus>> TRANSITIONS = new EnumMap<>(SubmissionStatus.class);

    static {
        TRANSITIONS.put(SubmissionStatus.NOT_STARTED, Set.of(SubmissionStatus.IN_PROGRESS));
        TRANSITIONS.put(SubmissionStatus.IN_PROGRESS, Set.of(SubmissionStatus.SUBMITTED));
        TRANSITIONS.put(SubmissionStatus.SUBMITTED, Set.of(SubmissionStatus.REVIEWED, SubmissionStatus.IN_PROGRESS));
        TRANSITIONS.put(SubmissionStatus.REVIEWED, Set.of());
    }

    public static void check(SubmissionStatus from, SubmissionStatus to) {
        if (!TRANSITIONS.getOrDefault(from, Set.of()).contains(to)) {
            throw new IllegalStateException("非法状态流转: " + from.getDesc() + " → " + to.getDesc());
        }
    }
}

public class TaskBusinessServiceImpl implements TaskBusinessService {

    private final SubmissionMapper submissionMapper;
    private final ReviewMapper reviewMapper;
    private final LogService logService;

    public TaskBusinessServiceImpl(SubmissionMapper s, ReviewMapper r, LogService l) {
        this.submissionMapper = s; this.reviewMapper = r; this.logService = l;
    }

    @Override
    @Transactional(rollbackFor = Exception.class, propagation = Propagation.REQUIRED)
    public void submitTask(Long submissionId, String content, String fileUrl) {
        Submission sub = submissionMapper.selectById(submissionId);
        SubmissionStatus from = SubmissionStatus.of(sub.getStatus());
        SubmissionStateMachine.check(from, SubmissionStatus.SUBMITTED);

        sub.setStatus(SubmissionStatus.SUBMITTED.getCode());
        sub.setContent(content);
        sub.setFileUrl(fileUrl);
        sub.setSubmitTime(LocalDateTime.now());
        submissionMapper.updateById(sub);

        logService.log(submissionId, "SUBMIT", "提交任务");
    }

    @Override
    @Transactional(rollbackFor = Exception.class, propagation = Propagation.REQUIRED)
    public void reviewTask(Long submissionId, Long teacherId, BigDecimal score, String comment) {
        // 1) 插入评审记录
        Review review = new Review();
        review.setSubmissionId(submissionId);
        review.setTeacherId(teacherId);
        review.setScore(score);
        review.setComment(comment);
        review.setReviewTime(LocalDateTime.now());
        reviewMapper.insert(review);

        // 2) 状态校验 + 更新
        Submission sub = submissionMapper.selectById(submissionId);
        SubmissionStatus from = SubmissionStatus.of(sub.getStatus());
        SubmissionStateMachine.check(from, SubmissionStatus.REVIEWED);
        sub.setStatus(SubmissionStatus.REVIEWED.getCode());
        submissionMapper.updateById(sub);

        // 3) 日志独立事务
        logService.log(submissionId, "REVIEW", "评审完成，成绩：" + score);
    }
