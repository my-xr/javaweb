一、单项选择题（30题）

15-D-01 ★

关于用户注册流程，下列顺序正确的是（ ）

  • A
    加密密码 → 校验用户名唯一 → 入库
  • B
    入库 → 加密密码 → 校验用户名唯一
  • C
    校验用户名唯一 → 加密密码 → 入库
  • D
    校验用户名唯一 → 入库 → 加密密码

答案：C 解析：注册流程应先校验用户名是否唯一，避免无效加密；再对密码做 BCrypt 加密；最后将加密后的密码与用户信息入库。若先入库后加密，则入库时密码为明文，存在安全风险。

15-D-02 ★

下列关于密码存储的说法，正确的是（ ）

  • A
    为方便找回密码，应明文存储
  • B
    为加快登录校验速度，可使用 MD5 存储并建立索引
  • C
    必须使用不可逆的哈希算法存储，推荐 BCrypt
  • D
    可使用对称加密（如 AES）加密后存储，便于解密

答案：C 解析：密码必须以不可逆哈希存储，BCrypt 是当前推荐方案。明文存储、可逆加密都违反安全底线；MD5 因彩虹表和计算过快已不推荐。

15-D-03 ★★

关于 BCrypt 加密，下列说法错误的是（ ）

  • A
    同一明文每次加密结果不同
  • B
    盐会作为密文的一部分存储
  • C
    校验密码时从密文中解析盐再哈希明文
  • D
    同一明文加密两次结果不同会导致校验失败

答案：D 解析：BCrypt 自带盐，盐嵌入在密文中。虽然每次加密结果不同，但 matches 会从密文解析盐并重新哈希明文进行比对，因此校验依然正确。D 说法错误。

15-D-04 ★★

BCryptPasswordEncoder 中 strength 参数的意义是（ ）

  • A
    密文长度
  • B
    盐的长度
  • C
    成本因子，表示 2 的 strength 次方轮哈希
  • D
    加密算法版本号

答案：C 解析：strength 是成本因子（log2 rounds），如 strength=10 表示 2^10=1024 轮哈希。值越大越安全但越慢，生产推荐 10-12。

15-D-05 ★

Spring Security 中 PasswordEncoder 接口校验密码的方法是（ ）

  • A
    encode(rawPassword, encodedPassword)
  • B
    matches(rawPassword, encodedPassword)
  • C
    verify(rawPassword, encodedPassword)
  • D
    check(rawPassword, encodedPassword)

答案：B 解析：PasswordEncoder 接口定义 encode 加密、matches 校验两个核心方法。

15-D-06 ★★

下列关于 MD5 密码存储不安全的原因，描述错误的是（ ）

  • A
    MD5 是可逆加密，能从密文还原明文
  • B
    MD5 计算速度过快，暴力破解成本低
  • C
    相同明文 MD5 结果相同，易被彩虹表攻击
  • D
    MD5 存在碰撞漏洞

答案：A 解析：MD5 是单向哈希，理论不可逆。不安全的原因是彩虹表、计算快、相同明文相同密文、存在碰撞。A 说法错误，MD5 不是"可逆加密"。

15-D-07 ★

用户登录时，根据用户名查询到用户后，校验密码应使用（ ）

  • A
    password.equals(user.getPassword())
  • B
    user.getPassword().equals(password)
  • C
    passwordEncoder.matches(password, user.getPassword())
  • D
    passwordEncoder.encode(password).equals(user.getPassword())

答案：C 解析：BCrypt 每次加密结果不同，不能用 equals 比对，必须用 matches(明文, 密文)。D 选项虽看似可行但每次加密结果不同必然失败。

15-D-08 ★★

关于 Session 认证，下列说法正确的是（ ）

  • A
    Session 存储在客户端
  • B
    SessionID 通过 HTTP Header 传递
  • C
    SessionID 通过 Cookie 返回客户端
  • D
    Session 认证是无状态的

答案：C 解析：Session 存储在服务端，SessionID 通过 Set-Cookie 响应头返回客户端，浏览器后续自动携带。Session 认证是有状态的。

15-D-09 ★★

关于 Token 认证，下列说法错误的是（ ）

  • A
    Token 通常存储在客户端 localStorage
  • B
    Token 通常通过 HTTP Header 携带到服务端
  • C
    Token 认证是有状态的
  • D
    JWT 是 Token 的一种常见格式

答案：C 解析：Token 认证是无状态的，服务端不存储 Session。C 错误。

15-D-10 ★

前后端分离架构通常选择 Token 认证而非 Session，主要原因是（ ）

  • A
    Token 比 Session 更安全
  • B
    Token 无状态、跨域友好、适配多端
  • C
    Token 实现比 Session 简单
  • D
    Session 已被淘汰

答案：B 解析：Token 无状态、易扩展、跨域友好、适配 Web/小程序/App 多端，是前后端分离的首选。Token 与 Session 安全性取决于实现，并非 Token 一定更安全；Session 在同域传统 Web 中仍广泛使用。

15-D-11 ★

注册接口应使用什么 HTTP 方法（ ）

  • D

答案：B 解析：注册是创建资源，语义上应使用 POST。GET 不应携带敏感信息（密码会出现在 URL 日志中）。

15-D-12 ★★

BCrypt 加密后密文长度约为多少字符（ ）

二、多项选择题（10题）

15-M-01 ★★

下列关于密码存储的说法，正确的有（ ）

  • A
    密码必须以不可逆哈希存储
  • B
    BCrypt 是推荐的密码加密算法
  • C
    明文存储违反《个人信息保护法》
  • D
    MD5 加盐后即与 BCrypt 安全性相当
  • E
    密码字段应建立索引以加速登录校验

答案：ABC 解析：ABC 正确。D 错误：MD5 计算太快即便加盐仍可被暴力破解，远不及 BCrypt。E 错误：密码字段不应建索引，登录依据用户名查询，且密码索引反而便于攻击者获取密文。

  • B
    密码长度校验
  • C
    用户名唯一性校验
  • D
    角色合法性校验
  • E
    Token 有效性校验

答案：ABCD 解析：ABCD 均为注册必备校验。E 错误：注册时用户尚未登录，无需 Token。

15-M-03 ★★

下列关于 BCrypt 的说法，正确的有（ ）

  • A
    同一明文每次加密结果不同
  • B
    盐嵌入在密文中
  • C
    校验时用 matches 方法
  • D
    计算速度比 MD5 快
  • E
    strength 越大越安全但越慢

答案：ABCE 解析：ABCE 正确。D 错误：BCrypt 是慢哈希算法，计算速度远慢于 MD5，这是其安全的特性之一。

15-M-04 ★★

下列属于 Token 认证特点的有（ ）

  • A
    无状态
  • B
    客户端存储 Token
  • C
    通过 Header 携带
  • D
    跨域友好

三、判断题（20题）

15-P-01 ★

密码可以使用 MD5 加密存储，因为 MD5 是不可逆的哈希算法。

答案：错误 解析：MD5 虽不可逆，但因计算速度快、存在彩虹表、相同明文相同密文，已不适合密码存储。应使用 BCrypt 等慢哈希算法。

15-P-02 ★

BCrypt 加密同一明文，每次产生的密文不同，但都能正确校验。

答案：正确 解析：BCrypt 自带随机盐，盐嵌入密文。matches 时从密文解析盐重新哈希明文比对，因此校验正确。

15-P-03 ★

用户注册时，应先加密密码再校验用户名是否唯一，以提升性能。

答案：错误 解析：应先校验用户名唯一性，避免对已存在用户的密码做无效加密。顺序错误会浪费计算资源。

15-P-04 ★

登录失败时分别提示"用户名不存在"和"密码错误"可以让用户更清楚问题，是推荐做法。

答案：错误 解析：分别提示会暴露用户是否注册，便于攻击者枚举用户名。应统一提示"用户名或密码错误"。

15-P-05 ★★

BCrypt 密文长度是 32 字符，数据库字段 VARCHAR(32) 足够。

答案：错误 解析：BCrypt 密文 60 字符，建议 VARCHAR(100)。32 字符是 MD5 密文长度。

15-P-06 ★

Session 认证是无状态认证，服务端不存储任何用户信息。

答案：错误 解析：Session 认证是有状态的，服务端存储 Session 对象。Token 认证才是无状态的。

15-P-07 ★

Token 认证中，Token 通常通过 HTTP Header Authorization 携带。

答案：正确 解析：约定通过 Authorization: Bearer <token> 携带，也可自定义 Header。

15-P-08 ★★

引入 spring-boot-starter-security 后默认放行所有接口无需认证。

答案：错误 解析：默认拦截所有请求需认证。需配置 permitAll() 或排除 SecurityAutoConfiguration。

15-P-09 ★

@Valid 注解可以触发 DTO 上的 JSR-303 校验注解。

答案：正确 解析：@Valid 配合 @NotBlank、@Size 等触发参数自动校验。

15-P-10 ★★

BCrypt 需要开发者自己生成盐并单独存储到数据库。

答案：错误 解析：BCrypt 自带盐，自动生成并嵌入密文，无需开发者单独管理盐字段。

15-P-11 ★

注册接口可以使用 GET 方法，将参数放在 URL 中。

答案：错误 解析：GET 将参数暴露在 URL 中，密码会出现在浏览器历史和服务器日志中，存在安全风险。注册应用 POST。

15-P-12 ★★

JWT 是自包含的 Token，服务端解析即可获得用户信息，无需查库。

答案：正确 解析：JWT 的 Payload 自包含用户信息，服务端解析校验签名后即可获得用户身份，无需查 Redis。

15-P-13 ★★

Session 认证在多服务器部署时无需任何额外配置即可天然共享 Session。

答案：错误 解析：默认 Session 存在服务器本地内存，多服务器需 Session 共享（粘性会话、Spring Session+Redis 等）。

15-P-14 ★

密码加密是为了防止数据库泄漏后密码被直接获取。

答案：正确 解析：密码加密核心目的就是即便数据库泄漏，攻击者也无法直接获得明文密码。

15-P-15 ★★

passwordEncoder.encode("123456").equals(passwordEncoder.encode("123456")) 的结果为 true。

答案：错误 解析：BCrypt 每次加密产生不同盐，结果不同，equals 返回 false。校验应用 matches。

15-P-16 ★

登出时只需前端清空本地 Token，服务端无需任何处理。

答案：错误 解析：仅前端清 Token 不够，攻击者可能已窃取。服务端应使 Token 失效（删 Redis 或加黑名单）。

BCryptPasswordEncoder 的 strength 参数值越大越安全，因此应设为最大值 31。

答案：错误 解析：strength 越大越慢，31 会导致单次加密数秒，严重影响登录性能。生产推荐 10-12。

答案：错误 解析：数据库 UNIQUE 约束兜底防重，但抛出的是 DuplicateKeyException，提示不友好。业务层应主动校验给出友好提示。

15-S-01 ★★

论述题：请从数据库泄漏、撞库攻击、内部审计三个角度，详细说明为什么密码不能明文存储。

参考答案与评分标准（满分10分）：

1. 数据库泄漏角度（3分）

  • 一旦数据库被 SQL 注入或拖库，所有用户密码直接以明文形式暴露（1分）。
  • 攻击者可立即登录所有账户，造成盗号、资金损失、信息篡改等严重后果（1分）。
  • 加密存储即便库泄漏，攻击者也无法直接获得明文，需付出极高破解成本（1分）。

2. 撞库攻击角度（3分）

  • 用户习惯在多个网站复用同一密码（1分）。
  • 明文泄漏后，攻击者将"用户名+密码"组合用于登录其他网站，即撞库（1分）。
  • 加密存储（尤其 BCrypt 加盐）使每个站点密文不同，即便泄漏也难以反推明文用于撞库（1分）。

3. 内部审计角度（2分）

  • 明文存储意味着有数据库读权限的内部员工可查看所有用户密码（1分）。
  • 违反最小权限原则和职业道德，加密存储使内部员工也只能看到密文（1分）。

4. 法律法规角度（2分）

  • 《个人信息保护法》第51条要求采取技术措施保障个人信息安全（1分）。
  • 明文存储属于未履行安全保护义务，可能面临行政处罚和民事赔偿（1分）。

评分要点：每个角度要点齐全得满分；论述清晰、有例证加分；仅泛泛而谈酌情扣分。

15-S-02 ★★

论述题：请对比 MD5 与 BCrypt 在密码存储场景下的差异，并说明 BCrypt 是如何解决 MD5 的安全问题的。

参考答案与评分标准（满分10分）：

1. MD5 的问题（4分）

  • 计算速度极快：现代 GPU 每秒可计算数十亿次 MD5，暴力破解成本低（1分）。
  • 彩虹表攻击：预先计算的明文→MD5 对照表可秒查反推（1分）。
  • 相同明文相同密文：一旦某站泄漏，相同密码账户都被识别（1分）。
  • 存在碰撞漏洞：虽对密码存储影响有限，但反映算法已被攻破（1分）。

2. BCrypt 的解决方案（4分）

  • 慢哈希：成本因子 strength 可调，计算慢，暴力破解成本极高（1分）。
  • 自带随机盐：每次加密产生不同盐，相同明文产生不同密文，防彩虹表（1分）。
  • 盐嵌入密文：无需单独维护盐字段，matches 自动解析盐重新哈希（1分）。
  • 不可逆：与 MD5 一样是单向哈希，但抗暴力破解能力远强于 MD5（1分）。

3. 对比小结（2分）

  • MD5：快、无盐、不安全（1分）。
  • BCrypt：慢、自带盐、安全，是密码存储推荐方案（1分）。

评分要点：要点齐全满分；只列现象不解释原理扣分；能结合"为什么慢更安全"加分。

15-S-03 ★★

评分要点：四个维度对照清晰满分；只答维度不展开扣分；结合实际场景论述加分。

String token = UUID.randomUUID().toString().replace("-", "");

（3）UserService.register：

package com.ctts.service;

import com.baomidou.mybatisplus.core.conditions.query.LambdaQueryWrapper;
import com.ctts.dto.UserRegisterDTO;
import com.ctts.entity.User;
import com.ctts.exception.BusinessException;
import com.ctts.mapper.UserMapper;
import lombok.RequiredArgsConstructor;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Service;

@Service
@RequiredArgsConstructor
public class UserService {

    private final UserMapper userMapper;
    private final PasswordEncoder passwordEncoder;

    public void register(UserRegisterDTO dto) {
        // 用户名唯一性校验
        Long count = userMapper.selectCount(
            new LambdaQueryWrapper<User>().eq(User::getUsername, dto.getUsername())
        );
        if (count > 0) {
            throw new BusinessException(400, "用户名已存在");
        }
        // BCrypt 加密 + 入库
        User user = new User();
        user.setUsername(dto.getUsername());
        user.setPassword(passwordEncoder.encode(dto.getPassword()));
        user.setName(dto.getName());
        user.setRole(dto.getRole());
        userMapper.insert(user);
    }
}

15-C-02 ★★

编程题：请基于上一题继续实现 CTTS 用户登录接口。

要求：

  1. 接口路径 POST /api/auth/login。
  2. 请求体字段：username、password，均非空校验。
  3. 根据用户名查询用户，不存在抛 BusinessException(400, "用户名或密码错误")。
  4. 用 passwordEncoder.matches 校验密码，不匹配抛同样异常（防止用户名枚举）。
  5. 生成简单 Token（UUID），返回 Result<Map<String, Object>>，包含 token 和 user（id/username/name/role，不含 password）。
  6. 编写：DTO、Controller 方法、UserService 方法。

参考答案：

（1）UserLoginDTO：

package com.ctts.dto;

import jakarta.validation.constraints.NotBlank;
import lombok.Data;

@Data
public class UserLoginDTO {
    @NotBlank(message = "用户名不能为空")
    private String username;

    @NotBlank(message = "密码不能为空")
    private String password;
}

（2）UserService.login：

public Map<String, Object> login(UserLoginDTO dto) {
    // 1. 查用户
    User user = userMapper.selectOne(
        new LambdaQueryWrapper<User>().eq(User::getUsername, dto.getUsername())
    );
    if (user == null) {
        throw new BusinessException(400, "用户名或密码错误");
    }

    // 2. BCrypt 校验密码
    if (!passwordEncoder.matches(dto.getPassword(), user.getPassword())) {
        throw new BusinessException(400, "用户名或密码错误");
    }

    // 3. 生成 Token
    String token = UUID.randomUUID().toString().replace("-", "");

    // 4. 封装返回（不含 password）
    Map<String, Object> result = new HashMap<>();
    result.put("token", token);
    Map<String, Object> userInfo = new HashMap<>();
    userInfo.put("id", user.getId());
    userInfo.put("username", user.getUsername());
    userInfo.put("name", user.getName());
    userInfo.put("role", user.getRole());
    result.put("user", userInfo);

    return result;
}

（3）UserController.login：

@PostMapping("/login")
public Result<Map<String, Object>> login(@Valid @RequestBody UserLoginDTO dto) {
    Map<String, Object> data = userService.login(dto);
    return Result.ok(data);
}
