二、教学目标

2.1 知识目标

  • K18-1：理解需求拆解方法，掌握功能需求与非功能需求的区分，了解用例图基本画法。
  • K18-2：理解ER图概念，掌握实体关系（一对多、多对一）的建模方法，了解数据库范式（1NF/2NF/3NF）的基本要求。
  • K18-3：掌握CTTS系统5张表（sys_user、training_project、task、task_submission、task_review）的字段设计、类型选择、约束设置与外键关系。
  • K18-4：理解索引的概念，掌握主键索引、唯一索引、普通索引的区别，明确"何时建索引"的判断依据。
  • K18-5：掌握数据库初始化脚本的编写规范，能独立完成CREATE DATABASE、CREATE TABLE、INSERT测试数据的编写与执行。

2.2 能力目标

  • 能够从真实业务场景出发，拆解并表述软件系统的功能需求与非功能需求。
  • 能够根据需求文档设计ER图，并将ER图转化为符合第三范式的数据库表结构。
  • 能够编写规范的建表SQL，合理设置主键、外键、非空、默认值、注释与索引。
  • 能够编写并执行数据库初始化脚本，插入测试数据并验证表间关系。
  • 具备对他人表结构设计进行评审、提出改进意见的协作能力。

2.3 素质目标（课程思政）

  • 深入业务、求真务实：理解"好的设计源于对业务的深入理解"，摒弃闭门造车的浮躁作风，培养从真实问题出发的工程师品格。
  • 严谨规范、精益求精：通过字段命名、类型选择、注释编写的规范训练，养成工业级开发习惯。
  • 团队协作、批判思维：通过小组表结构设计评审，学会倾听、表达、质疑与妥协。
  • 服务社会、技术向善：CTTS系统服务于高校实训管理这一真实场景，体会技术解决实际问题的价值。

三、教学重点与难点

3.1 教学重点

  1. CTTS系统需求拆解：三大角色、五大功能模块的边界划分。
  2. 5张表的字段设计、类型选择、约束设置与外键关系。
  3. 建表SQL的规范编写（含注释、索引、外键）。
  4. 数据库范式分析与第三范式的落地。

3.2 教学难点

  1. 实体关系的识别：一对多关系的正确建模（如一个项目包含多个任务、一个任务包含多个提交）。
  2. 外键设计与业务语义的对齐：如task_submission同时关联user与task，task_review同时关联submission与reviewer。
  3. 索引建立的时机判断：在查询频率与写入性能之间权衡。
  4. 需求到设计的转化思维：从自然语言需求到结构化表结构的映射。

3.3 突破策略

  • 采用"业务场景→需求描述→ER草图→表结构SQL"四步递进法，逐步抽象。
  • 通过"反例驱动"：先展示设计糟糕的表（如将学生、教师、管理员塞进一张无角色字段的表），再引导改进。
  • 通过小组互评，让学生在评审他人设计的过程中反思自己的设计。

7.2 详细教学过程

环节1：课程导入与思政引言（5分钟）

教师活动：

  • 提问："同学们在参加实训时，有没有遇到过任务提交混乱、评审进度不透明的问题？"
  • 引出CTTS系统：校园实训任务管理系统，解决实训过程中的任务下发、提交、评审全流程管理。
  • 思政引言：引用"墨菲定律"——设计阶段的疏漏会在后期被放大。强调"好的设计源于对业务的深入理解"，技术人要深入一线业务。

学生活动：思考并回答实训管理痛点。

设计意图：从真实痛点切入，激发兴趣；埋下"设计决定成败"的思政种子。

环节2：K18-1 需求分析（15分钟）

教师活动（讲授+案例）：

  • 需求拆解方法：自顶向下（系统→模块→功能）、自底向上（用户故事→功能聚合）。
  • CTTS功能需求拆解（5大模块）：
    • 用户管理：注册、登录、角色权限（学生/教师/管理员）。
    • 项目管理：教师创建/编辑实训项目，学生查看项目。
    • 任务管理：教师在项目下创建任务，学生查看任务。
    • 提交管理：学生提交任务成果，可多次提交。
    • 评审管理：教师评审提交，打分+评语。
  • 非功能需求：安全（密码加密、权限控制）、性能（列表查询<500ms）、可用性（7×24、易用界面）。
  • 用例图基础：参与者（Actor）与用例（Use Case）的关系，简笔画CTTS用例图。

学生活动：记录需求清单，尝试用一句话描述每个模块的核心用例。

设计意图：建立"先需求后设计"的认知，为后续表设计提供依据。

环节3：K18-2 数据库设计基础（12分钟）

教师活动（讲授+对比）：

  • ER图三要素：实体（矩形）、属性（椭圆）、关系（菱形）。
  • 实体关系：一对一、一对多、多对多。CTTS中重点是一对多：
    • 一个项目 → 多个任务
    • 一个任务 → 多个提交
    • 一个提交 → 多个评审（支持多人评审）
    • 一个学生 → 多个提交
    • 一个教师 → 多个项目、多个评审
  • 外键设计：在"多"的一方加外键引用"一"的一方主键。
  • 范式基础：
    • 1NF：字段原子性（不拆分）。
    • 2NF：非主属性完全依赖主键（消除部分依赖）。
    • 3NF：非主属性不传递依赖主键（消除传递依赖）。
  • 反例：把项目名、任务名塞进同一张表，导致数据冗余。

学生活动：在草稿纸上画出CTTS五个实体的ER草图。

设计意图：从概念模型过渡到逻辑模型，为表设计铺路。

环节4：K18-3 CTTS五张表详细设计（20分钟）

教师活动（逐表讲解）：

表1 sys_user（用户表）：

  • id BIGINT 主键自增、username VARCHAR(50) 唯一非空、password VARCHAR(100) 非空、real_name VARCHAR(50) 非空、role TINYINT 非空（1学生2教师3管理员）、phone VARCHAR(20)、email VARCHAR(100)、status TINYINT 默认1、create_time、update_time。
  • 索引：username唯一索引、role普通索引。

表2 training_project（实训项目表）：

  • id、title、description、teacher_id（外键→sys_user.id）、start_date、end_date、status、create_time、update_time。
  • 外键：teacher_id引用sys_user.id。
  • 索引：teacher_id普通索引、status普通索引。

表3 task（任务表）：

  • id、project_id（外键→training_project.id）、title、description、deadline、total_score INT、create_time、update_time。
  • 外键：project_id引用training_project.id。

表4 task_submission（提交表）：

  • id、task_id（外键→task.id）、user_id（外键→sys_user.id，提交学生）、content TEXT、file_url VARCHAR(255)、submit_time、status（1待评审2已评审）。
  • 外键：task_id、user_id。

表5 task_review（评审表）：

  • id、submission_id（外键→task_submission.id）、reviewer_id（外键→sys_user.id，评审教师）、score INT、comment VARCHAR(500)、review_time。
  • 外键：submission_id、reviewer_id。

学生活动：跟随讲解在IDEA中同步建表（可先听后做）。

设计意图：核心环节，落实5张表的工程级设计。

环节5：K18-4 索引基础（8分钟）

教师活动：

  • 索引概念：像书的目录，加快查询但拖慢写入。
  • 三类索引：
    • 主键索引：随PRIMARY KEY自动创建。
    • 唯一索引：UNIQUE，保证列值唯一（如username）。
    • 普通索引：INDEX，加速等值/范围查询（如role、status）。
  • 何时建索引：查询频繁、区分度高、数据量大的列。
  • 何时不建：写入极频繁、区分度低（如性别）、数据量小。
  • CTTS中的索引决策：username唯一、role/status普通索引；不对外键全部建索引，按查询需要取舍。

学生活动：判断CTTS各表哪些列该建索引，说明理由。

设计意图：建立"按需建索引"的工程判断力。

环节6：K18-5 数据库初始化脚本演示（10分钟）

教师活动（现场演示）：

  • 步骤1：CREATE DATABASE ctts DEFAULT CHARACTER SET utf8mb4;
  • 步骤2：依次执行5张表的CREATE TABLE（含外键、注释、索引）。
  • 步骤3：INSERT测试数据（3个角色用户、2个项目、若干任务、提交、评审）。
  • 步骤4：用JOIN查询验证外键关系（如查询某学生的所有提交及评审结果）。
  • 强调：字符集utf8mb4支持emoji；存储引擎InnoDB支持外键。

学生活动：观察执行结果，记录验证查询语句。

设计意图：让学生看到完整闭环，建立"设计→建表→数据→验证"的工程思维。

环节7：课堂任务实践（12分钟）

教师活动：布置课堂任务，巡视指导。

学生活动（独立完成）：

  1. 分析需求（阅读CTTS需求说明书）。
  2. 设计表（参照讲解，可在草稿纸画ER图）。
  3. 编写建表SQL（5张表）。
  4. 执行建表（在MySQL中执行）。
  5. 插入测试数据（参照INSERT脚本）。
  6. 验证：写2条JOIN查询验证外键关系。

任务工单：学生提交.sql文件至课程平台。

设计意图：动手实践，巩固表设计与SQL编写能力。

环节8：小组讨论——表结构设计评审（5分钟）

教师活动：组织4-5人小组互评，提供评审表（字段命名、类型合理、约束完整、外键正确、索引合理）。

学生活动：

  • 组内交换建表SQL，互相评审。
  • 每组推选1个"最佳设计"和1个"待改进点"。
  • 组长汇报，教师点评。

评审要点：

  • 字段命名是否规范（小写+下划线）。
  • 类型是否合理（如ID用BIGINT而非INT）。
  • 是否遗漏非空/默认值/注释。
  • 外键关系是否正确。
  • 索引是否合理。

设计意图：在评审中反思，培养批判性思维与协作能力。

环节9：课堂小结与作业布置（3分钟）

教师活动：

  • 小结：需求拆解→ER图→表结构→SQL→验证，是后端工程师的核心设计能力。
  • 作业：
    1. 完善CTTS建表脚本，补充测试数据至每表10条以上。
    2. 思考：如果CTTS要支持"小组任务"（一个任务由小组完成），表结构如何调整？写出设计思路。
    3. 预习：下节课将基于这5张表实现SpringBoot+MyBatis-Plus的实体类与Mapper。

学生活动：记录作业，整理笔记。

设计意图：承上启下，为下节课编码实现做铺垫。

9.2 融入点

十、教学反思与作业

10.1 教学反思要点

  • 学生对ER图的理解是否到位？是否需要增加课后绘图练习？
  • 5张表的设计是否在课堂内完整讲透？时间是否充裕？
  • 小组评审是否流于形式？是否需要更结构化的评审表？
  • 索引部分是否讲得太浅？是否需要补充执行计划(EXPLAIN)入门？

10.2 课后作业

  1. 必做：完善CTTS建表脚本与测试数据，提交.sql文件。
  2. 必做：思考题——支持"小组任务"的表结构调整方案（文档+ER草图）。
  3. 选做：用Navicat/DBeaver导出CTTS的ER图截图，标注实体关系。
  4. 预习：SpringBoot+MyBatis-Plus实体类与Mapper编写基础。

10.3 评价方式
