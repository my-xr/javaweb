二、教学目标

知识目标

  1. 理解 HTTP 协议的请求-响应模型，掌握 HTTP 请求报文与响应报文的结构。
  2. 掌握 URL 的组成，理解 GET/POST/PUT/DELETE 等请求方法的语义。
  3. 掌握常见 HTTP 状态码的含义（200/400/401/403/404/500 等）。
  4. 理解 Header、Cookie、Session 的概念与作用。
  5. 掌握 JSON 数据格式的语法与数据类型。
  6. 理解 RESTful API 的设计思想，能区分 RESTful 与非 RESTful 接口设计。

能力目标

  1. 能够阅读并分析一个 HTTP 请求与响应报文的各组成部分。
  2. 能够根据业务场景选择合适的 HTTP 方法和状态码。
  3. 能够编写规范的 JSON 数据结构。
  4. 能够对同一业务设计 RESTful 风格的接口路径，并说明设计理由。

索质目标（课程思政）

  1. 建立"接口契约"意识——良好的接口设计是前后端协作的基础，体现职业责任。
  2. 培养规范意识——遵循 HTTP 语义与 RESTful 约定，是工程师的基本素养。
  3. 树立"用户体验"视角——合理的状态码与错误信息让前端与用户更易理解问题。

三、主要知识点纲要

详细讲解内容见同文件夹 教学资料.md，此处为纲要。

编号 知识点 要点
K2-1 HTTP 协议与报文结构 请求-响应模型；请求行/请求头/请求体；状态行/响应头/响应体
K2-2 URL 与请求方法 URL 组成（协议/主机/端口/路径/参数）；GET/POST/PUT/DELETE 语义
K2-3 HTTP 状态码 1xx/2xx/3xx/4xx/5xx 分类；200/201/400/401/403/404/500 常用码
K2-4 Header / Cookie / Session 常见请求头/响应头；Cookie 与 Session 的区别与联系
K2-5 JSON 数据格式 JSON 语法、数据类型（对象/数组/字符串/数字/布尔/null）、嵌套结构
K2-6 RESTful API 设计思想 资源化路径、用 HTTP 方法表达操作、无状态、统一接口

四、项目任务或案例任务

贯穿项目任务：用 Apifox 分析公开 API 的请求与响应

本次课任务：

  1. 教师演示用 Apifox 访问一个公开 API（如模拟的 CTTS 接口 GET /api/projects/list），分析其请求行、请求头、响应状态码、响应体（JSON）。
  2. 学生使用 Apifox 自行访问教师提供的测试接口，记录并提交：请求方法、URL、请求头、响应状态码、响应 JSON 结构。
  3. 课堂互动环节：对"管理任务"这一业务，设计 RESTful 接口路径并投票。

📌 本节课不写 Java 代码，重点是理解 HTTP 协议与 RESTful 设计。动手写接口从第 3 次课开始。

五、课堂互动设计

互动 1：课前 5 分钟回顾讨论

项目 内容
互动问题 "上节课我们说前后端分离后后端返回 JSON。那前端到底是怎么把请求发给后端的？后端又是怎么知道请求对不对的？"
组织方式 自由发言，引出 HTTP 协议
预期学生输出 提到"网址""请求""网址带参数""网页报错 404"等
教师点评要点 肯定学生已有认知，引出 HTTP 协议是前后端通信的语言

互动 2：API 路径设计投票（讲解 K2-6 后）

项目 内容
互动任务 对"删除一个任务"这个操作，给出 4 种接口设计方案让学生投票，讨论哪种是 RESTful：
A. GET /api/deleteTask?id=5
B. POST /api/tasks/delete?id=5
C. DELETE /api/tasks/5
D. POST /api/tasks/5/delete
组织方式 全班投票 → 选 C 的学生陈述理由 → 教师点评
预期学生输出 能识别 C 是 RESTful（DELETE 方法 + 资源路径 + 资源 ID）
教师点评要点 强调 RESTful 三要素：资源用名词、操作用 HTTP 方法、ID 用路径参数；C 最规范

互动 3：状态码连连看（讲解 K2-3 后）

项目 内容
互动任务 给出 6 个场景，让学生匹配对应状态码：
① 请求成功返回数据 ② 资源不存在 ③ 未登录 ④ 已登录但无权限 ⑤ 服务器内部错误 ⑥ 参数错误
组织方式 教师报场景，学生抢答状态码
预期学生输出 ①200 ②404 ③401 ④403 ⑤500 ⑥400
教师点评要点 强调 401（未认证）与 403（已认证但无权限）的区别，这是面试高频考点

六、课程思政融入点

项目 内容
融入点 接口设计责任：良好的接口契约是前后端协作的基础
技术关联 RESTful 设计遵循 HTTP 语义，让接口可读、可维护、可预测；状态码准确反馈问题
引导问题 "如果接口路径乱起名、状态码乱返回，前端同事会怎样？用户会看到什么？"
预期价值目标 培养规范意识与职业责任——接口不仅是给自己写的，更是给协作团队和用户用的

七、课堂练习或随堂测验

随堂练习（5 分钟）

选择题（口头作答）：

  1. 查询数据应使用哪个 HTTP 方法？（GET）
  2. 服务器内部错误对应的状态码是？（500）
  3. 下列哪个是合法的 JSON？（{"name":"张三","age":20}）

详细题目与解析见 题库.md。此处仅作课堂快速互动，不计分。

八、课后任务

  1. 阅读：通读同文件夹 教学资料.md，重点掌握 HTTP 报文结构、状态码、JSON 语法、RESTful 设计。
  2. 实操：安装 Apifox 或 Postman，访问教师提供的测试接口，截图提交请求与响应分析。
  3. 设计练习：为 CTTS 的"学生""任务""提交"三个资源，各设计一套 CRUD 的 RESTful 接口路径（共约 12 个接口），下次课抽查。
  4. JSON 练习：手写一段描述"一个学生提交了一个任务"的 JSON 数据，包含学生信息、任务信息、提交内容、提交时间。
  5. 思考：Cookie 和 Session 有什么区别？为什么前后端分离后更倾向用 Token 而非 Session？（为第 6 模块铺垫）
