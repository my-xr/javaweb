二、教学目标

知识目标

  1. 理解 @RestController 与 @Controller 的区别，明确 @RestController = @Controller + @ResponseBody。
  2. 掌握请求映射注解 @RequestMapping、@GetMapping、@PostMapping、@PutMapping、@DeleteMapping 的用法及路径参数 {param} 的写法。
  3. 掌握四种参数接收方式：@RequestParam（query 参数）、@PathVariable（路径参数）、@RequestBody（请求体 JSON）、@RequestHeader（请求头）。
  4. 理解 Spring Boot 自动将返回对象序列化为 JSON 的机制，能正确返回 List/Map/自定义对象。
  5. 掌握接口参数设计原则：何时用 query 参数、何时用路径参数、何时用请求体。

能力目标

  1. 能独立编写一个完整的 Controller 类，包含类级注解、方法级注解、方法体。
  2. 能根据业务场景选择合适的参数接收方式（@RequestParam / @PathVariable / @RequestBody）。
  3. 能用浏览器、curl 或 Apifox 测试自己编写的接口，并解读返回的 JSON。
  4. 能为 CTTS 项目实现"查询项目列表""根据 ID 查询项目""新增项目"三个接口（使用模拟数据）。

素质目标（课程思政）

  1. 培养代码规范意识——命名、路径、参数的一致性是工程师的基本素养。
  2. 建立接口设计思维——好的接口设计让前后端协作顺畅，体现"为他人着想"的工程伦理。
  3. 树立RESTful 风格意识——遵循行业规范而非随意编码，体现专业精神。

三、主要知识点纲要

详细讲解内容见同文件夹 教学资料.md，此处为纲要。

编号 知识点 要点
K4-1 @RestController 与 @Controller 区别 @RestController = @Controller + @ResponseBody；前者返回 JSON，后者返回视图
K4-2 请求映射注解 @RequestMapping 通用映射；@GetMapping/@PostMapping/@PutMapping/@DeleteMapping 快捷方法；路径参数 {param}
K4-3 参数接收注解 @RequestParam（query）、@PathVariable（path）、@RequestBody（body JSON）、@RequestHeader（header）
K4-4 JSON 返回机制 @ResponseBody 作用；Spring Boot 自动序列化对象为 JSON；List/Map/自定义对象返回
K4-5 接口参数设计原则 query 参数用于查询过滤；路径参数用于定位资源；请求体用于提交复杂对象

四、项目任务或案例任务

贯穿项目任务：CTTS 实训项目接口（模拟数据版）

本次课任务：在已搭建的 Spring Boot 项目中，使用模拟数据（静态 List）实现 CTTS 的三个核心接口。

接口 方法 路径 参数接收方式 返回
查询实训项目列表 GET /api/projects 无 List<Project>
根据 ID 查询单个项目 GET /api/projects/{id} @PathVariable Project
新增项目 POST /api/projects @RequestBody Project

实现要求：

  1. 创建 com.ctts.entity.Project 实体类（含 id、title、description、status、creatorId、createTime 字段）。
  2. 创建 com.ctts.controller.ProjectController 控制器类，使用 @RestController。
  3. 使用静态 List 模拟数据（暂不连数据库，第 5 次课开始接入 MyBatis-Plus）。
  4. 用浏览器/curl/Apifox 测试每个接口，观察返回的 JSON。

📌 本节课重点掌握 Controller 层的写法和参数接收，不涉及 Service/Mapper/数据库。数据用静态 List 模拟，便于聚焦核心知识点。

项目 内容
互动问题 "上次课我们搭建了 Spring Boot 项目，谁能说说一个后端接口的'骨架'是什么样的？需要哪些注解？"

互动 2：接口设计讨论 — projectId 该用 path 还是 query？（讲解 K4-5 时）

项目 内容
互动问题 "查询某个具体项目时，projectId 该放在路径里 /api/projects/{id} 还是放在 query 里 /api/projects?id=1？两种写法都对吗？"
组织方式 全班分为两方辩论，每方派代表陈述理由（2 分钟准备）
预期学生输出 path 派："id 是定位资源的，应该用 path"；query 派："query 也能传，写法简单"
教师点评要点 两种都能用，但 RESTful 规范推荐 path——/projects/{id} 表示"定位到 id 为 xx 的资源"，更语义化；query 一般用于过滤查询（如 ?status=进行中）

互动 3：新增项目参数讨论 — @RequestBody 还是 @RequestParam？（讲解 K4-5 时）

项目 内容
互动问题 "新增项目时，前端要传 title、description、status、creatorId 等多个字段，该用 @RequestParam 一个个接，还是用 @RequestBody 接收一个 JSON 对象？"
组织方式 自由发言，教师板书两种写法的代码对比
预期学生输出 部分学生认为 @RequestParam 简单直观；部分学生认为字段多了用 @RequestBody 更清爽
教师点评要点 字段少（1~2 个）可用 @RequestParam；字段多或嵌套对象必须用 @RequestBody。企业开发中 POST/PUT/DELETE 几乎都用 @RequestBody，对应前端传 JSON

七、课堂练习或随堂测验

随堂练习（8 分钟，讲解结束前进行）

快速判断（口头作答）：

  1. @RestController 等价于 @Controller + @ResponseBody。（✓）
  2. @GetMapping 只能处理 GET 请求。（✓）
  3. @RequestParam 用于接收路径中的参数。（✗，路径参数用 @PathVariable）
  4. POST 请求的参数必须用 @RequestParam 接收。（✗，POST 的请求体参数用 @RequestBody）

代码补全（写在纸上或 IDE 中）： 补全以下根据项目名模糊查询的接口：

@RestController
@RequestMapping("/api/projects")
public class ProjectController {

    @GetMapping("/search")
    public List<Project> search(________ keyword) {
        // keyword 应从 query string 接收，如 /api/projects/search?keyword=Java
        return projectService.search(keyword);
    }
}

答案：@RequestParam String keyword。详细题目与解析见 题库.md。此处仅作课堂快速互动，不计分。

八、课后任务

  1. 阅读：通读同文件夹 教学资料.md，重点理解四种参数接收方式的使用场景。
  2. 动手实践：在已搭建的 CTTS 项目中，实现本次课的三个接口（列表查询、按 ID 查询、新增），并用 curl 或 Apifox 测试通过。
  3. 拓展练习：再实现两个接口——PUT /api/projects/{id} 修改项目、DELETE /api/projects/{id} 删除项目，体会 @PutMapping、@DeleteMapping 的用法。
  4. 思考题：如果一个接口既要接收路径参数 id，又要接收请求体的 JSON 对象，代码该怎么写？（提示：@PathVariable 与 @RequestBody 可同时使用）
  5. 面试准备：能用自己的话回答"@RestController 和 @Controller 的区别""@RequestParam、@PathVariable、@RequestBody 三者的区别和使用场景"。
