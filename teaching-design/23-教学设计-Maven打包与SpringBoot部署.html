二、教学目标

1. 知识目标

  • 理解Maven打包机制，掌握mvn clean package命令、target目录结构、spring-boot-maven-plugin插件作用
  • 理解Spring Boot可执行jar的运行原理，掌握java -jar命令、内嵌Tomcat机制、命令行参数传递
  • 掌握多环境配置方案（application-dev.yml/application-prod.yml、spring.profiles.active、外部配置文件）
  • 掌握数据库初始化脚本编写（schema.sql、data.sql）及自动执行机制
  • 了解Linux服务器部署完整流程，掌握JDK/MySQL安装、端口开放、Nginx反向代理基础

2. 能力目标

  • 能独立完成CTTS项目的Maven打包，生成可执行jar
  • 能通过命令行方式启动Spring Boot应用，并传递配置参数
  • 能针对开发/生产环境编写差异化的配置文件
  • 能编写数据库初始化脚本并完成数据库准备
  • 能在Linux服务器上完成CTTS项目的部署与验证

3. 素质目标（课程思政）

  • 树立"能运行不等于能交付"的软件交付责任意识
  • 培养严谨的生产环境运维态度，重视配置管理与版本一致性
  • 强化DevOps协作意识，理解开发与运维协同的价值

三、教学重点与难点

教学重点

  1. Maven打包命令与spring-boot-maven-plugin插件配置
  2. 多环境配置文件的组织与spring.profiles.active激活机制
  3. 数据库初始化脚本的编写与自动执行
  4. Spring Boot jar的命令行启动与参数传递

教学难点

  1. 可执行jar的内部结构：理解BOOT-INF、org.springframework.boot.loader启动器机制
  2. 配置优先级：命令行参数 > 外部配置文件 > 内部配置文件 > 默认值的覆盖关系
  3. 多环境配置的切换：开发环境与生产环境的差异化策略
  4. 生产环境部署的完整性：从代码到上线全链路的环节衔接

  • 知识储备：学生已掌握Spring Boot开发、MyBatis-Plus持久层、Knife4j接口文档、JWT鉴权，CTTS项目核心功能已完成
  • 能力基础：具备本地IDE运行项目的能力，但缺少从"代码"到"交付物"的全流程经验
  • 常见困惑：

  • 学习动机：临近项目交付，学生对"如何把项目跑起来给别人用"有较强需求，学习意愿较高

八、教学过程详细设计

环节1：课前导入（5分钟）

导入语：

"同学们，我们花了22次课把CTTS系统的功能开发完成了。现在的问题是——如果我把你们的代码拷贝到一台全新的服务器上，它能直接跑起来吗？如果交给客户使用，他们看到的会是什么？"

演示对比：

  • 在IDE中点击运行 → 项目启动 → 访问Swagger UI → 一切正常
  • 拷贝源码到另一台机器 → 缺JDK、缺MySQL、缺依赖、配置不对 → 启动失败

引出主题：从"代码能跑"到"项目能交付"，需要掌握打包、配置、部署的全流程。本次课我们就把CTTS项目从开发环境搬到生产环境。

环节2：K23-1 Maven打包（15分钟）

讲解要点：

  1. Maven生命周期回顾：clean → compile → test → package → install
  2. mvn clean package命令的作用与执行流程
  3. target目录结构解析：
    • classes/：编译后的class文件
    • test-classes/：测试class文件
    • ctts-1.0.0.jar：最终打包产物
    • ctts-1.0.0.jar.original：repackage前的原始jar
  4. spring-boot-maven-plugin插件作用：
    • 将依赖打入jar（fat jar）
    • 提供repackage目标
    • 添加Main-Class启动器
  5. 打包排除测试：-DskipTests（跳过测试执行）vs -Dmaven.test.skip=true（跳过测试编译+执行）

现场演示：

cd d:/ctts
mvn clean package -DskipTests

观察target目录生成过程，展示jar包内容（用解压工具查看BOOT-INF、META-INF）。

易错点提示：

  • 测试失败会导致打包失败，生产打包常用-DskipTests
  • pom.xml缺少spring-boot-maven-plugin时，生成的jar无法直接运行
  • jar.original是原始jar，jar是可执行jar，勿混淆

环节3：K23-2 Spring Boot jar运行（15分钟）

讲解要点：

  1. java -jar命令的标准用法
  2. 内嵌Tomcat机制：无需单独部署Tomcat，jar内已包含
  3. 命令行参数传递：
    • --server.port=9090：覆盖端口
    • --spring.profiles.active=prod：激活生产配置
  4. 后台运行：
    • Linux：nohup java -jar ctts.jar > ctts.log 2>&1 &
    • nohup：忽略挂断信号，终端关闭后继续运行
    • &：后台运行
    • > ctts.log 2>&1：标准输出和错误输出重定向到日志文件
  5. 停止服务：ps -ef | grep ctts.jar → kill -9 PID

现场演示：

# 前台运行
java -jar target/ctts-1.0.0.jar

# 指定端口
java -jar target/ctts-1.0.0.jar --server.port=9090

# 后台运行
nohup java -jar target/ctts-1.0.0.jar > ctts.log 2>&1 &

# 查看日志
tail -f ctts.log

对比说明：IDE运行 vs 命令行运行——开发用IDE，生产用命令行。

环节4：K23-3 配置文件管理（15分钟）

讲解要点：

  1. 为什么需要多环境配置？
    • 开发环境：本地MySQL、打印SQL、调试日志
    • 生产环境：服务器MySQL、关闭SQL打印、INFO日志
  2. 配置文件命名规则：
    • application.yml：主配置，公共部分
    • application-dev.yml：开发环境
    • application-prod.yml：生产环境
  3. 激活方式：
    • 配置文件中：spring.profiles.active=dev
    • 命令行：--spring.profiles.active=prod
    • 环境变量：export SPRING_PROFILES_ACTIVE=prod
  4. 配置优先级（高→低）：
    • 命令行参数
    • 环境变量
    • 外部配置文件（jar同目录application.yml）
    • jar内部配置文件
    • 默认值
  5. 外部配置文件：将application.yml放在jar同目录，会覆盖jar内配置，便于运维修改

现场演示：

  • 展示application.yml、application-dev.yml、application-prod.yml的差异
  • 演示--spring.profiles.active=prod切换配置
  • 演示外部application.yml覆盖效果

环节5：K23-4 数据库初始化脚本（10分钟）

讲解要点：

  1. 为什么需要初始化脚本？
    • 新服务器上MySQL是空的，需要建库建表
    • 初始数据（管理员账号、字典数据）需要预置
  2. schema.sql：建库建表脚本
    • CREATE DATABASE
    • CREATE TABLE
  3. data.sql：初始数据脚本
    • INSERT INTO
  4. Spring Boot自动执行SQL脚本：
    • 配置spring.sql.init.mode=always
    • schema-locations、data-locations
    • 注意：生产环境一般不自动执行，避免覆盖数据
  5. 手动执行SQL：
    • mysql -u root -p < schema.sql
    • 通过Navicat/DBeaver执行

现场演示：

  • 展示CTTS的schema.sql（用户表、任务表、角色表）
  • 展示data.sql（默认管理员账号）
  • 演示手动执行SQL脚本

环节6：K23-5 简单服务器部署（20分钟）

讲解要点：

  1. 部署流程全景图： 
    本地打包 → 上传jar → 服务器装环境(JDK/MySQL) → 初始化数据库 → 配置数据源 → 启动服务 → 防火墙放行 → Nginx代理 → 验证访问
  2. 上传jar：使用scp或Xftp 
    scp ctts-1.0.0.jar root@server-ip:/opt/ctts/
  3. 安装JDK 17： 
    yum install -y java-17-openjdk java-17-openjdk-devel
java -version
  4. 安装MySQL 8： 
    yum install -y mysql-server
systemctl start mysqld
systemctl enable mysqld
  5. 初始化数据库： 
    mysql -u root -p < schema.sql
mysql -u root -p ctts < data.sql
  6. 配置数据源：通过外部application-prod.yml或环境变量
  7. 启动服务： 
    nohup java -jar /opt/ctts/ctts-1.0.0.jar --spring.profiles.active=prod > /opt/ctts/ctts.log 2>&1 &
  8. 防火墙端口开放： 
    firewall-cmd --permanent --add-port=8080/tcp
firewall-cmd --reload
  9. Nginx反向代理：
    • 安装：yum install -y nginx
    • 配置：将80端口转发到8080
    • 启动：systemctl start nginx
  10. 验证访问：浏览器访问http://server-ip/api/doc.html

现场演示：通过SSH连接云服务器，逐步完成部署（或播放预录视频）。

环节7：课堂互动——面试题快问快答（7分钟）

组织方式：教师提问，学生抢答，答对加分（平时分）。

快问快答题库：

  1. mvn package和mvn install的区别？
  2. -DskipTests和-Dmaven.test.skip=true的区别？
  3. Spring Boot的可执行jar和普通jar有什么不同？
  4. 如何在启动时指定端口？
  5. nohup命令的作用是什么？
  6. spring.profiles.active有几种设置方式？
  7. 外部配置文件放在哪里能覆盖jar内配置？
  8. 生产环境为什么一般不自动执行schema.sql？
  9. 防火墙开放端口的命令是什么？
  10. Nginx反向代理的核心配置项是什么？

环节8：课程思政与总结（3分钟）

思政融入：

"同学们，今天我们完成了从代码到部署的全流程。但请记住——能运行不等于能交付。一个真正可以交付的项目，需要：

  • 配置正确无误，敏感信息不泄露
  • 数据库脚本可重放，数据可恢复
  • 日志可追溯，异常可监控
  • 部署可复现，回滚有预案

在2022年某互联网大厂的事故中，工程师将测试配置打包进了生产环境，导致用户数据写入错误数据库，损失惨重。这就是'能运行'但'不能交付'的典型反面案例。

软件工程师的责任，不只是让代码跑起来，更是让交付物可靠、可控、可维护。希望同学们在未来的工作中，始终怀着对交付的敬畏之心。"

课堂总结：

  • Maven打包：mvn clean package -DskipTests → 生成可执行jar
  • jar运行：java -jar + 命令行参数 → 灵活启动
  • 多环境配置：application-{profile}.yml + spring.profiles.active → 环境隔离
  • 数据库初始化：schema.sql + data.sql → 数据准备
  • 服务器部署：JDK + MySQL + Nginx → 完整上线

课后任务：

  1. 完成CTTS项目的Maven打包，提交jar包
  2. 编写application-prod.yml，配置生产环境参数
  3. （选做）在自己的云服务器上完成部署，提交访问截图

九、课程思政设计

思政元素 融入点 实现方式
软件交付责任意识 K23-3 配置文件管理 通过配置泄露事故案例，强调配置管理的严肃性
严谨的工程态度 K23-4 数据库初始化 强调"脚本可重放、数据可恢复"的工程要求
DevOps协作精神 K23-5 服务器部署 讲解开发与运维的协同，培养全链路视野

思政总结语：

"软件交付责任——能运行不等于能交付。一个合格的工程师，不仅要写出能跑的代码，更要交付可部署、可运维、可信任的系统。这是我们从'码农'走向'工程师'的必经之路。"

十、教学反思

预设反思点

  1. 时间控制：服务器部署环节内容较多（20分钟），若现场演示遇网络问题需切换录屏备份
  2. 学生参与：面试题快问快答环节需控制节奏，避免个别学生主导，确保多数参与
  3. 实操跟练：理论课无法让所有学生现场操作，需通过课后任务巩固
  4. 难点突破：可执行jar的内部结构较抽象，需借助解压工具可视化展示

课后改进方向

  1. 录制完整的部署演示视频，供学生课后反复观看
  2. 第24次课项目答辩前，安排一次实操答疑课，解决学生部署问题
  3. 收集学生部署过程中的共性问题，形成FAQ文档
  4. 探索Docker容器化部署的拓展内容（学有余力学生）
