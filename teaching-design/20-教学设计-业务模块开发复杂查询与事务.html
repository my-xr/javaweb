二、学情分析

维度 现状分析 教学应对
知识基础 已掌握 MyBatis-Plus 基础 CRUD、单表 QueryWrapper、Service 分层、多表关联查询 从单表查询自然过渡到多条件动态拼接与聚合统计
技能水平 能独立完成 Controller-Service-Mapper 三层开发，但事务使用停留在"加注解即可"的认知层面 通过反例（事务失效场景）纠正认知偏差
学习特点 偏爱"看代码跑通"，对纯理论（如传播行为枚举）兴趣低 用"任务提交→评审"业务链串联知识点，理论落在业务上
易错点 动态 SQL 拼接易丢括号；@Transactional 自调用失效；rollbackFor 默认只回 RuntimeException 专门设"事务失效四宗罪"小节 + 课堂小测验巩固
思政接受度 对"数据一致性"等抽象概念感知弱 借"评审成绩错乱"事故案例引入，让"事务=业务正确性保障"可感可触

三、教学目标

3.1 知识目标

  • K20-1 掌握 MyBatis-Plus QueryWrapper 的多条件动态拼接，理解嵌套条件（nested）、or/and 组合的写法与优先级。
  • K20-2 掌握 COUNT/SUM/AVG 等聚合函数与 GROUP BY 分组统计在 MyBatis-Plus 中的实现（selectMaps / selectCount / 自定义SQL）。
  • K20-3 理解 @Transactional 注解的核心属性 propagation、rollbackFor、isolation、timeout，掌握 7 种传播行为中 REQUIRED / REQUIRES_NEW / NESTED 三种的差异。
  • K20-4 理解任务状态机模型（未开始→进行中→已提交→已评审），掌握用状态字段驱动业务流转的设计方法。
  • K20-5 掌握"任务提交→状态更新→评审→成绩统计"完整业务链的事务设计与实现。

3.2 能力目标

  • 能根据业务需求编写多条件组合查询的 QueryWrapper，正确处理 and/or 优先级。
  • 能使用 MyBatis-Plus 完成分组统计查询并对结果进行 VO 封装。
  • 能在 Service 方法上正确使用 @Transactional，并按业务需要指定 rollbackFor 与传播行为。
  • 能识别事务失效的 4 类典型场景并给出修复方案。
  • 能设计并实现一个包含状态流转与多表写入的事务性业务方法。

3.3 素质目标（课程思政）

  • 数据一致性意识：理解事务是业务正确性的最后防线，"一行 @Transactional 背后是对用户负责的态度"。
  • 工程严谨性：通过事务失效反例，培养"代码不仅要跑通，更要跑得对"的工程素养。
  • 系统思维：从单条 SQL 到业务链，建立"局部正确 ≠ 全局正确"的系统观。
  • 职业操守：以"成绩统计错乱"为反面案例，强化数据处理岗位的责任意识。

四、教学重点与难点

类别 内容 突破策略
重点1 QueryWrapper 嵌套条件与 or/and 组合 画"条件树"图示 + 对比 SQL 执行结果
重点2 @Transactional 的 rollbackFor 与传播行为 三段对比代码（REQUIRED / REQUIRES_NEW / NESTED）
重点3 事务失效场景识别 "四宗罪"反例 + 课堂小测验
难点1 or/and 优先级导致的 SQL 语义偏差 同一需求两种写法对比，演示 SQL 输出
难点2 REQUIRES_NEW 与 NESTED 的边界 用"日志记录不受主事务回滚影响"案例区分
难点3 业务链中事务边界划分 画事务边界图，标注每段是否在同一事务

55-65 环节5 编程小测验 发布 5 道事务回滚场景判断题（含传播行为、rollbackFor、自调用） 独立作答，限时 10 分钟 测验题 + 答案讲评
65-72 环节6 业务状态流转（K20-4） 画任务状态机图（未开始→进行中→已提交→已评审）；讲解状态字段设计、非法流转拦截 画状态机草图，列出合法流转 状态流转图

86-90 环节8 总结与作业 总结 5 个知识点；布置作业：实现"批量评审"业务方法（含事务） 记录作业要求 课后作业

七、课堂互动设计

7.1 启发式提问（贯穿全课）

  1. "如果要查询'张三同学提交的所有已评审任务'，QueryWrapper 该怎么写？"（K20-1）
  2. "统计每个学生的平均成绩，SQL 用什么？MyBatis-Plus 怎么实现？"（K20-2）
  3. "如果任务提交成功，但状态更新失败，数据库会出现什么问题？"（K20-3 引入）
  4. "@Transactional 加在 private 方法上还有效吗？为什么？"（K20-3 失效场景）
  5. "为什么任务状态不能从'未开始'直接跳到'已评审'？"（K20-4 状态机）

7.2 编程小测验（10 分钟，环节5）

  • 形式：5 道事务回滚场景判断题（选择题 + 判断题混合）
  • 目的：检验对传播行为、rollbackFor、自调用失效的理解
  • 评分：每题 2 分，共 10 分，计入平时成绩
  • 讲评：当场对答案，重点讲 REQUIRES_NEW 与 NESTED 的区别

7.3 分组讨论（环节3，3 分钟）

  • 主题："如果你是教务系统开发负责人，如何保证成绩数据的正确性？"
  • 形式：4 人一组，1 人记录，1 人发言
  • 目的：引出事务与数据一致性的工程责任

第20次课 业务模块开发：复杂查询与事务
========================================
一、复杂条件查询          | 三、事务管理
   QueryWrapper           |   @Transactional
   - eq/like/in           |   - propagation: REQUIRED/REQUIRES_NEW/NESTED
   - nested (and/or)      |   - rollbackFor: 必须显式指定
                          |   - 失效四宗罪：自调用/catch/non-public/final
二、统计查询              |
   COUNT/SUM/AVG          | 四、状态机
   GROUP BY               |   未开始→进行中→已提交→已评审
   selectMaps             |
                          | 五、业务链：提交→状态→评审→统计（一个事务）
思政金句：事务不是注解的游戏，而是对数据负责的承诺。

提交物：

  1. ReviewService.batchReview 方法代码
  2. 运行成功截图
  3. 模拟异常后的回滚验证截图
