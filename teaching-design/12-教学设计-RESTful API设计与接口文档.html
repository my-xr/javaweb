二、教学目标

2.1 知识目标

  • K12-1：能准确复述RESTful六大设计原则（资源名词复数、HTTP方法表达操作、ID用路径参数、无状态、统一JSON响应、版本管理）。
  • K12-2：能区分资源命名规范与反例，能正确设计嵌套资源路径（如 /projects/1/tasks）与版本路径（/api/v1）。
  • K12-3：能说明query、path、body、header四类参数的使用场景与设计要点。
  • K12-4：能写出统一 Result<T> 与 PageResult<T> 响应结构，能描述错误响应的三要素（code/message/timestamp）。
  • K12-5：能说出Knife4j五大常用注解（@Tag/@Operation/@Parameter/@Schema/@ApiResponse）的作用与使用位置。

2.2 能力目标

  • 能为CTTS系统的用户、项目、任务、提交、评论五大模块独立完成RESTful接口路径设计。
  • 能使用Knife4j注解编写"自文档化"的Controller，使接口文档自动生成、无需手写。
  • 能对他人接口设计进行规范评审，指出至少3类常见问题（动词路径、方法误用、状态码缺失）。

2.3 素质目标（课程思政）

  • 树立"接口即契约"的工程责任感——契约一旦确定就是对前后端、对用户的承诺。
  • 培养规范意识与协作精神——统一规范是团队协作的基石。
  • 强化"用户视角"——好的接口文档是给同事和未来自己的礼物。

四、项目任务

4.1 总任务

完成CTTS全部接口的RESTful设计与Knife4j文档化，覆盖五大核心模块。

4.2 子任务分解

子任务 模块 接口数量 交付物
ST-1 用户模块 User 5 登录、注册、查询详情、更新、分页列表
ST-2 项目模块 Project 6 增删改查 + 分页 + 关闭项目
ST-3 任务模块 Task（嵌套于项目） 6 增删改查 + 分页 + 指派
ST-4 提交模块 Submission 4 提交、查询、评分、撤回
ST-5 评论模块 Comment 4 发表、查询、删除、点赞
ST-6 Knife4j文档化 全部 五大Controller加注解、分组、示例值

4.3 交付标准

  1. RESTful路径设计表：列出每个接口的方法、路径、参数位置、响应类型、说明。
  2. Knife4j注解完整的Controller：每个接口必须含 @Operation、@Parameter、@Schema。
  3. 统一响应类：Result<T> 与 PageResult<T> 可编译通过。
  4. 文档可访问：启动项目后访问 http://localhost:8080/doc.html 能看到分组化接口文档。

5.3 评审反例示例

反例1（动词路径）：

POST /api/getUserById?id=1
POST /api/createUser
POST /api/deleteUser?id=1

反例2（方法误用）：

GET    /api/users/create
POST   /api/users/1        （用于删除）
GET    /api/users/delete/1

反例3（层级混乱）：

GET /api/tasks/1/project
GET /api/projects/1/tasks/2/comments/3/users/4
GET /api/v1/getAllTaskListByProjectId?pid=1

5.4 评审表（学生填写样例）

接口反例 问题类型 问题描述 规范改写 改写理由
POST /api/getUserById?id=1 动词路径 + 方法误用 + 参数位置错 用GET语义却用POST；动词getUserById违反资源命名；id应在path GET /api/v1/users/1 资源用名词复数；ID用path参数；查询用GET

六、课程思政

6.1 思政主题：接口设计责任——契约一旦确定就是承诺

6.2 融入方式（5分钟，讲授结尾自然过渡）

案例导入：

某互联网公司因后端同学"随手"修改了 /api/users 的返回字段名（userName → username），导致前端 App 崩溃，影响30万用户2小时，直接损失订单约80万元。

思政要点：

  1. 契约精神：接口文档就是前后端签订的"工程合同"。一旦发布，任何字段名、类型、路径的变更都需要走"变更流程"——这是工程师对社会、对用户、对同事的承诺。
  2. 规范即责任：RESTful不是"美观问题"，是"工程问题"。统一规范让团队能协作、让代码可维护、让事故可追溯。
  3. 用户视角：写文档时心里要装着读文档的人——可能是新同事、可能是三个月后的自己。好的文档是工程师的"职业名片"。
  4. 职业素养：中国软件产业要走向高质量，靠的不是一两个"大牛"，而是千千万万遵守规范、敬畏契约的普通工程师。

思政小结：

"接口设计责任——契约一旦确定就是承诺。" 这句话不只是口号，而是每一位后端工程师每天写代码时的"底线意识"。

七、课堂练习

练习1（K12-2，5分钟）——路径设计改写

将下列非RESTful接口改写为规范形式：

  1. POST /api/getProjectList?page=1
  2. POST /api/project/1/task/2/delete
  3. GET /api/queryUserByName?name=张三

参考答案：

  1. GET /api/v1/projects?page=1
  2. DELETE /api/v1/projects/1/tasks/2
  3. GET /api/v1/users?name=张三

练习2（K12-4，5分钟）——响应结构设计

为"查询任务详情失败（任务不存在）"设计统一错误响应JSON，要求含 code、message、timestamp、path 四个字段。

参考答案：

{
  "code": 40401,
  "message": "任务不存在",
  "timestamp": "2026-07-22T10:30:00",
  "path": "/api/v1/projects/1/tasks/999"
}

练习3（K12-5，3分钟）——注解匹配

为下列Controller方法补充Knife4j注解（@Operation 的 summary 与 description）：

@GetMapping("/{id}")
public Result<UserVO> getById(@PathVariable Long id) { ... }

参考答案：

@Operation(summary = "查询用户详情", description = "根据用户ID查询用户的完整信息")
@GetMapping("/{id}")
public Result<UserVO> getById(@PathVariable Long id) { ... }

九、面试考点

编号 考点 难度 出现频率 简要说明
I-1 RESTful的六个设计原则 ★ 高 名词复数、HTTP方法、path参数、无状态、统一响应、版本
I-2 GET与POST的本质区别 ★ 高 幂等性、安全性、语义、缓存
I-3 PUT与PATCH的区别 ★★ 中 PUT全量替换、PATCH部分更新
I-4 HTTP状态码语义 ★★ 高 2xx成功、3xx重定向、4xx客户端错误、5xx服务端错误
I-5 接口版本管理策略 ★★ 中 URL版本、Header版本、Query版本优劣
I-6 如何设计统一响应结构 ★ 高 Result + 业务码 + 消息 + 数据
I-7 Knife4j/Swagger注解有哪些 ★ 中 @Tag/@Operation/@Parameter/@Schema/@ApiResponse
I-8 接口幂等性如何保证 ★★★ 中 token机制、唯一索引、状态机、乐观锁
I-9 嵌套资源的层级控制 ★★ 低 一般不超过2层，深层用query或独立资源
I-10 接口安全设计要点 ★★★ 中 认证、授权、防重放、限流、参数校验
